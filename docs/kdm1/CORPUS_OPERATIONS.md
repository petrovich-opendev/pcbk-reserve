# Карантин и версии корпуса КДМ-1 — команды оператора (Task 8, Этап 8)

Офлайн-командный этап, не маршрут API: `python -m pcbk_core.analytics.ingestion <подкоманда>`
(`core/pcbk_core/analytics/ingestion/`). Служба `core` эти команды не вызывает, сеть не используется.
Реализация, тесты и проверки — `.superpowers/sdd/PLAN-KDM1-analytics-2026-10-14/task-8-report.md`.

## Карантин входящих файлов

```sh
python -m pcbk_core.analytics.ingestion quarantine <файл_или_архив> --quarantine-dir <каталог> [--id <id>] [--scope KDM1_PCBK]
python -m pcbk_core.analytics.ingestion report <id> --quarantine-dir <каталог>
```

Каждый элемент получает `<quarantine_dir>/<id>/report.json` с вердиктом `accepted`/`rejected`/
`empty_or_unreadable`. Проверяется: путь с обходом каталога/абсолютный путь внутри архива, символическая/
жёсткая ссылка, превышение числа элементов и распакованного размера (одного элемента и суммы всех —
«zip-бомба»), несовпадение расширения с реальным содержимым. Для XLSX/DOCX (оба — ZIP-контейнеры) отдельно
отмечаются (не выполняются и не пересчитываются): формулы — текстом, без значения; макросы (`vbaProject.bin`)
— только флагом, содержимое макроса никогда не попадает в отчёт; внешние связи и командные поля документа
(Word field codes) — флагом и текстом инструкции, без исполнения. XML-часть с `<!DOCTYPE` не разбирается вовсе
(защита от XML-бомбы без новой зависимости). Пустой/нечитаемый файл — отчёт без выдуманного текста. Отклонённый
целиком элемент не оставляет в карантине ничего, кроме `report.json` — содержимое за пределы карантина не
попадает.

Карантин — только первый, безопасный разбор; какие факты из него действительно попадут в `knowledge/*.jsonl`
новой версии — решает человек отдельно (мастер-промпт §9: «проверка полноты/области/прав до поиска»), этот
этап не делает этого автоматически.

## Версии корпуса

Раскладка `ANALYTICS_CORPUS_DIR` (каталог версий, подключается `core` только для чтения, `mode=ro`):

```
ANALYTICS_CORPUS_DIR/
  CURRENT                 # указатель текущей версии — одна строка, имя подкаталога
  ingestion_log.jsonl      # журнал publish/rollback этого этапа (дозапись)
  <версия>/
    kdm1.seed.sqlite3      # ровно один файл корпуса
    build_report.json
    publish.json | rollback.json
```

```sh
python -m pcbk_core.analytics.ingestion build <версия> --knowledge-dir <knowledge/> --importer <tools/import_seed.py> --corpus-dir <каталог>
python -m pcbk_core.analytics.ingestion publish <версия> --approved-by <логин> --corpus-dir <каталог>
python -m pcbk_core.analytics.ingestion rollback <версия> --approved-by <логин> --corpus-dir <каталог>
python -m pcbk_core.analytics.ingestion list --corpus-dir <каталог>
```

`--corpus-dir` можно не указывать — тогда берётся `ANALYTICS_CORPUS_DIR` из окружения.

- `build` собирает новую версию в каталоге версий (кладёт туда новый подкаталог), запуская настоящий
  `tools/import_seed.py` пакета заказчика СУБПРОЦЕССОМ — ровно тем же интерфейсом командной строки, что в его
  README (`--knowledge`/`--output`); извлечение вложений не переписывается. Новую версию `build` НЕ публикует:
  указатель `CURRENT` не трогает, пока версий в каталоге только одна — `knowledge.open_corpus` всё равно
  откроет её (прежняя раскладка Task 1 без указателя — «одна версия», не тихая публикация); как только версий
  становится больше одной, не опубликованная не видна, пока её явно не опубликуют.
- `publish`/`rollback` требуют `--approved-by <логин>` (без него — отказ) и перед сменой указателя независимо
  (не доверяя тому, что версия собрана через `build`) проверяют: целостность манифеста/схемы (через
  `knowledge.open_corpus` на конкретный подкаталог), что все ссылки `source_refs`/`evidence_refs`/
  `process_ids`/`term_ids` существуют внутри ЭТОЙ версии, и что `machine_scope` записей не указывает на чужую
  машину (БДМ-2/КДМ-3 и подобные — не начинаются с `KDM1`; настоящая общая математическая теория КДМ-1-корпуса,
  например `machine_scope="KDM1_related_general_mathematics"`, — допустимое общее знание, не чужая машина).
  Любое нарушение — отказ с отчётом, указатель `CURRENT` не меняется. Смена указателя — один атомарный
  `os.replace` временного файла; запись журнала версии (`publish.json`/`rollback.json`) делается ДО него, так
  что сбой на этом шаге тоже не трогает указатель.
- `rollback` — то же самое действие, что `publish`, но на уже существующую (не новую) версию каталога. Ни
  `build`, ни `publish`, ни `rollback` никогда не удаляют и не изменяют уже существующий подкаталог версии:
  история версий (и любые пакеты доказательств, которые помнят версию по этой строке) не трогается откатом.
- `list` показывает все версии каталога, какая из них текущая, и помечает повреждённую версию (`status:
  "broken"`) без падения всего списка.

Подключение к `AnalyticsSettings.ANALYTICS_CORPUS_DIR`/запуск по расписанию — за Task 5/оператором;
назначение права на `--approved-by` (кто может подписывать публикацию) и связь с `reviews.py` — за Task 7/
контроллером (решение волны 3, не этого этапа).

## Новая версия подхватывается БЕЗ пересоздания `core` (правка итогового ревью F4a, 14.10)

До правки F4a `knowledge.open_corpus` читался РОВНО ОДИН РАЗ при старте процесса (`AnalyticsService.open()`,
lifespan шлюза), и бегущему `core` требовалось пересоздание контейнера, чтобы увидеть смену указателя `CURRENT`
(`ingestion publish`/`rollback`). Это больше не так: `AnalyticsService._maybe_reopen_corpus` сверяет дешёвый
признак текущей версии на диске (`knowledge.version_signature` — путь/размер/mtime выбранного файла, без
хеширования содержимого) В НАЧАЛЕ КАЖДОГО задания (каждого вопроса технолога/преподавателя), и, если он
изменился, переоткрывает корпус (`knowledge.open_corpus`) прямо в работающем процессе — `self._handle`
заменяется атомарно, старый дескриптор отбрасывается (у него и так нет постоянного соединения SQLite, см.
докстринг `knowledge.py`).

Поэтому после `publish`/`rollback` **пересоздавать контейнер не требуется** — публикация применяется к
СЛЕДУЮЩЕМУ вопросу в любом открытом диалоге (не к уже отправленному и обрабатывающемуся заданию: если смена
версии произошла МЕЖДУ поиском и выдачей ровно ЭТОГО задания, оно не публикует карточки «как ни в чём не
бывало» — отвечает `limited_answer` с просьбой задать вопрос ещё раз, см. `docs/kdm1/INTERFACES.md`, раздел
`service.py`/«Правка итогового ревью F4a», п.2). Уже отданные клиенту ИСТОРИЧЕСКИЕ ответы (отвеченные по
старой версии) при последующем чтении (`GET requests/{id}`, история диалога) получают предупреждение
«ответ исторический» — сам сохранённый ответ не переписывается (та же правка, п.3).

Пересоздание контейнера (`docker compose up -d --no-build --force-recreate core`) остаётся штатным средством
на случай других проблем (например, если признак версии не посчитался на диске из-за проблем с томом) — но
саму публикацию новой версии корпуса оно больше не обслуживает как обязательный шаг.
