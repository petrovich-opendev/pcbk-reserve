# Назначенное согласование КДМ-1 — операторская инструкция

Коротко: кто может решать заявки согласования (`reviews/*`), как это назначить, и что видит проверяющий.
Подробности реализации и сигнатуры — `docs/kdm1/INTERFACES.md`, раздел `analytics/reviews.py`.

## Режим ANALYTICS_REVIEWERS (решение владельца, 14.10.2026)

Переменная `ANALYTICS_REVIEWERS` (`.env` выкладки, `deploy/env.example`) переключает, кто может решать заявки
согласования — применяется пересозданием `core` (`docker compose up -d --no-build --force-recreate core`), как
`ANALYTICS_ENABLED`:

- **`grants`** (умолчание, пусто — как без переменной вовсе) — право только по явному назначению, всё
  описанное в этом файле ниже без изменений.
- **`all_students`** — решение владельца 14.10.2026 («любому студенту без утверждения со стороны
  преподавателя — это технологи, они сами всё знают»; «любой утверждает без дополнительных утверждений»):
  любой вошедший `student` (не `teacher`) решает ЛЮБУЮ заявку области КДМ-1 — всех четырёх видов
  (`local_claim`, `equipment_link`, `local_norm`, `conflict`) — БЕЗ какого-либо назначенного полномочия, в
  ОДНО действие:
  - видит ВСЕ заявки (не только свои и не только там, где есть назначение);
  - решает любую, включая СВОЮ собственную (самозапрет автора не действует для `student` в этом режиме);
  - «второй независимый согласующий» для `local_claim`/`local_norm` (см. ниже) не требуется — одного решения
    `student` достаточно.
  - `teacher` — ИСКЛЮЧЕНИЕ из этого режима, не «любой вошедший»: решает только по действующему полномочию
    (`bootstrap`/`grant`), ровно как в `grants` — роль `teacher` сама по себе права не даёт (мастер-промпт §6),
    это решение владельца не отменяет.
  - **Переключение `all_students` → `grants` обесценивает решения студентов без назначения для НОВОГО
    применения** (карточка/связь оборудования, подтверждённая студентом без реального права, перестаёт
    считаться действующей согласованной), но НЕ переписывает журнал — заявка остаётся `accepted`/`rejected`,
    видна в истории как решённая. Решения `teacher` (всегда по действующему на момент решения полномочию) этим
    переключением не затрагиваются.
- Опечатка (`All_Students`, `allstudents` и т.п.) — явная ошибка настройки процесса (видна на странице
  состояния шлюза), не тихий откат на `grants` и не на `all_students`.
- На сервере ПЦБК действует значение **`all_students`** по этому решению владельца.

Ниже (до конца файла) — описание режима `grants`; в `all_students` всё, что касается `teacher`, работает так
же, а для `student` — см. правила выше.

## Кто вправе решать заявки

Роль `teacher` сама по себе **не** даёт права утверждать технологические нормы, связи оборудования с
историаном или местные сокращения (мастер-промпт §6). Право — явно назначенное **полномочие**: логин +
область (`scope`, обычно `"KDM1_PCBK"` целиком или её подмножество — конкретный узел/процесс) + виды решений
(`local_claim`, `equipment_link`, `local_norm`, `conflict`). Полномочие может получить любая действующая
учётка технолога (`gateway.accounts`), роль учётки при этом не меняется.

**Назначить полномочие через веб-интерфейс нельзя** — такого маршрута нет и не будет (само назначение — это
не решение заявки, которое видно в интерфейсе проверяющего, а административная операция оператора). Заявки
на согласование создаёт и решает любой вошедший технолог/преподаватель через вкладку «Аналитический чат
технолога» → «Назначенное согласование» (видна только тем, у кого уже есть хоть одно действующее
полномочие); сами полномочия назначает и отзывает только оператор, из командной строки внутри контейнера.

## Команда оператора

Запускается внутри контейнера `core` (compose-служба `core`, контейнер `pcbk-core`):

```
docker compose exec core python -m pcbk_core.analytics.reviews <команда> [--db ПУТЬ] ...
```

`--db` не нужен в обычной работе — по умолчанию берётся `ANALYTICS_STATE_PATH` из настроек процесса
(фиксированный путь внутри контейнера, `/var/lib/pcbk-core/analytics.db`, том `core-data`).

### `bootstrap` — самое первое назначение

Нужна, когда в базе ещё нет ни одного полномочия вообще (только что включили аналитику впервые или база
только что создана):

```
docker compose exec core python -m pcbk_core.analytics.reviews bootstrap \
    --login tech1 --scope KDM1_PCBK --types local_claim,equipment_link,local_norm,conflict --by operator
```

- `--login` — логин учётки, которой назначается право (должен существовать в `gateway.accounts`, команда это
  не проверяет сама — за существование логина отвечает оператор).
- `--scope` — область: `KDM1_PCBK` (вся подсистема) или конкретный узел/процесс.
- `--types` — через запятую, какие виды заявок разрешено решать.
- `--by` — логин, который записывается как «назначивший» (`granted_by`); для самого первого назначения может
  быть любым, кроме совпадающего с `--login` (самоназначение запрещено всегда, в т.ч. здесь).
- `--until ГГГГ-ММ-ДД[ЧЧ:ММ]` (необязательно) — срок полномочия; без него полномочие без ограничения по
  сроку (как раньше). Пример: `--until 2026-12-31` (действует до начала суток 31 декабря UTC; если нужно «по
  конец дня» — указать время явно: `--until "2026-12-31 23:59"`, в кавычках, чтобы попасть одним аргументом).
  Истёкшее полномочие, которое не отозвали явно, отключается само: держатель перестаёт быть видимым заявкам
  на решение (как посторонний), а принятые им решения местных норм/фактов/связей оборудования перестают
  применяться, не трогая сам журнал заявок (см. ниже «Истечение срока»).

Повторный `bootstrap`, когда в базе уже есть хоть одно полномочие (даже отозванное) — отказ: дальше
назначения идут командой `grant`.

### `grant` — последующие назначения

Работает, только если у `--by` уже есть действующее полномочие (любого вида) в той же `--scope`; принимает
тот же необязательный `--until`, что и `bootstrap`:

```
docker compose exec core python -m pcbk_core.analytics.reviews grant \
    --login tech2 --scope KDM1_PCBK --types equipment_link --by tech1 --until 2027-06-30
```

### Истечение срока (`valid_until`) — без отдельной команды

Полномочие с заданным `--until` перестаёт действовать САМО, в момент, когда наступает указанный срок — без
отдельной операции оператора (как `revoke`, но автоматически, по времени, не по команде). Это проверяется
«здесь и сейчас» при каждом обращении (тем же приёмом, что и `revoke`, см. раздел «`revoke` — отзыв» ниже):
- держатель истёкшего полномочия больше не видит заявки на решение, которые ему было бы положено видеть, и
  не может их решить — сервер отвечает так же, как постороннему без права;
- связь оборудования с историаном (`resolved_link`) и согласование критической карточки (`approved_claim`),
  принятые этим держателем, перестают применяться с момента истечения;
- сама заявка и факт решения остаются в журнале как исторические (не переписываются и не удаляются) — то же
  поведение, что у отзыва (следующий раздел).

Если полномочие нужно отключить ДО наступления заданного `--until` (досрочно) — всё равно `revoke`, `--until`
не меняет и не отменяет сам по себе.

### `revoke` — отзыв

```
docker compose exec core python -m pcbk_core.analytics.reviews revoke --login tech1 --scope KDM1_PCBK --by operator
```

Отзыв действует немедленно: все решения, которые этот логин принял по этому праву (принятые заявки
`equipment_link`/`local_claim`/`local_norm`/`conflict`), сразу перестают применяться — связь с историаном
(`resolved_link`) и согласование критической карточки (`approved_claim`) перепроверяются «здесь и сейчас» при
каждом обращении, не доверяют факту решения в прошлом. Сами заявки и факт решения остаются в журнале
(историческая запись, с явной пометкой при показе — не переписывается).

### `list` — что назначено

```
docker compose exec core python -m pcbk_core.analytics.reviews list [--login tech1]
```

Печатает по одной строке на полномочие: логин, область, виды решений, кем назначено, когда, до какого срока
(`-`, если без ограничения) и статус текстом — «действует» / «истекло» (срок наступил, явного отзыва не
было) / «отозвано» (явный `revoke`, независимо от срока).

## Что видит проверяющий в вебе

Держатель хоть одного действующего полномочия видит во вкладке «Аналитический чат технолога» дополнительный
раздел «Назначенное согласование» (у остальных его нет вовсе — это и есть `capabilities.review_authority`).
В нём:

- список заявок: СВОИ созданные заявки (кто бы их ни создал — заявку может отправить любой вошедший технолог
  или преподаватель, право не требуется) **плюс** все заявки в области, где есть действующее полномочие на
  решение этого вида;
- по каждой заявке — основания (`rationale`), старое/новое значение, область/срок (если заданы), статус;
- решать заявку — принять/отклонить/запросить сведения — может только держатель действующего полномочия на
  эту область и этот вид решения, **и не автор самой заявки** (автор не решает свою же заявку, даже если у
  него есть нужное право — симметрично запрету самоназначения полномочия);
- **«запросить сведения» не закрывает заявку.** Заявка в статусе «запрошены сведения» остаётся открытой —
  по ней можно позже вынести окончательное решение (принять/отклонить), и можно повторно запросить сведения
  столько раз, сколько нужно. Решённая (принята/отклонена) заявка — закрыта окончательно: повторное решение
  — отказ, нужен новый отзыв полномочия и новая заявка, не «переголосование». Каждое решение по заявке (кем,
  когда, какое) остаётся в журнале — ничего не затирается более новым решением;
- **двухэтапное принятие местных фактов/нормативов.** Для заявок вида «местный факт» и «местный норматив»
  окончательное **принятие** (не отклонение и не запрос сведений) не может вынести тот же логин, который уже
  выносил по ЭТОЙ заявке любое решение ранее (в т.ч. свой же более ранний запрос сведений) — нужен ВТОРОЙ,
  независимый держатель права на эту область/вид; попытка решить самому получает явный отказ с объяснением
  причины. Для заявок на связь оборудования с историаном и на открытый конфликт корпуса такого ограничения
  нет — там достаточно одного правообладателя (включая случай, когда он сам ранее запросил по той же заявке
  сведения, а теперь готов принять решение).

## Связь оборудования с историаном

Принятая заявка вида `equipment_link` (связь подписи/`display_label` оборудования с реальным тегом
историана) становится действующей (`resolved_link`) только пока держится в силе: отзыв полномочия
решившего делает её недействующей немедленно, без отдельной команды «отозвать решение» (её нет — отзываете
полномочие того, кто принял решение). Срок (`period_start`/`period_end`) у заявок `equipment_link` не
действует — это не временное утверждение.
