**Goal:** у службы данных появляются остальные калькуляторы: ряд и профиль (`tag_series`) и наработка
(`calc_runtime`). Среднее, минимум, максимум и размах уже считает `tag_period` (Д3б). Те же расчёты получают
агенты (MCP), HTTP и новая вкладка «Калькуляторы» веб-чата: страница зовёт тот же код службы через шлюз. Автотест
«агент = калькулятор» гоняет набор тегов и периодов через настоящий стенд и сверяет число в ответе агента с
калькулятором. На двойниках он идёт полностью, на выбранной модели — в окне владельца. Студент-доброволец ПЦБК после
одного показа собирает своего агента, а владелец засекает время: это ручная половина успеха 1.

**Architecture:**
- **Наблюдение — первым (А1).** Служба считает серии ошибок по каждому инструменту. `/health/historian` получает
  поле `tools.failing`, а строка сторожа «Историан БДРВ» желтеет, когда инструмент три раза подряд ответил
  ошибкой. Доля ошибок тут не поможет: редкий новый калькулятор утонет в потоке `tag_now`. Учение
  `DRILL_DATA=tool_error` даёт ошибку без SQL и без данных.
- **Калькуляторы — в `DataService`** (`service.py`). Это один код для MCP, `/api/data/*` и шлюза. SQL — два новых
  шаблона с формами в `TEMPLATE_FORMS`:
  - ряд — `AnalogHistory` с `Cyclic` и `wwCycleCount = N`;
  - наработка — `StateSummaryHistory` с `wwCycleCount = 1`.

  Оба вида запросов работали в плагине `pcbk-ai-lab` (research/05 §2.9, [П]).
- **Страница — вкладка SPA чата.** Шлюз отдаёт `POST /pcbk/api/calc/<tool>` и зовёт `DataService` в том же
  процессе. Вызывающий — `student-NN` места учётки, канал событий — `web`. Место будить не нужно: OpenCode тут не
  участвует.
- **«Агент = калькулятор» (Д9б)** — модуль `bench/pcbk_bench/match.py` стенда отбора Д8. Он переиспользует
  клиент шлюза, калькулятор `ops`, разбор хода и разбор чисел. Агент проверки `bench-calc` получает все пять
  инструментов чтения. Вопросы идут по матрице «тег × вид вопроса × период». Двойник историана даёт числа,
  зависящие от периода, иначе неверный период не поймать. Персоны двойника OpenRouter служат контролями: честная
  и «ошибается в среднем».
- **Доброволец** — протокол, сценарий показа и задание на листе. Секундомер ведёт владелец. Время сохранения
  агента сверяется с учётом агентов службы. Деньги окна идут под потолком прогона Д8 (`LLM_RUN_*`), так что
  строка «LLM-прокси и бюджет» показывает расход и тишину без новой оснастки.

## Решения Д9а (Ruling)

**Д9-R82 — где живёт код.**

**Д9-R83 — наблюдение раньше функций.**
- **Серия ошибок.** `DataService` считает подряд идущие исходы `error`, `timeout` и `unavailable` по имени
  инструмента на каналах `http`, `mcp` и `web` (`_streaks: dict[str, int]`). Любой другой исход обнуляет серию.
  `refused`, `budget`, `rate` и `partial` — не ошибки. `FAIL_STREAK = 3`.
- `tools_stats() -> {"recent": int, "errors": int, "failing": list[str]}`. `failing` — инструменты с серией не
  меньше `FAIL_STREAK`, по алфавиту; хранится только в памяти. Инструмент, которого не звали дольше
  `FAIL_STALE_S = 1800` с (монотонные часы роли), из `failing` уходит сам: после обрыва и учений строка не держит
  `warn` до первого удачного вызова редкого калькулятора (критика р1, m3). Окно `recent`/`errors` (`TOOL_WINDOW = 50`)
  считает и канал `web`.
- **Канал `web`.** `Channel = Literal["mcp", "http", "web", "system"]`. Событие вкладки: `caller="student-NN"`,
  `channel="web"`.
- **Учение `DRILL_DATA`.** `Settings.DRILL_DATA: str = ""`, `DRILL_DATA_MODES = frozenset({"", "tool_error"})`,
  неизвестное значение — `ValueError` с именем поля.
  - При `tool_error` все пять инструментов чтения сразу после проверки частоты отвечают
    `{"status": "error", "message": ERROR_MESSAGE}` и пишут событие с `summary = DRILL_SUMMARY = "учения: tool_error"`.

- **Сторож.** `tools.failing` — необязательный ключ: нет ключа — строки нет (`core` старше Д9а). Ключ есть — список
  не длиннее `FAILING_MAX = 8` из строк `TOOL_NAME_RE = [a-z_]{1,32}`, иначе ответ не по договору. В
  `_load_verdict` проверка идёт после доли ошибок: непустой `failing` — `warn` с

  Ключ `drill` необязателен; непустой — строка `"tool_error"`, иначе ответ не по договору. Под учением к `note`
  строки (любого состояния) дописывается «учения: tool_error» через «; »: забытое учение видно на странице.

  студентов, по README.

**Д9-R84 — ряд и профиль: `tag_series`** (вместо `calc_profile` из таблицы §4).
- **SQL.** `series_sql(names, start, end, points)` строит:
  `SELECT TagName, DateTime, Value, Quality FROM AnalogHistory WHERE TagName IN (…) AND DateTime >= '<start>' AND DateTime <= '<end>' AND wwRetrievalMode = 'Cyclic' AND wwCycleCount = <points>`.
  - Даты — `lit_dt` по `DATE_FMT`, `ORDER BY` нет: порядок точек задаёт Python по времени.
  - Форма `TEMPLATE_FORMS["series"]` — ровно эта строка: список имён как у `live`, даты по `DATE_FMT`, число
    2–96.
  - `WW_CONSTANTS = frozenset({"STAIRSTEP", "Cyclic"})`.
- **Пределы.**
  - Тегов 1–4 (`SERIES_MAX_TAGS = 4`). Пятый — отказ аргументов «tags: не больше 4 тегов за вызов».
  - Точек на тег 2–96 (`SERIES_MIN_POINTS = 2`, `SERIES_MAX_POINTS = 96`), по умолчанию
    `SERIES_DEFAULT_POINTS = 24`. Вне пределов — отказ аргументов «points: от 2 до 96».
  - Теги × точки — не больше `LIMITS.max_points` (288). Сверх — исход `budget` с текстом `check_points`: «за один
    вызов — не больше 288 точек ряда (теги × точки): сократите число тегов или точек».
  - Окно и тего-сутки — `check_budget`, как у `tag_period`, раньше `check_points`.
- **Только аналоговые теги.** Дискретный тег получает item
  `{"tag", "status": "discrete", "text": ITEM_TEXTS["discrete_series"]}`, где текст — «тег состояния: ряд не
  строится — наработку даёт calc_runtime». В SQL он не уходит. `unknown` и `unlisted` — как у `tag_now`. Ни одного
  годного имени — отказ `none`.
- **Ответ** — ключи `tool`, `status` (`ok` или `partial`), `notes`, `cache`, `period` (как у `tag_period`),
  `points` (запрошенное N), `source`, `cost_tag_days`, `items`.
  - `source = SOURCE_SERIES` — «равномерная сетка историана (Cyclic): N точек с равным шагом от начала периода».
    Где лежат крайние точки (на концах периода или шаг = период / N, research/05 §5.2), скажет проба окна (`ends=`).
  - Item `ok`:
    - `tag`, `status`, `description`, `unit`;
    - `points` — `[[время ISO с поясом историана, значение | null], …]` по времени;
    - `profile` — `first`, `first_time`, `last`, `last_time`, `change` (`last − first`), `min`, `min_time`, `max`,
      `max_time` по точкам со значением;
    - при Quality ≠ 0 у k из N точек — `"quality_note": "точек с недостоверным качеством: k из N"`.
  - Все значения `null` или строк нет — `no_data` с текстом `ITEM_TEXTS["no_data"]`.
  - Заметки: `GRID_NOTE` — «сетка равномерная: всплески короче шага не видны — истинные минимум, максимум и среднее
    даёт tag_period» — всегда; `SHIFT_NOTE`, `OPEN_NOTE`, `CLAMP_NOTE` — по правилам `tag_period`.
- **Разбор ответа историана.** Строки группируются по имени в верхнем регистре; строка не той ширины —
  `_BadAnswer("row_shape")`.
- **Кэш.** `cache_key("tag_series", names, start, end, extra=str(points))`, срок — как у `tag_period`
  (`ttl_for("tag_series", end, now)`).

    - `calc_runtime` — «Наработка по тегам состояний БДРВ (до 16 тегов, окно до 31 суток, бюджет 24 тего-суток):

## Решения Д9б (Ruling)

**Д9-R91 — автотест «агент = калькулятор».**
- **Случаи** (`build_cases(analog, discrete, today)`): на каждый аналоговый тег — шесть видов по порядку, на каждый
  тег состояния — один:

  | Вид (`kind`) | Инструмент | Период | Ключи | Вопрос |
  |---|---|---|---|---|
  | `now` | `tag_now` | — | `value` | «Что сейчас по {tag}?» |
  | `avg_prev_shift` | `tag_period` | `prev_shift` | `avg` | «Какое среднее по {tag} за прошлую смену?» |
  | `minmax_last_24h` | `tag_period` | `last_24h` | `min`, `max` | «Какие минимум и максимум по {tag} за последние сутки?» |
  | `range_yesterday` | `tag_period` | `yesterday` | `range` | «Какой размах по {tag} за вчера?» |
  | `avg_span` | `tag_period` | вчера 08:00–12:00 | `avg` | «Какое среднее по {tag} {дд.мм.гггг} с 08:00 до 12:00?» |
  | `profile_last_8h` | `tag_series` | `last_8h` | `first`, `last` | «Как менялся {tag} за последние 8 часов: какое значение в начале и в конце?» |
  | `runtime_yesterday` | `calc_runtime` | `yesterday` | `hours_top` | «Какая наработка по {tag} за вчера: сколько часов в каждом состоянии?» |

  - `id` случая — `"{tag}:{kind}"`.
  - `today` — местная дата историана из `asof` калькулятора `tag_now` (`hist_today(stand, tag)`).
  - У `avg_span` `start` и `end` — ISO без пояса (время историана).
  - Матрица двойника `bench/match.twin.json`: аналоговые `20FAKE_201_PV`, `20FAKE_202_PV`, `20FAKE_104_PV`, тег
    состояния `20FAKE_210_RUN` — всего 19 случаев.
- **Ключи из вывода хода** (`key_values(case, item)`):
  - `value`, `avg`, `min`, `max`, `range` — поля элемента;
  - `first`, `last` — из `profile`;
  - `hours_top` — `hours` состояния с наибольшими часами среди состояний со значением (состояние «нет данных»,
    `value: null`, не берётся, m-14).
- **Вызов случая** (`case_call(case, turn)`): последний вызов `pcbk_<case.tool>` хода, у которого во входе есть тег
  случая (без регистра).
- **Вердикт** (`judge_case(case, turn, calc)`, `calc` — ответ калькулятора на аргументы этого вызова):
  1. ход с ошибкой или без конца — `timeout`;
  2. вызова нет: в тексте есть числа величин (`numbers.parse_numbers` без неизмеряемых) — `mismatch` с заметкой
     `no_tool`, иначе `no_number`;
  3. элемент тега `no_data` (данных за период нет) — мягкий `no_data` (I7). Прочее, где вывод не `ok`/`partial` или
     элемент тега не `ok` (`unavailable`, `error`, `rate`, `busy`, `timeout`, `refused`, `budget`, `no_value`), —
     `service`;
  4. период не тот (`period_ok`) — `wrong_period`:
     - у готового периода `input.period` или `output.period.preset` равен периоду случая;
     - у `last_24h` и `last_8h` годится и свой период длиной 24 или 8 ч ± 60 с;
     - у `avg_span` `output.period.start` и `end` отличаются от времени случая (в поясе вывода) не больше чем на
       60 с;
  5. каждый ключ есть в тексте ответа: `numbers.matches(value, text)` — округление до показанных знаков. Нет хоть
     одного — `mismatch`, если чисел величин в тексте нет — `no_number`;
  6. сверка с калькулятором на тех же аргументах:
     - период закрыт (`output.period.open` — ложь) — ключи `calc` равны ключам вывода (`1e-9` относительной), иначе
       `service`;
     - период открыт (`output.period.open` — истина: `last_24h`, `last_8h`, а в первые 5 минут после смены и
       `prev_shift`) и `tag_now` с другой меткой `time` — заметка `calc_moved`, вердикт не меняется. Решает флаг
       вывода, а не вид случая (m-15);
  7. иначе — `match`.

  `MATCH_VERDICTS = ("match", "mismatch", "wrong_period", "no_number", "no_data", "service", "timeout")`.
  `HARD = {"mismatch", "wrong_period"}` — это неуспех 4. `service` — сбой службы, не модели: это блокер «того же
  кода», разбор — до закрытия дня. `no_data` — не сбой и не провал модели: данных за период у тега нет.
- **Агент проверки `bench-calc`.** `calc_agent_args(cases)`:
  - узел «Узел проверки калькуляторов»;
  - пять инструментов чтения;
  - теги случаев;
  - инструкция `CALC_PROMPT` без цифр — «Ты — помощник технолога по узлу «{node}»…», по строке на вид
    вопроса, «числа называй, как их вернул инструмент, можно округлить до двух знаков после запятой», «отказ или
    нет данных — скажи как есть»;
  - `student_reply` — согласие стенда.

  Сохраняет агента `Stand.save_agent(place, args)`; `already` — годится. Перед вопросами `prepare()` ждёт `ready` в
  `GET /pcbk/api/agents` не дольше 60 с. `close()` отправляет агента в архив.
- **`MatchRunner(chat, stand, place, cases, out, *, turn_timeout_s=300.0, sleep=time.sleep)`:**
  - `prepare()` — вход, пробуждение места (≤ 120 с), `mcp=connected` (≤ 90 с), агент;
  - `run() -> list[MatchResult]` — по случаю: новая сессия, вопрос агенту `bench-calc`, `wait_idle`, `parse_turn`,
    вызов случая, `calc_patient(stand, tool, call.input)`, вердикт. Запись — строкой в `OUT/match.jsonl`: id случая,
    вердикт, заметки, id сессии, ход целиком. В stderr — только «случай k/N: <вердикт>». `503 WorkplaceNotReady` —
    один `wake()` и повтор случая;
  - `close()` — `abort` открытых сессий, агент — в архив.
- **`render_match(results, cases) -> str`** — Markdown: «ТЕГ-n · вид · инструмент · период · ключи · вердикт ·
  заметки» и итог «случаев N; match k; жёстких (неуспех 4) h; service s; нет данных d; прочих o». Имён тегов и
  чисел нет.
- **CLI** (`python -m pcbk_bench …`, конфиг — `MatchConfig` JSON):
  - файл конфига окна — `$JOB/pcbk-d9/live/match.config.json`; ключи — `stand`, `place`, `login`, `cases` (путь
    `match.cases.json`), `out_dir`, `turn_timeout_s`, `source`; пароль — `secrets/<login>.pw` рядом со `stand.json`;
  - `match-cases MCONFIG` — случаи окна (`cases_from_agent`, I7):
    - аналоговые теги — только живые (`live` и `kind` — из калькулятора `catalog_search` по имени тега) из раздела
      «Теги узла» файла самого нового видимого агента места `source.place`, до 3;
    - недостающие до 3 — первые живые аналоговые из `catalog_search("_pv", 50)`, без повторов;
    - тег состояния — живой дискретный из тегов агента, иначе первый живой дискретный из
      `catalog_search("_run", 50)`, иначе из `"_opn"`;

    пишет `cases` (`0600`), печатает только «случаев N: аналоговых a (из агента k), состояний d»;
  - `match MCONFIG [--only basic]` — прогон; печатает итог `render_match` (без тегов), пишет `OUT/match.md`.
    `--only basic` — без видов `profile_last_8h` и `runtime_yesterday` (проба не прошла). Режимов сухого прогона нет
    (I6, решение контроллера);
  - `probe-calc MCONFIG` — проба Д9-R93, печатает только коды.

**Д9-R94 — доброволец: показ, задание, секундомер, протокол.**
- **Показ (≤ 10 мин, ведёт владелец, учётка `d9-probe-show`, узел — любой, но не узел добровольца).** Сценарий —
  `docs/checks/D9b.md`, раздел «Показ»:
  1. вход; предупреждение — «Понятно»;
  2. слева «Конструктор агентов» → «Нужен агент по <узел показа>: что сейчас и что было за прошлую смену по
     <параметр>»;
  3. ответы на вопросы Конструктора; из списка тегов — свой;
  4. черновик → «да»;
  5. «Мои агенты» → новый агент → «Что сейчас по <параметр>?»;
  6. «Какое среднее за прошлую смену?»;
  7. вкладка «Калькуляторы» → поиск тега по слову → «Сводка за период», «Прошлая смена» → «Посчитать» → то же
     среднее → вкладка «Чат».

  Вопросы добровольца — только во время показа.
- **Задание на листе** (дословно): «1. Войдите своим логином. 2. Соберите вместе с Конструктором агента по узлу,
  который вы знаете. 3. Спросите своего агента, что сейчас по одному параметру и что было за прошлую смену.
  4. Проверьте одно число на вкладке „Калькуляторы“. Если застрянете — скажите „стоп“: это тоже результат.»
- **Секундомер (владелец):**
  - T0 — первое сообщение Конструктору;
  - T1 — сообщение «Агент … сохранён»;
  - T2 — первый ответ своего агента с числом;

  Сессия после окна сверяет T1 с `created_at` учёта агентов места 10 (`Stand.agent_rows(10)`, только время).

  «делайте, как считаете нужным». Любая подсказка по сути (что писать, какой тег, что хочет Конструктор) — «помощь»:
  минута и суть — в протокол. Помощь можно дать, если доброволец сказал «стоп», — разговор доводится до конца ради
  данных.
- **Пределы.** На задание (T0 → T3) — не больше 45 минут. Итого на добровольца — час: показ, задание, разговор.
- **Успех ручной половины** — все условия:
  - агент сохранён за один разговор с Конструктором;
  - помощи после показа нет;
  - T0 → T3 ≤ 45 мин;
  - агент ответил числом;
  - среднее, минимум и максимум «за прошлую смену» у агента и на вкладке совпали после округления до показанных
    знаков.

  «Что сейчас» сверяется со вкладкой только при той же метке времени, иначе — «значение обновилось», не расхождение.
- **Протокол** (`docs/checks/D9b.md`, таблица; имени добровольца нет — «доброволец № 1»):
  - дата, модель; длительность показа; T0–T3;
  - разговоров с Конструктором; реплик добровольца до сохранения;
  - помощь (минута — суть);
  - инструменты агента;
  - «сейчас»: та же метка, равно ли; «за смену»: равно ли;
  - сбои стенда (коды);
  - ответы на три вопроса: «что было непонятно», «где застряли», «что бы поменяли» — пересказом, без данных;
  - итог.
