# Д19 — подсчёт агрегатов: инструмент службы `equipment` (15.10.2026)

**Повод.** Занятие 15.10: на «Какие насосы?» агенты дают список, на «Сколько насосов?» — нет ответа. Воспроизведено
под student_test (Opus 5.5): `catalog_search` отдаёт ≤ 50 тегов за запрос («Работа Насос» — найдено 76, показано 50);
у насоса несколько тегов (`_RUN`, `_LOD`), группировать их модели приходится самой при 8 шагах; правило «числа — только
из ответов инструментов» (AGENTS.md п.1) — число по списку модель считает своим и оговаривается; «по описаниям не
подтвердить, что это КДМ-1».

**Решение владельца 15.10:** инструмент службы «Агрегаты» — служба сама группирует теги и считает, агенты называют её
число; в инструкциях агентов — «все теги стенда относятся к КДМ-1». Принцип тот же, что у `calc_deviation` (Д13):
считает служба, а не модель.

## Определения

- **Основа** тега — имя без последнего `_ХВОСТА` (`catalog._stem`): `21FAKE30_RUN` → `21FAKE30`.
- **Агрегат** — основа, у которой в белом списке есть хотя бы один тег с хвостом привода или состояния:
  `RUN, LOD, SPD, CUR, OP, OPN, CLS, ON, OFF, STOP, FLT, ALM` (docs/research/05 §3.5).
- **Точка измерения** — основа только с хвостами измерений (`MV`, `PV`, `SP` и прочие) — агрегатом не считается
  («Расход после насоса» — не насос).
- Агрегат подходит запросу, если все слова запроса есть в `norm(имя + описание)` хотя бы одного его тега — тот же
  разбор, что у `Catalog.search`.

## Task 1: служба — `equipment` (core/pcbk_core/data)

**Files:** `catalog.py` (группировка), `service.py` (`equipment`, `_equipment`), `mcp_server.py` (инструмент,
описание), тесты `core/tests/test_catalog*.py`/`test_service.py`/`test_mcp.py` (по месту существующих).

**Interfaces — Produces:**
- MCP-инструмент `equipment(query: str, with_state: bool = False)` → в местах `pcbk_equipment`; только чтение.
- Ответ (`status: ok`): `query`; `units_total` — число агрегатов; `tags_total` — число тегов этих агрегатов;
  `measure_points_total` — число подходящих точек измерения (отдельно, не агрегаты); `units` — ПОЛНЫЙ список без
  обрезки на 50 (до 300; больше — `truncated: true` и честная заметка): по агрегату `code` (основа), `description`
  (описание тега `_RUN`, иначе первого тега агрегата), `signals` (хвосты, отсортированные), `group` (префикс кода до
  первой буквы или до `_`: `21`, `22`, `TVF` …); `groups` — число агрегатов по группам; `notes` — по-русски:
  что такое агрегат здесь («основа имени с сигналом привода или состояния»), что пары кодов с одинаковым описанием
  могут быть одним механизмом, что каталог стенда — участок КДМ-1.
- `with_state=true`: для агрегатов с тегом `_RUN` служба читает текущие значения тем же путём, что `tag_now`
  (внутренние пачки по пределу `tag_now`, один вызов инструмента — один счёт частоты), и добавляет `state`:
  `running` (1), `stopped` (0), `no_data` (нет значения или качество недостоверное), `no_run_tag` (у агрегата нет
  `_RUN`); `state_counts` по этим четырём; по агрегату — `state`, время значения и пометка «не менялось больше суток»,
  если служба её даёт для `tag_now`. Предел — 120 агрегатов с `_RUN` за вызов; больше — отказ с подсказкой сузить запрос.
- Пустой или слишком общий запрос — тот же отказ по аргументам, что у `catalog_search`. Учения, частота, журнал
  вызова (`call.summary`: «агрегатов N, тегов M») — как у остальных инструментов.
- Описание инструмента (TOOL_DESCRIPTIONS): когда звать («сколько насосов/задвижек/мешалок…», «сколько в работе»),
  что считает служба, что число из ответа называть как есть.

**Тесты (вымышленные теги):** группировка `_RUN`+`_LOD` одной основы → 1 агрегат; основа только с `_MV` → точка
измерения, не агрегат; 76 тегов → полный список без обрезки; `with_state`: 1/0/недостоверное/нет `_RUN` → четыре
счётчика; > 120 агрегатов с `_RUN` при `with_state` → отказ; MCP — инструмент в списке, схема аргументов.
