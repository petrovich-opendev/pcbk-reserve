**Долг** (осознанно не делаем в Д4а):
- оценка по байтам (делитель 3) — не строгая верхняя граница для
  патологического тела (base64, длинные числа). Расхождение ловит сверка с
  `/key`, настоящий токенайзер в прокси не ставим;
- плата Gemini за хранение кэша ($0,042 за млн токенов в час) в оценку не
  входит: это доли цента на вызов;
- `/generation` не дозапрашивается для `unknown` старше 9 минут: такие вызовы
  остаются в бюджете по оценке. Досверка по `/key` — вся, а не по вызовам.

**Goal:** серверный слой `pcbk-core` получает вторую роль — LLM-прокси. Это
OpenAI-совместимая точка `/llm/v1/chat/completions`: токен места, точный
список моделей, тело запроса собирается заново, провайдер закреплён, предел
шагов на ход, цена каждого вызова — в журнале SQLite, доли $100 и общий
бюджет $1000 с жёстким стопом. Вызов, цена которого ещё не пришла или так и
не нашлась, стоит в бюджете по верхней оценке. Владелец видит на странице состояния строку
«LLM-прокси и бюджет» с «расход $X из $1000». Учения «LLM-прокси остановлен» и
«402 от OpenRouter» (заглушкой, без денег) показывают сбой снимками. Живая
проверка §11 п. 4 отвечает, приходит ли цена в последнем чанке потока и видит
ли её прокси. Рабочие места к прокси подключает Д4б.

**Architecture:** продолжение `pcbk_core` из Д3а/Д3б. Добавляются:
- роль `llm` (`LlmRole`) — на протоколе `Role`, её крючки уровня приложения
  ставятся только через `install(app)`;
- общий реестр крючков приложения (`hooks.py`): один обработчик 422 с
  разбором по префиксу пути и один `BodyLimit` с пределом по префиксу. Без него
  предел тела Д3б в 64 КиБ отказывал бы каждому запросу к модели;
- проход к OpenRouter на `httpx`. Поток идёт клиенту байт в байт, рядом его
  читает наблюдатель SSE: берёт цену из последнего чанка, иначе дозапрашивает
  `/generation` по `X-Generation-Id`;
- журнал вызовов `llm_calls` в той же SQLite, что журнал событий Д3б. Каждый
  вызов при открытии получает верхнюю оценку цены. Пока цены нет, в долях и в
  общем бюджете стоит оценка. Общий расход сверяется с расходом ключа по
  `GET /key`.

Пороги бюджета держит сторож (как пороги свежести историана в Д3а). Текст
строки в «внимании» и «сбое» постоянный, а число расхода уходит в новое поле
`note` — его журнал сторожа не сравнивает.

## Global Constraints

Действуют Global Constraints Д1, Д2, Д3а и Д3б целиком: закреплённые образы
через `deploy/images.lock`; секреты и данные заказчика никогда не попадают в
git и в вывод проверок; секреты контейнерам — только файлами; `docker.sock` —
только у `sp-ro`/`sp-ctl`; сети с закреплёнными подсетями; наружу — только
8443 `edge`; людям — по-русски, в коде — английские имена; Dify не трогаем;
свои скрипты — в `$JOB` (каталог `pcbk-d4` внутри `$CLAUDE_JOB_DIR/tmp`);
`CORE_PYTEST`, охрана выхода, крючки только через `Role.install(app)`. Д4а
добавляет:

- **Ключи OpenRouter — только файлами** `${SECRETS_DIR}/openrouter.key` и
  `${SECRETS_DIR}/openrouter-mgmt.key` (`0444` в каталоге `0700`, Д2-решение 5).
  Кладёт их владелец; ключ — отдельный для резервного контура, с лимитом
  $1000 без сброса. Пустой файл ключа управления означает «нет ключа». Файл
  `0444` не перезаписывается: смена — `rm -f`, запись, затем
  `docker compose up -d --no-build --force-recreate core`. Ключ читается при
  старте процесса, а привязанный файл секрета — это прежний inode. Сессия
  ключ не читает: ни `cat` на экран, ни в `$JOB`, ни в файл заголовка. Для
  проверок — только `stat`, `grep -c`, `grep -c -F -f <файл ключа>` (с
  положительным контролем `[ -s <файл> ] && grep -c -F -f <файл> <файл>` →
  `1`). Запросы с ключом делает `curl` в контейнере, файл смонтирован только
  на чтение: `--variable KEY@/k --expand-header 'Authorization: Bearer {{KEY:trim}}'`.
  Ключ не появляется ни в
  окружении контейнера, ни в журнале процесса, ни в журнале вызовов, ни в
  `docs/checks`. Файл шаблонов проверки на секреты дополняется строкой
  `sk-or-[A-Za-z0-9-]{16,}`. Положительный контроль:
  `printf 'sk-or-v1-%s\n' 0123456789abcdef0123 | grep -c -E -f <шаблоны>` → `1`.
- **Токены LLM** — файлы `student-NN.llm-token` из Д2 и новый `ops.llm-token`
  (48 шестнадцатеричных знаков, `0400`, только на сервере). Хеши sha256 лежат в
  `${SECRETS_DIR}/llm-tokens` (формат `TokenTable` Д3б: `<id> <sha256>`, файл
  `0444`). Это отдельная таблица: токен данных к `/llm` не подходит, токен LLM к
  `/api/data` и `/mcp` — тоже. Тестовые токены — не 48 hex
  (`"test-llm-token-student-01"`).
- **Деньги.** У каждой живой проверки с моделью записан потолок: весь Д4а
  тратит не больше $0,05 (сырой поток и 3–4 вызова через прокси; модель
  `openai/gpt-6-luna`, `max_tokens` ≤ 400). До первой траты проверяется
  остаток: `/key` и, если есть ключ управления, `/credits`. Учения до OpenRouter
  не доходят: `DRILL_LLM=402` подменяет ответ внутри процесса. Все вызовы идут
  на счёт `ops`, доли студентов не трогаются.
- **Учёт денег не знает нуля по умолчанию.** Вызов без известной цены (идёт,
  ждёт `/generation`, цена не нашлась, потерян при перезапуске) стоит в долях и
  в общем бюджете по верхней оценке (Д4а-R13). Настоящая цена её заменяет.
  Молчание учёта видно на странице: неизвестная цена, долгий дозапрос,
  расхождение с `/key`, «журнал вызовов не пишется».
- **Содержимого разговоров нет нигде, кроме потока клиенту.** В журнале
  процесса, журнале вызовов, журнале сторожа и `docs/checks` — только числа,
  коды, имена моделей и провайдеров, `ses_…` (id сессии OpenCode). Фильтр
  `OneLine` Д3б пишет в журнал первую строку текста исключения, поэтому в
  тексты исключений кода LLM не кладутся тело запроса, чанки и ответ модели —
  только коды, имена и длины (П21). Логгеры `httpx` и `httpcore` — не ниже
  WARNING (`logs.QUIET_LOGGERS`): на INFO они пишут адрес каждого запроса.
- **Запрос к OpenRouter собирает прокси.** Тело строится заново из белого
  списка, заголовки — свои (`Authorization`, `Content-Type`, `Accept`), от
  клиента не пересылается ничего.
- **Отказы прокси** — HTTP-ошибки с телом OpenAI вида
  `{"error": {"message": <русский текст>, "type": "pcbk", "code": "pcbk_…"}}`.
  Повторяемые коды (429, 502) — только для временного; отказы по бюджету,
  модели, шагам и выключателю — 400/402/403. В `code` нет слов `exhausted`,
  `unavailable`, `overloaded`, `rate`: по ним OpenCode может счесть ошибку
  повторяемой. В текстах отказов нет чисел, кроме предела шагов (16), и нет
  сумм. OpenCode 1.18.33 сверяет с `/429|500|502|503|504|524/` и текст, и
  тело ответа (`session/retry.ts:34`, `:96`), так что «$500» в тексте
  превратило бы отказ в пять повторов. Как OpenCode показывает отказ в чате,
  проверяет интеграционный тест Д4б. 401 и 413 на `/llm/` — тоже в этой форме
  (П19): у 401 — `pcbk_unauthorized` и `WWW-Authenticate: Bearer`, у 413 —
  `pcbk_body_too_large`; строки журнала — прежнего вида Д3б
  (`outcome=unauthorized channel=llm path=…`, `outcome=too_large path=… limit=N`).
- **Строки сторожа:** в `warn`/`fail` текст `detail` постоянный, меняющиеся
  числа — только в `note` (правило журнала Д1: переход — смена `state` или
  смена `detail` в `warn`/`fail`).
- **Охрана выхода** (Д3б-R6, Д4а-R18) пускает историан и хост OpenRouter из
  `OPENROUTER_BASE_URL` — по имени. Адреса разрешённых имён держит кэш:
  всё, что видели за последние 30 мин, сбой DNS прежние адреса не затирает.
  Кэш обновляет фоновый поток раз в 30 с. В потоке цикла событий хук DNS не
  зовёт никогда: промах там — отказ и внеочередное обновление в фоне. Строку
  «охрана выхода: разрешено N направлений» пишет `egress.install_guard`.
- **Ход и предел шагов** (research/09 §2.4, §9 п. 6; OpenCode 1.18.33). Ключ
  хода — `(вызывающий, x-parent-session-id или X-Session-Id)`. Инструмент
  `task` в образе места закрыт (Д4б, `"task": "deny"`), а счёт подагента в ход
  родителя остаётся защитой (`session/llm/request.ts:196–200`). Что начинает
  новый ход:
  - последнее сообщение — «настоящее» `user` с новой меткой. Метка —
    «хеш текста + число сообщений». Повтор того же запроса (OpenCode повторяет
    до 5 раз, `session/retry.ts:31`) метку не меняет и ход не сбрасывает;
  - последнее сообщение — продолжение после сжатия, а последнее «настоящее»
    `user` в теле — с другим текстом, чем у текущего хода. Так бывает, когда
    OpenCode сжимает разговор на первом шаге нового вопроса
    (`session/prompt.ts:1164–1166`). После сжатия модели уходит
    `[user «What did we do so far?», сводка, …сохранённый хвост…, user
    продолжения]` (`session/message-v2.ts:235`, комментарий `:582–583`), и новый вопрос
    лежит в хвосте (`session/message-v2.ts:569–572`).

  Продолжение — сообщение `user`, у которого любая часть `text` равна строке
  OpenCode «Continue if you have next steps, or stop and ask for
  clarification if you are unsure how to proceed.» или оканчивается ею
  (`session/compaction.ts:531`, вариант с префиксом о вложениях — `:529`).
  Рядом бывает часть `PROMPT_PLAN` или `BUILD_SWITCH`
  (`session/reminders.ts:25–46`). «Настоящее» `user` — не продолжение и не
  «What did we do so far?». Продолжение без «настоящего» `user` в теле или с
  тем же текстом — тот же ход. Подагент нового хода не начинает. Запрос без
  инструментов (заголовок разговора, сам запрос сжатия с `tools: {}`,
  `session/compaction.ts:429`) шагом не считается, в журнале у него
  `step = 0`. Отказ OpenRouter до начала ответа (`cost_source = none`) шаг
  возвращает: модель не отвечала.
- **Роль по договору `Role` Д3а** (`core/pcbk_core/app.py`: `health()` —
  «быстрая проверка без ввода-вывода: вызывается в цикле событий»;
  `main.build_roles`: ошибка настройки — роль с причиной, процесс жив;
  предпроверка Д3б F4, F9, F23):
  - конструкторы `LlmRole`, `Ledger`, `Upstream` без ввода-вывода.
    `core.db` и таблицы открываются в начале `lifespan` через
    `asyncio.to_thread`;
  - проверка записи журнала — в фоне раз в 30 с (`asyncio.to_thread`),
    `health()` и `health_json()` читают только запомненный итог;
  - учёт журнала вызовов в памяти — синхронно, в том же участке без `await`,
    что проверки (атомарность «проверки → резерв»). SQLite в цикле событий не
    трогается (F9 Д3а; Д3б пишет события только через `to_thread`, решение I2
    задачи 5): строки пишет **один поток-писатель** `Ledger` из очереди FIFO,
    порядок `INSERT` → `INSERT OR REPLACE` держит он один. Запись ждёт
    блокировку не дольше `WRITE_TIMEOUT_S = 0.5`: долгая блокировка — сбой
    записи со счётчиком, а не остановка цикла. Открытие, проверка и чтение —
    до `SQLITE_TIMEOUT_S = 5.0`, только в потоках (имена — как в `events.py`);
  - ошибки настройки LLM (переменные `LLM_*`, нечитаемый файл ключа, журнал
    не открылся) — `config_error` роли `llm`. `/healthz/llm` и строка сторожа —
    сбой с причиной, `/llm/` — 403 `pcbk_config`. Процесс жив, служба данных
    работает;
  - нечитаемый `llm-tokens` — не ошибка настройки, а `tokens_error`, как у
    `core-tokens` Д3б (F4): `/llm/` — всем 401, строка — сбой «токены LLM не
    читаются», опрос `/key` и дозапрос цен идут (П23);
  - тесты не читают `/run/secrets`: `build_roles(settings, LLM_ENV)` берёт
    пути ключей и `llm-tokens` из каталога сессии тестов (П6, F4 Д3б).

## Решения по умолчанию (Ruling)

**Д4а-R11 — пороги и число на странице.** Служба отдаёт числа
(`/health/llm`). Число строки `spent_usd` — без резервов идущих вызовов:
резерв ставится на каждый вызов и снимается через секунды, и полоса у порога
мигала бы на каждом такте. Резервы — отдельным числом `reserved_usd` в
`note`. Отказывает прокси по итогу с резервами (Д4а-R13). Пороги 50/80/95 % и
стоп на 100 % считает сторож. «Внимание»
на 50, 80 и 95 %, «сбой» на 100 %. Текст полосы постоянный («израсходовано
больше 80 % бюджета»), а «расход $X из $1000» — в `note`. Журнал сторожа
записывает смену полосы, но не каждый цент. Строка называется «LLM-прокси и
бюджет» — это своя строка роли, как обещал Д3а-R5: учение с прокси не
окрашивает «Службу данных». **Цена ошибки:** переход порога виден с задержкой
не больше такта сторожа.

**Д4а-R12 — как прокси отказывает.** Отказ — ошибка HTTP с русским текстом, а
не поддельный ответ ассистента: преподаватель не должен принять текст прокси за
слова модели. Коды:

| Случай | Статус | `code` |
|---|---|---|
| нет или неверный токен (и всем при нечитаемом `llm-tokens`) | 401 + `WWW-Authenticate: Bearer` | `pcbk_unauthorized` |
| тело `/llm/` больше `LLM_MAX_BODY_BYTES` (отвечает `BodyLimit` до маршрута) | 413 | `pcbk_body_too_large` |
| выключатель `LLM_STATE=stopped` | 403 | `pcbk_stopped` |
| нет ключа OpenRouter | 403 | `pcbk_key_missing` |
| тело не объект, плохие сообщения | 400 | `pcbk_body_refused` |
| модель не из списка | 403 | `pcbk_model_refused` |
| доля вызывающего израсходована | 402 | `pcbk_share_spent` |
| общий бюджет израсходован | 402 | `pcbk_budget_spent` |
| больше 16 обращений за ход | 403 | `pcbk_turn_limit` |
| у вызывающего уже `LLM_CALLER_CONCURRENCY` (3) идущих вызовов | 429 + `Retry-After: 2` | `pcbk_busy` |
| ошибка настройки роли (`config_error`) | 403 | `pcbk_config` |
| OpenRouter: кончились деньги / лимит ключа | 402 | `pcbk_money_out` / `pcbk_key_limit` |
| OpenRouter: ключ отклонён / отказ по региону | 403 | `pcbk_key_rejected` / `pcbk_region` |
| OpenRouter: 429 или 402 `in_flight_budget` | 429 (+ `Retry-After`, если был) | `pcbk_upstream_wait` |
| OpenRouter: прочие 4xx | тот же статус, текст OpenRouter до 300 знаков | `pcbk_upstream_rejected` |
| OpenRouter: 5xx, 408, нет связи | 502 | `pcbk_upstream_down` |

Ошибка посреди потока (событие SSE `error` при статусе 200) идёт клиенту как
есть. Прокси её классифицирует и учитывает, но текст не переписывает.
**Цена ошибки:** если OpenCode всё же повторяет 402/403, в Д4б коды меняются
одной строкой таблицы `REFUSALS`.

**Д4а-R13 — цена вызова и что стоит в бюджете, пока её нет.** Источник цены по
порядку: `usage.cost` из последнего чанка потока (`stream`), затем из тела
ответа без потока (`body`), затем `GET /generation?id=` (`generation`). Дозапрос
повторяется после 404 через 1, 2, 4, 8, 15, 30, 60, 120 и 300 с, в сумме около
9 минут. Генерация у точки Vertex после обрыва идёт до конца, и цена
появляется только после неё. Если цена так и не нашлась — `unknown`.

Каждый вызов при открытии получает **верхнюю оценку** по ценам закреплённой
точки (`ModelPolicy`, research/08 §3):
`ceil(байты собранного тела / 3) × max(цена входа, цена записи кэша) + max_tokens × цена выхода`.
В доле вызывающего и в общем бюджете вызов стоит так:
- идёт (`open`), ждёт дозапроса (`pending`), цена не нашлась (`unknown`),
  потерян при перезапуске (`lost`) — по оценке;
- цена пришла — по цене.

OpenRouter не останавливает генерацию после обрыва потока у Google Vertex
(там Gemini и Claude) и берёт деньги за весь ответ (документация streaming,
раздел Stream Cancellation). Поэтому ноль вместо оценки был бы тратой мимо
бюджета.

Проверка до вызова: учтённое вызывающего (с оценками идущих вызовов) ≥ его
доли → отказ; то же для общего бюджета. Оценку самого вызова проверка не
прибавляет, иначе последний доллар доли был бы недоступен премиуму.
Перерасход поэтому не больше оценки одного вызова:
- настоящая цена вызова премиума при окне образа 131 072 — до ≈$0,49
  (131 072 × $2,50/млн за запись кэша + 16 000 × $10/млн), оценка того же
  вызова по байтам — около $0,6;
- оценка на пределе тела 1 МиБ — ≤ $1,03.

Окно 131 072 само вход не ограничивает. OpenCode сверяет переполнение по
токенам прошлого шага (`session/prompt.ts:1161–1167`), и следующий запрос
больше окна на выводы инструментов. Вход ограничивает прокси: `/llm/` — не
больше `LLM_MAX_BODY_BYTES` = 1 МиБ. Одновременных вызовов у вызывающего — не
больше `LLM_CALLER_CONCURRENCY` = 3 (шаг, заголовок разговора и подагент).
Сверх этого — 429 `pcbk_busy`, и OpenCode повторяет его сам, не больше 5 раз.

Общий расход сверяется с OpenRouter. Точка отсчёта хранится под отпечатком
ключа: `llm_meta` ключ `key_base_usd:<первые 12 знаков sha256 ключа>`, сам ключ
не хранится. Она ставится при первом удачном опросе `/key` этим ключом, только
при `LLM_KEY_DEDICATED=on` и только когда в журнале нет идущих (`open`) и
ожидающих (`pending`) вызовов. Иначе их оценка потом сменится ценой, и
расхождение навсегда сдвинется. Ставится так:
`key_base_usd = usage ключа − учтённое журналом`.
Дальше `key_spent_usd = usage − key_base_usd`, пока точки отсчёта нет —
`null`. Новый ключ (другой отпечаток) или переход `off → on` — новая точка
отсчёта: у нового ключа прежний расход в бюджет не попадает, а сверка не
глохнет. Итог для отказов прокси — `max(учтённое журналом, key_spent_usd +
резервы идущих вызовов)`: при расходе по ключу выше журнала резервы тоже в
итоге. Сторож предупреждает при `key_spent_usd` больше учтённого на $1.
Условие — отдельный ключ под резервный контур (требование к владельцу). Если
ключ общий, `LLM_KEY_DEDICATED=off`: сверки нет, `key_spent_usd` = `null`.
Второй, независимый от журнала стоп — лимит ключа $1000 без сброса на
стороне OpenRouter (просьба к владельцу, прокси понимает его отказ как
`key_limit`).

Предел `LLM_CALLER_CONCURRENCY` = 3 рассчитан на шаг хода, заголовок
разговора и один запас (вторая вкладка студента). Подагентов в образе нет:
`task` закрыт (Д4б). Если `task` понадобится (Д7), подагентам нужны свои 16
шагов и предел одновременности «подагенты + 2» — это решение Д7, не
Д4.

**Цена ошибки:** оценка по байтам завышает цену обычного текста примерно
вдвое, поэтому неизвестная цена съедает долю быстрее настоящей. На
патологическом теле (длинные числа, base64) оценка может оказаться ниже
настоящей цены — такое расхождение ловит сверка с `/key`.

**Д4а-R14 — «кончились деньги» не защёлкивается.** Каждый вызов идёт в
OpenRouter: отказ 402 бесплатный. Первый удачный вызов снимает признак. Опрос
снимает только свой признак: `/key` с `limit_remaining` > 0 или `null` снимает
`key_limit`, `/credits` с остатком > 0 снимает `money_out`. Признак учения
`DRILL_LLM=402` опрос не снимает вовсе, его снимает только пересоздание `core`
без учения. Состояние живёт в памяти. После перезапуска `core` признак вернётся
с первым же вызовом, а с ключом управления — с первым опросом. **Цена
ошибки:** до первого вызова после перезапуска страница может показывать
«норму» при пустом счёте.

**Д4а-R15 — выключатель и учения.** `LLM_STATE=stopped` — настоящий выключатель
администратора: вызовов к модели нет, опросов OpenRouter нет, строка — «сбой».
Учение «LLM-прокси остановлен» пользуется им, а не отдельной ручкой.
`DRILL_LLM=402` отвечает «кончились деньги (учения)» внутри процесса, опрос
`/key` при этом настоящий — он и доказывает, что денег не потрачено. Оба
режима включаются пересозданием `core`
(`docker compose up -d --no-build --force-recreate core`). **Цена ошибки:**
около 20 с на время пересоздания мигают и строки службы данных.

**Д4а-R16 — ключ управления необязателен.** Без него страница не показывает
остаток счёта, а «кончились деньги» видно только по ответам на вызовы. С ним
строка предупреждает при остатке меньше $20. Если `/credits` отверг ключ
управления (401/403 — например, положен обычный ключ), это своё
предупреждение «ключ управления OpenRouter отклонён — остаток счёта не виден».
Состояние основного ключа оно не трогает. Счёт общий с Dify-стендом — это
принятый риск постановки.

**Д4а-R17 — список моделей — константы кода, выбор — переменная.** Семь
кандидатов research/08 с закреплённой точкой и уровнем рассуждения лежат в
`llm/models.py`. `LLM_MODELS` в `.env` сужает список: пусто — все семь (на
время отбора), после Д8 — одно имя. Смена — `.env` и пересоздание `core`, без
пересборки образа. Имя сверяется точным совпадением, поэтому суффиксы
(`:nitro`, `:online`, `:floor` и другие), алиасы `~…` и роутеры `openrouter/*`
отсекаются сами.

**Д4а-R18 — охрана выхода держит адреса разрешённых имён в кэше, DNS в потоке
цикла событий нет** (предпроверка, П2; журнал Д3б: «решить в брифе Д4а»). В Д3б
хук разрешал имя из `allowed` сам, через `getaddrinfo`, в том потоке, что зовёт
`connect`. У `httpx` на asyncio это поток цикла событий. Кэш жил 60 с на любую
запись, неудача тоже кэшировалась. Итог: раз в минуту все потоки SSE и служба
данных ждали блокирующий DNS; одна неудача DNS закрывала OpenRouter на 60 с
(502 `pcbk_upstream_down` у всех, строка «OpenRouter недоступен»); смена набора
адресов CDN между разрешением `httpx` и хука давала ложный `EgressDenied`.
Теперь, для имён из `allowed` (задача 2а):
- множество адресов имени — объединение всех адресов, виденных за последние
  `NAME_KEEP_S = 1800` с. Неудача разрешения множество не меняет
  (stale-if-error); адреса старше 30 мин уходят только при удачном
  разрешении;
- фоновый поток-демон `egress.start_refresh()` разрешает все имена из
  `allowed` сразу (`serve()` ждёт первый круг не дольше `FIRST_WAIT_S = 5` с,
  цикл событий ещё не запущен) и дальше раз в `NAME_REFRESH_S = 30` с;
- в потоке, где идёт цикл событий (`asyncio` видит запущенный цикл), хук
  только читает кэш. Промах — `EgressDenied` и внеочередное обновление в
  фоне, без ожидания;
- в прочих потоках (ворота историана, `to_thread`) промах, как в Д3б,
  разрешается синхронно, не чаще раза в `RESOLVE_RETRY_S = 60` с на имя, и
  найденное входит в множество;
- имя в самом кортеже `connect` в потоке цикла событий — отказ без DNS

      роль зовёт её в фоне раз в `LEDGER_CHECK_S` через `asyncio.to_thread`;
    - **Память — синхронно, SQLite — один поток-писатель** (П5). Каждый метод
      записи сначала меняет память в вызывающем потоке без ожидания, затем
      кладёт операцию в очередь FIFO. Её выполняет один поток-писатель,
      соединение на операцию (`_connect()`, срок `WRITE_TIMEOUT_S`). Поэтому
      порядок `INSERT` → `INSERT OR REPLACE` одной строки держится;
      `asyncio.to_thread` на общем пуле его не гарантировал бы. Цикл событий
      SQLite не касается никогда (F9). При `opened = False` в очередь ничего
      не идёт, работает только память;

      затем `INSERT` с этим `id` — в очередь;

      память: оценка заменяется `charge` закрытой строки; затем
      `INSERT OR REPLACE` всей строки — в очередь. При `cost_source = "pending"` —
      `pending_since[id] = now or ts + duration`;
    - `resolve_started(self, call_id: int, now: datetime) -> None` —
      `pending_since[id] = now` (запуск дозапроса, и после перезапуска);
    - `refused(self, *, ts: datetime, caller: str, session: str | None, model: str, code: str, http_status: int) -> None` —
      строка с ценой 0, `cost_est = 0` и `cost_source="none"`;

      `pending` → `generation` (в сумме оценку сменяет цена) или `unknown`
      (сумма не меняется: остаётся оценка);

      `generation_id`, для дозапроса после перезапуска;
    - `spent(self, caller: str | None = None) -> float` — сумма `charge` из
      памяти, с оценками идущих и безценовых вызовов;
    - `estimated(self, caller: str | None = None) -> float` — часть `spent`,

      `meta_set(self, key: str, value: float) -> None` — память, затем
      `INSERT OR REPLACE` в очередь;
    - `flush(self, timeout: float = 5.0) -> None` — ждёт, пока писатель
      выполнит всё, что поставлено до вызова; не успел — `TimeoutError`.
      Писатель не запущен — сразу выходит. Для тестов и `close()`; в цикле
      событий не зовётся;
    - `close(self) -> None` — `flush()`, остановка писателя, `opened = False`
      (дальше — только память, до нового `open()`). Роль зовёт её на выходе из
      `lifespan` через `asyncio.to_thread`;
    - `totals(self, now: datetime) -> dict` — только из памяти, без SQLite:

      Ключи `spent_usd`, `estimated_usd`, `reserved_usd`, `by_caller`,

      `cost_unknown_24h` (`unknown` за 24 ч, `lost` входит),
      `provider_mismatch_24h` (`provider_ok = 0` за 24 ч);
    - `recent(self, limit: int = 10) -> list[CallRow]` — сначала `flush()`,
      затем чтение из SQLite (`SQLITE_TIMEOUT_S`); новые сверху. Для тестов и

      **Атомарность.** Шаги 7–9 и `begin_call` — один синхронный участок без
      `await`: иначе два одновременных запроса пройдут проверки раньше, чем
      любой поставил резерв. Учёт `ledger` в памяти синхронный, SQLite пишет
      его поток-писатель (задача 4): в участке нет ни ожидания, ни
      ввода-вывода (П5).

      **Учёт — в `finish()`, а не в генераторе** (П7). Starlette 1.7.0 при
      `spec_version` 2.3 (uvicorn 0.54.0) на обрыве клиента отменяет задачу
      `stream_response`, а генератор без `aclosing`: если он ещё не начат
      (обрыв до первого байта — `http.disconnect` уже в очереди) или стоит на
      `yield`, пока `stream_response` ждёт `send`, его `finally` не
      выполнится до сборки мусора. Поэтому:
      - `class LlmCall` — вызов после `begin_call`: `role`, `call_id`,
        `caller`, `session`, `parent`, `step`, время начала, `observer`
        (`SseObserver`), `response: httpx.Response | None`, флаги
        `completed` (поток OpenRouter дочитан) и `upstream_broken` (`httpx`
        бросил при чтении);
      - `async def finish(self, *, error: UpstreamError | None = None) -> None` —
        **идемпотентна** (второй вызов ничего не делает). Сначала синхронный
        учёт без `await`: `inflight − 1` (ключ убирается на нуле),
        `close_call` (статус и цена — по таблице итогов ниже и по `error`),
        `turns.refund(…)` при `cost_source = none`, `role.state.record(…)`,
        строка журнала, `asyncio.create_task(role.resolve_cost(…))` при
        `pending`. Потом `await response.aclose()` под
        `anyio.CancelScope(shield=True)`. Статус без `error`: `completed` —
        по наблюдателю; `upstream_broken` — `upstream_error`; иначе (генератор
        не начат или снят) — `cancelled`;
      - `class LlmStream(StreamingResponse)`: `__init__(self, call: LlmCall, upstream: httpx.Response)`,
        `media_type="text/event-stream"`. Генератор только перекачивает
        `aiter_raw()` и кормит `call.observer`; дочитал — `completed = True`;
        `httpx.HTTPError` — `upstream_broken = True` и конец потока. Учёт —
        в `async def __call__(self, scope, receive, send)`:
        `try: await super().__call__(scope, receive, send)` /
        `finally: await self.call.finish()`;
      - обработчик держит свой `try/finally` на участке от `begin_call` до
        выдачи ответа: `UpstreamError` из `open_chat` → `await call.finish(error=e)`
        и отказ по `REFUSALS`; любое другое исключение → `await call.finish()`
        и дальше. Без потока (`stream: false`) — `await response.aread()` и
        `finish()` в `finally` обработчика.
    - Поток: `LlmStream` отдаёт байты `aiter_raw()` как есть. Обрыв клиента —
      это `cancelled`: поток к OpenRouter закрывается сразу.

    `fmt_total(x: float) -> str` — целое без дробной части (`$1000`).
  - `LLM_STALE_S = 180`, `ACCOUNT_WARN_USD = 20.0`, `DRIFT_WARN_USD = 1.0`,
    `BUDGET_STEPS = (95, 80, 50)`. Вывод `LLM_STALE_S` — комментарием над
    константой, как у `HIST_STALE_S` Д3а: опрос раз в `LLM_POLL_S` (60 с), в
    нём до двух запросов по `POLL_TIMEOUT_S` (15 с), такт сторожа 10 с и запас
    60 с на медленный старт: 60 + 2 × 15 + 10 + 60 = 160 ≤ 180. Тест держит
    неравенство;
  - `check_llm(component: str, title: str, url: str, now: datetime, timeout: float = NET_CHECK_TIMEOUT_S) -> Check` —
    первая подходящая строка. Порядок: сбои, затем «неизвестно», затем
    предупреждения о деньгах мимо учёта и о провайдере, и только в конце
    полосы бюджета. Полоса «больше 50 %» после $500 держится до конца обучения
    и не должна прятать остальное; число расхода при этом не пропадает — оно в
    `note`.
