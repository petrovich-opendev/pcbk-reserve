**Общая оценка.** Код написан тщательно: явные пределы, атомарные записи файлов, строгий разбор входа,
продуманная изоляция мест, тесты-двойники внешних систем. Слабые места — не в отдельных функциях, а в стыках:

- одна SQLite `core.db` на все роли, а повторы записи при блокировке есть не у всех писателей;
- сетевой путь до модели без деградации;
- наблюдаемость: о сбое никто не узнаёт, пока не откроет страницу состояния;
- согласованность мест OpenCode после перезапуска `core`.

## Сильные стороны — сохранить

- **Историан** вынесен из цикла событий в отдельный пул потоков по числу слотов ворот. SQL собирается только из
  закрытых шаблонов, имена тегов проверяются по белому списку.
- **«Сейчас» и периоды** считаются от часов историана, а не от часов сервера.
- **Кэш с «ведущим» вызовом**: обрыв одного клиента не обрывает общую работу. Запись агента и события доводится
  до конца даже при отмене вызова.
- **Файлы агентов** пишутся атомарно (временный файл → fsync → link без перезаписи → fsync каталога).
  Карантин и архив ничего не удаляют.
- **LLM-прокси**:
  - путь от токена до записи вызова атомарен, без `await` в середине;
  - стоимость считается по верхней оценке;
  - тело запроса пересобирается по белому списку полей;
  - наблюдатель SSE не может испортить поток.
- **Шлюз**:
  - пробуждение места — одной задачей на место;
  - scrypt-сверка с ограниченной очередью;
  - сессии хранятся как sha256, cookie `HttpOnly/Secure/SameSite=Strict`;
  - белый список путей OpenCode сверяется по сырому пути.
- **Защита от XSS**: нет `dangerouslySetInnerHTML`, markdown без сырого HTML. Ответы службы разбираются по
  белому списку полей.
- **Контейнеры**: корень только для чтения, `cap_drop: ALL`, пределы памяти и процессов, образы по дайджесту,
  секреты только файлами. Самолечение защищено от петель перезапуска.
- **Двойники внешних систем** (историан, OpenRouter, Docker) в тестах — настоящие объекты с тем же протоколом.

### DATA-04 · критическая · подтверждена · защищённый файл

**equipment(with_state=true) считает агрегат «в работе»/«стоит» по значению с недостоверным (NULL) качеством, не отмечая это**  
`core/pcbk_core/data/service.py` — `_run_state`

- **Код:** service.py:490-506 — `_run_state`: `quality = _quality(row[3])`; переход в `no_data` срабатывает только по `value is None or (quality is not None and quality.startswith("недостоверное"))` — то есть `Quality IS NULL` (из-за чего `_quality()` на service.py:468-472 возвращает `None`) НЕ считается недостоверным и состояние `running`/`stopped` выставляется как доверенное. Это противоречит обработке качества в том же файле: `_series_item` (строка ~1716) считает битым любое `_num(row[3]) != 0`, включая `NULL`; `_spc_valid_points` (service.py:475-487) пропускает точку при `_quality(row[3]) != "хорошее"`, что тоже верно и для `None`.
- **Сценарий отказа:** У агрегата, найденного запросом `equipment(query="насос", with_state=true)`, тег `_RUN` в `Live` имеет последнее значение `1` (например застрявшее при сбое связи с конкретным датчиком/контроллером), а поле `Quality` в этой строке — `NULL` (качество неизвестно/недостоверно, иначе провайдер поставил бы явный ненулевой код). `_run_state` вернёт `"running"` без единой заметки о сомнительном качестве, и это попадёт в `state_counts["running"]` и в `item["state"]` ответа — то есть студенту будет показано заведомо не проверенное на достоверность число «работающих насосов», в отличие от `tag_now`, который честно отдаёт `quality: null` в ответе на тот же случай.
- **Исправление:** В `_run_state` заменить условие `if value is None or (quality is not None and quality.startswith("недостоверное")):` на `if value is None or quality != "хорошее":` — одна строка, поведенчески эквивалентная для всех явных кодов «недостоверное...», но теперь правильно относящая `Quality IS NULL` к `no_data`, как уже сделано для `_series_item`/`_spc_valid_points`/`calc_flow_total` в этом же файле.
- **Уточнение проверяющего:** Предложенное исправление (`if value is None or quality != "хорошее":`) корректно и минимально, приводит `_run_state` в согласие с уже существующим в этом же файле паттерном `_spc_valid_points`. Повышаю серьёзность до critical относительно исходной high: по критерию задачи «неверные числа студенту» — явно показываемый агрегату статус running/stopped без учёта неизвестного качества данных — это именно тот класс дефекта (ложно-доверенное показание на непроверенных данных), который попадает в critical, а не high, независимо от частоты встречаемости.

**Конструктор и все агенты, собранные студентами, не переопределяют read и наследуют глобальный read:{'*':allow} из opencode.json**

- **Уточнение проверяющего:** Предложенное исправление верное и минимальное — добавить явный блок read: {"*": deny} в permission konstruktor.md (после строки 11) и в шаблон render_agent_file (между "*": deny и allow-строками инструментов). ### AGENTS-04 · высокая · подтверждена

**pcbk-health проверяет и самостоятельно лечит только MCP-сервер «pcbk» — про «kb» он не говорит ни слова и не чинит его**  
`student/pcbk-health` — `проверка слова mcp и переподключение /mcp/pcbk/connect`

- **Код:** student/pcbk-health, строки 32–33: регэксп `'"pcbk":\{"status":"([a-z_]+)"'` вытаскивает статус только сервера pcbk из тела ответа GET /mcp; строки 36–50: переподключение делается только `POST /mcp/pcbk/connect`, по метке `/tmp/pcbk-mcp-retry`. Итоговая строка вывода, которую видит сторож — `"200 mcp=$word"` (строка 51), несёт только статус pcbk. Между тем student/config/opencode.json (строки 69–77) настраивает ВТОРОЙ, идентичный по форме remote MCP-сервер `kb` (`http://core:8000/mcp-kb`), подверженный тому же документированному сбою «core лежал при старте места / core перезапустился — место держит состояние failed», что и pcbk (сам же заголовок pcbk-health это описывает для pcbk).
- **Сценарий отказа:** core перезапускается (деплой, авария) при работающих местах студентов. Оба MCP-клиента места («pcbk» и «kb») переходят в failed. pcbk-health каждые ~60 с переподключает ТОЛЬКО pcbk — через пару тактов инструменты службы данных у Помощника снова работают, и health отдаёт «200 mcp=ok» (полностью здоровое место с точки зрения сторожа). Клиент «kb» остаётся failed: его статус в этом же JSON-ответе /mcp просто не читается скриптом, поэтому ни сторож, ни администратор не видят проблему. kb_corrections/kb_correction_add/kb_correction_withdraw у Помощника не работают до следующей ПОЛНОЙ перезагрузки места (которую запускает только очередь agent_reloads при сохранении/правке агента этим же студентом, или ручная команда admin reload) — то есть поправки базы знаний могут быть сломаны у части мест всё занятие без единого внешнего сигнала.
- **Исправление:** В student/pcbk-health добавить такую же проверку для «kb»: вторую регэксп-выборку `"kb":\{"status":"([a-z_]+)"` из того же `resp`, и при failed — аналогичный `POST /mcp/kb/connect` со своей отдельной меткой файла (например `/tmp/pcbk-mcp-retry-kb`, чтобы не делить 60-секундное окно с pcbk), и включить оба статуса в итоговую строку вывода (например «200 mcp=pcbk:ok kb:failed»), чтобы сторож видел состояние обоих MCP-серверов, а не только одного.
- **Уточнение проверяющего:** Предложение в целом верное — добавить вторую проверку статуса "kb" из того же ответа GET /mcp (без нового сетевого запроса), отдельную метку-файл для троттлинга переподключения (не делить 60-секундное окно с pcbk) и отдельный POST /mcp/kb/connect, включив оба статуса в выходную строку. Важное уточнение: сторож уже разбирает строку «mcp=<слово>» по фиксированному протоколу (docs §18, строка 252: ожидает ровно одно из {connected, unknown, disabled} либо помечает warn на прочих словах) — изменение формата строки (например на «mcp=pcbk:ok kb:failed») требует согласованной правки и на стороне watchdog, иначе новый формат может восприняться как неизвестное слово и дать ложный warn вместо точной …

### LLM-02 · высокая · подтверждена

**flush() журнала ждёт текущее значение общей очереди, а не свою операцию — чужая застрявшая запись блокирует несколько одновременных вызовов**  
`core/pcbk_core/llm/ledger.py` — `Ledger.flush / Ledger._put / Ledger._drain`

- **Код:** _put() (строки 512-518) увеличивает общий self._seq и кладёт операцию в общую FIFO self._queue без привязки к конкретному вызывающему. flush(timeout) (520-540) берёт `upto = self._seq` — ТЕКУЩЕЕ значение общего счётчика в момент своего вызова (а не номер именно той операции, ради которой вызван flush), и ждёт метку _MARK, поставленную следом в ту же очередь. Писатель _drain (451-476) обрабатывает очередь строго по порядку и, упёршись в sqlite3.Error у любой операции, повторяет именно её (`while outcome == _RETRY and not stop.is_set(): stop.wait(retry_pause_s); outcome = self._write(...)`), не переходя к последующим элементам, включая метки других вызовов.
- **Сценарий отказа:** 10 мест одновременно присылают запросы. begin_call() каждого кладёт в очередь свою строку open_call. forward() (api.py) вызывает `await asyncio.to_thread(role.ledger.flush, LEDGER_DURABLE_S)` для СВОЕГО вызова A не мгновенно — между тем, как запись A встала в очередь, и тем, как flush(A) реально выполнится на потоке-воркере, event loop успевает обработать begin_call() других мест B, C, D, которые добавляют в очередь СВОИ операции. flush(A) захватывает `upto`, который уже включает записи B/C/D, поставленные ПОСЛЕ записи A. Если хотя бы одна из операций B/C/D застревает в повторах (например, из-за блокировки SQLite от параллельной операции Shares.apply учителя или от своего же ретрая) на несколько секунд, писатель не продвигается дальше неё — и flush(A), а также flush() всех ОСТАЛЬНЫХ вызовов, чей `upto` тоже оказался ≥ застрявшей операции, ждут эти же секунды внутри своего окна …
- **Исправление:** Привязать ожидание в flush() к конкретной операции вызывающего, а не к текущему значению self._seq: методы записи (open_call, close_call, refused, set_cost) под тем же self._lock, где сейчас вызывается _put(), сразу ставят в ту же очередь следом свою собственную метку _MARK с отдельным threading.Event и возвращают этот event (или номер своей операции) вызывающему — так никакая последующая вставка от другого места не может физически встать между записью этого вызова и его же меткой. forward() в api.py тогда ждёт именно эту метку, а не общий flush(LEDGER_DURABLE_S), и перестаёт зависеть от чужих застрявших записей.
- **Уточнение проверяющего:** Исправление в находке корректно и достижимо: достаточно под тем же self._lock, где уже происходит _put() своей строки, сразу ставить в ту же очередь собственную _MARK с отдельным threading.Event и возвращать её вызывающему, вместо отдельного позднего flush(). Важное уточнение, которое стоит добавить к формулировке фикса, чтобы не переобещать: это устраняет только «лишнюю» привязку к операциям, вставленным ПОСЛЕ своей (из-за гонки планирования asyncio.to_thread), но не убирает сам факт, что если застрявшая операция была вставлена ДО операции вызывающего (например, Shares.apply учителя), FIFO-писатель всё равно не продвинется дальше неё — это неотъемлемое свойство одного последовательного …

На такте уборщика ровно в этот момент место перегружено обработкой хода и не успевает ответить на /session/status за BUSY_CHECK_S=2 с (сетевой всплеск, нагрузка gVisor-песочницы) — запрос падает по таймауту, _session_busy возвращает False. _reap видит busy=False и idle>=limit → останавливает место (`self._stop_quiet`) прямо посреди активного хода студента: текущая генерация обрывается, место переходит в sleeping, студент должен заново разбудить место и повторить ход.
- **Исправление:** В _reap/_session_busy не приравнивать сбой пробы к «не занято»: при исключении _NO_ANSWER, не-200 ответе или ошибке разбора — считать результат неизвестным и пропускать остановку на этом такте (как если бы busy было True), а не продолжать к stop. Например, пусть _session_busy сигнализирует отдельно «проба не удалась» (raise или sentinel), и _reap на этот сигнал делает return без остановки, давая следующему такту (через GW_REAPER_TICK_S) шанс на успешную проверку.
- **Уточнение проверяющего:** Если фикс нужен — точнее развести ветки: при `except _NO_ANSWER` (таймаут/обрыв соединения — состояние неизвестно) не приравнивать к «не занято», а дать _reap пропустить останов на этом такте (как будто busy=True); при явном не-200 ответе или ошибке разбора JSON (ответ пришёл, но он некорректен) — оставить текущее «не занято», чтобы не ломать test_bogus_session_status_does_not_break_tick, который проверяет ровно эти случаи. Предложение автора находки сделать то же самое в целом корректно, но стоит явно сохранить разницу между «ответ есть, но мусор» (тестируемый, намеренный путь) и «ответа нет совсем» (непроверенный, более спорный путь).

- **Исправление:** В `TokenTable.from_file` (и/или в `__init__`) добавить проверку повторного ЗНАЧЕНИЯ хеша по аналогии с уже существующей проверкой повтора id — например вести `seen_hashes: set[str] = set()` и бросать `ValueError(f"{path}: строка {n} — хеш уже использован другим id")`, если `parts[1]` уже встречался.
- **Уточнение проверяющего:** Предложение корректно: добавить проверку повторного значения хеша (`seen_hashes`) в `from_file`/`__init__` по аналогии с уже существующей проверкой повтора id. Уточнение серьёзности: триггер — операторская ошибка при ручном заведении токенов (копипаста без перегенерации хеша), а не внешняя атака, поэтому low оправдан; эффект — путаница атрибуции и создающий confusion 401, а не пролом изоляции (сетевая проверка по-прежнему отказывает «чужому», просто неверно диагностирует кто чужой).

### GWB-02 · низкая · вероятна

**После перезапуска core место не получает принудительный reload — старые описания MCP-инструментов**  
`core/pcbk_core/gateway/reload.py` — `AgentReloads.place_ready / AgentReloads._mark_if_needed`

- **Код:** place_ready(n) — крючок Workplaces.on_ready, который зовётся и первым проходом уборщика после старта core (_restore места.py) — ставит место в очередь только через _mark_if_needed: `if n in self.store.pending() or self.store.has_saved(n): self.store.mark_reload(n, now, reset_since=True)`. Условие завязано исключительно на очередь/сохранённые строки AgentStore; ни здесь, ни где-либо ещё в reload.py нет логики, завязанной на сам факт перезапуска процесса core. Модуль сам явно описывает свою задачу как обновление конфигурации агента по dispose, про MCP-схему инструментов в докстринге вообще не упоминается.
- **Сценарий отказа:** core перезапускается (например, после деплоя), а контейнер OpenCode места не перезапускается и продолжает работать. Первый проход уборщика видит место уже готовым и зовёт on_ready→place_ready(n); у этого места нет pending/saved строк агента — reload не ставится, dispose не вызывается. Студент на этом месте продолжает получать от OpenCode старые описания MCP-инструментов, пока что-то другое (новое сохранение агента, ручной перезапуск места) не вызовет dispose — это ровно известный эксплуатационный случай №4 из постановки («После перезапуска core запущенное место OpenCode держит старые описания MCP-инструментов до перезагрузки места»), для которого в коде шлюза нет компенсирующего механизма.
- **Исправление:** В AgentReloads добавить множество «мест, для которых уже сделан reload после старта процесса» (например self._booted: set[int] = set() в конструкторе) и в place_ready/_mark_if_needed форсировать store.mark_reload(n, now, reset_since=True) на первый вызов для каждого места за время жизни процесса, независимо от pending()/has_saved(); дальше обычный tick()/dispose подхватит место и обновит его конфигурацию (и тем самым даст OpenCode шанс переподключить MCP). Это добавление новой ветки условия, не меняющее поведение для последующих вызовов place_ready в рамках того же процесса.
- **Уточнение проверяющего:** Предложенный автоматический force-reload на каждый place_ready после старта процесса — избыточен и небезопасен как «автофикс»: он добавит dispose на КАЖДОМ перезапуске core (включая рутинные/аварийные, не трогающие описания инструментов) для всех уже открытых мест, и прямо противоречит намеренному поведению, зафиксированному test_place_ready_hook_marks_only_needed (комментарий m-н6) — эту спецификацию придётся менять осознанно, не как локальный баг-фикс. Если автоматизация нужна, правильнее встроить вызов `agents.admin reload --place NN` по всем работающим местам в сам деплой-скрипт/ранбук как шаг, выполняемый именно когда деплой меняет TOOL_DESCRIPTIONS (а не в reload.py), не трогая …

### GWB-03 · низкая · подтверждена · защищённый файл

**Мелкие разборщики тела JSON дублируются по нескольким файлам шлюза вместо общих в api.py**  
`core/pcbk_core/gateway/web.py` — `_unique_keys / _body_object / _json_object`

- **Код:** web.py определяет свою локальную `_unique_keys` (object_pairs_hook, проверка повтора ключа), хотя буквально та же функция уже экспортируется из api.py (строки 425-430 там) и используется оттуда другими файлами, например teacher_api.py («from .api import ... _unique_keys ...»). Отдельно: calc_api.py._body_object (защищённый файл) и analytics_api.py._json_object — тождественная логика («try: json.loads(raw) except (ValueError, RecursionError): return None; return body if isinstance(body, dict) else None»); комментарий самого analytics_api.py признаёт дублирование («приём calc_api._body_object»).
- **Сценарий отказа:** Правка поведения разбора тела (например, добавление предела глубины/размера — тема, уже вставшая в проекте для похожих парсеров) в одной копии и забытая в другой приводит к тому, что тело /pcbk/api/web/report и тела ручек /pcbk/api/calc и /pcbk/api/analytics начинают разбираться по чуть разным правилам незаметно для того, кто правил только одно место.
- **Исправление:** В web.py удалить локальную _unique_keys и импортировать её из .api (`from .api import _unique_keys`), как уже делает teacher_api.py — чисто удаление дубля, без calc_api.py. Для _body_object/_json_object — добавить общую функцию в api.py (например _json_object_body) и переключить на неё analytics_api.py; защищённый calc_api.py можно не трогать вовсе (решение о переводе его на общую функцию — за владельцем, отдельным добавлением импорта без изменения семантики).
- **Уточнение проверяющего:** Предложенное исправление верно и безопасно как есть: в web.py удалить локальную _unique_keys и импортировать её из .api (без изменения calc_api.py); для _body_object/_json_object — завести общую функцию в api.py и переключить на неё только analytics_api.py, защищённый calc_api.py не трогать.
