## Итоговая постановка — по ответам владельца 29.09.2026

Это единственный действующий раздел для следующих этапов. Разделы 1–11 ниже —
исходный анализ редакции 2, сохранены для истории; где они расходятся с этим
разделом, верен этот раздел. Раздел 0 — журнал ответов, из которого он собран.

### Цель

Отдельный, никак не привязанный к Dify контур: **студент через наш веб-чат
разговором заводит собственных ИИ-агентов**; агенты работают на модели через
OpenRouter и **прозрачно видят данные БДРВ** через готовые калькуляторы и запрос
по тегу; в том же веб-ресурсе — **свой редактор мнемосхем** по аналогии с PI
Vision, с живыми данными и событиями агентов.

### Кто работает и что может

| Роль | Что может |
|---|---|
| Студент (до 10) | вход в веб своим логином; разговор; свои агенты; калькуляторы; мнемосхемы — смотрит общие, рисует личные, может взять общую за основу. Не видит других студентов |
| Преподаватель | то же, плюс публикует общие мнемосхемы; видит разговоры и агентов всех студентов **только на чтение**; доступ по SSH |
| Администратор | доступ по SSH, сопровождение |

Студент предупреждается при первом входе, что его разговоры видит
преподаватель.

### Состав задачи

1. **Свой веб-ресурс.** Вход на каждого, чат, «мои агенты», калькуляторы,
   мнемосхемы. Серверный слой пропускает только разрешённые действия: оболочку,
   файлы и произвольные команды — никогда. Предупреждение о статусе стенда видно
   постоянно.
2. **Движок агентов — OpenCode**, за нашим серверным слоем; встроенный
   веб-интерфейс OpenCode студенту не показывается. Агент-конструктор создаёт
   агента студента в разговоре — пишет только файл агента.
3. **Служба данных БДРВ — одна на стенд.** Калькуляторы — готовые
   Python-скрипты (среднее, минимум, максимум, размах, профиль, наработка).
   Запрос по тегу — текущее значение, ряд, сводка по любому тегу белого списка
   за любой период в пределах бюджета. Каталог тегов берётся из историана и
   ищется по словам. **SQL строит служба, модель — никогда.** Пароль БДРВ — у
   службы, не у агента и не у студента. Бюджет и кэш общие на весь стенд.
4. **Редактор и просмотр мнемосхем, свой.** Общие схемы (преподаватель) и
   личные (студент); права «моё / чужое / общее»; отмена действий; живые значения
   раз в **5 секунд** одним общим запросом через службу; тренды раз в минуту;
   слой событий агента.
5. **Модель — OpenRouter, без локальных моделей.** Бюджет на модель — **до $1000
   на всё обучение** (решение 18; заменяет $50 в месяц), прогноз пересчитывается
   по факту через две недели работы.
6. **Порт 3389** — опознать слушателя и закрыть, если не нужен.

### Dify на время постройки

Dify работает параллельно всё время постройки, курс остаётся на нём. Выключается
только на время проверки критерия успеха 3 и затем включается обратно. Заменяет
ли резерв Dify насовсем — решение после пилота, по фактам.

### Не делаем

* базу знаний в любом виде, включая словарь сокращений; каталог тегов из
  историана — часть инструмента, а не база;
* резерв курса с зачётом З1–З6;
* свободный SQL — ни у агентов, ни у преподавателя;
* локальные модели;
* резервирование отказа провайдера модели и второй сервер;
* готовые редакторы мнемосхем (Grafana и подобные) — выбран свой;
* шифрование входа, SSH на ключи плюс VPN, привязку 1433 по адресу источника —
  это отдельный долг;
* перенос кода из `pcbk-ai-lab` — резерв делается **с нуля** (решение 17).

### Принятые риски

* **отказ OpenRouter кладёт резерв вместе с Dify**: баланс у ключей одного
  аккаунта общий, при нуле — 402 на все модели;
* лимит бюджета — жёсткая остановка ключа: при исчерпании модель молчит до
  пополнения;
* оба контура на одном сервере: общая память (Dify занимает около половины из
  15 ГБ) и общая точка отказа;
* отдельной работы по шифрованию входа студента нет.

### Вопрос 1 — что резервируем. Ответ 29.09.2026

Рекомендация была: C с прицелом на B. Ответ владельца дословно:

> «Полный резерв доступа к LLM и возможность создавать агентов через web ресурс,
> не привязанный никак к dify, с полным доступ к LLM через OpenRouter (без
> локальных моделей LLM), с готовыми наборами калькуляторов в виде скриптов PY
> настроенных на доступ к БДРВ (чтобы рассчеты шли не через LLM для экономии
> токенов и повышения скорости рассчета), с прозрачным доступом к БДРВ агентами
> OpenCode»

Как понято:

* **отдельный продукт, не привязанный к Dify** — ближе всего к чтению B; резерв
  курса с зачётом (A) не делается;
* **новое требование: агентов создают через веб-ресурс**, а не только по SSH;
* **модель — только OpenRouter, локальных моделей нет.** Закрывает вопрос 7:
  работа без интернета не требуется, зависимость от облачной модели принята.
  Идея `ollama` как заглушки из К3 снята;
* **калькуляторы — готовые Python-скрипты с доступом к БДРВ**, расчёт без модели:
  экономия токенов и скорость;
* **агенты OpenCode видят БДРВ прозрачно** — смысл «прозрачно» уточняется
  вопросом 3.

**Что проверено под этот ответ** [Д] (документация серверного режима OpenCode,
29.09.2026): `opencode serve` поднимает HTTP-сервер с описанием OpenAPI;
среди ручек есть **`POST /session/:id/shell` — выполнить команду оболочки** и
`POST /session/:id/command`; авторизация **только HTTP Basic, один логин и
пароль на весь сервер**, многопользовательского режима в документации нет; есть
встроенный веб-интерфейс `opencode web` с той же авторизацией. Это меняет
вопрос 2: веб-ресурс, который смотрит в API OpenCode напрямую, отдаёт
пользователю оболочку одним HTTP-запросом.

### Вопрос 5 — отказ провайдера модели. Ответ 29.09.2026: не резервируем

Ответ владельца дословно: «Резерв отказа модели не резервируем.»

Рекомендация была: отдельный аккаунт OpenRouter со своим балансом, лимит на
ключ, сторож остатка, запасная модель. Не принята.

**Принятый риск, фиксирую явно.** Все ключи одного аккаунта OpenRouter тянут
один баланс [Д]; при нулевом балансе приходит 402 на все модели, включая
бесплатные. Значит резервный контур ложится от того же отказа, что Dify
14.09.2026. Резерв закрывает отказ платформы Dify, а не отказ модели.

### Вопрос 6 — каталог тегов и запрет на базу знаний. Ответ 29.09.2026: часть инструмента

Выбор совпал с рекомендацией. Каталог тегов — часть инструмента «запрос по
тегу», а не база знаний:

* служба сама берёт имена и описания тегов из историана; руками их никто не
  пишет и не выверяет;
* агент не загружает каталог целиком, а ищет тег по словам студента;
* описания в историане обрезаны на 50 символах, поэтому при промахе агент
  показывает студенту несколько похожих тегов на выбор.

Словарь сокращений («НЯ», «ПС», …) не делается — это был бы первый шаг к базе
знаний.

### Вопрос 8 — мнемосхемы. Ответ 29.09.2026: свой редактор в нашем вебе

Рекомендация была: Grafana Canvas внутри нашего веб-ресурса, данные через нашу
службу. Выбор владельца: **«Свой редактор в нашем вебе»**.

Как понято:

* редактор мнемосхем «быстро накидать, как PI Vision» строится **в нашем же

* события агента — слой на схеме;
* это **самая дорогая часть задачи**; готовый редактор не берётся, значит объём
  и порядок её постройки — главный предмет брейншторма.

### Вопрос 9 — кто рисует мнемосхемы. Ответ 29.09.2026: оба — общие и личные

Рекомендация была: сначала рисует преподаватель, студенты — вторым шагом. Выбор

### Вопрос 10 — такт обновления мнемосхем. Ответ 29.09.2026: 5 секунд

Рекомендация была: 10 с для живых значений. Выбор владельца: **5 секунд**.

* служба раз в 5 с одним запросом забирает текущие значения всех тегов со всех
  открытых схем и раздаёт всем зрителям — нагрузку задаёт такт, а не число
  студентов;
* тренды на схеме — раз в минуту (моё допущение, владелец не возражал;
  уточняется на брейншторме);
* схема — для разбора и обучения, не для ведения процесса: на ней постоянно
  видно предупреждение о статусе стенда.

проверяется): терминальный агент, MIT, свои провайдеры моделей включая
OpenRouter, поддержка MCP — локальный `stdio` и удалённый HTTP, свои команды,
режимы Plan/Build, сессии в SQLite. Есть система разрешений со значениями
`allow` / `ask` / `deny` по каждому инструменту (`bash`, `edit`, `read`,
`webfetch`, `glob`, `grep`, …), с шаблонами и переопределением по агенту. На
Linux есть управляемый конфиг `/etc/opencode/`, который пользователь
переопределить не может — он старше и конфига в домашнем каталоге, и переменных
окружения.

**И главное, что меняет постановку.** В том же интерфейсе **пользователь сам
получает оболочку**: сообщение, начатое с `!`, выполняется как команда оболочки и
её вывод попадает в диалог; команды `/editor` и `/export` открывают внешний
редактор из переменной `EDITOR` [Д]. Среди документированных ключей системы
разрешений (`bash`, `edit`, `read`, `webfetch`, `glob`, `grep`, …) этих трёх
возможностей нет: разрешения ограничивают **инструменты агента**, а не действия
человека. То есть `deny` на `bash` не закрывает человеку путь к оболочке, а
редактор с командой `:!sh` — это оболочка тоже.

Всё перечисленное перед реализацией надо подтвердить на живой установке [?], и в
первую очередь — можно ли управляемым конфигом отключить `!`, `/editor` и
`/export`.

## 3. Цель: развилка, которую надо снять первой

Просьба читается тремя способами, и от выбора зависит всё остальное.

### Чтение A — резервный стенд для того же курса

Dify ломается до или посреди курса, и 16 академических часов надо провести на
другом контуре. Тогда резерв обязан воспроизвести закреплённое учебным планом:
ответы по узлу с **меткой источника**, калькуляторы, создание агента, экран «Мой
агент», персональный зачёт З1–З6, ведомость для СМК.

**Внутреннее противоречие.** Пункт 7 просьбы запрещает базу знаний. Но метка
источника «база знаний КДМ-1» против «общие знания» существует только потому,
что есть выверенная база. Без неё:

* **З3 — обязательный код зачёта** («ответ с меткой источника, открытые под ним
  источники, объяснение почему метка такая») [О] предъявить нечем;
* главный навык курса, вынесенный в критерии успеха и неуспеха, теряет
  основание;
* реестр пробелов базы знаний — «главный результат для завода» по формулировке
  плана [О] — не возникает.

Чтение A с пунктом 7 несовместимо: либо курс, либо «без базы знаний».

### Чтение B — отдельный рабочий инструмент технолога

Технолог сам разговаривает с сильной моделью, у него прозрачный доступ к
телеметрии, детерминированные калькуляторы и мнемосхемы; обучение происходит от
работы, а не от занятий с зачётом. Формулировка просьбы «технолог **сам**
общается с LLM и выходит на создание агента» читается именно так.

Согласовано со всеми восемью пунктами. Но это **не резерв курса, а второй
продукт**: 16-часовой курс с ведомостью на нём провести нельзя без переработки
учебного плана.

### Чтение C — непрерывность инструмента участка

Резерв нужен не курсу, а участку: если Dify встанет **после** курса, технологи не
должны остаться без инструмента. Обучение остаётся на Dify, пока тот жив.

### Моя рекомендация

**Начинать с чтения C, с прицелом на B.** Причины:

1. C не конфликтует с пунктом 7: непрерывность рабочего инструмента не требует ни
   метки источника, ни зачёта, ни базы знаний;
2. C снимает самый дорогой блок требований — оценивание и воспроизводство
   учебного плана;
3. C и B отличаются не архитектурой, а объёмом: B — это C плюс сценарий
   самостоятельного выхода технолога на своего агента. Строить можно один контур
   и расширять;
4. A я рекомендую отклонить в текущей формулировке: он требует базы знаний,
   которую владелец запретил. Если резерв курса всё-таки нужен, обсуждать надо
   не архитектуру, а исключение из пункта 7.

Вопрос 1 раздела 10 — это запрос подтверждения или вето на эту рекомендацию, а не
вопрос без ориентира.

## 4. Не-цели

Из просьбы:

* **не делать базу знаний** — ни выверенную, ни кураторскую, ни ночное
  пополнение;
* не воспроизводить устройство Dify: ни воркфлоу-граф, ни датасеты, ни плагинную

Из анализа, **требуют подтверждения владельцем**:

* не переносить конструктор агентов отдельным приложением: в OpenCode роль агента
  задаётся конфигом и промптом;
* не строить второй портал: лента узлов либо переиспользуется, либо становится

* **реестр тегов участка** (название тега плюс короткое описание прямо из

## 5. Разбор по компонентам

### К1. OpenCode на сервере ПЦБК

Что нужно: пакет, управляемый конфиг, профиль агента-технолога, своя команда
запуска, журнал сессий.

Переиспользуется: сервер.

Чего не хватает и что решать:

* **несоответствие инструмента аудитории.** OpenCode — агент для кода: его
  встроенные инструменты читают и правят файлы и запускают команды оболочки [Д].
  Технологу без программирования не нужен ни один. Значит профиль технолога —
  `deny` на файловые и оболочечные инструменты и разрешение только на инструменты
  MCP. Технически поддержано [Д]; вопрос в том, остаётся ли после такой обрезки
  терминальный интерфейс уместным для десяти технологов, привыкших к двум окнам
  портала и чата;
* **служба доступа к телеметрии обязана быть одна на стенд, а не по процессу на
  сессию.** Сегодня защита историана работает потому, что плагин — один
  долгоживущий процесс: счётчик частоты, кэш и дедупликация одинаковых
  параллельных запросов (`RATE`, `CACHE`, `FLIGHT`) — это переменные уровня
  модуля, общие для всех пользователей [П]. Если доступ сделать локальным
  `stdio`-сервером (свой процесс на сессию), у каждой из десяти сессий будет свой
  счётчик и свой кэш, и общий бюджет запросов к боевому историану молча
  умножится на число занятых студентов. Это отдельная и не менее важная причина
  для общей службы, чем изоляция пароля (раздел 6);
* **журнал.** Сессии лежат в домашнем каталоге пользователя [Д]. Для разбора
  занятий и для реестра находок это надо забирать централизованно, иначе
  преподаватель не увидит, кто что спрашивал.

### К2. Доступ по SSH

Развилка, переписывающая топологию, — см. раздел 6.

### К3. Модель через OpenRouter

Требование владельца: качественно рассуждает, медленная — не страшно, бюджет
минимальный.

Что решать:

* **какая модель.** Критерий — качество рассуждения на русском техническом
  тексте и в диалоге с технологом, а не скорость. Кандидатов сравнивать по цене
  за миллион токенов и по поведению на наших же 53 золотых вопросах: измеритель
  и набор уже есть [П];
* **потолок.** Учебный план требовал отдельного ключа с потолком $50 и проверки
  остатка в предзанятийном чек-листе — потому что ошибка 402 при нулевом балансе
  не повторяется автоматически и лечится только деньгами [О]. 14.09.2026 это и
  случилось: кредиты кончились посреди прогона [П];
* **режим данных.** Гарантия невхождения данных в обучение платформой OpenRouter
  больше не обеспечивается [О]. При прозрачном доступе к телеметрии за периметр
  уходят не только вопросы, но и значения тегов. Памятка курса это допускает, но
  объём уходящего растёт — владельцу подтвердить осознанно;
* **локальная модель как резерв.** `ollama` на сервере уже стоит [П]. Но 8 ядер
  без видеокарты и ~7 ГБ свободной памяти не дают модели уровня рассуждения на
  десять одновременных сессий. Локальная модель реалистична как заглушка для
  простых ответов, не как замена.

### К4. Доступ к телеметрии

Два разных технических смысла слова «прозрачно».

**(i) Модель пишет SQL сама.** Доводы против — измеренные:

* провайдер `INSQL` не принимает параметры, поэтому имя тега подставляется
  литералом и белый список обязателен [О];
* `IN` и `OR` не работают на ww-параметрах; `OPENQUERY` не поддерживает `JOIN` и
  агрегаты [О];
* из 125 обозначений базы знаний 102 существуют только в суффиксной форме, и
  запрос по базовому имени возвращает ошибку [О] `kb/data-access.md`, стр. 218;
* описания тегов обрезаны на 50 символах — из-за этого белый список сам однажды
  потерял 125 живых тегов участка [П], а смысл суффикса `_MV` на регуляторах в
  базе противоречив и до сих пор не установлен [П];
* провайдер допускает **только один предикат `LIKE`** в запросе. В отчётах
  проекта этого нет; наблюдение моё, 14.09.2026, дословный текст ошибки:
  `Only one LIKE predicate is allowed for this version of the OLE DB provider`
  [П]. Стоит внести в `kb/data-access.md` отдельно от этой задачи.

**Прецедент проекта.** Готовый плагин `junjiem/db_query_pre_auth` был отвергнут
именно потому, что даёт модели произвольный SQL, и вместо него написан свой
плагин с белым списком [О]. Тот же план отмечает, что права `AI_reader`
ограничивают ущерб нагрузкой, но «поверхность 4-компонентных имён открыта, что и
есть довод против произвольного SQL» [О].

**(ii) Кураторские инструменты, прозрачные для технолога.** Технолог спрашивает
словами, агент сам выбирает инструмент. Это и делает `pcbk_bdrv`, и вместе с
инструментом идут белый список, бюджет и кэш.

**Рекомендация:** (ii) как основной путь — по прецеденту проекта и по списку
ловушек выше. Вопрос владельцу (раздел 10, вопрос 3) сформулирован как право
вето, а не как открытый выбор.

Отдельно — «форточка» произвольного чтения для преподавателя. Если она нужна, у
неё должны быть не только потолок строк и таймаут, но и **журнал
привилегированного действия и ограничение частоты** — ровно то, что есть у
основного пути [П] и чего в моей прежней формулировке не было. Права
`db_datareader` [О] означают, что риск форточки — нагрузка и лишнее чтение, а не
порча данных: тревогу здесь надо калибровать по нагрузке.

### К5. Калькуляторы

Пункт 6 просьбы фактически выполнен: расчёт идёт кодом, модель в вычислении не
участвует, расход токенов нулевой, приёмка 71/71 [П]. Важная поправка к слову
«локально»: калькулятор не считает на месте, он обращается к боевому историану, и
при бюджете `p95 ≤ 5 с` живые замеры были 3,3–3,9 с [О]. Для «живых значений» на
мнемосхеме это существенно.

Что решать: остаются ли калькуляторы отдельными по узлам (сегодня 7 приложений,
потому что в Dify приложение — единица) или становятся одним инструментом с
параметром «узел». Во втором контуре второе проще и честнее.

### К6. Веб-ресурс мнемосхем — самая большая и неопределённая часть

Аналогия с PI Vision раскладывается на четыре разные задачи:

| Часть | Что это | Сложность |
|---|---|---|
| Рантайм-просмотр | схема на экране, живые значения тегов, цветовые состояния по порогам | средняя |
| Привязка к тегам | выбор тега из белого списка, единицы, пороги | низкая, список уже есть |
| Редактор «быстро накидать» | перетаскивание символов, рисование связей, сохранение схемы | **высокая, отдельный продукт** |
| События агента на схеме | что агент спрашивал и нашёл, привязанное к узлу, тегу и времени | средняя, **аналога в PI Vision нет** |

Ключевая развилка по стоимости: рисовать схемы редактором с нуля или взять
подложкой существующие экраны SCADA и расставить на них горячие точки. У проекта
есть снимки экранов SCADA от 14.10.2024 и разбор восьми узлов участка [П].

**Рекомендация:** начать с подложки и горячих точек как минимального работающего
варианта; редактор с нуля — только если после него подтвердится спрос на
регулярное самостоятельное рисование новых схем. Отдельно учесть времена — они разные, и в
первой редакции я слил их в одно неверное число:

* **мгновенное значение** (таблица `Live`, режим «Текущее значение») — 0,1 с [П];
* приёмочные лёгкие запросы — 0,3–0,49 с [П];
* **сводка за период с перцентилями** на границе бюджета — 3,3–3,9 с при
  контракте `p95 ≤ 5 с` [О];
* за пределами бюджета было 6,8 с — именно поэтому бюджет и введён [О].

Частоту обновления схемы задавать раздельно: живые значения — секунды,
агрегаты — минуты. Иначе схема либо отстаёт, либо долбит историан.

### К7. Обучение без базы знаний

Честный разбор, что уходит вместе с базой:

* **смысл параметра.** Телеметрия даёт число, но не название, назначение и связь
  с соседним узлом. На вопрос «что такое губа напорного ящика» историан не
  отвечает;
* **методики М-1…М-7** со слов технолога — они в базе, не в телеметрии;
* **границы «норматив не задан».** Главное дисциплинирующее свойство текущего
  контура. Без базы модель отвечает из общих знаний — и это ровно тот отказ,
  который в проекте уже ловили числами: при включении веб-фолбэка вредные ответы
  выросли с 3 до 9 из 36, потому что **фолбэк начал выдумывать числовые нормы
  под видом отраслевой практики**; правило пришлось переписать запретом любых
  нормативов, допусков и порогов [О];
* **реестр пробелов** как результат для завода.

Что при этом **не** является базой знаний: реестр тегов участка — 1104
обозначения с описаниями прямо из историана [П]. Поля сырые
(`tag`/`kind`/`desc`/`unit`/`min_eu`/`max_eu`/`live`), взяты механически, никто их
не курирует — в отличие от пяти датасетов, которые правит и утверждает методолог.
Различие позволяет выполнить пункт 7 буквально и всё же дать модели понимание,
как называется параметр. **Решение за владельцем** — вопрос 6.

## 6. Границы доверия: главный архитектурный вопрос

**Место сервера в уровнях производства.** Фиксирую один раз и дальше пользуюсь
этим определением: сервер стенда — аналитический узел **на границе уровня 3**
(уровень операций участка), с одним маршрутизируемым переходом до историана
через шлюз ИТ,
который сам относится к уровню 2–3. Это не корпоративная сеть и не сегмент АСУТП
с контроллерами: прямого доступа к управлению отсюда нет, обратного канала в
АСУТП тоже [О].

Сегодняшняя картина: у студента нет оболочки на сервере; единственный путь к
историану — инструмент плагина с белым списком и только чтением; учётные данные
историана лежат в файле, недоступном обычному пользователю [П].

Предлагаемая картина: десять интерактивных оболочек на том самом узле, у которого
есть маршрут к историану на порт 1433 [П].

Отсюда три следствия.

**Первое. Запрет инструментов в OpenCode защищает модель, а не человека.** `deny`
на `bash` мешает агенту выполнить команду, но SSH и есть оболочка: человек
получает её напрямую, минуя агента. Ограничение инструментов — про то, чтобы
модель не увели в историан подсказкой, а не про то, что студент туда не дойдёт
сам.

**Второе. Учётные данные историана не должны быть доступны процессу студента.**
Если сервер MCP запускается дочерним процессом агента (локальный `stdio`), его
окружение — это окружение пользователя, и пароль читается тем же пользователем.
Это требование, а не решение; конкретный механизм (например, отдельная служба под
своей учётной записью с токеном на пользователя) выбирается вместе с ответами на
вопросы 2 и 3, а не здесь. К тому же требованию ведёт и К1: общая служба нужна,
чтобы бюджет и кэш остались общими.

**Третье. «Просто через SSH» — оболочку человек получает при любом прочтении.**

Так я написал в первой редакции и ошибся: я предлагал владельцу выбор между
«полной оболочкой» и «SSH как транспортом с принудительной командой», где второе
будто бы границу держит. **Второй ветви не существует.** В интерфейсе OpenCode
человек запускает команды оболочки сам — сообщением с `!` — и открывает внешний
редактор через `/editor` и `/export`, а разрешения `allow`/`ask`/`deny`
ограничивают только инструменты агента [Д]. Принудительная команда на входе
убирает bash *до* агента, но не *внутри* агента.

Значит выбор другой, и он про то, где стоит граница:

* **отключить побеги на месте** — если управляемым конфигом удаётся выключить
  `!`, `/editor` и `/export`. Среди документированных ключей разрешений их нет,
  поэтому это в первую очередь **проверка на живой установке**, а не решение;
* **песочница на том же узле** — агент работает под отдельной учётной записью в
  контейнере без маршрута к 1433 и без учётных данных историана, а к телеметрии
  обращается только через общую службу;
* **отдельный узел** для интерактивных сессий, без маршрута к историану.

Первый вариант дешёвый, но может оказаться невозможным; второй и третий границу
держат. Порядок решения: сперва проверка, потом выбор. И при любом варианте
остаётся верным требование «второго» пункта: учётные данные историана не должны
быть доступны процессу, в котором сидит человек.

**Честная граница, названная в проекте раньше.** «От полного root на хосте
технически не защититься — только разделение и аудит» [О]. Это ограничение
остаётся верным при любом ответе на вопрос 2.

**Незакрытый долг, на который ложится эта задача.** 26.08.2026 владельцу была
представлена модель угроз ОС этого же сервера с тремя развилками: перевод SSH с
пароля на ключи плюс VPN, TLS на веб, и привязка доступа к порту 1433 историана
по адресу источника силами ИТ. Реализация не начата, решений нет [О]. Плюс сейчас
обнаружен слушатель на порту 3389 наружу, процесс не опознан [П]. Десять новых
интерактивных учётных записей ложатся поверх этого долга — см. вопрос 7.

резервный контур ляжет от того же отказа, от которого лёг основной. Объём —
вопрос 5.

## 8. Критерии успеха и неуспеха резерва — приняты 29.09.2026

**Успех** — выполнены все:

1. студент входит в веб своим логином и **за один разговор** создаёт агента по
   своему узлу — без помощи преподавателя после одного показа;
2. агент на вопросы «что сейчас» и «что было за смену» по тегу своего узла
   приносит число из БДРВ, и оно **совпадает с калькулятором** на том же теге и
   периоде;
3. Dify выключен целиком — контур работает;
4. ни один запрос к БДРВ не идёт мимо белого списка и бюджета; при десяти
   студентах одновременно общий бюджет не превышен;
5. студент видит только своих агентов и свои разговоры;
6. расход на модель за всё обучение — не выше **$1000** (решение 18, заменило
   $50 в месяц; прогноз пересчитывается по фактическому расходу через две
   недели работы).

**Неуспех** — достаточно одного:

1. студент получил оболочку или файлы сервера, либо пароль БДРВ оказался
   доступен его процессу;
2. агент назвал числовой норматив, которого нет в данных, и не пометил его как
   общие знания (этот отказ уже ловили на стенде числами [О]);
3. студент увидел чужого агента или чужой разговор;
4. число агента разошлось с калькулятором.

Критерия скорости ответа нет намеренно: владелец допускает медленную модель ради
качества рассуждения.

**Мнемосхемы: успех** — выполнены все (приняты 29.09.2026, вопрос 16):

- М1. Преподаватель после одного показа собирает схему узла (около 10 элементов,
  8–10 тегов, один тренд) не дольше чем за **30 минут** и без правки кода или
  файлов.
- М2. К пилоту опубликованы общие схемы **восьми узлов** участка.
- М3. Значение на схеме совпадает с запросом по тегу на тот же момент. Обновляется
  раз в **5 секунд**, и десять зрителей дают один общий запрос, а не десять.
- М4. Действие агента (запрос, расчёт, вывод) появляется на слое событий у своего
  тега не позже чем через **10 секунд**, с временем и именем агента.
- М5. Студент рисует свою схему и может взять общую за основу. Общую и чужие
  схемы менять не может, чужие личные не видит.

**Мнемосхемы: неуспех** — достаточно одного:

- Н1. Данные не приходят дольше **15 секунд** (три такта), а схема показывает
  старое число как живое, без пометки «устарело» и без времени последнего
  значения.
- Н2. Число на схеме разошлось с запросом по тегу для того же тега и момента.
- Н3. Схема ходит в БДРВ мимо службы, то есть мимо белого списка и бюджета.
- Н4. Студент изменил общую или чужую схему либо увидел чужую личную.
