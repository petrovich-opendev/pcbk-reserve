# План и решения: бот «Подборка для КДМ-1»

Документ для владельца-технолога и для разработчика: что сделано, что в плане на день 2 и день 3, и отдельно —
новая смежная функция «сценарный эффект практики по данным БДРВ». Состояние на 16.10.2026.

## 1. Статус

День 1 закрыт (ветка `day1` → `main`, тег `v0.1.0`; окно банка расширено до 5 лет отдельным тегом `v0.1.1`).
Владелец получил настоящий выпуск из посеянного банка (2 случая) в чате разработки через `publish --dry-run`;
сторож проверен сквозным сценарием с подменённой сетью и Telegram. Решение владельца 15.10 остановило запуск
самого Telegram-бота («Сам бот для телеграмма позже») — подробный план и шаги для его запуска, когда владелец
даст слово, — в [эксплуатации](operations.md), раздел 9.

## 2. День 2 — сборщик (план, не реализовано)

Два прохода через `claude -p` (как у Promo Agent): проход 1 — поиск кандидатов по узлам и темам; проход 2 —
модель открывает статью и отвечает по той же схеме полей, что проверяет `checks.py`, пачками до 8 кандидатов на
вызов. Дальше — те же проверки без модели, что уже работают для посева вручную (цитата, числа, компания,
повторы). Курсор покрытия окна поиска по месяцам (`coverage`); первый запуск `harvest --initial` вручную
(бюджет до 12 вызовов `claude -p`, около 3 месяцев за раз) — даёт оценку объёма случаев за год; остаток окна
дозакрывается ночными прогонами (решение дизайна — не больше 4 вызовов модели за ночь, недельный лимит
подписки общий с Promo Agent).

**Оценка:** около 1 рабочего дня (укладывается в стоп-условие задачи «готовность к пробе — не позже 3 рабочих
дней» вместе с днём 3).

## 3. День 3 — кнопки, запуск пробы (план, не реализовано)

- Слушатель (`listener.py`, модуль пока не написан): `long polling` Telegram, обновления не от владельца
  игнорируются без ответа, пульс в `state/listener.heartbeat` (его видит проверка сторожа № 4).
- Кнопки «Полезно» / «Не по теме» / «Подробнее» под сообщением выпуска; оценка — запись в банк и правка кнопок.
- «Подробнее» — `details_ru` из банка, без обращения к модели.
- `stats --since <дата>` — отчёт по критериям задачи (доля «полезно», доля «не по теме», доля «не сверено
  автоматически», повторы, выпуски по дням, прогоны сборщика, запас банка, покрытие окна).
- Догоняющий запуск `--if-missing` — уже реализован в день 1, в день 3 входит в состав cron.
- cron (строки уже описаны в README) и `systemd --user` для слушателя.
- **Старт пробы 14 дней** — живой выпуск с кнопками. Отсчёт по решению владельца (вариант «а» из двух,
  предложенных на брейншторме): с момента запуска кнопок в день 3, а не с момента, когда окно поиска закрыто
  целиком — риск серии дней «новых нет» в начале пробы виден и честно учитывается, а не прячется.

**Оценка:** около 1 рабочего дня, вместе с днём 2 — в пределах стоп-условия «3 рабочих дня на готовность к
пробе».

## 4. Быстрый запуск из готового банка

Банк уже содержит 2 случая (посеяны вручную в день 1): рекорд эффективности на картонной машине «КАМА»
(источник — Lesprom, 13.08.2026) и Voith SteamBooster на бумажной фабрике Koehler Kehl (источник —
paper-world, 29.09.2026). Когда владелец даст слово на запуск Telegram (раздел 9 документа
[эксплуатация](operations.md)), первый выпуск можно отправить сразу из этого банка, не дожидаясь сборщика дня
2 — ровно так это уже было показано в чате разработки через `publish --dry-run`.

## 5. Новая функция: сценарный эффект практики по данным БДРВ (кратко)

Отдельная задача `docs/TASK-effect.md` (версия 4, 16.10.2026, черновик на согласование владельцу; прошла три
раунда критиков) расширяет подпроект: по названной практике или гипотезе технолог получает сценарный
экономический эффект **в натуральном выражении** (т пара, т волокна, м³ воды, ч простоя и т. п.) за последние
12 месяцев по данным БДРВ. Денежный эффект не считается — это отдельное решение на будущее (Р6 ниже).

**Где считается и почему.** Не в этом боте и не в Telegram, а **на учебном стенде `pcbk-reserve`** — потому что
только там есть доступ к БДРВ; бот работает вне сети ПЦБК и данных предприятия не видит (см.
[достоверность и приватность](quality-and-privacy.md), раздел 5). Общее между ботом и стендом — только банк
открытых случаев: его предлагается выгружать из бота в JSON (новая команда `export-cases`, не реализована) и
грузить на стенд через `scp` и команду оператора; выгружаются только открытые поля (без оценок владельца).

**Слайсы (план, не больше дня на каждый, не реализовано):**

| Слайс | Содержание |
|---|---|
| 0 (проба, 2–3 ч) | глубина архива историана: есть ли 12 месяцев по 5 величинам из набора приёмки |
| 1 | роль `effect`, сбор базы за 12 месяцев по подтверждённым тегам, строка сторожа, тесты на синтетике |
| 2 | формулы расчёта (источник, практики, протокол заказчика, время), журнал расчёта |
| 3 | подключение чата стенда и банка бота, приёмка по 5 примерам, урок для студентов, журнал выпуска |

Если слайс 0 покажет, что 12 месяцев в архиве нет, — решение остаётся за владельцем (пункт Р5 ниже).

**Решения владельца Р1–Р8 (раздел 12 `docs/TASK-effect.md`; рекомендация составителя задачи — по умолчанию,
если владелец не укажет иное):**

| № | Вопрос | Рекомендация | Открыт? |
|---|---|---|---|
| Р1 | Где видна оценка | только в чате стенда, не в боте и не в Telegram | нет |
| Р2 | Кто подтверждает связь «величина → тег» | как сейчас — любой вошедший студент, одним действием в чате | нет |
| Р3 | Доля переноса чужого эффекта на КДМ-1 | сценарии 25/50/100 % от заявленного, либо число технолога | нет |
| Р4 | Когда и как часто собирать базу | ночью, порог достоверности месяца 80 % | нет |
| Р5 | Если в архиве меньше 12 месяцев | считать по доступным месяцам с пометкой «база N мес.» | нет |
| Р6 | Денежный эффект | не считать сейчас, отдельная задача позже | нет |
| Р7 | Риск незамеченного сброса счётчика между точками выборки | допускать, с пометкой в ответе | нет |
| **Р8** | **Кто «технолог» при подтверждении тега из чата** | вариант (а) — см. ниже | **да** |

Р1 — рекомендация составителя: оценка только в чате стенда, иначе данные ПЦБК выходят за пределы стенда и
правило приватности бота (раздел 5 документа [достоверность и приватность](quality-and-privacy.md)) меняется.

**Р8 — единственный пункт без принятой рекомендации по умолчанию**, открыт после трёх раундов критики. Личность
технолога нужна механизму `reviews.decide`, а из тела запроса её брать запрещено правилом безопасности пакета
заказчика. Вариант (а), который рекомендует составитель: роль `effect` строит личность на сервере — токен места
→ учётная запись, закреплённая за местом, — без данных из самого запроса; нужен отдельный просмотр безопасности.
Два альтернативных варианта отклонены предыдущими раундами критиков: кнопка в веб-сессии шлюза нарушает правило
«всё через чат, без форм»; свой журнал подтверждений вместо механизма `equipment_link` заказчика — отступление
от пакета заказчика. Решение — за владельцем.
