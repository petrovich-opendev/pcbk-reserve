# Бот «Подборка для КДМ-1»: архитектура

Документ для разработчика и владельца-технолога. Состояние на 16.10.2026. Источники:
код `kdm1digest/*.py` в репозитории бота `tg-bot-kdm1` (сверено построчно) и дизайн
`docs/specs/2026-10-15-kdm1-digest-design.md` (ред. 4) — где они расходятся, отмечено
отдельно. Обзор задачи и целей — [overview.md](overview.md).

## Процессы

| Процесс | Статус | Запуск | Модель |
|---|---|---|---|
| Сборщик (`harvest`) | план (день 2) | cron 21:00 UTC / 02:00 Пермь (план) | да, план |
| Выдача (`publish`) | реализован | cron 04:00 + 04:20 `--if-missing` (план, не в cron) | нет |
| Слушатель (кнопки) | план (день 3) | systemd --user, постоянно (план) | нет |
| Сторож (`watchdog`) | реализован | cron раз в 30 мин (план, не в cron) | нет |

Cron-строки есть только в README как инструкция для владельца; `crontab -e` владельцем
не выполнен — бот не запущен (решение `docs/TASK.md` п.14.2, см. [overview.md](overview.md)).

## Модули `kdm1digest` и их роли

Файлы, которые есть в `kdm1digest/` (проверено `ls`), по одной строке на модуль:

| Модуль | Роль |
|---|---|
| `__init__.py` | пустой, маркер пакета |
| `__main__.py` | точка входа `python3 -m kdm1digest`, зовёт `cli.main` |
| `config.py` | чтение `.env`, часовой пояс Пермь (`PERM`, `perm_now`, `perm_date`), `Config` |
| `db.py` | открытие SQLite (WAL, `timeout=30`), повтор записи `write()` при `database is locked` |
| `journal.py` | дозапись строк в `logs/<component>.log` (время UTC и по Перми) |
| `vocab.py` | закрытые списки: узлы КДМ-1, типы решений, типы источника, русские подписи |
| `store.py` | схема банка (`cases`, `runs`, `rejects`, `coverage`, `deliveries`), доступ, backup |
| `dedup.py` | нормализация URL/компании/машины, `case_key`, правило повтора `find_repeat` |
| `linkcheck.py` | загрузка страницы (`urllib`), извлечение видимого текста, читаемость |
| `checks.py` | схема, закрытые списки, цитата/числа/компания на странице, окно 5 лет |
| `telegram.py` | голый Bot API: отправка, нарезка по 3800 знаков, маскирование токена |
| `publish.py` | отбор случаев, рендер HTML, отправка, запись `deliveries`/`runs`, замок |
| `watchdog.py` | 5 проверок молчания, своё состояние, троттлинг 6 ч, замок |
| `cli.py` | команды `publish`, `watchdog`, `seed`, `init` |
| `seed.py` | ручной посев банка из JSON-файла той же проверкой, что и будущий сборщик |

Модули из дизайна (спец. п.3), которых в коде нет (план дней 2–3, проверено отсутствием
файлов): `claude_runner.py`, `prompts.py`, `harvest.py`, `listener.py`, `stats.py`.

## Где вызывается модель

По дизайну (спец. п.2) модель (`claude -p`) вызывается только сборщиком — модулями
`harvest.py`/`claude_runner.py`/`prompts.py`, которых пока нет. В реализованном коде
(день 1) вызовов модели нет вообще: ни `publish.py`, ни `watchdog.py`, ни `seed.py`,
ни `cli.py` не импортируют `subprocess` и не вызывают `claude` — выдача и сторож
работают только по данным банка и своего состояния, посев проверяет файл той же
логикой `checks.py`, что в будущем будет применять сборщик, но без LLM.

## Поток данных

```
(план, день 2, не реализовано)                     (реализовано, день 1)
Источники в сети ──► СБОРЩИК ──► checks.py ──► БАНК ──► ВЫДАЧА ──► Telegram (владелец)
                    (claude -p)  (без модели)  (bank.   (publish.py,
                                               sqlite3)  без модели)
                                                  ▲
                            seed.py (ручной путь, день 1, тоже через checks.py)
                                                  │ только чтение (mode=ro)
                                             СТОРОЖ (watchdog.py, без модели)
                                                  │
                                                  ▼
                                          Telegram (тревога / «снова работает»)
```

Сегодня единственный путь наполнения банка — `seed.py` (ручной посев). Сборщик вставал
бы в ту же точку банка через те же проверки `checks.py`/`dedup.py`.

## Файлы состояния

| Путь | Что | Статус |
|---|---|---|
| `state/bank.sqlite3` | банк случаев (5 таблиц, п. [data-model.md](data-model.md)) | реализован |
| `state/watchdog.sqlite3` | состояние тревог сторожа (таблица `alerts`) | реализован |
| `state/publish.lock` | межпроцессный замок выдачи (`fcntl.flock`) | реализован |
| `state/watchdog.lock` | межпроцессный замок сторожа (`fcntl.flock`) | реализован |
| `state/watchdog.crash` | метка времени последней аварийной тревоги сторожа | реализован |
| `state/listener.heartbeat` | пульс слушателя (кнопки) | план — файла и писателя нет |
| `state/backups/bank-YYYYMMDD.sqlite3` | ежедневная копия банка, хранится 14 копий | реализован |
| `logs/<component>.log` | журнал процесса, время UTC и по Перми | реализован |
| `logs/run-YYYYMMDD.log` | вывод запуска через `bin/run.sh` за день | реализован |

Сторож читает `state/listener.heartbeat`, но проверка п.4 («кнопки не работают») молчит
(`_SKIP`), пока в `.env` не включён `LISTENER_ENABLED` — по умолчанию выключено.

## Расписание (план, README)

Строки в crontab владельца пока не добавлены (бот не запущен):

```cron
0  4 * * * ~/tg-bot-kdm1/bin/run.sh publish
20 4 * * * ~/tg-bot-kdm1/bin/run.sh publish --if-missing
*/30 * * * * ~/tg-bot-kdm1/bin/run.sh watchdog
```

Пояснение: `0 4 * * *` (09:00 Пермь) — основной выпуск; `20 4 * * *` (09:20 Пермь) —
догоняющий запуск с `--if-missing` (ничего не делает, если выпуск уже ушёл); `*/30` —
сторож каждые полчаса. Сборщик (cron 21:00 UTC / 02:00 Пермь) и слушатель кнопок — план
дней 2–3, в README помечены как «пока в cron не добавляются».
