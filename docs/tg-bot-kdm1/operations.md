# Эксплуатация: бот «Подборка для КДМ-1»

Документ для владельца-технолога и для разработчика, обслуживающих Telegram-бота «Подборка для КДМ-1»
(отдельный локальный git-репозиторий `tg-bot-kdm1`, пакет `kdm1digest`). Состояние на 16.10.2026: день 1
закрыт (тег `v0.1.0`, окно банка 5 лет — тег `v0.1.1`), сам Telegram-бот ещё не запущен — ждёт слова владельца.

## 2. Требования к среде

- **Язык.** README заявляет Python 3.14, только стандартная библиотека.
- **Зависимости.** Проверено по исходникам: во всех модулях `kdm1digest/*.py` импортируются только модули
  стандартной библиотеки (`sqlite3`, `urllib`, `html.parser`, `json`, `re`, `gzip`, `io`, `argparse`, `fcntl`,
  `dataclasses`, `pathlib`, `datetime` и т. п.). Сторонних пакетов нет, `pip install` для работы бота не нужен.
- **ОС.** Код и комментарии ориентированы на Linux (сервер `app.aifusion.site`, упомянут в `watchdog.py` и
  `publish.py`). Модуль `fcntl` (межпроцессные замки `flock`) — только Linux/Unix; код предусматривает его
  отсутствие (`try/except ImportError`), но тогда защита от параллельного запуска не работает.
- **Планировщик.** День 1 — cron. День 3 (план) добавляет `systemd --user` для слушателя кнопок (служба,
  перезапуск при падении) — модуль слушателя пока не написан.

## 3. Рабочая копия и каталоги

- **Разработка** — локальный репозиторий `tg-bot-kdm1`, ветка `main`. Git-репозиторий без
  настроенного `origin` — удалённого адреса (в том числе на GitHub) у него сейчас нет.
- **Продакшен** — отдельная рабочая копия `~/tg-bot-kdm1/`, разворачивается из тега (например,
  `v0.1.0`). Правки из разработки не попадают туда сами — только новым тегом и переустановкой (README,
  раздел «Установка»). Копия создана 15.10 клоном тега для проверки выпуска (сейчас `v0.1.1`, банк засеян
  25 случаями); `.env` с токеном и cron в ней нет — в Telegram бот не запущен.
- **`state/`** — рабочие данные бота, вне git: банк (`bank.sqlite3`), состояние сторожа (`watchdog.sqlite3`),
  замки процессов (`publish.lock`, `watchdog.lock`), резервные копии банка (`backups/bank-YYYYMMDD.sqlite3`,
  последние 14), метка аварии сторожа (`watchdog.crash`), пульс слушателя (`listener.heartbeat`, день 3).
  Создаётся сам при первом запуске.
- **`logs/`** — журналы по компонентам и журнал запуска cron за день; тоже вне git.

## 4. Настройки (`.env`)

Файл в корне рабочей копии, права `600`, заполняет владелец. Ниже — только имена и смысл, без значений
(источник — `kdm1digest/config.py`):

| Переменная | Обязательна | Смысл |
|---|---|---|
| `TELEGRAM_TOKEN` | да | токен Telegram-бота |
| `OWNER_CHAT_ID` | да | chat id владельца — единственный получатель выпусков и тревог |
| `PUBLISH_HOUR_PERM` | нет, по умолчанию 9 | час выпуска по Перми — от него считается дедлайн сторожа |
| `LISTENER_ENABLED` | нет, по умолчанию выключено | включает в стороже проверку «кнопки не работают» (день 3) |

Без `TELEGRAM_TOKEN` или `OWNER_CHAT_ID` `load_config` останавливается с ошибкой; само значение (и значения
других настроек) в текст ошибки не попадает — только имя недостающего ключа. Переменные окружения приоритетнее
файла `.env` (если задано и там, и там — побеждает окружение). Файл-образец — `.env.example`; в нём перечислены
`TELEGRAM_TOKEN`, `OWNER_CHAT_ID`, `LISTENER_ENABLED` — `PUBLISH_HOUR_PERM` там не упомянута, хотя код её читает.

## 5. Команды CLI

Все команды — `python3 -m kdm1digest <команда>`, запускаются из корня рабочей копии (там, где `.env`). Ключи —
точно по `kdm1digest/cli.py`:

| Команда | Ключи | Что делает |
|---|---|---|
| `init` | — | создаёт схему банка, если её ещё нет |
| `seed <файл.json>` | `--dry-run` | посев банка из JSON-файла случаев |
| `publish` | `--if-missing`, `--dry-run`, `--now ISO` | выдаёт 1–2 случая из банка |
| `watchdog` | `--now ISO`, `--test` | разовый прогон пяти проверок сторожа |

Пояснения к ключам:
- `seed --dry-run` — только проверяет файл (включая настоящую сверку со страницами), в банк не пишет.
- `publish --if-missing` — отправляет, только если выпуска за сегодня (по Перми) ещё не было.
- `publish --dry-run` — печатает тексты вместо отправки, банк не меняет (раздел 6).
- `--now ISO` (у `publish` и `watchdog`) — момент UTC вместо текущего, для проверки или разбора инцидента.
- `watchdog --test` — тревога и восстановление уходят с префиксом «ТЕСТ: ».

Коды выхода одинаковы для всех команд: `0` — успех (или не было повода для тревоги/отправки), `1` — сбой
отправки или сбой проверки, `2` — ошибка настроек или аргументов командной строки.

## 6. Пробная выдача (`publish --dry-run`)

Печатает в консоль тексты, которые ушли бы владельцу в Telegram — включая текст «Сегодня новых подходящих
случаев нет», если подходящих случаев нет. Банк при этом не трогает: не помечает случаи отправленными, не
фиксирует мёртвые ссылки, не пишет записи `deliveries` и `runs`, не делает резервную копию. Ссылка каждого
случая всё равно по-настоящему запрашивается — это проверка без записи в банк, а не имитация без сети.

Этим способом 15.10 владельцу показали вид выпуска прямо в чате разработки, без запуска самого бота в
Telegram (день 1, `docs/checks/day1.md`).

## 7. Сторож (`watchdog`)

Пять проверок без модели, со своим состоянием в `state/watchdog.sqlite3` (отдельно от банка — повреждение банка
не лишает сторож памяти о прежних тревогах):

| № | Причина | Когда срабатывает |
|---|---|---|
| 1 | Выпуск не пришёл | после `PUBLISH_HOUR_PERM:30` по Перми нет успешного выпуска за сегодня |
| 2 | Сборщик не работает | последний успешный прогон сборщика старше 72 часов |
| 3 | Запас банка | неотправленных случаев меньше чем на 7 дней при 2 случаях в день |
| 4 | Кнопки не работают | пульс слушателя старше 10 минут |
| 5 | Банк повреждён | банк не открывается на чтение, или упала одна из проверок 1–3 |

Проверки 2 и 3 молчат, пока в `runs` нет ни одного прогона сборщика — пока это так (сборщика пока нет, день 2).
Проверка 4 работает только при `LISTENER_ENABLED=1` (пока выключено — слушатель день 3 не реализован).

**Что значит тревога.** По каждой причине — одно сообщение на переходе «норма → тревога», затем не чаще раза в
6 часов, пока причина держится; на возврате в норму — отдельное сообщение «\<причина\>: снова работает».
Отправка тревоги не зависит от того, открылся банк или нет: сторож открывает банк только на чтение (`mode=ro`)
и никогда не создаёт и не правит его схему.

**Собственная защита сторожа:** второй параллельный прогон тихо выходит (замок `state/watchdog.lock`);
повреждённое состояние сторожа переносится в сторону (`.corrupt-<метка>`) и создаётся заново; любое
непредвиденное исключение после взятия замка превращается в аварийное сообщение владельцу напрямую (не чаще
раза в 6 часов, метка `state/watchdog.crash`) — прогон cron никогда не падает необработанным.

## 8. Журнал и что делать при сбое

- `logs/<component>.log` (`publish.log`, `watchdog.log`, `seed.log`, `cli.log`) — пишет сам бот
  (`kdm1digest/journal.py`): время UTC и по Перми, уровень, сообщение. Токен и chat id сюда не попадают.
- `logs/run-YYYYMMDD.log` — вывод (stdout/stderr) конкретного запуска через `bin/run.sh` за день; смотреть
  первым, если команда упала раньше, чем успела что-то записать в свой журнал.

**Порядок разбора сбоя:**
1. `logs/run-<дата>.log` — упала ли команда целиком (например, по жёсткому таймауту `bin/run.sh`, 600 секунд).
2. `logs/<component>.log` — что записал сам модуль (ошибка Telegram, сбой проверки ссылки и т. п.).
3. Тревога сторожа, если она пришла (день 3) или видна по содержимому `state/watchdog.sqlite3`.
4. При повреждении банка — восстановление из последней целой копии `state/backups/bank-YYYYMMDD.sqlite3`
   (последние 14 дней хранятся; команды автоматического восстановления в коде нет — файл копируется вручную).

## 9. Запуск в Telegram — что нужно от владельца (план дня 3)

Решение владельца 15.10 (`docs/TASK.md`, п.14.2, дословно: «Сам бот для телеграмма позже»): до этого шага не
создаются токен бота, рабочая копия `~/tg-bot-kdm1`, cron и слушатель кнопок — результаты показываются
прямо в чате разработки через `publish --dry-run` (раздел 6). Когда владелец даст слово, порядок такой:

1. **Токен бота.** Завести бота у `@BotFather` в Telegram и передать токен **файлом**, а не сообщением в общий
   чат — чтобы токен не осел в истории переписки. Токен сразу уходит в `.env` рабочей копии (`chmod 600`).
2. **Chat id владельца.** Отправить любое сообщение заведённому боту и считать `chat_id` из ответа Bot API
   (например, методом `getUpdates`); значение — в `OWNER_CHAT_ID` того же `.env`.
3. **Рабочая копия и тег.** `git clone` в `~/tg-bot-kdm1`, `git checkout <тег выпуска>` (README,
   раздел «Установка»).
4. **Пробный и настоящий выпуск.** Сначала `publish --dry-run` — проверить вид сообщений; затем `publish` —
   владелец получает первый настоящий выпуск.
5. **Проверка сторожа вживую.** `watchdog --test` на дне без выпуска — должно прийти «ТЕСТ: Выпуск не
   пришёл…»; затем штатный прогон должен пройти тихо.
6. **cron (готово по плану) и systemd (день 3, план).** Строки cron из README: основной выпуск, догоняющий
   `--if-missing`, сторож каждые 30 минут — все через `bin/run.sh`. Для слушателя кнопок — служба
   `systemd --user` с перезапуском при падении; сам модуль слушателя пока не написан.
7. **Старт пробной эксплуатации.** 14 дней по критериям `docs/TASK.md`, раздел 8; отсчёт — с дня 3, когда бот
   заработает с кнопками (решение владельца, см. [план и решения](roadmap-and-decisions.md)).

Этот документ только описывает устройство и порядок действий — сам он ничего не запускает и не меняет.
