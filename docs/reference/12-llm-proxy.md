# LLM-прокси (роль `llm`)

Роль `llm` (класс `LlmRole`, пакет `core/pcbk_core/llm/`) — единственная точка, через которую рабочие места
OpenCode и роль аналитики достают ответы языковой модели. Сама роль живёт не отдельным контейнером, а внутри
одного процесса `core` (FastAPI, `core/pcbk_core/app.py:create_app`) рядом с ролями данных, шлюза и поправок
базы знаний — см. [01-architecture.md](01-architecture.md). Ключ OpenRouter знает только `core`; у рабочих мест
есть лишь свой токен к `/llm/v1/chat/completions`.

Роль отдаёт:

- вход, совместимый с `POST /v1/chat/completions` OpenAI (`core/pcbk_core/llm/api.py`, `request.py`);
- белый список моделей с закреплённой точкой провайдера и верхней ценой (`models.py`);
- запасную модель на отказ «подождите/недоступен» (один повтор, без цикла);
- учёт денег: общий бюджет, доля каждого вызывающего, журнал вызовов `llm_calls` в `core.db`
  (`ledger.py`, `shares.py`);
- тормоз отдельного режима «прогон отбора модели» по памяти хоста (`brake.py`);
- предел числа обращений к модели на один ход разговора (`turns.py`);
- `GET /health/llm` — всё это одним JSON для страницы состояния и сторожа.

**Переносимость.** Механика — бюджет, журнал, доли, тормоз, предел ходов, перекачка SSE, белый список моделей
и запасная модель — не знает ни про КДМ-1, ни про ПЦБК и переносится на другой стенд как есть. Специфично для
этого заказчика:

- сам список `CANDIDATES` в `models.py` — имена моделей, закреплённые точки провайдера и цены подобраны и
  проверены именно для этого стенда; на другом стенде список переписывается целиком;
- схема идентификаторов вызывающих `student-NN`/`ops` (`core/pcbk_core/places.py`, `CALLER_RE`) — она пришла
  из понятия «рабочее место»; `Shares.usd`, `Budget._shares` (в составе роли) и `RUN_CALLER_RE` в
  `core/pcbk_core/settings.py` разбирают именно такие идентификаторы. Остальной код ledger/budget принимает
  `caller` как произвольную строку;
- OpenRouter как единственный путь к модели: класс `Upstream` и поля `provider.only`/`zdr`/`max_price`/
  `data_collection` в собранном теле — это протокол именно OpenRouter, а не произвольного OpenAI-совместимого
  сервера. Раздел 13 ниже — что менять, чтобы подключить другого провайдера напрямую;
- «прогон отбора модели» (`LLM_RUN_*`, раздел 4) — рабочий процесс сравнения моделей-кандидатов этого стенда;
  механизм (отдельный потолок расхода у части вызывающих, точка отсчёта, тормоз по памяти) ничего не знает про
  КДМ-1 и годится для любой задачи «выделить лимит под эксперимент».

## 1. Вход прокси: маршрут, токен, тело запроса

| Маршрут | Метод | Доступ | Что делает |
|---|---|---|---|
| `/llm/v1/chat/completions` | `POST` | токен `Bearer` из таблицы LLM-токенов, из сети своего места или из admin-сетей | чат с моделью: поток SSE или тело JSON, в формате ответа OpenAI |
| `/health/llm` | `GET` | без токена; поля счёта OpenRouter — только из admin-сетей | здоровье роли, бюджет, журнал, состояние OpenRouter, прогон отбора, тормоз — одним JSON |

Файл: `core/pcbk_core/llm/api.py` (`llm_router`), пути — константы `CHAT_PATH`, `HEALTH_PATH`.

**Аутентификация.** Вызывающий определяется функцией `bearer_caller` (`core/pcbk_core/data/http_api.py`) по
заголовку `Authorization: Bearer <токен>` (схема без учёта регистра). Токен сверяется с таблицей `TokenTable`,
построенной из файла `LLM_TOKENS_FILE` (строки `<id> <sha256-хеш токена>`, сверка — `hmac.compare_digest` без
раннего выхода). Токен места `student-NN` принимается только из сети этого места или из admin-сетей; прочие
идентификаторы (например `ops`) — из любой сети, которая видит порт `core`. Нет заголовка, схема не `Bearer`,
токен не найден или пришёл не из своей сети — `caller is None`, ответ `401 pcbk_unauthorized` без строки в
журнале вызовов (строка процесса — `outcome=unauthorized channel=llm`).

Токены LLM (`llm-tokens`) и токены службы данных (`core-tokens`) — разные таблицы: токен данных к `/llm/` не
подходит и наоборот (отдельный секрет `LLM_TOKENS_FILE`, по умолчанию `/run/secrets/llm-tokens`).

**Проверки запроса, по порядку** (первая сработавшая отвечает; коды — раздел 10):

1. токен (выше) → `401`;
2. ошибка настройки роли (`config_error`) → `403 pcbk_config`;
3. выключатель `LLM_STATE=stopped` → `403 pcbk_stopped`;
4. нет ключа OpenRouter → `403 pcbk_key_missing`;
5. тело запроса — не объект JSON → `400 pcbk_body_refused`;
6. поле `model` — точное совпадение с одним из разрешённых имён (раздел 2) → иначе `403 pcbk_model_refused`
   (суффиксы вида `:nitro`, другой регистр — тоже отказ; имя модели в текст ответа не идёт, только в строку
   журнала);
7. тело собирается заново белым списком полей (`rebuild_body`, раздел 1а) → ошибка сборки `BodyRefused` →
   `400 pcbk_body_refused` с причиной;
8. журнал вызовов не пишется прямо сейчас → `503 pcbk_ledger`, без резерва и без обращения к OpenRouter;
9. у вызывающего уже `LLM_CALLER_CONCURRENCY` идущих вызовов → `429 pcbk_busy`;
10. общий бюджет, тормоз и потолок прогона отбора (только вызывающим прогона), доля вызывающего — раздел 4;
11. предел шагов хода — только у запроса с полем `tools` (раздел 8).

Шаги 9–11 — один синхронный участок без единого `await` между проверкой бюджета и резервом вызова: это не даёт
двум одновременным запросам одного вызывающего пройти проверку раньше, чем один из них поставит резерв.

**Тело запроса — заново, не пересылка.** `rebuild_body` (`core/pcbk_core/llm/request.py`) строит новое тело
для OpenRouter только из белого списка полей; всё, чего нет в списке (`models`, `route`, `plugins`, `preset`,
`service_tier`, `transforms`, свой `provider`, серверные инструменты), пропадает. Разобранные поля:

| Поле входа | Что происходит |
|---|---|
| `messages` | заново по ролям `system`/`user`/`assistant`/`tool`; `name` и `cache_control` сообщений пропадают; не более `MAX_MESSAGES` = 4000 сообщений |
| части `image_url`/`file`/`input_audio` и любые нетекстовые части `content` | заменяются постоянным текстом `[вложение не передаётся на учебном стенде]` — ни один байт вложения наружу не уходит |
| `tools`/`tool_choice` | только функции (`type: function`), ровно `name`/`description`/`parameters`; серверные и кривые инструменты пропадают |
| `stream` | если булево — проходит как есть; при `true` добавляется `stream_options.include_usage: true` |
| `max_tokens`/`max_completion_tokens` | целое больше нуля, не больше `LLM_MAX_TOKENS` (умолчание 16000); иначе — сам предел |
| `stop`, `seed`, `response_format` (`text`/`json_object`/`json_schema`), `temperature` (0…2), `top_p` (0…1) | проходят, если годного вида; иначе не ставятся |
| `model`, `route`, `provider`, `plugins`, `service_tier`, `transforms`, … | не копируются вовсе — ставит прокси (ниже) |

Поля, которые ставит сам прокси, а не клиент: `model` (точное имя из белого списка), `reasoning.effort` (из
`ModelPolicy.effort`), `provider` (раздел 2), `user` = `pcbk-<caller>`, `session_id` = `<caller>:<session или
"none">`, и, у моделей с `auto_cache=True`, `cache_control: {"type": "ephemeral"}` верхнего уровня. Тела без
объекта JSON, с сообщением не по правилам или со значением, не кодируемым в JSON/UTF-8 (`NaN`, одиночный
суррогат), — `BodyRefused`, текст отказа — постоянный (без чисел и без значений запроса: OpenCode ищет в
тексте отказа коды `429|500|502|503|504|524`).

**Предел тела запроса.** Независимо от `rebuild_body`, на маршрут `/llm/` ставится общий предел размера тела —
`LLM_MAX_BODY_BYTES` (`LlmRole.install`, `core/pcbk_core/hooks.py`); тело больше предела получает `413
pcbk_body_too_large` до разбора JSON.

**Как места обращаются к прокси.** Конфигурация OpenCode `student/config/opencode.json` объявляет провайдер
`pcbk` (пакет `@ai-sdk/openai-compatible`):

```json
"pcbk": {
  "npm": "@ai-sdk/openai-compatible",
  "options": {
    "baseURL": "http://core:8000/llm/v1",
    "apiKey": "{file:/run/secrets/llm-token}"
  },
  "models": { "z-ai/glm-5.3": {"limit": {"context": 131072, "output": 16000}}, "…": "…" }
}
```

и второй провайдер, `pcbk-or` (пакет `@openrouter/ai-sdk-provider`, тот же `baseURL` и тот же токен) — он
нужен для моделей Claude: только этот клиент возвращает `reasoning_details` с подписями, которые модель
Claude требует обратно на следующем шаге с инструментами; `pcbk-or` объявляет только модели Claude и
Gemini. `baseURL` у обоих — адрес роли `llm` внутри сети `core` (места достают `core` по имени через
`extra_hosts`, раздел [20-security.md](20-security.md)); заканчивается на `/llm/v1`, а не на `/v1`, —
`@ai-sdk/openai-compatible` и `@openrouter/ai-sdk-provider` сами дописывают `/chat/completions`. Токен места —
файл секрета `/run/secrets/llm-token` (сырой токен, 48 знаков hex, не хеш) — секрет Compose, тот же для
MCP-токена данных не годится. Модель выбирается полем `"model": "pcbk/<имя>"` (или `"pcbk-or/<имя>"` для
моделей Claude) верхнего уровня конфига места, а у отдельного агента — своим `agent.<имя-агента>.model` в том
же конфиге (OpenCode берёт модель агента оттуда, остальным — верхнее `model`; включается переопределением
`OPENCODE_CONFIG_CONTENT` при развёртывании места, deploy/README.md «Модели по ролям») — список моделей и их
пределы в `provider.pcbk.models`/`provider.pcbk-or.models` только информируют OpenCode (контекст/вывод для
подсчёта токенов клиентом), сервер эти числа не читает: действующий предел вывода —
`LLM_MAX_TOKENS`/`max_tokens` в собранном теле.

## 2. Белый список моделей

Файл: `core/pcbk_core/llm/models.py`. Модель — `ModelPolicy` (frozen-dataclass):

| Поле | Смысл |
|---|---|
| `model` | точное имя модели в запросах клиента и в `LLM_MODELS`/`LLM_FALLBACK` |
| `provider_only` | единственная закреплённая точка провайдера OpenRouter (`provider.only` запроса); базовое имя без суффикса региона/уровня (например `fireworks`) пускает и варианты (`fireworks/us`) |
| `effort` | `low`/`medium`/`high` — значение `reasoning.effort` каждого запроса к этой модели |
| `in_usd_m`, `out_usd_m`, `write_usd_m` | верхняя цена точки, $ за 1 млн токенов: вход, выход, запись кэша |
| `auto_cache` | `True` — в тело добавляется `cache_control: {"type": "ephemeral"}` верхнего уровня (сейчас — только у моделей Claude) |
| `tier_tokens`, `tier_in_usd_m`, `tier_out_usd_m`, `tier_write_usd_m` | с `tier_tokens` и больше оценённых токенов входа — цены длинного входа (сейчас — у моделей на точке `azure`, порог 272 000) |
| `zdr` | значение поля `provider.zdr` запроса; `True` у всех моделей, кроме одной — см. ниже |

Полный список `CANDIDATES` (девять моделей, порядок — как в коде):

|---|---|---|---|---|---|---|
| `z-ai/glm-5.3` | `fireworks` | high | 1.40 / 4.40 / 0.0 | — | нет | да |
| `deepseek/deepseek-v4.1-flash` | `deepinfra/fp8` | high | 0.20 / 0.60 / 0.20 | — | нет | да |
| `google/gemini-3.8-flash` | `google-vertex/global` | medium | 1.50 / 7.50 / 0.0 | — | нет | да |
| `openai/gpt-6-sol` | `azure` | medium | 2.20 / 11.00 / 2.75 | 272 000: 4.40 / 16.50 / 5.50 | нет | да |
| `z-ai/glm-5.3-flash` | `fireworks` | low | 0.225 / 0.75 / 0.0 | — | нет | да |
| `openai/gpt-6-luna` | `azure` | medium | 0.11 / 0.55 / 0.1375 | 272 000: 0.22 / 0.825 / 0.275 | нет | да |

`anthropic/claude-fable-5.1` — единственная модель списка без ZDR у OpenRouter (её провайдер не входит в
список `GET /api/v1/endpoints/zdr`). Включать её в действующий `LLM_MODELS` имеет смысл только по явному
решению владельца стенда: без ZDR данные уходят провайдеру без гарантии нулевого хранения.

**ZDR и прочие фиксированные параметры провайдера.** Независимо от конкретной модели, блок `provider`
собранного тела — это `PROVIDER_FIXED` плюс поля модели:

```
provider = {
  "only": [<provider_only модели>],
  "allow_fallbacks": false,
  "data_collection": "deny",
  "require_parameters": true,
  "zdr": <zdr модели>,
  "max_price": {"prompt": <цена входа текущей ступени>, "completion": <цена выхода>, "request": 0}
}
```

`allow_fallbacks: false` и `only: [<одна точка>]` не дают OpenRouter самому перевести вызов на другую точку
провайдера — точка всегда ровно та, что в таблице; `data_collection: "deny"` и `zdr` — запрос нулевого
хранения у провайдера; `require_parameters: true` — отказ, если точка не поддерживает один из переданных
параметров (например `reasoning.effort`), а не тихая его отбрасывание.

**`provider.max_price` и верхняя оценка.** Вход оценивается как `ceil(байты собранного тела UTF-8 /
BYTES_PER_TOKEN)`; делитель `BYTES_PER_TOKEN = 1` у всех моделей — это намеренно верхняя оценка (токенов не
больше, чем байт тела). `ModelPolicy.estimate_usd(body_bytes, max_tokens)` = `n × max(вход, запись) / 1e6 +
max_tokens × выход / 1e6`, где `n` — оценённые токены входа, а цена берётся по ступени (базовая или
`tier_*`, если `n ≥ tier_tokens`). Эта оценка идёт в резерв бюджета при открытии вызова (раздел 4) и в
`provider.max_price` запроса (`ModelPolicy.max_price`, та же ступень цен): если фактическая цена закреплённой
точки у OpenRouter в момент вызова выше этого предела, OpenRouter сам откажет вызову 404-м («No endpoints
found matching your max_price»), и прокси передаёт этот же статус клиенту как `404 pcbk_upstream_rejected`
(раздел 10, строка `rejected`: статус 404 — один из тех, что прокси передаёт как есть), а не даст списать
больше, чем было зарезервировано.

**Проверка ответа провайдера.** `provider_matches(pinned, reported)` (без учёта регистра и знаков: строка
"Google Vertex" ~ `google-vertex/global`, слэш у `pinned` обрезает суффикс точки) сверяет провайдер из поля
`provider` ответа OpenRouter с закреплённым `provider_only` модели. Несовпадение не отказ — `provider_ok =
false` в строке журнала вызова (счётчик `provider_mismatch_24h` в `/health/llm`): такой вызов всё равно
оплачен и отдан клиенту, расхождение — только сигнал на страницу.

## 3. Выбор моделей (`LLM_MODELS`) и запасная модель (`LLM_FALLBACK`)

**`LLM_MODELS`** сужает список разрешённых моделей (`select_models`, `models.py`): пусто — разрешены все
девять кандидатов по порядку таблицы; иначе — имена через запятую (пробелы по краям срезаются), порядок — как
в строке, каждое имя — точно одно из `CANDIDATES`. Пустое или неизвестное имя, либо имя, повторённое дважды, —
`ValueError("LLM_MODELS: …")`; такая ошибка переводит всю роль в `config_error` (все вызовы к `/llm/` получают
`403 pcbk_config`, см. раздел 10). Запрос с `model`, не входящей в этот (уже суженный) список, получает `403
pcbk_model_refused`, даже если имя есть среди всех девяти кандидатов.

**`LLM_FALLBACK`** — пары `<основная>=<запасная>` через запятую (`parse_fallback`), оба имени — точные имена
`CANDIDATES`; пусто — запасного пути нет. Правила: основная не равна запасной, основная не повторяется,
запасная модель должна входить в действующий `LLM_MODELS` (если он сузил список); иначе — `ValueError` и
`config_error`, как у `LLM_MODELS`.

**Когда срабатывает.** Отказ основной модели **до первого байта ответа** одного из видов «подождите» или
«недоступен» — упомянутый ниже вид `UpstreamKind` `rate`, `in_flight`, `server` или `unreachable` (не денежные
и не ключевые отказы, не отказ по существу запроса, не переполнение контекста) — запускает `_attempt_fallback`
(`api.py`): резерв основного вызова закрывается как неудача, та же собранная из исходного тела клиента заявка
пересобирается уже политикой запасной модели (свой провайдер, усилие, цены), и если доля/бюджет/тормоз/
потолок прогона это позволяют — уходит на запасную модель тем же HTTP-ответом клиенту. Клиент (OpenCode) не
видит первого отказа вовсе. Повтор — **один на вызов**: если и запасная модель отказывает тем же видом,
второго переключения нет — клиент получает отказ запасной модели как обычный отказ OpenRouter.

**Что видно в журнале.** В `/health/llm` срабатывания фолбэка отдельных полей не получают; строка журнала
процесса (`docker compose logs core` в проде, `caplog` в тестах) несёт `fallback_from=<основная модель>
fallback_reason=<rate|in_flight|server|unreachable>` на строке успешного (или неуспешного) вызова запасной
модели.

**Формат `.env`**, без исторических значений — только синтаксис:

```
LLM_MODELS=<модель-1>,<модель-2>,…         # пусто — все девять кандидатов
LLM_FALLBACK=<модель-A>=<модель-B>,<модель-C>=<модель-D>   # пусто — запасного пути нет
```

Цепочку можно строить дальше одного шага (`A=B,B=C`) — это просто две независимые пары; второй переход внутри
одного вызова всё равно не происходит (правило «один повтор на вызов» выше), цепочка влияет только на то, с
какой запасной моделью отказ A обрабатывается, и с какой — отказ B, если B вызвана как основная сама по себе.

## 4. Бюджет и доли вызывающих

Файлы: `core/pcbk_core/llm/ledger.py` (`Budget`, `RunSpec`, `run_spec`), `core/pcbk_core/llm/shares.py`
(`Shares`).

**Порядок проверки при каждом запросе** (`Budget.refusal(caller)`):

1. общий бюджет: `total_spent() ≥ LLM_TOTAL_USD` → `budget_spent`;
2. если вызывающий участвует в прогоне отбора (`LLM_RUN_CALLERS`) — тормоз прогона защёлкнут → `run_halted`;
   иначе расход прогона `run_spent() ≥ LLM_RUN_USD` → `run_spent`;
3. доля вызывающего (`share_of(caller)`) израсходована → `share_spent`.

Эти четыре кода становятся HTTP-ответами `402 pcbk_budget_spent`/`pcbk_run_halted`/`pcbk_run_spent`/
`pcbk_share_spent` (раздел 10).

**Доля вызывающего** (`Budget.share_of`):

- вызывающий `ops` — `LLM_OPS_SHARE_USD` (умолчание 100);
- место `student-NN` — его доля из `Shares` (если доли загружены), иначе общая `LLM_SHARE_USD`;
- любой другой вызывающий — `LLM_SHARE_USD` (умолчание 100).

**`Shares`** — доли мест в целых центах, таблица `llm_shares` в `core.db` (`place INTEGER PRIMARY KEY`, `cents
INTEGER`, `updated_at`, `updated_by`). Строка есть только у места, долю которого когда-либо меняли; у
остальных — `default_cents = round(LLM_SHARE_USD × 100)`. Доля `ops` вне этой таблицы — её держит сам `Budget`
(`LLM_OPS_SHARE_USD`). Изменение доли — «всё или ничего» (`Shares.apply`: проверка «было» по диску для каждого
изменяемого места, новая доля не ниже уже оплаченного этим местом, и сумма всех долей не растёт выше
`LLM_TOTAL_USD` — уменьшение суммы разрешено всегда, даже если она и после этого больше общего бюджета) и
«остановить место» (`Shares.apply_floor` — доля одного места одной операцией сводится к уже оплаченному,
разница уходит другому месту). Обе операции — часть HTTP API кабинета преподавателя, а не роли `llm`; сверяет
их такт шлюза (`Shares.verify`) — см. [13-gateway.md](13-gateway.md). Роль `llm` только читает память `Shares`
(`usd(caller)`) при каждом отказе и отдаёт `ledger.settled` в `Shares.settled_of` при старте — это нужно
классу `Shares`, чтобы не опустить долю места ниже уже потраченного.

Доли не загрузились (`Shares.open()` вернул `False`) — это `config_error` роли: все вызовы к `/llm/` получают
`403 pcbk_config`, а не долю по умолчанию по ошибке.

**Общий бюджет** (`Budget.total_spent()`): берётся максимум из суммы по журналу вызовов и «расхода по ключу
плюс текущие резервы» (`key_spent() + ledger.reserved_open()`), если `LLM_KEY_DEDICATED=on` и известен расход
ключа по `/key` (раздел 11). Так расхождение между журналом и настоящим счётом (например, после потери
строки журнала при перезапуске) не даёт бюджету показаться меньше, чем он есть на самом деле у OpenRouter —
при сомнении лимит считается исчерпанным раньше, не позже. Число, которое видит страница состояния
(`Budget.page_spent()`), — без текущих резервов идущих вызовов: `max(ledger.spent() − reserved_open(),
key_spent())`.

**Прогон отбора модели** (`RunSpec`, `run_spec`, переменные `LLM_RUN_ID`/`LLM_RUN_USD`/`LLM_RUN_CALLERS`) —
отдельный потолок расхода в долларах, который действует **сверх** долей и общего бюджета, но только для
перечисленных вызывающих. Все три переменные задаются или не задаются вместе; потолок — больше нуля и не
больше `LLM_TOTAL_USD`. Точка отсчёта каждого вызывающего прогона (`run_base`, ключ `llm_meta` вида
`run_base_usd:<id прогона>:<caller>`) ставится один раз при старте роли (до первого вызова) — уже оплаченное
(`ledger.settled`) на этот момент; `Budget.run_spent()` — сумма `max(0, расход сейчас − точка отсчёта)` по
всем вызывающим прогона. Новый `LLM_RUN_ID` — новая точка отсчёта (старый расход в новый потолок не входит);
тот же `LLM_RUN_ID` после перезапуска `core` — продолжение того же счёта (точка лежит на диске). Третий
отдельный тормоз именно прогона — раздел 7.

## 5. Журнал вызовов (`Ledger`, таблица `llm_calls`)

Файл: `core/pcbk_core/llm/ledger.py`. Таблица SQLite в `core.db` (та же база, что у роли данных и доль
`llm_shares`), только числа, коды и имена — без текста модели и без токенов:

| Столбец | Тип | Смысл |
|---|---|---|
| `id` | `INTEGER PRIMARY KEY` | счётчик в памяти процесса |
| `ts` | `TEXT` | момент открытия вызова, ISO-8601 UTC |
| `caller` | `TEXT` | вызывающий (`student-NN`, `ops`, …) |
| `session` | `TEXT`/`NULL` | `X-Session-Id` клиента (ровно `ses_` + 26 знаков) |
| `model` | `TEXT` | имя модели клиента (до 100 знаков) |
| `step` | `INTEGER` | номер шага хода (раздел 8); 0 у запросов без инструментов |
| `status` | `TEXT` | одно из `open`, `ok`, `upstream_error`, `money`, `refused`, `cancelled`, `lost`, `unknown` |
| `code` | `TEXT` | код `REFUSALS`/`UpstreamKind` (раздел 10), пусто у удачных |
| `http_status` | `INTEGER` | статус ответа клиенту; 0 у идущего вызова |
| `provider` | `TEXT`/`NULL` | провайдер из ответа OpenRouter |
| `provider_ok` | `INTEGER`(bool)/`NULL` | совпал ли провайдер с закреплённой точкой (`provider_matches`) |
| `generation_id` | `TEXT`/`NULL` | id генерации OpenRouter (`X-Generation-Id` или поле `id` потока) |
| `cost` | `REAL`/`NULL` | цена, если пришла |
| `cost_est` | `REAL` | верхняя оценка при открытии вызова (`ModelPolicy.estimate_usd`) |
| `cost_source` | `TEXT` | `stream`, `body`, `generation`, `pending`, `unknown`, `none` |
| `prompt_tokens`, `completion_tokens`, `cached_tokens`, `cache_write_tokens`, `reasoning_tokens` | `INTEGER` | из `usage` ответа, 0 если поля нет |
| `duration_ms` | `INTEGER` | длительность вызова |

Отдельная таблица `llm_meta` (`key TEXT PRIMARY KEY`, `value REAL`) — числовая память между перезапусками:
ключи вида `key_base_usd:<отпечаток ключа>` (точка отсчёта расхода ключа, раздел 11),
`run_base_usd:<id прогона>:<caller>` (точка отсчёта прогона, раздел 4), `brake:<id прогона>:reason`/
`halted_at`/`swap_base_mib`/`oom_base` (тормоз, раздел 7).

**Что входит в сумму (`charge`).** У статусов с пришедшей ценой (`cost_source` в `stream`/`body`/`generation`,
`cost` не `NULL`) и у `cost_source = none` (отказ до обращения к модели) — в сумму идёт `cost` (у `none` это
всегда `0.0`). Во всех остальных случаях (`pending`, `unknown`, `lost`, вызов ещё открыт) — в сумму идёт
`cost_est`, то есть верхняя оценка: когда цена не известна или ещё не получена, бюджет списывается по худшему
предположению, а не по нулю.

**Запись — не в цикле событий.** Память журнала меняется синхронно в вызывающем потоке (бюджет виден сразу
же), а запись строки в SQLite идёт через очередь FIFO одному потоку-писателю (`pcbk-ledger-writer`): порядок
операций одной строки сохраняется, сам цикл событий `asyncio` блокировки диска никогда не ждёт. Упавшая с
ошибкой SQLite операция (блокировка, диск полон, файл испорчен) не бросается вызывающему — писатель повторяет
её во главе очереди, пока она не пройдёт или процесс не остановится; `consecutive_failures` растёт, а
`flush()` с таймаутом `LEDGER_DURABLE_S` = 8 секунд (вызывается перед обращением к OpenRouter, раздел 1) не
дождавшись — `TimeoutError`, и прокси отвечает `503 pcbk_ledger` **до** запроса к модели: строка вызова должна
лечь на диск раньше, чем деньги могут быть потрачены у провайдера. Исключение не из SQLite — операция «отравлена» и бросается сразу
(`writes_dropped_total`), а каждый `flush()`, чья метка стоит после неё, получает `LedgerWriteLost` (это
держится до следующего открытия журнала при перезапуске `core`).

**Что видно на `/health/llm`** (метод `LlmRole.health_json`, без токенов и id вызывающих):

| Поле | Смысл |
|---|---|
| `spent_usd` | число для страницы — `Budget.page_spent()` |
| `reserved_usd` | сумма оценок идущих сейчас вызовов |
| `ledger_usd` | `Ledger.spent()` — пришедшие цены плюс оценки по безценовым строкам; **включает** резервы идущих (`open`) и ждущих дозапроса (`pending`) вызовов (они не вычитаются, в отличие от `spent_usd` страницы выше) |
| `estimated_usd` | часть `ledger_usd`, которая стоит оценкой, а не пришедшей ценой (`Ledger.estimated()`; тоже включает резервы идущих и ждущих) |
| `key_spent_usd`, `key_usage_usd`, `account_remaining_usd` | только из admin-сетей (`ACCOUNT_KEYS`) — расход по ключу от его точки отсчёта, расход ключа по `/key`, остаток счёта по `/credits` |
| `total_usd` | `LLM_TOTAL_USD` |
| `ops_usd` | расход вызывающего `ops` |
| `shares` | `{"over_80": N, "spent": N}` — число мест `student-NN`, чья доля потрачена больше 80 % / полностью |
| `pending` | строк в ожидании дозапроса цены сейчас |
| `pending_stuck` | из них — дозапрос идёт дольше 15 минут (`PENDING_STUCK_S`) |
| `cost_unknown_24h`, `provider_mismatch_24h` | число строк с `cost_source=unknown` / `provider_ok=false` за последние 24 часа |
| `models` | действующий список имён моделей (`LLM_MODELS` после разбора) |
| `ledger_ok`, `ledger_error`, `ledger_queue`, `ledger_fresh`, `ledger_reset` | состояние журнала: пишется ли сейчас, причина (`dropped`/`write`), длина очереди, создана ли таблица только что, похож ли свежий `core.db` на пропавший при ненулевом расходе ключа |
| `upstream` | `{"state", "text", "since"}` — состояние связи с OpenRouter (раздел 10) |
| `run` | `null` без прогона, иначе `{"id", "cap_usd", "spent_usd", "callers", "calls_10m", "idle_s"}` |
| `run_brake` | `null` без прогона, иначе блок тормоза (раздел 7) |
| `egress`, `refresh_started_age_s` | состояние охраны выхода по адресу OpenRouter — см. [20-security.md](20-security.md) |

Остальные поля без разбора: `checked_at` (конец последней попытки опроса OpenRouter), `config_error`,
`tokens_error`, `stopped` (булево, `LLM_STATE=stopped`), `key` (`ok`/`missing`), `mgmt_key`
(`ok`/`missing`/`rejected`/`error`), `drill` (значение `DRILL_LLM`).

## 6. Цена вызова: `usage`, `/generation`, дозапрос

Класс `Usage` (`ledger.py`) разбирает поле `usage` ответа OpenRouter без исключений (негодное значение —
поле отсутствует): `cost`, `prompt_tokens`, `completion_tokens`, `cached_tokens` (из
`prompt_tokens_details.cached_tokens`), `cache_write_tokens` (`prompt_tokens_details.cache_write_tokens`),
`reasoning_tokens` (`completion_tokens_details.reasoning_tokens`).

**Источник цены по виду ответа** (`cost_source`, см. docstring `api.py`):

- отказ до первого байта ответа (статус не 200, запрос не ушёл или соединение не открылось) — `none`, в сумму
  идёт `0`;
- ответ без потока, пришедший целиком, — `body`: цена, если есть, из `usage.cost` тела;
- поток — только последний чанк перед `data: [DONE]` с полем `usage` (наблюдатель `SseObserver`, раздел 9) —
  `stream`;
- ответ 200 получен, но ни один из двух способов не дал цены сразу (например обычный ответ для модели без
  потока ещё не дочитан до конца, либо поток закрылся без финального `usage`, но с известным id генерации) —
  строка остаётся `pending`, и запускается фоновый дозапрос;
- тело ушло, а ответа нет вовсе (разрыв соединения после отправки, срок чтения) — `unknown`: деньги могли быть
  списаны у провайдера, оценка остаётся в силе.

**Дозапрос** (`LlmRole.resolve_cost`, `spawn_resolve`): фоновая задача ждёт по очереди паузы из
`COST_RETRY_DELAYS_S` — `1, 2, 4, 8, 15, 30, 60, 120, 300` секунд (итого около 9 минут) — и после каждой паузы
спрашивает `GET /generation?id=<generation_id>` у OpenRouter (`Upstream.generation_cost`). Цена нашлась —
строка переходит в `generation` с настоящей ценой; весь список пауз пройден без ответа — `unknown`, сумма
остаётся по оценке. Строки `pending` с известным `generation_id`, не дождавшиеся ответа до перезапуска `core`,
дозапрашиваются заново при следующем старте роли (`pending_to_resolve`); строки без `generation_id` при старте
переводятся в `unknown` сразу (дозапросить нечем).

## 7. Тормоз прогона отбора по памяти (`RunBrake`)

Файл: `core/pcbk_core/llm/brake.py`. Работает **только** при заданных `LLM_RUN_*` (раздел 4); без прогона
тормоза нет вовсе. Раз в `RUN_BRAKE_POLL_S` (5 секунд) роль читает в отдельном потоке:

- `/proc/meminfo` (путь — `LLM_RUN_MEMINFO`) — `MemAvailable`, `MemTotal`, занятый `swap`;
- `/proc/vmstat` (`LLM_RUN_VMSTAT`) — счётчик ядра `oom_kill`;
- `/proc/pressure/memory` (`LLM_RUN_PRESSURE`) — давление `full avg10`, %.

**Причины защёлки** (`BRAKE_REASONS`):

| Причина | Условие |
|---|---|
| `memory` | свободно меньше `LLM_RUN_MEM_FAIL_MIB` (умолчание 1024 МиБ) |
| `swap` | занятый swap минус база не меньше `LLM_RUN_SWAP_GROW_MIB` (умолчание 512 МиБ), **или** рост swap за 10 минут не меньше того же порога; база — `LLM_RUN_SWAP_BASE_MIB` (умолчание −1 — взять с первой проверки) |
| `psi` | давление `full avg10` выше `LLM_RUN_PSI_FULL_MAX` (умолчание 10 %) |
| `oom` | счётчик `oom_kill` вырос от базы (базой берётся первое прочитанное значение) — защёлкивается **сразу**, без серии проверок |
| `blind` | память не читается: нет `MemAvailable` или `oom_kill` (оба файла обязательны), либо датчик, который раньше в этом процессе уже давал данные (swap, давление), замолчал или ответил не по формату |

`memory`, `swap`, `psi`, `blind` защёлкиваются после `BRAKE_HOLD_CHECKS` = 3 проверок подряд с этим условием —
один шумный отсчёт прогон не роняет; `oom` — сразу, одним отсчётом.

**Защёлка навсегда в пределах прогона.** Условие ушло — защёлка не снимается сама. Под защёлкой вызовы мест
прогона получают `402 pcbk_run_halted` (раздел 10), а шлюз усыпляет места прогона и не даёт им проснуться.
Причина, время и базы (swap, oom) записаны в `llm_meta` с принудительным сбросом журнала на диск — перезапуск
`core` с тем же `LLM_RUN_ID` не снимает защёлку, собственное убийство процесса по памяти сразу после защёлки
её не теряет.

**Снять защёлку** — либо новый `LLM_RUN_ID` (новый прогон), либо вручную в контейнере `core`:

```bash
docker exec pcbk-core python -m pcbk_core.llm.brake clear --run <id> --yes
```

— удаляет ключи `brake:<id>:…` из `llm_meta` своим соединением (без открытия `Ledger`, идущие вызовы
работающего процесса не трогаются), после чего нужно пересоздать `core`: работающий процесс держит защёлку в
памяти.

`--db <путь>` — необязательный путь к `core.db`; по умолчанию — переменная окружения `DB_PATH` процесса, иначе
`Settings.DB_PATH` (`/var/lib/pcbk-core/core.db`).

**Блок `run_brake` в `/health/llm`** (ключи `BRAKE_KEYS`): `state` (`watching`/`halted`), `reason`,
`avail_mib`, `total_mib`, `fail_mib`, `swap_base_mib`, `swap_growth_mib`, `swap_grow_mib`, `psi_full10`,
`psi_full_max`, `oom_kills`, `age_s` (с последней проверки), `halted_at`.

## 8. Предел шагов хода (`TurnLimiter`)

Файл: `core/pcbk_core/llm/turns.py`. Ход — ответ модели на один вопрос человека, который может занять
несколько обращений к модели (инструменты, уточнения). Счётчик ведётся только у запросов с полем `tools` в
собранном теле (`step = 0` у прочих — фоновые заголовки разговора, сжатие без инструментов и т. п., они не
считаются и не ограничиваются).

Ключ хода — `(вызывающий, x-parent-session-id или X-Session-Id)`: обращения подагента (`x-parent-session-id`)
считаются в ход родителя. Новый ход (шаг 1) начинается, если последнее сообщение `user` — новый текст (не
совпадает по хешу с запомненным началом хода), или это продолжение после сжатия разговора, перед которым стоит
новый «настоящий» вопрос; простой повтор той же метки (OpenCode повторяет запрос до пяти раз при сбое) ход не
сбрасывает. Эта проверка «новый ли вопрос» работает только у запроса без `x-parent-session-id`: обращение
подагента всегда просто продолжает счётчик хода родителя (или открывает ход шагом 1, если это первый
запрос по данному ключу вообще) и сам новый ход эта проверка не начинает. Предел — `LLM_TURN_CALLS` (умолчание
16, допустимо 1…100); превышение — `403 pcbk_turn_limit`,
счётчик не растёт. Если шаг оказался без цены (например отказ до первого байта ответа, `cost_source = none`),
он возвращается: `TurnLimiter.refund` отнимает единицу от счётчика хода. Ходы, к которым не было обращения
дольше `TURN_IDLE_S` (час), забываются — память не растёт без предела на долгоживущем процессе.

## 9. SSE-поток и учёт вызова

Поток OpenRouter (`Content-Type: text/event-stream`) отдаётся клиенту байт-в-байт (`LlmStream._pump`,
`core/pcbk_core/llm/api.py`), а копия тех же кусков кормит `SseObserver` (`core/pcbk_core/llm/sse.py`) —
отдельный разбор, который не меняет и не прерывает перекачку клиенту. Наблюдатель собирает из событий `data:
{...}`, разделённых пустой строкой: первый `id` (id генерации, если не пришёл заголовок `X-Generation-Id`),
первый `provider`, последний встретившийся `usage`, первый объект `error` (ошибка посреди уже открытого
потока), и флаг `done` — пришёл ли `data: [DONE]`. Событие неожиданной формы не рвёт поток — только счётчик
`bad_events` и одна строка в журнал процесса на наблюдателя.

**Учёт — не в генераторе потока, а в `finish()`** (вызывается и из `__call__` потока, и из обработчика всюду,
где ответ клиенту не отдан потоком): так обрыв соединения клиентом гарантированно закрывает резерв места
одновременности и пишет итоговую строку журнала, даже если генератор перекачки Starlette не успел дойти до
своего `finally`.

**Общий срок вызова** — `CHAT_DEADLINE_S` = 600 секунд (10 минут — при 16 000 токенов ответа и скорости не
ниже ≈27 токенов/с), считается от открытия резерва (`begin_call`) до конца потока или тела; отдельный срок
чтения кусков потока у клиента HTTP — 120 секунд (таймаут `read` у `httpx`, `core/pcbk_core/llm/upstream.py`).
Если клиент (место) перестал читать поток (например, браузер не присылает данные дальше), перекачка снимается
через `CHAT_DEADLINE_S` плюс запас `STREAM_SEND_GRACE_S` = 5 секунд — резерв места одновременности и журнал не
держатся вечно.

## 10. Ошибки и HTTP-коды для места

Все отказы прокси — JSON в форме OpenAI: `{"error": {"message": "...", "type": "pcbk", "code": "<код>"}}`.
Тексты клиенту — постоянные (без чисел, без содержимого запроса — OpenCode ищет в тексте коды `429|500|502|
503|504|524`), кроме предела шагов хода (само число предела, не больше 100).

| Ключ | HTTP | `code` | Когда |
|---|---|---|---|
| `unauthorized` | 401 | `pcbk_unauthorized` | нет токена, не `Bearer`, токен неизвестен или пришёл не из своей сети |
| `too_large` | 413 | `pcbk_body_too_large` | тело больше `LLM_MAX_BODY_BYTES`, **или** OpenRouter отказал переполнением контекста (статус 413 или текст по образцам сообщений провайдеров) |
| `stopped` | 403 | `pcbk_stopped` | `LLM_STATE=stopped` |
| `key_missing` | 403 | `pcbk_key_missing` | нет ключа OpenRouter (не прочитан или ошибка настройки) |
| `body` | 400 | `pcbk_body_refused` | тело — не объект JSON, или `rebuild_body` не смог собрать запрос (`BodyRefused`) |
| `model` | 403 | `pcbk_model_refused` | `model` не входит в действующий белый список |
| `share_spent` | 402 | `pcbk_share_spent` | доля вызывающего израсходована |
| `budget_spent` | 402 | `pcbk_budget_spent` | общий бюджет (`LLM_TOTAL_USD`) исчерпан |
| `run_spent` | 402 | `pcbk_run_spent` | потолок прогона отбора (`LLM_RUN_USD`) исчерпан — только вызывающим прогона |
| `run_halted` | 402 | `pcbk_run_halted` | тормоз прогона защёлкнут — только вызывающим прогона |
| `turn_limit` | 403 | `pcbk_turn_limit` | шагов за ход больше `LLM_TURN_CALLS` |
| `busy` | 429 | `pcbk_busy` | у вызывающего уже `LLM_CALLER_CONCURRENCY` идущих вызовов; заголовок `Retry-After: 2` |
| `config` | 403 | `pcbk_config` | роль в `config_error` (ошибка `LLM_*`, недогруженные доли и т. п.) |
| `money_out` | 402 | `pcbk_money_out` | на счёте OpenRouter кончились деньги (сам ключ или общий счёт по `/credits`) |
| `key_limit` | 402 | `pcbk_key_limit` | исчерпан лимит ключа OpenRouter |
| `key_rejected` | 403 | `pcbk_key_rejected` | OpenRouter отклонил ключ (401) |
| `region` | 403 | `pcbk_region` | OpenRouter отказывает по региону |
| `wait` | 429 | `pcbk_upstream_wait` | OpenRouter просит подождать (429, в т. ч. предел одновременных запросов по ключу) — переносит заголовок `Retry-After`, если он есть и состоит из цифр |
| `rejected` | статус OpenRouter, если это 400/404/422, иначе 400 | `pcbk_upstream_rejected` | OpenRouter отказал по существу запроса (4xx вне прочих категорий, не переполнение контекста) |
| `ledger` | 503 | `pcbk_ledger` | журнал вызовов не пишется прямо сейчас; заголовок `Retry-After: 5` |
| `down` | 502 | `pcbk_upstream_down` | OpenRouter не ответил, ответил 5xx/408, либо связь не открылась |

**Как HTTP-статус OpenRouter превращается в один из этих кодов** (`classify`, `core/pcbk_core/llm/upstream.py`
— по первой подходящей строке):

| Статус/условие ответа OpenRouter | `UpstreamKind` |
|---|---|
| 401 | `key_rejected` |
| 402, `error.metadata.limit_source == "in_flight_budget"` | `in_flight` → у прокси `wait` |
| 402 или 403, текст содержит «key limit exceeded»/«budget limit exceeded» | `key_limit` |
| 402 (прочее), или 403 с текстом «insufficient credits» | `money_out` |
| 403 с текстом «not available in your region» | `region` |
| 429 | `rate` → у прокси `wait` |
| 408 или ≥ 500 | `server` → у прокси `down` |
| прочий 4xx | `rejected` |
| связь не открылась, не удалось отправить тело или не пришёл ответ | `unreachable` → у прокси `down` |

Запасная модель (раздел 3) переключается только на видах `rate`, `in_flight`, `server`, `unreachable` —
столбец «у прокси `wait`/`down`» выше; денежные, ключевые, региональные отказы и отказ по существу запроса
фолбэк не запускают.

## 11. Ключ OpenRouter и секреты роли

| Файл секрета (переменная) | Формат | Что делает |
|---|---|---|
| `OPENROUTER_KEY_FILE` (умолчание `/run/secrets/openrouter.key`) | один ключ, печатные знаки ASCII, пробелы/переводы строк/BOM по краям срезаются | ключ прокси к OpenRouter (чат, `/key`, `/generation`); нет файла или он пуст после очистки — ключа нет, но это не `config_error`: роль просто без ключа, `/llm/` отвечает `403 pcbk_key_missing` (раздел 10); файл не читается (права, не UTF-8, больше 4096 байт) или содержимое — не печатные знаки ASCII — это ошибка настройки, роль в `config_error` (`403 pcbk_config` всем вызовам) |
| `OPENROUTER_MGMT_KEY_FILE` (умолчание `/run/secrets/openrouter-mgmt.key`) | тот же формат | ключ **управления** — только опрос `GET /credits` (остаток счёта); необязателен: нет или негоден — просто не виден остаток счёта (`mgmt_key: "missing"/"error"`), сам прокси работает |
| `LLM_TOKENS_FILE` (умолчание `/run/secrets/llm-tokens`) | строки `<id> <sha256-хеш токена>` | кто может звать `/llm/v1/chat/completions`; не прочитан — не `config_error` (`tokens_error`), таблица пустая, все вызовы `401` |

Опрос OpenRouter (`LlmRole.poll`, раз в `LLM_POLL_S`, умолчание 60 секунд, не чаще раза в 5 секунд) берёт
`GET /key` (расход и лимит именно этого ключа) всегда, `GET /credits` (остаток счёта) — только если есть ключ
управления.

**`LLM_KEY_DEDICATED`**: `on` (умолчание) — ключ считается выделенным только этому стенду, прокси ставит
точку отсчёта `key_base_usd:<отпечаток ключа>` в `llm_meta` при первом удачном `/key` без идущих и ждущих
дозапроса вызовов, и сверяет расход журнала с `usage − точка` (раздел 4, `Budget.total_spent`); `off` — ключ
общий с чем-то ещё, сверки с `/key` нет (иначе чужой расход того же ключа останавливал бы этот прокси раньше
срока). Отпечаток ключа (`key_fingerprint`, первые 12 знаков sha256) используется только как часть ключа
`llm_meta`, сам ключ наружу (в журналы, в `/health/llm`, в исключения) не попадает ни в каком виде.

## 13. Как подключить другой OpenAI-совместимый провайдер

Три места кода написаны именно под OpenRouter, их нужно заменить или переписать, чтобы говорить с другим
провайдером напрямую (прямой Azure OpenAI, собственный шлюз и т. п.):

1. **`core/pcbk_core/llm/upstream.py`, класс `Upstream`.** `open_chat` шлёт `POST <base>/chat/completions`
   (путь и формат тела — стандартный OpenAI, этот кусок годится почти для любого совместимого провайдера),
   но `key_info` (`GET /key`), `credits` (`GET /credits`) и `generation_cost` (`GET /generation?id=…`) — это
   собственные ручки именно OpenRouter для учёта денег. У прямого провайдера таких ручек, скорее всего, нет:
   `key_info`/`credits` придётся убрать или подменить мониторингом провайдера (или просто оставить без ответа
   — `LlmRole.poll` переживает отказ `/key`/`/credits` сам, роль продолжает работать, только страница не
   покажет остаток счёта), а `generation_cost` — либо отдавать `None` всегда (цена вызовов тогда всегда оценка,
   `cost_source` не выйдет из `pending`/`unknown`), либо найти эквивалент своего провайдера.
2. **`core/pcbk_core/llm/models.py`, `ModelPolicy`/`CANDIDATES`/`PROVIDER_FIXED`.** Поля `provider_only`,
   `zdr`, и блок `PROVIDER_FIXED` (`allow_fallbacks`, `data_collection`, `require_parameters`,
   `provider.max_price`) — расширения протокола именно OpenRouter («маршрутизация к конкретной точке
   провайдера», «нулевое хранение», «не выбирать точку дороже цены»). У провайдера без них `rebuild_body`
   (`request.py`, функция `_set_max_price`) нужно упростить: оставить `model`/`messages`/`tools`/`stream`/…
   белого списка, но не собирать поле `provider` вовсе (или собрать то, что поддерживает конкретный
   провайдер) и не считать `max_price`. Цены (`in_usd_m`/`out_usd_m`/`write_usd_m`/`tier_*`) и `effort`
   (`reasoning.effort` — не у всех провайдеров есть этот параметр) переписываются по прайсу и возможностям
   нового провайдера; сама оценка (`estimate_usd`, `BYTES_PER_TOKEN = 1`) и журнал/бюджет/доли не меняются.
3. **Проверка ответа (`provider_matches`, `api.py`).** Если новый провайдер не возвращает поле `provider` в
   ответе (как делает OpenRouter, у которого за одним именем модели может стоять несколько реальных точек),
   проверку `provider_ok` можно просто не делать (оставить `None`): остальной журнал и бюджет от неё не
   зависят.

Всё остальное — вход `/llm/v1/chat/completions`, белый список моделей как механизм (а не конкретные цены),
бюджет, доли, журнал, тормоз, предел ходов, SSE-перекачка, запасная модель — не знает про OpenRouter и не
меняется.

## 14. Как поднять LLM-прокси отдельно

Команды compose для этого случая (службы, обязательные секреты и тома) — рецепт (D) в
[02-build-and-deploy.md](02-build-and-deploy.md), §6.3 «Только LLM-прокси».

Роль `llm` не выделена в отдельный Docker-сервис — в контейнере `core` она всегда идёт вместе с ролями данных,
шлюза и базы знаний (`core/pcbk_core/main.py:build_roles`). Два пути получить **только** эту функциональность.

**А. Весь образ `core`, но настроить только роль `llm`.** Остальные роли не обязательны для работы прокси:
ошибка в учётных данных историана или в белом списке тегов делает роль данных «с ошибкой настройки», но не
останавливает `core` и не трогает роль `llm` — она независима (`LlmRole` ничего не знает про `DataRole`,
`GatewayRole`, `KbRole`). Нужны: ключ OpenRouter (`OPENROUTER_KEY_FILE`, раздел 11 — для проверки без реальных
трат удобнее двойник `core/tests/fake_openrouter.py`, см. [19-tests-and-bench.md](19-tests-and-bench.md)) и
хотя бы одна строка в `LLM_TOKENS_FILE`. Пример для разработки — без Docker secrets, прямыми путями:

```bash
printf 'sk-or-свой-ключ' > /tmp/openrouter.key
: > /tmp/openrouter-mgmt.key                       # пустой файл — ключа управления нет
TOKEN=$(openssl rand -hex 24)
printf 'student-01 %s\n' "$(printf '%s' "$TOKEN" | sha256sum | cut -d' ' -f1)" > /tmp/llm-tokens
OPENROUTER_KEY_FILE=/tmp/openrouter.key OPENROUTER_MGMT_KEY_FILE=/tmp/openrouter-mgmt.key \
  LLM_TOKENS_FILE=/tmp/llm-tokens DB_PATH=/tmp/core.db \
  python -m pcbk_core.main
```

Проверка — `GET http://127.0.0.1:8000/health/llm` и чат с токеном из `$TOKEN`:

```bash
curl -s -X POST http://127.0.0.1:8000/llm/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"model": "z-ai/glm-5.3", "messages": [{"role": "user", "content": "привет"}]}'
```

**Б. Только код роли, без остальных ролей и без Docker** — для разработки или нестандартного развёртывания:
`create_app` (`core/pcbk_core/app.py`) принимает список ролей любой длины, роль `llm` — одна из них:

```python
import uvicorn
from pcbk_core.app import create_app
from pcbk_core.llm import LlmRole
from pcbk_core.llm.ledger import Ledger
from pcbk_core.llm.shares import Shares
from pcbk_core.llm.upstream import Upstream
from pcbk_core.secrets import TokenTable, key_fingerprint, read_key_file
from pcbk_core.settings import LlmSettings, Settings

settings = Settings(DB_PATH="/путь/к/core.db")
llm = LlmSettings(OPENROUTER_BASE_URL="http://127.0.0.1:8080/api/v1",   # например fake_openrouter.py
                   LLM_TOKENS_FILE="/путь/к/llm-tokens")
key = read_key_file(llm.OPENROUTER_KEY_FILE)
upstream = Upstream(llm.OPENROUTER_BASE_URL, key, None) if key else None
role = LlmRole(settings, llm, tokens=TokenTable.from_file(llm.LLM_TOKENS_FILE), upstream=upstream,
               ledger=Ledger(settings.DB_PATH), key_fingerprint=key_fingerprint(key) if key else None,
               shares=Shares(settings.DB_PATH, total_usd=llm.LLM_TOTAL_USD, default_usd=llm.LLM_SHARE_USD))
app = create_app(settings, [role])
uvicorn.run(app, host="0.0.0.0", port=settings.CORE_PORT)
```

Это ровно то, что собирает `build_llm_role` (`core/pcbk_core/main.py`) внутри полного `build_roles`, без трёх
остальных ролей. Без `Shares(...)` (аргумент `shares=None`) все вызывающие делят одну `LLM_SHARE_USD` — доли
по месту не нужны для одиночной проверки прокси.

**В процессе роль используется и напрямую, без HTTP.** Роль аналитики (опциональная, см.
[16-analytics.md](16-analytics.md)) не ходит на `/llm/v1/chat/completions` через сеть, а вызывает те же
методы и поля `LlmRole` (`role.models` для выбора модели, `role.inflight`/`role.llm.LLM_CALLER_CONCURRENCY`,
`role.budget.refusal`, `role.begin_call`) внутри одного процесса — тот же бюджет, журнал и белый список
моделей, но без HTTP-слоя и без запасной модели (`LLM_FALLBACK` у прямых вызовов роли не задействован). Это
пример того, как роль можно встроить в другой код на Python без поднятия отдельного сервера вовсе.

Тестовый двойник OpenRouter (`core/tests/fake_openrouter.py`, только `stdlib`, без каких-либо внешних
зависимостей) умеет отвечать как настоящий OpenRouter: ключи `test-openrouter-key`/`test-openrouter-key-b`,
ключ управления `test-mgmt-key`, обычный ответ (поток или тело) с `usage.cost`, выдачу разных отказов словом
`FAKE…` в последнем сообщении `user` (`FAKE402`, `FAKE403REGION`, `FAKE500`, `FAKEFLAKY` — два отказа 502
подряд, затем обычный ответ, обрыв потока `FAKEBREAK`, задержку `POST /_delay` и т. д. — полный список слов и
