# Веб-чат (`web/`) и вход nginx (`edge/`)

Эти два каталога дают пользователю интерфейс в браузере и общий входной узел стенда:

- `web/` — одностраничное приложение (SPA) на React: чат с ИИ-агентами рабочего места,
  вкладки «Калькуляторы», «События», «Уроки» и кабинет преподавателя. Собирается в статику
  (HTML+JS+CSS без сервера) и отдаётся через `edge`.
- `edge/` — образ `nginx`, который слушает TLS-порт для людей, отдаёт статику чата и страницы
  входа/состояния и проксирует вызовы `/pcbk/api/...` в службу `core` (шлюз). Собственного кода
  на сервере у `edge` нет — только шаблон конфигурации и статические файлы.

Оба каталога не знают о БДРВ, историане или конкретном предприятии: весь разбор ответов службы
данных и вся авторизация — на стороне `core` (шлюза); SPA и nginx — витрина и общий вход. Роли
агентов, разговоров, аутентификации и конфигурации контейнеров разобраны в
[архитектуре](01-architecture.md), сборка и выкладка всего стенда целиком — в
[02-build-and-deploy.md](02-build-and-deploy.md), сам шлюз — в [13-gateway.md](13-gateway.md), а
служба данных и её инструменты — в [10-data-service.md](10-data-service.md). Здесь — только то,
что относится к браузерному слою.

## 1. Веб-чат: стек и сборка

### 1.1 Состав каталога

```
web/
  package.json            зависимости и npm-команды
  vite.config.ts          сборка (Vite) и настройка тестов (Vitest)
  tsconfig.json           опции TypeScript (строгий режим, ES2022, JSX)
  index.html              единственная HTML-страница SPA
  public/boot.js          загрузчик, копируется в сборку как есть
  scripts/check-dist.mjs  проверка собранной статики перед выкладкой
  build/buildInfo.ts      плагин Vite: метка сборки и опись файлов
  src/                    исходники приложения (TypeScript + TSX)
  tests/                  тесты Vitest (*.test.ts, *.test.tsx) и один тест Node (boot.test.mjs)
```

Зависимости (`package.json`, версии закреплены точно, `save-exact=true` в `.npmrc`,
`ignore-scripts=true`): `react` и `react-dom` 19.3.0, `zod` 4.6.5, `@opencode-ai/sdk` 1.18.33
(версия прибита дополнительно через `overrides`, чтобы более свежий диапазон у адаптера её не
увёл), `@assistant-ui/react` 0.15.22, `@assistant-ui/react-markdown` 0.14.17,
`@assistant-ui/react-opencode` 0.2.25, `remark-gfm` 4.0.1. Движок — `node 22.x` (поле `engines`).
Тест `tests/deps.test.ts` следит, что в `package-lock.json` эти пакеты присутствуют ровно в одном
экземпляре (важно для `zod`: настройка без JIT должна подействовать на единственный экземпляр
библиотеки, которым пользуется и `@assistant-ui`), что все пакеты реестра `npm` имеют сумму
`sha512`, и что пакет с install-скриптом помечен `optional` (иначе `ignore-scripts=true` незаметно
пропустит нужный шаг).

Команды `package.json`:

```bash
npm run build   # tsc --noEmit -p . && vite build && node scripts/check-dist.mjs <каталог>
npm test        # vitest run && node --test tests/*.test.mjs
```

`build` сначала проверяет типы без вывода файлов (`tsc --noEmit`), затем собирает Vite-ом, затем
сам прогоняет проверку собранной статики (`check-dist.mjs`); каталог для проверки —
`${PCBK_WEB_OUT:-../edge/static/chat}` (см. ниже).

### 1.2 Сборка — `vite.config.ts`

Ключевые настройки `defineConfig`:

| Параметр | Значение | Смысл |
|---|---|---|
| `base` | `"/chat/"` | SPA всегда собирается под префиксом `/chat/`; все пути ассетов — относительно него |
| `build.outDir` | `process.env.PCBK_WEB_OUT ?? "../edge/static/chat"` | куда пишутся файлы сборки |
| `build.emptyOutDir` | `true` | каталог вывода стирается перед сборкой — под оградой `outDirGuard` (ниже) |
| `build.target` | `["chrome109", "edge109", "firefox115"]` | минимальные версии браузеров, под которые собирается бандл |
| `build.assetsInlineLimit` | `0` | ничего не инлайнится как `data:` — CSP страницы запрещает `img-src`/`font-src` вне `'self'` |
| `build.modulePreload.polyfill` | `false` | без встроенного скрипта-полифила модульной предзагрузки |
| `build.sourcemap` | `false` | карты исходников не публикуются |

Переменные окружения сборки:

| Переменная | Умолчание | Что делает |
|---|---|---|
| `PCBK_WEB_OUT` | `../edge/static/chat` | каталог вывода сборки (относительно `web/`) |
| `PCBK_BUILD` | `"dev"` | метка сборки — пишется в `<meta name="pcbk-build">` и в `build.json` (должна отвечать `/^[A-Za-z0-9._-]{1,64}$/`, иначе сборка падает с ошибкой) |

Плагин `pcbk-out-dir-guard` (функция `guardOutDir`, экспортирована из `vite.config.ts`) не даёт
`vite build` стереть посторонний каталог: если каталог вывода не пуст и в нём нет файла
`build.json`, сборка завершается ошибкой («каталог вывода … не пуст и в нём нет build.json — это
не сборка чата»). Это защита от опечатки в `PCBK_WEB_OUT` (например, указать `../edge/static`
вместо `../edge/static/chat`), которая иначе стёрла бы остальную статику `edge`.

Плюс обычный плагин `@vitejs/plugin-react` и плагин сборки метки `pcbkBuildInfo(PCBK_BUILD)` (см.
§1.3).

Тесты (`vitest`, настроены в том же файле): окружение `jsdom`, файлы `tests/**/*.test.ts?(x)`,
`setupFiles: ["tests/setup.ts"]`.

### 1.3 Метка сборки и опись файлов — `build/buildInfo.ts`

Плагин `pcbkBuildInfo(build: string)` работает только на `vite build` (`apply: "build"` — в
`vitest` и `dev`-сервере описи нет):

- `transformIndexHtml` вставляет в `<head>` тег `<meta name="pcbk-build" content="<build>">`.
- `closeBundle` после записи всех файлов обходит весь каталог вывода (включая файлы из `public/`,
  которых не было в бандле — то есть `boot.js`) и пишет `build.json`:
  ```json
  { "build": "<build>", "files": { "<путь>": "<sha256 содержимого в hex>" } }
  ```
  В опись не попадают сами `index.html` и `build.json`.

Эту же метку (`<meta name="pcbk-build">`) и эту же опись (`build.json`) читает сторож
стенда, чтобы показать строку «Веб-чат» на странице состояния (см.
[18-watchdog-and-ops.md](18-watchdog-and-ops.md)); договор путей и форм — ниже.

### 1.4 Проверка собранной статики — `scripts/check-dist.mjs`

Запускается последним шагом `npm run build` и самостоятельно:

```bash
node scripts/check-dist.mjs <каталог сборки>
```

Код выхода `1` — есть ошибки (сборку нельзя выкладывать), `0` — ошибок нет (предупреждения и
известные исключения не роняют сборку, но печатаются). Проверяет:

1. **`index.html`.** Каждый тег вида `<…` обязан разобраться (иначе — ошибка «тег не разобран»,
   а не молчаливый пропуск); нет встроенных `<style>`, атрибутов `style=`, обработчиков `on*=`,
   встроенных `<script>` без `src`. У `src`/`srcset`/`href` схема или `//хост` — ошибка (CSP
   `'self'`); адрес должен начинаться с `/chat/` и указывать на существующий файл сборки (кроме
   `<a href>` — переходы не часть сборки). Скрипт с `src`, отличным от `/chat/boot.js`, обязан
   быть `type="module"`. Загрузчик `/chat/boot.js` обязан встретиться ровно одним классическим
   `<script src>` — без `type`, `async`, `defer` и `nomodule` (иначе в браузерах с поддержкой
   модулей он не исполнится, и признак сбоя загрузки `boot_failed` молча пропадёт).
2. **Метка сборки.** `<meta name="pcbk-build" content="…">` должна присутствовать в первых
   `64 КиБ` страницы (`MAX_BODY_BYTES = 65536`) — ровно столько читает сторож.
3. **`build.json`.** Форма `{ "build": string, "files": { путь: sha256-в-hex } }`; метка в
   `index.html` и в `build.json` должны совпадать; путей в описи — от 1 до `WEB_MAX_FILES = 8`;
   каждый путь — вида `assets/<1-100 символов из A-Za-z0-9._->` или ровно `boot.js`
   (`WEB_FILE_RE`); каждая сумма пересчитывается с диска и сверяется; каждый файл диска (кроме
   `index.html` и `build.json`) обязан быть в описи, и наоборот.
4. **Файлы `assets/`.** Не больше `WEB_MAX_FILES` штук; никаких файлов `*.map` в сборке вообще.
5. **Запрещённые строки** — в любом файле сборки (поиск по байтам, без учёта кодировки):
   домены заказчика (производственный домен и внутренний алиас — конкретные значения в
   исходнике `FORBIDDEN`, здесь не воспроизводятся по правилам этого набора документов), адрес
   IPv4 (кроме `127.0.0.1`), имя тега БДРВ по форме `\d{2}[A-Z][A-Z0-9]*_[A-Z0-9_]*(?:PV|SP|MV|LMN)`
   (например `20FAKE_001_PV` — вид тега, не настоящее имя). Список открыт (`KNOWN_STRINGS`) для
   задокументированных исключений (сейчас пуст).
6. **Предупреждения по `*.js`** (включая `boot.js` из `public/`): использование API браузера новее
   Chrome 109 (`Promise.withResolvers`, `Array.prototype.toSorted/toReversed/toSpliced/with`,
   `Object.groupBy`/`Map.groupBy`, `Array.fromAsync`, операции `Set` (`union`, `intersection`, …),
   `String.prototype.isWellFormed/toWellFormed`, `Iterator.from`, вызовы цепочкой на самом
   итераторе, флаг регулярки `v`) — список не исчерпывает все API, но покрывает типичные; и
   признаки кода, несовместимого с `unsafe-eval` CSP (`new Function`, `=Function`, `eval(`).
   Известное исключение (`KNOWN`): вызов `.toSorted(` на собственном упорядоченном словаре
   `@radix-ui/react-collection` (не на `Array.prototype`) — помечается отдельно, не как
   предупреждение.
7. **Предупреждения по `*.css`.** `url(...)` и `@import` со схемой или `//хост` — вне CSP
   `style-src/img-src/font-src 'self'`.

### 1.5 Как собранная статика попадает в `edge`

В Git каталога `edge/static/chat/` нет: на сервер уходит только собранный результат, не `web/` и
не `node_modules`. Общая процедура (сокращённо; полный порядок выкладки и откатов всего стенда —
[02-build-and-deploy.md](02-build-and-deploy.md)):

1. **Сборка на машине разработки** из зафиксированного коммита (нужен `node 22.x`):
   ```bash
   REV=$(git rev-parse --short=12 <коммит>) && B=$(mktemp -d)/web-$REV && mkdir -p "$B" &&
   git archive "$REV" web edge | tar -x -C "$B" &&
   (cd "$B/web" && npm ci --ignore-scripts && PCBK_WEB_OUT="$B/chat" PCBK_BUILD="$REV" npm run build)
   ```
   `npm run build` сам прогоняет `check-dist.mjs`; метка сборки — короткий хеш коммита.
2. **Копия на сервер — в соседний каталог, не поверх рабочего**: `chat.new` рядом с `chat`
   (`scp -r "$B/chat" <сервер>:/opt/pcbk-reserve/edge/static/chat.new`), затем
   `chmod -R o+rX .../chat.new` (nginx в контейнере читает файлы от другого пользователя
   хоста).
3. **Сверка на сервере** — суммы файлов по описи совпадают с диском, на диске нет лишних и не
   хватает файлов из описи, метка `index.html` совпадает с меткой `build.json` (скрипт на
   Python — в `deploy/README.md`, раздел «Статика чата»).
4. **Атомарная подмена.** `mv -T` не допускает вложить каталог в уже существующий — это
   защита от двойного запуска: сначала текущий `chat` переименовывается в каталог для отката
   (например `chat.<предыдущая метка>`), и только затем `chat.new` переименовывается в `chat`.
   Между двумя `mv` возможен короткий ответ `404` на `/chat/...` — он не кэшируется
   (`Cache-Control: no-store` у `index.html`/`boot.js`), а кэш на ассеты с хешем в имени
   (`Cache-Control: public, max-age=31536000, immutable`) не страдает, потому что их имена не
   повторяются между сборками. `edge` (nginx) не перезапускается: файлы читаются при каждом
   запросе.
5. **Проверка.** `curl -sk https://127.0.0.1:8443/chat/ | grep -o 'pcbk-build" content="[^"]*"'`
   должен показать новую метку; строка «Веб-чат» на `/status` (читается сторожем через внутренний
   порт `8080`, см. §7.3) должна подтвердить ту же сборку.

**Откат** — симметричная атомарная подмена: текущий `chat` уходит в сторону (например
`chat.bad-<метка>`), на его место встаёт сохранённая на шаге 4 предыдущая копия.

Если на сервере каталога `chat` ещё нет вовсе (самое первое размещение чата), откатывать нечего —
в этом случае откатывается весь `edge/` целиком.

## 2. Структура SPA

### 2.1 Точки входа

- **`index.html`** — одна страница на весь SPA. В `<head>` — классический скрипт
  `<script src="/boot.js">` (в сборке — `/chat/boot.js`, путь задаёт `base` сборки), в `<body>` —
  `<div id="root">` и модульный скрипт `<script type="module" src="/src/main.tsx">`.
- **`public/boot.js`** — загрузчик на ES5 без модулей и без `fetch` (только `XMLHttpRequest`),
  копируется Vite-ом в сборку как есть (имя без хеша — значит, кэшируется с `no-store`, не на
  год). Он подключается раньше основного бандла и следит, не провалился ли старт чата в этом
  браузере:
  - слушает `error` на `window` в фазе захвата (ошибка выполнения `ErrorEvent`, либо сбой
    загрузки именно `<script>` — сбой стилей и картинок не считается),
  - слушает `unhandledrejection`,
  - через `20000` мс (`BOOT_TIMEOUT_MS`) после `DOMContentLoaded`, если старт ещё не отмечен.

  Как только любое из этого срабатывает (и старт ещё не отмечен), загрузчик один раз отправляет
  `POST /pcbk/api/web/report` с телом `{"kind":"boot_failed"}` (без чтения ответа, без повтора) и
  меняет текст `#root` на «Чат не запустился в этом браузере. Сообщите преподавателю — сбой
  отмечен.». После того как приложение вызвало `window.__pcbkStarted()`, загрузчик больше ничего
  не делает — дальнейшие сбои React ловит граница ошибок (`ErrorBoundary`, §3).
- **`src/main.tsx`** — первым импортом подключает `./zodJitless` (настройка `zod` без JIT —
  `z.config({ jitless: true })`, иначе `zod 4` при сборке схемы пробует `new Function`, что нарушает
  CSP без `'unsafe-eval'`; порядок важен — ES-модули исполняются в порядке импортов, и настройка
  должна встать раньше, чем библиотеки, использующие `zod`), затем стили (`./chat.css`,
  `./analytics.css` — импортированы здесь, а не лениво, чтобы классы вкладок были доступны даже до
  первого открытия вкладки), затем монтирует приложение: `mountChat(root, { api: createApi(),
  navigate: (u) => location.assign(u) })`.
- **`src/mount.tsx`** (`mountChat`) — создаёт корень React (`createRoot`) с обработчиком
  `onUncaughtError`: если что-то упало до того, как отработала собственная граница ошибок чата
  (`ErrorBoundary` внутри `App`, §3) — например, сбой в самом `App`, в шапке или до монтирования
  чата — React снимает всё дерево целиком. Обработчик в этом случае сам отмечает старт
  загрузчику (`window.__pcbkStarted?.()`, чтобы таймер `boot.js` не сработал второй раз), шлёт
  отчёт `ui_crash` через переданный `api.report`, и заменяет содержимое контейнера на один абзац с
  текстом `T_UI_CRASH` — без кнопки «Перезапустить», потому что дерево снято целиком и помогает
  только перезагрузка страницы.

### 2.2 Фазы `App` (экраны верхнего уровня)

`src/App.tsx` — единственный компонент, который решает, что показывать. Внутреннее состояние —
дискриминированный тип `Phase`:

| Фаза | Когда | Что видно |
|---|---|---|
| `loading` | сразу после монтирования, до ответа `GET /pcbk/api/auth/me` | текст «Чат загружается…» |
| `error` | `/me` ответил не по договору или сетевой сбой | текст ошибки и кнопка «Повторить» |
| `teacher` | `/me` вернул роль `teacher` | кабинет преподавателя (`TeacherPage`, §3) — без обращений к рабочим местам и OpenCode вовсе |
| `notice` | у студента в ответе `/me` поле `notice` не `null` и не отсутствует, текст редакции известен | текст предупреждения и кнопка «Понятно» (`NoticeScreen`) |
| `workplace` | предупреждение подтверждено (или его не было), место ещё не готово | экран пробуждения места (`WorkplaceScreen`, §3) |
| `asleep` | обёртка вызовов получила `503 WorkplaceNotReady` во время работы чата | «Рабочее место спит» и кнопка «Разбудить» |
| `chat` | место готово | сам чат (`Chat`/`ChatView`, §3) |
| `leaving` | идёт выход или конец сессии | пустое тело; шапка скрыта, если ещё не было известно, кто вошёл |

Поле `notice` в ответе `/me`: отсутствует (`undefined`) или равно `null` — предупреждение не
нужно, страница сразу идёт к месту; незнакомое числовое или строковое значение, текст которого
клиент не знает (сверка со словарём `NOTICES` в `texts.ts`), — отдельная ошибка «Стенд просит
подтвердить предупреждение, которого эта версия чата не знает…», подтверждение не отправляется.

Переходы между фазами:

- `loading → error`, если `/me` вернул не 200/401 или тело не по форме `{login, role, place?,
  notice?}`; кнопка «Повторить» просто повторяет весь переход с начала.
- `loading → teacher | notice | workplace | chat`, в зависимости от роли, поля `notice` и
  текущей готовности места (`GET /pcbk/api/workplace`): если место уже `ready`, экран
  пробуждения не показывается вовсе — сразу открывается чат.
- `notice → workplace | chat` после успешного `POST /pcbk/api/auth/notice {notice}`.
- `workplace → chat`, когда `onReady` сообщает, что место готово.
- `chat → asleep`, когда во время работы чата обёртка вызовов получает «место уснуло»
  (`503 WorkplaceNotReady`); «Разбудить» ведёт обратно в `workplace`, сама фаза `asleep` место не
  будит.
- любая фаза `→ leaving → /login`, по 401 от любого вызова или по кнопке «Выйти».

`App` помнит последний открытый разговор (`onThreadIdChange`, по `id` сессии OpenCode) и при
повторном монтировании чата (после «Разбудить» или после перезапуска границей ошибок) открывает
именно его, а не всегда новый разговор. Если сам перезапуск вызвала авария чата, который уже был
результатом предыдущего перезапуска (второй подряд), — следующий перезапуск открывает новый
разговор, а не тот же самый: предотвращает цикл «разговор валит чат → чат восстанавливается с ним
же → валит снова».

денежная арифметика (целые центы) — чистые функции `src/teacher.ts`.

## 4. Вызовы, которые SPA делает к шлюзу и к OpenCode

Все вызовы — через `fetch` с `credentials: "same-origin"`, заголовком `Accept:
application/json`; если отправляется тело — JSON с `Content-Type: application/json`. Ответ всегда
разбирается в `{status, body}` (`callJson` в `src/api.ts`): сеть оборвалась — `status: 0`; тело не
JSON — строка как есть (HTML страницы ошибки прокси и т. п.).

Серверная сторона этого вызова — `core/pcbk_core/gateway/web.py`. Тело обязано быть ровно
`{"kind": K}` с `K` из `REPORT_KINDS = ("boot_failed", "ui_crash", "turn_silent", "stream_down")`
(лишний или задвоенный ключ, не JSON, не те значения — `400`); тело читается не длиннее
`WEB_REPORT_MAX_BYTES = 256` байт (сверх — тоже `400`; `edge` перед этим уже отрезал бы `413` на
`1 КиБ`, см. §7.2). Проверки идут в порядке: зона → настроенность роли → сессия (`401` без
учётки) → источник запроса → тело — сессия проверяется раньше источника, чтобы запрос вовсе без
учётки не растил счётчики и не писал строку журнала. Ответ — всегда `204`, независимо от того,
засчитан отчёт или отброшен: засчитывается не чаще одного раза за `WEB_REPORT_EVERY_S = 60` с на
пару (логин, вид); засчитанный отчёт даёт одну строку журнала уровня `INFO`, отброшенный —
ничего. Тот же модуль отдаёт `GET /health/web` (тоже только внутри зоны `front`) —
`{"<вид>_1h": <число>}` по всем четырём видам за скользящий час (`WINDOW_S = 3600` с); это не
вызов SPA, а показатель для сторожа (см. [18-watchdog-and-ops.md](18-watchdog-and-ops.md)).

### 4.3 Прямой канал к рабочему месту (OpenCode)

Сам диалог ведётся не через `Api`, а через SDK `@opencode-ai/sdk`
(`createOpencodeClient({ baseUrl: \`${location.origin}/pcbk/api/oc\`, fetch: gatewayFetch })`,
в `src/components/Chat.tsx`). SDK сам решает, какие пути и методы вызвать внутри
`/pcbk/api/oc/...` (сессии, сообщения, разрешения и т. п.) — SPA не формирует их напрямую.
Единственный путь, который код SPA знает по имени, — `/pcbk/api/oc/event` (`EVENT_PATH` в
`src/gateway.ts`): это долгоживущий поток событий места (SSE-подобный), и для него обёртка `fetch`
ведёт собственный учёт сбоев и повторов.

Обёртка `createGatewayFetch` (`src/gateway.ts`) — единственная точка, через которую SDK стучится в
сеть:

- разбирает ответ по коду и телу вида шлюза (`{"name", "data": {"message"}}`) в один из исходов
  `ok | signed_out | asleep | too_many_tabs | busy | down | refused | offline | unknown | halted`
  (функция `classify`); конкретные соответствия — `401` → `signed_out`, `503 WorkplaceNotReady` →
  `asleep`, `503 WorkplaceBusy` (а также лимит соединений `edge`, отданный как тот же код) →
  `busy`, `503 Unavailable` → `down`, `429 TooManyRequests` → `too_many_tabs`, прочие `4xx` и `502`
  → `refused`;
- на `signed_out`/`asleep` останавливает себя целиком (`HaltedError` для всех новых вызовов,
  текущий поток ждёт отмены) — решает об этом `App` через `onHalt`;
- на `503 WorkplaceBusy` обычного вызова повторяет его до `BUSY_RETRIES = 3` раз с паузой
  `eventDelayMs` (на основе числа попыток, с разбросом ±20 %, не больше `EVENT_MAX_MS = 30000` мс,
  база — `EVENT_BASE_MS = 1000` мс);
- перед каждым запросом потока `/pcbk/api/oc/event` ждёт такую же паузу по числу подряд идущих
  сбоев потока; поток короче `SHORT_STREAM_S = 5` секунд засчитывается как сбой, чем бы он ни
  кончился.

Сторож молчания (`src/watch.ts`, используется из `Chat.tsx` через `useTurnWatch`): если с начала
хода прошло `TURN_SILENT_S = 180` с без прироста ответа (и поток не на паузе) — строка «Ответа нет
уже 3 минуты…» и один отчёт `turn_silent`; если без прироста прошло `QUIET_REFRESH_S = 30` c —
чат один раз за ход тихо перечитывает историю разговора (`refresh()` адаптера), не дожидаясь
отчёта. Сторож обрыва потока: если поток не был `"ok"` дольше `STREAM_DOWN_S = 120` c и затем
восстановился — один отчёт `stream_down` за эпизод. Оба сторожа понимают «сон машины»/троттлинг
фоновой вкладки (разрыв между тиками дольше `TICK_GAP_S = 30` c, тики — раз в `TICK_MS = 1000` мс
и на возврат видимости страницы) и не путают его со сбоем.

## 5. Тексты интерфейса — `src/texts.ts`

Все строки, которые видит человек в чате и кабинете, собраны в одном файле как именованные
константы и функции (`T_...`, словари `..._LABELS`). Чтобы поменять текст — меняется значение
константы здесь; передавать строки по месту использования в коде не нужно и не принято.

Важно: часть констант **сверяется тестами** с другими частями стенда, и правка текста без правки
соответствующего места на другой стороне сломает тест или (хуже) разойдётся в проверке:

- `STAND_WARNING` — тот же текст, что `.stand` на `edge/static/login.html` (тест
  `tests/workplace.test.ts`, и см. §6.2 ниже про `login.html`/`login.js`);

## 7. `edge/`: вход nginx

### 7.1 Устройство

Контейнер `edge` — образ `nginx` без собственного кода: конфигурация подставляется шаблоном
`edge/pcbk.conf.template` (монтируется в `/etc/nginx/templates/pcbk.conf.template` — это
стандартный механизм образа `nginx`, который сам прогоняет `envsubst` по файлам в `templates/` при
старте; в самом шаблоне переменных окружения нет, потому что своих переменных у `edge` нет —
`envsubst` его не меняет), статика чата и страниц входа монтируется из `edge/static/` в
`/usr/share/nginx/pcbk`, сертификат и ключ TLS — из каталога `${TLS_DIR}` в `/etc/nginx/tls`
(переменная окружения `compose.yaml` обязательна: `${TLS_DIR:?TLS_DIR не задан}`). Контейнер
слушает только два порта: `8443` (TLS, для людей и для `/pcbk/api/...`) и `8080` (без TLS, только
внутри docker-сети — живость и статика чата для сторожа).

Шаблон целиком — один файл; верхний уровень (вне `server{}`) задаёт то, что `nginx` разрешает
только на уровне `http{}`:

| Директива | Смысл |
|---|---|
| `map $request_uri $pcbk_bad_api_uri` | сырой путь (до первого `?`) под `/pcbk/api/` с кодированными `%2e`/`%5c`, `/.`/`//` — отказ `400` до шлюза (строку запроса эту карту не судит — её фильтрует сам шлюз) |
| `limit_req_zone … zone=pcbk_login:1m rate=5r/s` | предел на вход/выход — по IP |
| `map $uri $pcbk_api_csp` | `default-src 'none'` для ответов `/pcbk/api/...` и внутренних страниц ошибок `/pcbk-errors/...` (по пути **после** нормализации nginx и после перехода `error_page`) |
| `map $status $pcbk_asset_cache` | кэш на год (`public, max-age=31536000, immutable`) только у ответов `200`/`304`; всё прочее — `no-store` |
| `map $request $pcbk_log_request` | своя запись в журнал доступа порта `8443` — без строки запроса целиком (в ней бывает токен адаптера OpenCode), только метод, путь до `?` и версия |
| `log_format pcbk ...` | формат журнала, использующий `$pcbk_log_request` |
| `map $cookie_pcbk_session $pcbk_oc_session` | ключ пределов `/pcbk/api/oc/*` — значение cookie сессии ровно нужного вида (43 знака из `A-Za-z0-9_-`), иначе общая корзина `"-"` |
| `limit_conn_zone`/`limit_req_zone` (несколько, зоны `pcbk_oc_session`, `pcbk_oc_all`, `pcbk_oc_rate`, `pcbk_oc_event`, `pcbk_place_rate`, `pcbk_web`) | пределы одновременных соединений и частоты запросов — по cookie сессии (или по порту целиком для общего предела) |
| `map $cookie_pcbk_session $pcbk_me_key` / `limit_req_zone … zone=pcbk_auth_session` | своя зона для `/pcbk/api/auth/me` и `/pcbk/api/auth/notice`: ключ — cookie сессии, а без неё — адрес клиента (не общая корзина "-", чтобы целый класс за одним NAT не делил один счётчик) |
| `client_body_temp_path`, `proxy_temp_path` | временные файлы тел запросов/ответов — на томе `pcbk-edge-temp` (диск), не в `tmpfs` (который ограничен `mem_limit: 64m` контейнера) |

### 7.2 Сервер `8443` — вход для людей

Общие для всего сервера настройки: `http2 on`, `ssl_certificate`/`ssl_certificate_key` из
`/etc/nginx/tls/{cert,key}.pem`, `ssl_protocols TLSv1.2 TLSv1.3`, `server_name _` (нет
привязки к конкретному домену — подробнее в §8), `resolver 127.0.0.11` (служебный DNS docker,
имена `pcbk-watchdog`/`pcbk-core` разрешаются в момент запроса, так что `nginx` стартует даже если
они ещё не поднялись), заголовки ответа по умолчанию `Cache-Control: no-store`,
`X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Content-Security-Policy`
только там, где её задаёт карта `$pcbk_api_csp` (т. е. под `/pcbk/api/` и `/pcbk-errors/`);
`proxy_set_header` (включая `X-Forwarded-Host: $host`, и **очистку** `X-Forwarded-For`,
`X-Real-IP`, `Forwarded` от значений, присланных клиентом) задан один раз на уровне `server`, чтобы
никакой `location` их не мог незаметно потерять, переопределив `proxy_set_header` у себя.

Проверка имени хоста до выбора `location`: `$host` обязан быть либо последовательностью из 1–6
меток `[a-z0-9-]{1,63}`, разделённых точками, либо (этот же шаблон допускает и это) выглядеть как
адрес IPv4 — иначе `400 BadRequest` до шлюза. Никакого конкретного домена в проверке не зашито.

**Ошибки самого nginx** — через внутренние `location`, JSON, код сохраняется:

| Код | `error_page` → | Тело |
|---|---|---|
| `400` | `/pcbk-errors/400.json` | `{"name":"BadRequest","data":{"message":"Неверный запрос"}}` |
| `405` | `/pcbk-errors/405.json` | `{"name":"MethodNotAllowed", ...}` |
| `413` | `/pcbk-errors/413.json` | `{"name":"PayloadTooLarge", ...}` |
| `414` | `/pcbk-errors/414.json` | `{"name":"URITooLong", ...}` |
| `494` → `400` | `/pcbk-errors/400.json` | слишком большие заголовки/cookie |
| `429` | `/pcbk-errors/429.json` | `{"name":"TooManyAttempts","data":{"message":"Слишком много попыток входа — подождите"}}` |
| `502`/`503`/`504` → `503` | `/pcbk-errors/503.json` | `{"name":"Unavailable","data":{"message":"Серверный слой не отвечает"}}` |
| `509` → `503` | `/pcbk-errors/busy.json` | `{"name":"WorkplaceBusy","data":{"message":"Слишком много одновременных запросов — повторите позже"}}` |

Код `509` — собственный код `nginx` для `limit_conn`/`limit_req` (настраивается директивами
`limit_conn_status`/`limit_req_status` у конкретных `location`); так SPA и страница входа видят
локальную перегрузку тем же видом ответа, что и занятость места на стороне шлюза
(`503 WorkplaceBusy`), и повторяют действие вместо отказа.

**Статика страниц (не `/pcbk/api/` и не `/chat/`):**

| `location` | Отдаёт | Заметки |
|---|---|---|
| `= /` | `index.html` (через `try_files`) | резервная страница-визитка: предупреждение `.stand`, заголовок «Резервный контур в постройке», ссылки на `/login`, `/chat/` и `/status` |
| `= /login`, `= /login.js`, `= /login.css` | `login.html`, `login.js`, `login.css` | свой `Content-Security-Policy` на каждый: `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src 'self'; form-action 'none'; frame-ancestors 'none'; base-uri 'none'` (заголовки `server` не наследуются `location` со своим `add_header` — повторены явно) |
| `= /status`, `= /status.js`, `= /status.json` | проксируются на `pcbk-watchdog:8090` | у всех трёх — своя `error_page 502 503 504 /watchdog-down.html` (сторож завис или умер — отдельная страница, не общая «сервер не отвечает»); `/status.json` — без журнала доступа (опрашивается часто) |
| `= /watchdog-down.html` | внутренняя статическая страница | показывается вместо `/status`, `/status.js`, `/status.json` при `502`/`503`/`504` от сторожа; сама обновляется раз в 10 с (`meta http-equiv="refresh"`) |
| `= /favicon.ico` | `204` без тела, без журнала | чтобы автозапрос браузера не засорял журнал каждой загрузки |

**Чат (`/chat/...`):**

| `location` | Поведение |
|---|---|
| `= /chat` | `301` на `/chat/` (`absolute_redirect off` — адрес в `Location` относительный, иначе через туннель он увёл бы на `8443` в другом внешнем виде) |
| `= /chat/` | `try_files /chat/index.html =404` |
| `^~ /chat/assets/` | кэш по карте `$pcbk_asset_cache` (год на `200`/`304`), `gzip` для `application/javascript`, `text/javascript`, `text/css` |
| `= /chat/boot.js` | `no-store` (имя без хеша — нельзя кэшировать как ассет) |
| `^~ /chat/` (всё прочее под `/chat/`, включая `build.json`) | `404` как `text/plain` — опись `build.json` отдаётся только по порту `8080` (сторожу), не наружу |

У всех пяти локаций `/chat*` — свой `Content-Security-Policy: default-src 'none'; script-src
'self'; style-src 'self'; connect-src 'self'; img-src 'self'; font-src 'self'; form-action 'none';
frame-ancestors 'none'; base-uri 'none'` (отличается от `/login*` добавленным `font-src 'self'`) и
свои `Cache-Control`/`X-Content-Type-Options`/`Referrer-Policy` — заголовок стоит даже на
перенаправлении и на `404`, чтобы CSP чата действовала на всём, что отдаётся под этим префиксом.

**Пути шлюза** — проксируются на `pcbk-core:8000`; таймауты и пределы заданы на уровне каждого
`location` (сами `error_page`/`proxy_set_header`/заголовки ответа — общие, заданы на уровне
`server`, в `location` под `/pcbk/api/` своих нет):

| `location` | Зона предела | Код отказа предела | Тело, срок, таймаут |
|---|---|---|---|
| `/pcbk/api/auth/` (вход/выход, всё прочее под `auth/`) | `pcbk_login` (по IP), `burst=20` | `429` | `64k`, `30s` |
| `= /pcbk/api/auth/me` | `pcbk_auth_session`, `burst=40` | `509` (→`busy.json`) | `64k`, `30s` |
| `= /pcbk/api/auth/notice` | `pcbk_auth_session`, `burst=40` | `509` | `64k`, `30s` |
| `= /pcbk/api/workplace`, `= /pcbk/api/workplace/wake` | `pcbk_place_rate`, `burst=20` | `509` | `64k`, `30s` |
| `= /pcbk/api/agents`, `= /pcbk/api/events` | `pcbk_place_rate`, `burst=20` | `509` | `64k`, `30s` |
| `= /pcbk/api/lessons`, `/pcbk/api/lessons/` (префикс — урок и картинка) | `pcbk_place_rate`, `burst=20` | `509` | `64k`, `30s` |
| `/pcbk/api/calc/` (префикс) | `pcbk_place_rate`, `burst=20` | `509` | `64k`, `30s` |
| `/pcbk/api/teacher/` (префикс) | `pcbk_place_rate`, `burst=20` | `509` | `64k`, `30s` |
| `/pcbk/api/analytics/` (префикс; открыт всегда, включённость решает сам шлюз) | `pcbk_place_rate`, `burst=20` | `509` | `64k`, `30s` |
| `= /pcbk/api/web/report` | `pcbk_web`, `burst=10` | `509` | `1k`, `10s` |
| `/pcbk/api/oc/` (префикс — весь адаптер OpenCode, кроме потока) | `limit_conn pcbk_oc_session 10` + `pcbk_oc_all 64`, `limit_req pcbk_oc_rate burst=200` | `509` (оба предела) | `512k`, таймаут тела `10s`, `proxy_read_timeout 45s`, буферизация ответа включена (`proxy_buffering` не отключена), сверх буферов — во временный файл (`proxy_max_temp_file_size 8m`) |
| `= /pcbk/api/oc/event` (поток) | то же `limit_conn`, `limit_req pcbk_oc_event burst=60` | `509` | `512k`, `proxy_buffering off`, `gzip off`, `proxy_read_timeout 90s`, `send_timeout 60s` |

Точные (без завершающего `/`) `location = /pcbk/api`, `= /pcbk/api/auth`, `= /pcbk/api/oc`, `=
/pcbk/api/calc`, `= /pcbk/api/teacher`, `= /pcbk/api/analytics` отдают свой `404`/`403` JSON (без
`/` в конце — чтобы `nginx` не ответил стандартным HTML-редиректом на `.../`); всё прочее под
`/pcbk/api/` — `404 NotFound` в JSON. Всё, что не подошло ни под один `location` вообще — `404`
как `text/plain`.

### 7.3 Сервер `8080` — внутренний

Не публикуется (не маппится на хост в `compose.yaml`, виден только внутри сети контейнеров):

- `= /healthz` → `200 "ok\n"` — простой признак живости для других контейнеров;
- `= /chat/` и `^~ /chat/` — тот же корень `/usr/share/nginx/pcbk`, без TLS; именно отсюда сторож
  читает `build.json` и `index.html` для строки «Веб-чат» на `/status` (через порт `8443` опись не
  отдаётся — `location ^~ /chat/` там возвращает `404` на всё, что не `index.html`/`assets/*`,
  см. §7.2);
- `/` → `404`.

### 7.4 Тесты `edge/`

`edge/tests/login.test.mjs` (запускается как часть `node --test tests/*.test.mjs` из `web/`, то
есть тот же `npm test`, что и у SPA) проверяет три вещи:

1. **Чистые функции `login.js`** (`viewFor`, `loginError`, `meView`) — на входных данных, без DOM.
2. **Весь ход страницы входа** на поддельных DOM/`fetch`/таймерах (`startPage` вызывается с

   на `/chat/`; уже вошедший студент сразу идёт будить место; преподаватель — прямо в кабинет,
   место не трогается; истечение `GIVE_UP_S = 90` c без ответа; сбой опроса, который «перетерпели»
   (временный `5xx`/обрыв сети не останавливает опрос); «Выйти» гасит опрос; ответ, пришедший
   после выхода или после истечения срока, не перебивает уже показанный текст; переход на `/chat/`
   случается не больше одного раза за ход ожидания; предупреждение при первом входе (`notice` в
   ответе `/me`) не даёт странице будить место до отдельного подтверждения — это делает чат.
3. **Статика как файлы** (`login.html`, `login.js`, `login.css`) — ровно один `<script>` тег,
   стили и скрипт только отдельными файлами, никаких встроенных `style`/`on*=`/`javascript:`,
   никаких внешних адресов, никаких `localStorage`/`sessionStorage`/`indexedDB`/`document.cookie`/
   `innerHTML`/`eval`.
4. **Сам шаблон `edge/pcbk.conf.template`** — отдельным разборщиком локаций (простой парсер:
   комментарии `#` вне строк в кавычках вычищаются, фигурные скобки считаются с учётом строк в
   одинарных кавычках, каждому `location` сопоставляется `server`, которому он принадлежит, по
   порядку блоков `server {`). Проверяется дословное присутствие ключевых строк (карты, зоны,
   `error_page`, временные каталоги), что в `location` под `/pcbk/api/` нет собственных
   `error_page`/`proxy_set_header`/`add_header` (чтобы не потерять общие для `server`), что набор
   `proxy_pass` соответствует ожидаемому списку путей и ни один путь не встречается дважды, что
   пределы и таймауты у «похожих» локаций (`/pcbk/api/agents` и `/pcbk/api/events`, `/pcbk/api/
   calc/` и `/pcbk/api/teacher/` и т. д.) буквально совпадают, и что у `/chat*`-локаций ровно
   четыре заголовка `add_header` (CSP, `Cache-Control`, `X-Content-Type-Options`,
   `Referrer-Policy`) без примесей `unsafe-*`/`data:`/`blob:`/`proxy_pass`.

Все перечисленные тесты не поднимают настоящий `nginx` и не требуют `nginx -t`; синтаксическая
валидность самого шаблона (как конфигурации nginx) проверяется не здесь, а при реальном запуске
контейнера `edge` (`docker compose up`) или командой `nginx -t` внутри него.

## 8. Как поднять чат за своим доменом и сертификатом

Ни SPA, ни шаблон `edge` не зашивают конкретный домен — весь существующий механизм рассчитан на
то, что внешнее имя сервера задаётся снаружи:

1. **Домен/адрес.** `server_name _;` — `nginx` отвечает на любое имя хоста, прошедшее проверку
   формата (до 6 меток `[a-z0-9-]{1,63}`, разделённых точками, либо вид IPv4 — см. §7.2); никакой
   белый список конкретных имён в шаблоне не задан. Значит, достаточно направить DNS (или просто
   открыть по IP) на сервер, где поднят `edge`, и слушать TLS-порт `8443` — ничего в
   `pcbk.conf.template` менять не нужно.
2. **Сертификат.** `compose.yaml` требует переменную окружения `TLS_DIR` (без умолчания:
   `${TLS_DIR:?TLS_DIR не задан}`) — каталог на хосте, в котором лежат `cert.pem` (владелец
   `root`, права `0644`) и `key.pem` (владелец `root`, права `0600`); он монтируется в контейнер
   как `/etc/nginx/tls`, откуда шаблон их и берёт (`ssl_certificate`/`ssl_certificate_key`). Для
   своего домена — обычная пара «сертификат + закрытый ключ» от любого источника (включая
   самоподписанный для внутреннего стенда), выложенная в этот каталог с такими правами и
   владельцем: мастер-процесс `nginx` в контейнере стартует от `root` именно для того, чтобы
   прочитать закрытый ключ, который недоступен остальным (`cap_add: [CHOWN, SETUID, SETGID]` в
   `compose.yaml`, рабочие процессы уже понижают права).
3. **Код SPA домена не знает.** Все обращения из браузера — относительные пути (`/pcbk/api/...`)
   или вычисленные в рантайме через `location.origin` (клиент OpenCode:
   `${location.origin}/pcbk/api/oc`); пересборка чата под другой домен не нужна — один и тот же
   собранный бандл работает под любым именем хоста, под которым его отдают.
4. **CSP не завязана на домен.** Все `Content-Security-Policy` в шаблоне используют только
   `'self'`/`'none'` — доменных значений в директивах нет, значит, при смене домена их незачем
   трогать.
5. **Что всё-таки специфично для этого стенда и годится в текст, а не в код** — предупреждение
   «Учебный стенд: не для ведения технологического процесса…» (константа `STAND_WARNING` в
   `web/src/texts.ts` и буквально тот же текст в `edge/static/login.html`/`index.html`) и заголовок
   страницы-визитки `index.html` («Резервный контур в постройке»): это обычный текст, не часть
   протокола, меняется заменой строк в этих файлах без пересборки чего-либо, кроме самого SPA (для
   `STAND_WARNING`) — или вовсе без пересборки (для статики `edge/static/*.html`, которая
   монтируется как обычные файлы).
