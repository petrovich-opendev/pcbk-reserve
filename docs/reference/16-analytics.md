# Аналитика корпуса КДМ-1 (роль `analytics`, опциональная)

Аналитика — отдельная, по умолчанию выключенная подсистема `core`: предварительный разбор вопроса технолога
по заранее подготовленному и провеверенному корпусу знаний участка (документы, определения, механизмы,
согласованные связи оборудования с историаном), с необязательным платным уточнением выбора через LLM-роль.
Весь код живёт в `core/pcbk_core/analytics/` и в маршрутах `core/pcbk_core/gateway/analytics_api.py`; подробности
самой службы данных (историан, каталог тегов, периоды, расчётные MCP/HTTP-инструменты) — в
[службе данных](10-data-service.md) и [расчётах](11-calculations.md), аналитика их не заменяет и не дублирует,
а переиспользует через `data_bridge.py`.

## Состояние в текущей сборке: роль выключена и не вызывается веб-чатом

- **По умолчанию выключена.** `ANALYTICS_ENABLED` (переменная окружения `core`) по умолчанию пуста — подсистема
  не инициализируется, маршруты `/pcbk/api/analytics/*` не регистрируются вовсе (404, как у несуществующего
  пути), остальные роли (вход, чат, калькуляторы, уроки) это не затрагивает.
- **Веб-чат текущей сборки эту роль не вызывает.** В `web/src/App.tsx` переменная `showAnalytics` зафиксирована
  как `false` с комментарием «отдельная аналитика убрана: технолог работает в обычном чате»; шапка (`Header`)
  не получает вкладку «Аналитика», компонент `AnalyticsPage`/пропс `AnalyticsImpl` объявлены в `AppProps`, но
  помечены как неиспользуемая инъекция и ни разу не монтируются в JSX. Код `web/src/analytics.ts`,
  `web/src/analyticsApi.ts`, `web/src/components/AnalyticsPage.tsx`, `AnalyticsLinks.tsx`, `AnalyticsReviews.tsx`,
  `AnalyticsSources.tsx` и `analytics.css` в репозитории присутствует и совместим с серверными ручками (формы
  ответов зеркалят друг друга, см. ниже), но ни один из этих файлов не подключён к дереву компонентов, которое
  реально рендерится — без правки `App.tsx` эта веб-часть мёртвый код, с правкой — рабочая вкладка.
- **Сервер-часть независима от веба и может использоваться напрямую.** Маршруты `gateway/analytics_api.py`
  работают полностью без браузерного клиента (curl/любой HTTP-клиент с сессионной куки шлюза) — это обычный
  REST-слой поверх координатора `AnalyticsService`, а не «бэкенд ровно под один фронтенд».
- **Перенос/включение.** Чтобы снова показывать вкладку в вебе, нужно вернуть `showAnalytics` к значению,
  зависящему от роли/разрешения (как у «Калькуляторов»/«Уроков»), и отрисовать `AnalyticsImpl`/`AnalyticsPage` в
  дереве `App.tsx` — серверная часть этого не требует и не блокирует.

## Включение и настройки (`core/pcbk_core/analytics/settings.py`)

Класс `AnalyticsSettings` (frozen dataclass, `from_env`/`valid_from_env`, тот же приём, что у прочих настроек
проекта — см. [конфигурацию](03-configuration.md)) разбирает переменные окружения по отдельности: опечатка в
одном поле не сбрасывает прочие и не включает/выключает подсистему молча — ошибка всплывает отдельной строкой.

| Переменная | Умолчание | Смысл |
|---|---|---|
| `ANALYTICS_ENABLED` | `False` | выключатель целиком (`1/true/on/yes` или `0/false/off/no`, без учёта регистра/пробелов; иное значение — ошибка настройки) |
| `ANALYTICS_CORPUS_DIR` | `/srv/analytics` | каталог с версиями корпуса, монтируется только на чтение |
| `ANALYTICS_STATE_PATH` | `/var/lib/pcbk-core/analytics.db` | файл состояния диалогов/заданий/согласования, отдельный от `core.db` |
| `ANALYTICS_LLM_MODELS` | `""` (без доп. сужения) | подмножество имён моделей-кандидатов (`llm/models.py`), которым разрешено отвечать на задания аналитики — пересечение с активным `LLM_MODELS` LLM-роли, не замена ему |
| `ANALYTICS_LLM_EXPORT_POLICY` | `"public_only"` | что уходит в исходящий запрос к модели — `public_only` \| `approved_subset` \| `none` (подробности — раздел про `llm_adapter.py`) |
| `ANALYTICS_REVIEWERS` | `"grants"` | кто решает заявки согласования — `grants` \| `all_students` (раздел про `reviews.py`) |
| `ANALYTICS_TEACHER_PAYER` | `""` | непустая строка-флаг «у преподавателя настроен платящий»; пусто — платный путь модели преподавателю недоступен, справка без модели остаётся |
| `ANALYTICS_HISTORY_RETENTION_DAYS` | `365.0` | срок хранения диалогов/заданий (минимум 1.0) |
| `ANALYTICS_EVIDENCE_RETENTION_DAYS` | `365.0` | срок хранения неизменяемых пакетов доказательств (минимум 1.0) |
| `ANALYTICS_JOB_TIMEOUT_S` | `120.0` | срок одной стадии задания до перехода в `failed` по таймауту (минимум 5.0, `settings.MIN_JOB_TIMEOUT_S`) |

Секретов у этой подсистемы нет: ключ LLM и токены вызывающих остаются у ролей `llm`/`gateway`, модуль их не
копирует. `AnalyticsSettings.valid_from_env` — запасной путь при ошибке (поля, прошедшие проверку, — из `env`,
прочие — умолчания, `ANALYTICS_ENABLED` при собственной ошибке — `False`); `AnalyticsSettings.from_env` — строгий
путь, поднимает `ValueError` на первой ошибке по порядку полей. В compose-файле (`compose.yaml`) `core` получает
`ANALYTICS_*` как обычные переменные окружения; `ANALYTICS_CORPUS_DIR` и `ANALYTICS_STATE_PATH` **не** передаются
контейнеру — путь внутри него фиксирован умолчанием кода (`/srv/analytics`/`/var/lib/pcbk-core/analytics.db`), а
переменная `ANALYTICS_CORPUS_DIR` в `.env` выкладки управляет только хостовым путём bind-mount тома. Без
переменной `ANALYTICS_CORPUS_DIR` в `.env` используется пустой именованный том — `docker compose` не падает, даже
если аналитика включена без настоящего корпуса (ответ тогда — понятный 503, см. ниже).

## Поток запроса и состав пакета

```
gateway/analytics_api.py  (роутер; сессия/источник записи — как у прочих ручек шлюза)
        │  AnalysisRequest (models.py) + RequestIdentity (из сессии, НЕ из тела запроса)
        ▼
analytics/service.py — AnalyticsService (координатор; фоновая asyncio-задача на вопрос)
        │
        ▼
analytics/preanalysis.py — analyze() → (Preanalysis, пакет EvidenceCard)
        │                                   │
        │ (knowledge.py / terms.py)        │ (retrieval.py — поиск; calculations.py — расчёт при intent=calculation)
        ▼                                   ▼
   decision: ready / needs_clarification / limited_answer / refused
        │
        │ только если ready, LLM-роль подключена и политика экспорта не "none"
        ▼
analytics/llm_adapter.py — request_selection() → LlmSelection (строго id, по JSON-схеме)
        │
        ▼
analytics/validator.py — validate_selection() → ValidationOutcome (каждый id сверен с пакетом заново)
        │
        ▼
analytics/rendering.py — render_*_section() / render_response() → JobResponse (models.py)
        │
        ▼
analytics/store.py — AnalyticsStore.publish_response() (атомарно: ответ + неизменяемый пакет доказательств)
        │
        ▼
gateway/analytics_api.py — GET requests/{id} отдаёт сохранённый JobResponse клиенту
```

`data_bridge.py`/`reviews.py` подключаются к этому потоку отдельно: `data_bridge.py` вызывается из
`service.py` только когда у подписи оборудования из вопроса есть действующая согласованная связь
(`reviews.resolved_link`) — без неё путь работает целиком (справка), просто без чтения историана.

Модули пакета `core/pcbk_core/analytics/` и их ответственность:

| Модуль | Ответственность |
|---|---|

### Личность вызывающего (`RequestIdentity`)

Источник — только серверная сессия (`pcbk_core.gateway.accounts.Account`), никогда тело запроса:
`AnalysisRequest` объявлен с `extra="forbid"` и не несёт полей `place`/`caller`/`login`/`owner`/`role` вовсе, а
`gateway/analytics_api.py` строит `RequestIdentity` из `Account` отдельным параметром обработчика
(`_identity_of`):

```python
caller = "teacher" if account.role == "teacher" else f"student-{account.place:02d}"
identity = RequestIdentity(login=account.login, role=account.role, place=account.place, caller=caller)
```

Тот же вид `caller`, что у калькуляторов страницы (`gateway.calc_api.caller_for`). Владелец диалога
(`store.py`) — `identity.login` (человек), не `identity.place` (место можно переназначить, история диалога —
нет). LLM видит только `identity.caller`, не логин. Студент без привязанного рабочего места (`account.place is
None`) получает `None` от `_identity_of` и 403 на любой ручке — как у калькуляторов страницы.

## Корпус: хранение, схема, версии (`analytics/knowledge.py`)

Корпус — один файл SQLite `*.seed.sqlite3`, открываемый в режиме `mode=ro`: ни одна функция модуля не хранит
постоянное соединение (`CorpusHandle` — просто `path, version`), каждый вызов открывает своё соединение и
закрывает его до возврата (вызывающие зовут функции через `asyncio.to_thread`, разные вызовы одного запроса
могут исполниться в разных потоках пула).

**Таблицы корпуса** (`RowKind`): `sources`, `fragments`, `processes`, `terms`, `claims`, `conflicts`,
`equipment_links`, `mechanisms` — каждая `(id TEXT PRIMARY KEY, payload TEXT NOT NULL CHECK(json_valid(payload)))`,
плюс `seed_meta(key, value)` с единственной записью `key="manifest"` (JSON вида `{"scope": "KDM1_PCBK",
"schema_version": …}`) и виртуальная таблица полнотекстового поиска FTS5 `kb_search(kind, id, text,
tokenize='unicode61')`. Значения `kind` в `kb_search`, с которыми реально индексирует существующий импортёр —
`claim`, `mechanism`, `processe` (так, с опечаткой множественного числа, не исправлять молча — код ищет именно
эту строку), `term`; у `fragments` записи в `kb_search` нет вовсе — сырые страницы/ячейки (в т.ч. в карантине)
структурно не могут попасть в выдачу поиска.

**Функции** (`core/pcbk_core/analytics/knowledge.py`):

| Функция | Делает |
|---|---|
| `open_corpus(root: str) -> CorpusHandle` | открыть текущую версию (или прямой файл `*.seed.sqlite3`); проверяет схему и манифест, версия — `f"{schema_version}:{sha256(файла)[:16]}"` |
| `close(handle)` | нет-оп (соединения не хранятся); оставлена для симметрии интерфейса |
| `corpus_version(handle) -> str` | версия, зафиксированная при `open_corpus` |
| `version_signature(root: str) -> str` | дешёвый признак текущей версии на диске (путь выбранного файла + его размер + mtime, **без** хеширования содержимого) — для решения «нужно ли переоткрывать корпус», без дорогой операции на каждый вопрос |
| `get_row(handle, kind, row_id) -> dict \| None` | одна запись `payload` (уже разобранный JSON) |
| `get_rows(handle, kind, row_ids) -> dict[str, dict]` | пакетно, чанками по 400 параметров `IN (…)`, только найденные id |
| `all_ids(handle, kind) -> tuple[str, ...]` | все `id` таблицы по возрастанию |
| `corpus_report(handle) -> dict` | число записей по каждой таблице + число строк `kb_search`, без текста — безопасно для журнала/состояния |
| `corpus_dirs(root) -> list[Path]` | подкаталоги версий (где есть хотя бы один `*.seed.sqlite3`), по убыванию имени |

`CorpusError` — любой сбой открытия/чтения (битый файл, нет файла, SQLite вернул ошибку, манифест не JSON или
`manifest["scope"] != "KDM1_PCBK"`); текст — без путей хоста. Сбой корпуса не бросается из общего жизненного
цикла шлюза — его ловит `service.py` и превращает в понятный 503, вход/чат/калькуляторы/уроки не затрагиваются.

**Выбор файла корпуса** (`_find_seed_file`) — по порядку приоритета:
1. `root` — сам файл `*.seed.sqlite3` (прямой путь);
2. если в каталоге `root` есть файл-указатель `CURRENT` (одна строка — имя подкаталога версии) — версия, на
   которую он указывает;
3. иначе — самый новый по имени подкаталог версий (`corpus_dirs`), если в нём ровно один файл корпуса;
4. иначе (подкаталогов версий нет вовсе — заказчик публикует один файл прямо в `root`) — сам `root`, если в нём
   ровно один такой файл.

Указатель `CURRENT` пишет и меняет только `analytics/ingestion/versions.py` (см. ниже) — `knowledge.py` его
только читает.

## Загрузка и публикация версий корпуса — офлайн-команды (`analytics/ingestion/`)

Отдельный, оффлайн-командный этап оператора — **не** маршрут API и не код, который исполняется во время
обычного вопроса; сеть не используется ни одной подкомандой. Запускается внутри контейнера `core`:

```sh
docker compose exec core python -m pcbk_core.analytics.ingestion <подкоманда> ...
```

### Карантин входящих файлов (`ingestion/quarantine.py`)

```sh
python -m pcbk_core.analytics.ingestion quarantine <файл_или_архив> --quarantine-dir <каталог> [--id <id>] [--scope KDM1_PCBK]
python -m pcbk_core.analytics.ingestion report <id> --quarantine-dir <каталог>
```

Каждый элемент получает `<quarantine_dir>/<id>/report.json` с вердиктом `accepted` / `rejected` /
`empty_or_unreadable`; отклонённый целиком элемент не оставляет в карантине ничего, кроме этого отчёта.
Проверяется: путь с обходом каталога (`..`) или абсолютный путь внутри ЛЮБОЙ записи архива (файла и каталога
одинаково), символическая/жёсткая ссылка, несовпадение расширения с реальной сигнатурой (ZIP или не ZIP),
конфликт имён между записями, превышение предела элементов/размера одного элемента/суммарного распакованного
размера («zip-бомба» — чтение каждой записи идёт с жёстким пределом байт, не доверяя заявленному в метаданных
размеру). Для XLSX/DOCX (оба — ZIP-контейнеры) отдельно: формулы — текстом, без пересчёта значения; макросы
(`vbaProject.bin`) — только флагом, содержимое никогда не читается как текст; внешние связи и командные поля
документа (Word field codes) — флагом и текстом инструкции, без исполнения. XML-часть, которая не проходит
строгую проверку кодировки (UTF-8 без BOM другой кодировки, без `encoding=` в прологе ≠ UTF-8, без байта `\x00`)
или содержит `<!DOCTYPE`/сущность — не разбирается вовсе, ни на одном уровне (структурная защита через
`xml.parsers.expat` с обработчиками, которые прерывают разбор на первом `DOCTYPE`/`ENTITY`, а не эвристика по
сигнатуре). Пустой/нечитаемый файл — отчёт без выдуманного текста.

Пределы по умолчанию (`quarantine.Limits`): не более 100 МиБ на поданный файл, не более 2000 элементов архива,
не более 50 МиБ на распакованный элемент, не более 200 МиБ суммарного распакованного размера, подозрительное
соотношение сжатия — свыше 100:1.

Карантин — только первый, безопасный разбор; какие факты из него попадут в `knowledge/*.jsonl` новой версии,
решает человек отдельно — этот шаг не делает этого автоматически.

### Версии корпуса (`ingestion/versions.py`)

Раскладка каталога версий (`ANALYTICS_CORPUS_DIR`):

```
ANALYTICS_CORPUS_DIR/
  CURRENT                 # указатель текущей версии — одна строка с именем подкаталога
  ingestion_log.jsonl     # журнал публикаций/откатов, построчный JSON, только дозапись
  <version-id>/
    kdm1.seed.sqlite3     # ровно один файл корпуса
    build_report.json     # сведения сборки
    publish.json | rollback.json   # запись утверждения (кто/когда)
```

```sh
python -m pcbk_core.analytics.ingestion build <версия> --knowledge-dir <knowledge/> --importer <tools/import_seed.py> [--corpus-dir <каталог>]
python -m pcbk_core.analytics.ingestion publish <версия> --approved-by <логин> [--corpus-dir <каталог>]
python -m pcbk_core.analytics.ingestion rollback <версия> --approved-by <логин> [--corpus-dir <каталог>]
python -m pcbk_core.analytics.ingestion list [--corpus-dir <каталог>]
```

`--corpus-dir` можно не указывать — тогда берётся `ANALYTICS_CORPUS_DIR` из окружения.

- **`build`** собирает новую версию из каталога `knowledge/` (построчный JSON + `seed_manifest.json`) в
  `<corpus-dir>/<версия>/`, запуская импортёр заказчика (`tools/import_seed.py`) **субпроцессом**, ровно тем же
  интерфейсом командной строки, что в его собственном README (`--knowledge DIR --output FILE`); путь к импортёру
  — обязательный аргумент, не константа модуля (он лежит вне `core` и вне git). После сборки `build` **независимо**
  (не доверяя одному импортёру) перепроверяет результат той же проверкой, что `publish`/`rollback`. Не публикует
  версию — указатель `CURRENT` не трогает.
- **`publish`/`rollback`** требуют `--approved-by <логин>` (без него — отказ) и перед сменой указателя
  **независимо** проверяют: целостность манифеста/схемы (через `knowledge.open_corpus` на конкретный подкаталог),
  что каждая ссылка `claims`/`processes`/`terms`/`mechanisms` на источник/фрагмент/процесс/термин существует
  именно в этой версии, и что `machine_scope` строк `processes`/`terms`/`equipment_links` начинается с токена
  `KDM1` (а не буквально `KDM1_PCBK` — допустимая общая теория может иметь более широкий, но всё ещё «свой»
  `machine_scope`, например `KDM1_related_general_mathematics`; чужая машина — любой другой код — отклоняется).
  Любое нарушение — отказ с отчётом, указатель `CURRENT` не меняется. Смена указателя — один атомарный
  `os.replace` временного файла; журнал версии (`publish.json`/`rollback.json`) пишется **до** него, так что сбой
  на этом шаге тоже не трогает указатель.
- **`rollback`** — то же действие, что `publish`, но на уже существующую (не новую) версию. Ни `build`, ни
  `publish`, ни `rollback` никогда не удаляют и не изменяют уже существующий подкаталог версии — история версий
  (и любые пакеты доказательств, которые помнят версию по этой строке) не трогается откатом.
- **`list`** — все версии каталога, какая текущая, и помечает повреждённую версию (`status: "broken"`) без
  падения всего списка.

Пока в каталоге нет указателя `CURRENT`, `core` открывает самый новый по имени подкаталог версии сразу, хотя
`list` покажет её как неопубликованную — поэтому прежде чем положить в каталог новую версию, нужно опубликовать
текущую (чтобы появился указатель), и только после этого класть и публиковать новую. Файлы и подкаталоги версии
должны читаться пользователем контейнера `core` (0755 для каталогов, 0644 для файлов).

**Новая версия подхватывается без пересоздания контейнера `core`.** `AnalyticsService` сверяет
`knowledge.version_signature` в начале каждого задания (каждого вопроса) и, если он изменился, переоткрывает
корпус (`knowledge.open_corpus`) прямо в работающем процессе; сбой переоткрытия — строка журнала, прежний
дескриптор остаётся рабочим. Если версия сменилась МЕЖДУ поиском и выдачей ровно этого задания (платный вызов
модели занял время), ответ не публикует карточки «как ни в чём не бывало» — клиент получает `limited_answer` с
единственной секцией-ограничением «версия корпуса сменилась — задайте вопрос ещё раз». Уже отданные клиенту
исторические ответы (отвеченные по старой версии) при последующем чтении получают добавленное (не
сохраняемое) предупреждение «ответ исторический» — сам сохранённый ответ не переписывается. Пересоздание
контейнера остаётся штатным средством на случай других проблем (например, признак версии не считался из-за
проблем с томом), но саму публикацию оно больше не обслуживает как обязательный шаг.

## Термины и точные подписи (`analytics/terms.py`)

Отдельно от полнотекстового поиска (`retrieval.py`): термины — словарь корпуса (`terms`: `preferred_ru`,
`aliases`, `definition`, `ambiguous`, `machine_scope`, …), а `retrieval.py` ищет по карточкам/механизмам/
процессам. `terms.py` превращает слово или фразу вопроса в `ResolvedTerm` (`models.py`).

- `normalize_ru(text) -> str` — наивный эвристический стеммер своими силами (снимает частые падежные/родовые
  окончания существительных и прилагательных по списку суффиксов, без словарей и без новых зависимостей): не
  полная морфология, а только нормализованная форма для сравнения со словарём корпуса.
- `resolve_term(handle, original) -> ResolvedTerm` — слово/фраза → до 10 кандидатов словаря (сравнение по
  множествам нормализованных слов, подмножеством в любую сторону); `selected_id` — единственный явный кандидат
  или `None` при неоднозначности; `requires_confirmation=True`, если кандидатов больше одного, термин помечен
  `ambiguous` в корпусе, или кандидатов нет вовсе. `original` — непустая строка (пустая — `ValueError`
  вызывающему, строка из пробелов — обычный «не найдено» результат, не исключение).
- `resolve_term_exact_phrase(handle, words) -> ResolvedTerm | None` — та же сборка, но для фразы (два и более
  слова), совпадающей с формой термина **равенством** множества основ, не подмножеством: отличает термин, чьё
  название фраза называет целиком, от более длинного термина, который содержит ту же пару слов как часть своего
  названия (например «короткий узел» как часть «более длинное название узла, включающее короткий узел»).
- `exact_tag_candidates(handle, text) -> list[str]` — точные подписи оборудования/узлов в тексте вопроса
  (`equipment_links.display_label`/`processes.source_label`), по точному вхождению известной подписи целиком
  (границы — не буква/цифра/`_` по краям), без морфологии и без нечёткого сходства — похожая, но неизвестная
  корпусу строка не возвращается как «похожий» тег. Настоящие подписи оборудования предприятия в код и тесты не
  попадают — тестовая фикстура использует вид `20FAKE_001_PV`/`20FAKE_QT31` (цифровой префикс + буквы/цифры).
- `known_ambiguous_words(handle) -> frozenset[str]` — слова, про которые корпус уже знает, что они неоднозначны
  без контекста (из `terms.ambiguous`, не хардкод модуля); сегодня не вызывается на обычном пути вопроса —
  `resolve_term` уже даёт `requires_confirmation`/`candidate_ids`, функция остаётся готовым инструментом на
  будущее (например, подсветка в вебе «это слово неоднозначно» до отправки вопроса).

## Поиск по корпусу (`analytics/retrieval.py`)

Начальный поиск — SQLite FTS5 (`kb_search`, `tokenize='unicode61'`) плюс точный поиск по id и подготовленный
набор видов (`unicode61` не решает русскую морфологию — нормализацию запроса даёт `terms.normalize_ru`).
Векторный поиск не подключён.

| Функция | Делает |
|---|---|
| `search(handle, query, *, kinds=(), limit=20, process_ids=()) -> list[SearchHit]` | полнотекстовый поиск; `kinds` сужает виды записей, `process_ids` сужает область до уже определённых узлов |
| `exact_id_lookup(handle, kind, token) -> str \| None` | токен — точно существующий `id` записи вида `kind` (не через FTS5 — прямой `get_row`) |
| `related_fragments(handle, claim_or_mechanism_id) -> list[str]` | `id` фрагментов, на которые ссылается карточка/механизм (основа `EvidenceRef`) |

`SearchHit` — `kind` (`claim`/`mechanism`/`processe`/`term`), `id`, `score` (ранг FTS5, меньше — релевантнее),
`snippet` (короткий фрагмент совпадения для журнала, не для прямого показа клиенту). На каждый найденный
кандидат дополнительно проверяется `machine_scope` записи (если есть в `payload`) — должен быть токеном `KDM1`
целиком или начинаться с `KDM1_` (с границей, не произвольный префикс: `KDM10…`/`KDM1x…` не считаются своими) —
это защита от слишком узкого понимания «своей» области, не от текущих данных чужой машины (их в корпусе нет по
построению). Область поиска — только процессы/карточки/механизмы КДМ-1 и связанная допустимая общая теория;
закрытые по `publication_state`/области записи и карантинные/непересчитанные фрагменты поиском вовсе не
возвращаются — структурно (у `fragments` нет записи в `kb_search`), не постфактум-фильтром.

## Преданализ (`analytics/preanalysis.py`)

Единственная точка, через которую проходит каждый вопрос, включая путь без LLM. Не обращается к LLM и не читает
историан сам — это делают `llm_adapter.py` и `data_bridge.py`, и только после преданализа. Текст вопроса
(включая любые инструкции, которые технолог мог вставить в него намеренно или случайно) никогда не исполняется
как системная команда: классификация намерения — фиксированный серверный список ключевых слов, а не вызов
модели «что делать с этим текстом».

**`original_and_normalized(request) -> NormalizedQuestion`** — `original` (как пришло) отдельно от
`normalized` (после `terms.normalize_ru`); `unit_hint`/`process_hint` — из явного `context.unit_hint`/`process_id`
запроса или из буквально написанных в тексте обозначений единиц (таблица токенов вида `%`, `м³/ч`, `т/м³`,
`г/м²`, `кН/м`, `бар`, `кПа`, `л/мин`, `м/мин`, `кг/ч`, словесных форм расхода и т.п.) — единица **не
угадывается**, если в тексте её нет.

**`classify_intent(parsed) -> Intent`** — `definition | lookup | calculation | deviation | control |
out_of_scope`, фиксированным порядком проверок без LLM:
1. `control` — вопрос просит управляющее действие в любой естественной форме (повелительная, инфинитивная, «как
   мне…», вопрос о процедуре) — определительная/теоретическая рамка («что такое…», «расскажи про…») снимает
   признак, но только если в предложении нет явного императива (императив важнее рамки);
2. явное упоминание другой машины участка (код вида «кдм»/«бдм»/«пм» + номер, кроме «кдм»+«1», в любом
   регистре/написании) → `out_of_scope`, **кроме** смешанного вопроса, где есть допустимая часть про КДМ-1
   (определительная рамка или явное упоминание КДМ-1 в том же тексте) — тогда отказ ограничивается только
   частью вопроса про другую машину (отдельная секция-ограничение в ответе), остальная часть разбирается как
   обычно;
3. упоминание смежного технологического процесса вне корпуса (например, гофроагрегат/варка целлюлозы) →
   `out_of_scope`;
4. стебли слов (без LLM, по началу словоформы) — `calculation` (включая явный глагол «сложить» для объединения
   периодов простоя), `deviation`, `lookup`, `definition`; ничего не совпало — `lookup` (справочный поиск по
   умолчанию безопаснее придуманного определения).

**`requires_clarification(parsed, resolved_terms, process_ids, *, mode=None, period_given=False,
has_equipment_label=False, is_enumeration=False, basis_sensitive_single_candidate_term_ids=frozenset())
-> (bool, tuple[str, ...])`** — решает, нужно ли уточнение **раньше** оплачиваемого вызова модели и чтения
данных (`missing_fields`, значения строго из `models.ClarificationKey`: `quantity`, `process`, `unit`, `basis`,
`period`, `timezone`, `grade`, `measurement_quality`, `source_applicability`). Ключевые правила:
- термин, для которого словарь не нашёл вообще никакого кандидата, — обычная лексика вопроса, не повод для
  уточнения; уточнение `"quantity"` запрашивается только когда кандидат(ы) **есть**, но выбрать один нельзя;
- `"process"` — несколько кандидатов узла одновременно (кроме вопроса-перечисления «какие…»/«все…»/«перечисли…»
  с фразой узла, совпавшей сразу с несколькими узлами — тогда все узлы идут в `process_ids` без уточнения);
- `"unit"`/`"basis"` не запрашиваются, если `calculations.known_refusal_reason` уже даёт структурную причину
  отказа (вопрос всё равно получит отказ по роду задачи, не зависящий от названной единицы/базы) или если
  `calculations.plan_from_question` уже дал полный, самодостаточный план расчёта;
- `"period"` снимается буквальным интервалом `ЧЧ:ММ–ЧЧ:ММ` (включая словесное «до») или буквальной календарной
  датой `ДД.ММ[.ГГГГ]`, или явным `context.period` запроса (`period_given=True`); `"timezone"` — явным поясом/
  городом в тексте («по Москве», «МСК», «UTC», смещение) или тем же `period_given=True`; обе проверки
  независимы (день может быть назван без пояса и наоборот). Для `mode == "deviation_review"` (режим диалога,
  выбранный заранее для чтения историана) период/пояс проверяются строже, чем просто по намерению `deviation`
  текста одного вопроса;
- точная подпись оборудования в вопросе (`_mentions_equipment_link_label`, по `equipment_links.display_label`,
  не по подписи узла) снимает `"quantity"`/`"basis"` **кроме** `intent == "calculation"` — подпись прибора сама
  однозначно задаёт измеряемую величину (её отдаёт служба данных по самой подписи), но ничего не говорит про
  формулу расчёта.

**`build_evidence_pack(handle, process_ids, parsed) -> tuple[EvidenceCard, ...]`** — поиск только доступных
источников КДМ-1 и связанной общей теории; явно названный в тексте вопроса `id` карточки/механизма
(`retrieval.exact_id_lookup`, вид `ПРЕФИКС-сегмент-сегмент…`) ищется точно и ставится первым в пакете, раньше
результатов нечёткого `retrieval.search`. Пакет ограничен `_PACK_MAX_CARDS = 20` карточками.

**`clarification_candidates(handle, parsed, resolved_terms) -> tuple[str, ...]`** — до 6
(`MAX_CLARIFICATION_CANDIDATES`) готовых подписей кандидатов первого спорного термина вопроса (`preferred_ru`
словаря) или, если спорен сам узел, подписи узлов-кандидатов — для секции уточнения с явными вариантами, а не
только с открытым вопросом.

**`analyze(identity, request, handle, corpus_version) -> (Preanalysis, tuple[EvidenceCard, ...])`** — точка
входа `service.py`, собирает решение одним вызовом:

| `intent` | `decision` | Пакет | `llm_export_policy` | Комментарий |
|---|---|---|---|---|
| `out_of_scope` | `refused` | пуст | `public_only` | ни термины, ни узлы, ни пакет не собираются |
| `control` | `limited_answer` | только неоперационные карточки (`risk_level` из `non_operational_reference`/`historical_document`/`general_mechanism`), чей текст сам не читается как команда | `none` | модель не вызывается; `risk="control"`, `data_access_ready=False` |
| прочее, нужно уточнение | `needs_clarification` | пуст | `public_only` | уточнение не требует чтения данных |
| прочее, пакет не пуст | `ready` | собранный пакет | `public_only` (сервер может заменить перед вызовом модели — см. ниже) | |
| прочее, пакет пуст | `limited_answer` | пуст | `public_only` | нет совпавших доказательств в разрешённой области — не выдумка, честное ограничение |

`identity` в сигнатуре не читается самим модулем — личность и права уже проверены слоем API/`service.py` до
преданализа. `evidence_pack_id` преданализ всегда отдаёт `None` — реальный id после сохранения пакета
проставляет `service.py`.

## Расчёты по формулам (`analytics/calculations.py`)

Отдельный модуль от расчётных MCP/HTTP-инструментов службы данных (`calc_runtime`/`calc_spc`/… —
[11-calculations.md](11-calculations.md)): те читают историан через `DataService`, этот модуль — чистая
арифметика (`Decimal`, без `eval`) над входами, которые уже разобрал `preanalysis.py` или назвал сам технолог в
тексте вопроса. Ровно четыре именованные формулы (`CalculationId`):

| `calculation_id` | Формула | Единица результата |
|---|---|---|
| `dry_solid_flow` | объёмный расход (м³/ч) × плотность (т/м³) × доля сухого вещества | т/ч |
| `geometric_output` | ширина (м) × скорость (м/мин) × масса 1 м² (г/м²) × 60 / 10⁶ | т/ч |
| `dry_grammage` | масса 1 м² (как есть, г/м²) × доля сухого вещества | г/м² |
| `interval_union` | объединение (не сумма!) пересекающихся/соприкасающихся интервалов времени простоя | ч |

- `run_calculation(calculation_id, inputs, units) -> CalculationResult` — диспетчер для трёх `Decimal`-формул:
  проверяет физический род единицы каждого входа против ожидаемого (например, `кН/м` — линейная нагрузка, не
  принимается там, где нужна плотность/давление — автоматического перевода между физическими родами нет и не
  будет: «80 кН/м нельзя напрямую перевести в бар» без ширины зоны контакта/калибровки, это отдельный, явный
  отказ, не подмена единицы). Отсутствующий именованный вход — не ошибка, а `CalculationResult.value=None` с
  этим именем в `missing_basis` (ноль ≠ отсутствие данных: распознанный, но ровно нулевой вход остаётся
  `Decimal(0)`, не выпадает). `interval_union` вызывается отдельно, не через этот диспетчер (у неё другая форма
  входа — последовательность пар `datetime`, не `Mapping[str, Decimal]`).
- `plan_from_question(text) -> CalculationPlan | None` — разбирает исходный (не нормализованный) текст вопроса
  в план одной из четырёх формул или структурный отказ; буквальное чтение написанного (знак, десятичная запятая
  или точка, единица сразу после числа), без угадывания отсутствующей единицы/базы. Два разных числа одного
  рода в тексте (например, две разные массы 1 м²) — явный отказ-неоднозначность, не выбор первого по порядку.
- `known_refusal_reason(text) -> str | None` — четыре структурные категории отказа, не зависящие от того, какую
  единицу/базу назовёт технолог: перевод линейной нагрузки (кН/м) в давление; перевод избыточного/
  манометрического давления в абсолютное без явной базы (местное атмосферное давление/способ измерения);
  расчёт показателя COV экрана (алгоритм которого в корпусе нет — общий статистический коэффициент вариации не
  то же самое); сравнение с данными других предприятий/стран/отрасли (которых в корпусе нет — статистика не
  выдумывается). Используется и в `plan_from_question` (готовый план-отказ), и в
  `preanalysis.requires_clarification` (не запрашивать уточнение единицы/базы раньше этого отказа).
- `mentions_time_range(text)`/`mentions_literal_date(text)` — вспомогательные признаки для
  `preanalysis.requires_clarification` (снимают `"period"` по буквальному интервалу/дате в тексте).

`CalculationInputError` (подкласс `ValueError`) — вход не того физического рода, не в допустимом диапазоне
(отрицательный расход, доля вне 0…1) или не `Decimal`. Независимые эталоны проверки формул (для разработки и
тестов) — не повторный вызов той же функции, а значения, посчитанные вручную `Decimal`-арифметикой по условию
задачи.

## Связь со службой данных (`analytics/data_bridge.py`)

Тонкий проброс в уже существующий `DataService` (`core/pcbk_core/data/service.py`, тот же приём, что у
`gateway/calc_api.py` — служба данных и её белый список/бюджет/кэш не меняются аналитикой ни на строку).
Единственные вызовы — `catalog_search`, `tag_now`, `tag_period`, `tag_series`, `calc_runtime`, ровно с той же
сигнатурой, что у `DataService` (подробности этих методов — [служба данных](10-data-service.md)). `channel`
всегда `"web"`; `caller` — `identity.caller` (`student-NN`/`teacher`), тот же вызывающий, что видят
калькуляторы страницы, с теми же пределами частоты.

- `catalog_search(svc, identity, query, limit=10)` — справочный поиск по разрешённому каталогу имён тегов (как у
  калькуляторов страницы), **не** чтение значения: точное совпадение подписи оборудования с именем тега сам по
  себе не включает доступ к данным.
- `tag_now`/`tag_period`/`tag_series`/`calc_runtime` принимают обязательный параметр `link:
  reviews.ResolvedLink` — согласованную связь оборудования с историаном; без неё эти функции не вызываются
  вовсе (решает `service.py`). Ответ `DataService` (единицы, пробелы, свежесть, качество, отказ) передаётся как
  есть, без собственной интерпретации полей — отказ прежней службы не оборачивается и не прячется.

Связь оборудования (подписи `equipment_links.display_label`) с конкретным именем тега историана **не** хранится
в самом корпусе (`equipment_links.historian_tag` в `*.seed.sqlite3` остаётся `null`) — она живёт отдельно, как
принятая заявка согласования (`reviews.ResolvedLink`, следующий раздел). `AnalyticsService` показывает значение
телеметрии в ответе отдельной секцией (`SectionKind.telemetry_observation`): значение «сейчас» или за период
строится буквально из полей ответа `DataService` (без пересчёта), с явной подписью часового пояса источника
времени и явной единицей (или плейсхолдером «единица в историане не задана»); дискретный тег показывает
`state_label`, не число. До трёх подписей оборудования на один ответ (остальные найденные — отдельной строкой
«показаны первые N из M»); подпись без согласованной связи, неподключённая/неисправная служба данных и прямой
отказ `DataService` — три разные фиксированные секции-ограничения, не падение задания.

## Модель LLM (`analytics/llm_adapter.py`)

Единственная точка вызова LLM-роли (`LlmRole`, [LLM-прокси](12-llm-proxy.md)) для аналитики — использует только
уже проверенные для обычного чата функции (`rebuild_body`, `LlmRole.begin_call`/`LlmCall.finish`, `forward`),
**не** вызывает поставщика напрямую. Повторяет тот же порядок допуска, что обычный путь прокси, минуя только
разбор `Authorization` (личность здесь уже есть из сессии шлюза):

0. преподаватель без непустого `ANALYTICS_TEACHER_PAYER` — отказ до журнала/бюджета/сети;
1. ошибка настройки LLM-роли (`role.config_error`) — отказ;
2. LLM-роль остановлена (`role.stopped`) — отказ;
3. ключа у роли нет (`role.upstream is None`) — отказ; справка без LLM остаётся доступной;
4. выбор модели — активный набор `LLM_MODELS` роли, дополнительно суженный `ANALYTICS_LLM_MODELS`, если он не
   пуст (пересечение, не замена); первая по порядку кандидатов модуля моделей, не самая дешёвая и не самая
   сильная;
5. сборка тела (`rebuild_body`) и оценка стоимости;
6. ошибка журнала расходов (`role.ledger_error()`) — отказ раньше резерва бюджета;
7. один синхронный участок без `await` между проверкой предела параллельности вызывающего/бюджета и резервом
   (та же дисциплина, что у обычного чата: приём/резерв/счётчики — атомарно);
8. `forward(role, call, body, raw)` — резерв/журнал/запасную модель/отмену несёт целиком сам `forward`, адаптер
   эту логику не повторяет.

**Выбор моделей.** `select_model(role, analytics_models) -> ModelPolicy` — пересечение активных моделей роли и
`ANALYTICS_LLM_MODELS` (пусто — без доп. сужения); пусто после пересечения — отказ `LlmAdapterRefusal("model")`.

**Политика передачи содержимого (`ANALYTICS_LLM_EXPORT_POLICY`)** — решает, что ВИДИТ модель в запросе, не что
она имеет право вернуть клиенту (ответ модели — всегда только список `id` по строгой JSON-схеме, см. ниже):

| Значение | В системном сообщении | В пользовательском сообщении |
|---|---|---|
| `public_only` (умолчание) | только `id` разрешённого пакета (`allowed_reference_claim_ids`/`allowed_mechanism_ids`) и `calculation_allowed` | намерение, риск, `id` разрешённых терминов/узлов/конфликтов — без текста карточек и без текста вопроса |
| `approved_subset` | то же, что `public_only` | **дополнительно** исходный текст вопроса и тексты карточек разрешённого пакета (`{"id","text","fragments":[{"fragment_id","locator"}]}`), урезанные пропорционально под общий предел 60 000 символов с явной пометкой урезания |
| `none` | модель не вызывается вовсе | — |

`build_raw_body` отклоняет любое значение политики кроме `public_only`/`approved_subset` — `none` отключается
на уровень выше (`service.py` не доходит до адаптера, если политика `"none"`). Независимо от политики: id
карточки/механизма сверяется **дважды** — и как разрешённый преданализом (`allowed_claim_ids`/
`allowed_mechanism_ids`), и как реально присутствующий в пакете этого запроса; `response_format` — строгая
JSON Schema (`json_schema`, обёртка `name`/`strict`/`schema`), дополнительно суженная под конкретный
пакет (`enum` у `reference_claim_ids`/`mechanism_ids` — ровно разрешённые id, или `maxItems: 0` при пустом
пакете; `calculation_ids` — `maxItems: 0` вне `intent == "calculation"`); ключи, не реализуемые грамматикой
строгого вывода у некоторых поставщиков (`uniqueItems`), снимаются из переданной схемы — уникальность всё равно
перепроверяет сервер (`models.LlmSelection`/`validator.validate_selection`).

**Ответ модели** разбирается строго: не-200 статус → отказ с кодом из тела `forward()`; статус 200, но
содержимое не проходит `LlmSelection.model_validate` (`extra="forbid"`, строгие перечисления и пределы) →
`LlmAdapterRefusal("invalid_selection")`. Сырой текст ответа модели (поток, заголовки, рассуждения) клиенту не
возвращается никогда — наружу идёт только разобранный и провалидированный `LlmSelection`. Предел повторов на
отказ адаптера — ровно ноль: `service.py` не переспрашивает модель, а откатывается на детерминированный путь
через тот же `validator.validate_selection`.

`request_selection(role, identity, session, raw_body, *, analytics_models, teacher_payer="") -> LlmSelection` —
единственная точка вызова; `session` — `conversation_id` (у аналитических диалогов сессия всегда есть, в
отличие от обычного чата). `teacher_payer` — значение `ANALYTICS_TEACHER_PAYER`, передаёт `service.py`.

## Проверка выбора модели (`analytics/validator.py`)

Отделяет то, что *предложила* модель (`LlmSelection`), от того, что сервер действительно разрешает показать
(`ValidationOutcome`). Наличие ссылки недостаточно — каждый `id` сверяется с пакетом доказательств преданализа,
а не просто с тем, что он синтаксически похож на идентификатор корпуса.

`validate_selection(selection, preanalysis, pack, approved_card_ids=frozenset()) -> ValidationOutcome`:
каждый `reference_claim_ids`/`mechanism_ids` должен входить **и** в `allowed_claim_ids`/`allowed_mechanism_ids`
преданализа, **и** реально существовать в `pack` с тем же `id` и тем же видом (двойная сверка — схема модели уже
сужает `enum` под пакет, но сервер не доверяет только этому). Для каждой выбранной карточки заново (не доверяя
тому, что она когда-то прошла преданализ) проверяется:
- `publication_state` — белый список `RENDERABLE_PUBLICATION_STATES = {"desk_verified_draft",
  "reviewer_approved"}` (неизвестное/новое состояние корпуса по умолчанию запрещено, не разрешено);
- `critical_local_fact` — требует более узкого состояния `APPROVED_CRITICAL_FACT_STATES = {"reviewer_approved"}`
  **или** присутствия `id` в `approved_card_ids` (действующее согласование, собранное `service.py` через
  `reviews.ReviewStore.approved_claim` непосредственно перед вызовом);
- `applicability` — не пусто (не «общее правило без указанной области/срока»);
- версия корпуса каждой ссылки `evidence_refs[].corpus_version` — совпадает с версией самого `preanalysis`
  (старый пакет доказательств не даёт нового разрешения — несовпадение после публикации новой версии корпуса
  между поиском и выдачей блокирует карточку);
- источник карточки не входит в `RESTRICTED_SOURCE_IDS` (список источников, чьё содержимое не передаётся LLM и
  не отображается без отдельного подтверждённого основания — в текущем корпусе это страницы правообладателя
  стандартов, помеченные в `sources.jsonl` как `llm_context_allowed=false`).

Не прошедшие — в `ValidationOutcome.rejected` с причиной, не отбрасываются молча; `refused=True` ставится
только когда отказ вызван нарушением одной из перечисленных политик, не просто «id вне пакета».

`check_claim_mutation(card, proposed_text) -> str | None` — эвристика на регулярных выражениях (без
зависимостей), ловит подмену тега/номера узла (с учётом порядка упоминания, не множеством), единицы измерения
(привязанной к конкретному числу), отрицания (по количеству маркеров, не только по наличию), верх/низ,
«гипотеза → установленная причина» и опасное управляющее действие внутри справочного текста. В текущей
архитектуре у модели нет канала свободного текста вовсе (`LlmSelection` несёт только `id`) — функция остаётся
переиспользуемым инструментом проверки произвольного текста против карточки, а не действующим фильтром живого
текста модели.

`check_calculation_consistency(result, preanalysis) -> str | None` — отклоняет расчёт, если его база
противоречит преданализу (другой период/участок/сорт, чем подтвердил технолог, или преданализ не подтвердил
готовность расчёта); `result.value is None` само по себе не противоречие — это ограничение, которое строит
`rendering.py`.

## Серверное отображение ответа (`analytics/rendering.py`)

Единственное место, которое строит `Section`/`JobResponse` — произвольная модельная проза сюда не попадает мимо
проверки; каждая секция — один из фиксированных серверных шаблонов по `SectionKind`, не текст модели как есть:

| `SectionKind` | Шаблон/содержимое | Строит |
|---|---|---|
| `document_observation` | «В предоставленной модели указано: …» (или «На снимке указано: …» — если ссылка карточки типа `image_label`) + текст карточки | `render_claim_section` (режим `attributed_document_literal`) |
| `public_definition` | текст карточки из допустимого публичного источника | `render_claim_section` (режим `attributed_reference`) |
| `calculation` | вход/единицы/формула/допущения расчёта | `render_calculation_section` |
| `qualified_hypothesis` | текст механизма + обязательная оговорка «Общий возможный механизм; причина на КДМ-1 не установлена.» | `render_mechanism_section` |
| `limitation` | чего не хватает или что отклонено (единица/период/подтверждение, отказ от команды, занятость диалога, смена версии корпуса, смешанный вопрос про другую машину, отказ службы данных, открытое расхождение корпуса) | `render_control_refusal_section` и ряд `render_telemetry_*`/`render_conflict_*`, плюс внутренние шаблоны `service.py` |
| `clarification` | адресный вопрос (участок/единица/период/сорт…), с готовыми подписями кандидатов, если преданализ их нашёл | `render_clarification_section` |
| `telemetry_observation` | значение/период историана буквально из ответа `DataService`, с подписью часового пояса источника | `render_telemetry_section`/`render_telemetry_period_section` |

Местный критический факт (`critical_local_fact=True`) рендерится только при согласованном состоянии
(`APPROVED_CRITICAL_FACT_STATES`/`approved_card_ids`) — иначе `render_claim_section` сама отказывает
(`ValueError`), не рендерит с предупреждением: решение «не показывать вовсе» уже должно быть принято раньше, на
уровне `validator.py`/`service.py`. Числа в тексте секции — с десятичной запятой, не точкой (как и весь
остальной интерфейс: «18,716334 т/ч», не «18.716334»).

`render_response(request_id, conversation_id, state, corpus_version, stage_label, outcome, sections) ->
JobResponse` — финальная сборка с проверкой пределов контракта (не больше 24 секций, без повторов секции целиком,
не больше 12 ключей уточнения) до вызова конструктора модели, чтобы причина отказа была понятнее, чем
`ValidationError` без контекста.

## Координатор заданий (`analytics/service.py`)

`AnalyticsService` — единственная точка, которую вызывают маршруты шлюза; сам он — единственный вызывающий
`preanalysis.py`/`llm_adapter.py`/`validator.py`/`calculations.py`/`rendering.py`/`store.py`/`reviews.py`/
`data_bridge.py`/`knowledge.py`.

**Жизненный цикл.** Конструктор `AnalyticsService(settings, *, calc=None, llm=None)` ничего не открывает;
`open()` (из lifespan шлюза) открывает корпус (`knowledge.open_corpus`, в потоке), состояние
(`AnalyticsStore.open`) и согласование (`ReviewStore.open`, тот же файл, свои таблицы — деградирует отдельно от
основного состояния); при успехе обрывает незавершённые задания после перезапуска процесса
(`store.reap_unfinished_after_restart` → `failed`, без повторной оплаты) и запускает фоновую очистку сроков
хранения (`_sweep_retention_once` сразу, затем раз в час, `RETENTION_SWEEP_INTERVAL_S = 3600.0`). Любой сбой
корпуса/состояния/согласования не бросает исключение из `open()` — пишется в `self.corpus_error`/
`self.config_error`/`self.reviews_error`, маршруты отвечают понятным 503 (своим на каждый вид сбоя), процесс
живёт.

**Асинхронные задания.** `submit_question` создаёт запись в `store.py` (идемпотентно по
`client_request_id`, см. `store.create_request`) и сразу возвращает `request_id` клиенту (202) — весь разбор
идёт в фоновой `asyncio.Task` (`_guarded_run_job` → `_run_job`); одновременно обрабатывается до
`MAX_CONCURRENT_JOBS = 4` заданий (`asyncio.Semaphore`), очередь остальных — естественная (стадия `queued`).
Срок одного прохода — `ANALYTICS_JOB_TIMEOUT_S`; превышен или любое исключение внутри прохода — стадия
`failed`, без повторной оплаты (новая отправка того же вопроса или отмена видят уже терминальную стадию).

Стадии задания (`JobState`): `queued → preanalysis → retrieving (если decision="ready") | validating (прочие
решения) → completed | needs_clarification | limited_answer | cancelled | failed`. Терминальную стадию и
клиентский `JobResponse` для всех исходов преданализа (включая `ready`) даёт только `store.publish_response` —
`set_preanalysis` переводит нетерминальные решения в `validating` как «парковку» перед публикацией, не как
отдельную фазу проверки модели. Значение `generating` объявлено в перечислении `JobState`/контракте, но в
текущем коде ни один переход (`store.advance_stage`/`store.set_preanalysis`) его не выставляет — зарезервировано
на будущее (например, для отдельной видимой стадии «идёт платный вызов модели»), сегодня клиент его не увидит.

**Сборка исхода (`_build_outcome`)** — по решению преданализа:
- `needs_clarification` → секция `clarification` с подписями кандидатов (`preanalysis.clarification_candidates`);
- `refused` → пустой ответ, `error_code="policy_refused"`;
- иначе пакет **перечитывается из корпуса заново** (`_refresh_pack`) непосредственно перед проверкой — снимок
  карточек со времени поиска не доверяется напрямую (отозванная/удалённая карточка не выходит из этого шага
  вовсе, изменившийся текст/статус — используется свежий);
- `intent == "control"` → первая секция — отказ от управляющей части (`render_control_refusal_section`),
  карточки пакета — через тот же `validator.validate_selection`, что и обычный путь без LLM
  (`_deterministic_outcome`), LLM не вызывается;
- `ready`/`limited_answer` без LLM или при отказе LLM (`self.llm is None`, политика `"none"`, диалог уже занят
  платным вызовом, `LlmAdapterRefusal`, невалидный ответ модели — **любая** из причин) → `_deterministic_outcome`:
  синтетический `LlmSelection` ровно из разрешённого пакета (до пределов контракта — 20 карточек/6 механизмов),
  проведённый через ТУ ЖЕ проверку `validator.validate_selection`, что настоящий выбор модели — карточка не
  попадает в ответ только потому, что преданализ когда-то счёл её допустимой, без проверки «здесь и сейчас»;
- настоящий выбор модели (`_select_with_llm`) после успешного ответа **повторно** перечитывает пакет и
  согласования и проводит принятые карточки через проверку ещё раз (`_recheck_outcome`) — платный вызов мог
  занять заметное время, в течение которого карточку/полномочие могли отозвать;
- расчётная секция (`intent == "calculation"`) строится только сервером, LLM в выбор формулы и в само число не
  участвует вовсе — идёт первой в ответе;
- секции телеметрии историана (до `MAX_TELEMETRY_LABELS = 3` подписей на ответ) и открытых расхождений корпуса
  (до `MAX_CONFLICT_SECTIONS = 2`) добавляются после расчётной (если есть) и перед карточками справки;
- непосредственно перед публикацией признак версии корпуса на диске сверяется ещё раз с тем, с которым задание
  стартовало — расхождение (корпус сменился, пока шёл поиск/платный вызов) отменяет публикацию карточек,
  ответ — `limited_answer` с единственным ограничением «версия корпуса сменилась».

**Пакет доказательств** сохраняется (`store.save_evidence_pack`) до публикации ответа, и ссылки секций
(`EvidenceRef.fragment_id`) перезаписываются в составной `evidence_id` (`encode_evidence_id`:
`request_id:pack_id:item_id`) — без этого `GET .../evidence/{id}` не находил бы то, что показал ответ. Элемент
пакета дополнительно несёт `source_title`/`source_type`/`source_date` (из записи источника корпуса, если она
есть) — только в этом внутреннем формате GET-ответа, не в самом контракте `JobResponse`.

**`Capabilities` (ответ `GET capabilities`)** — что доступно именно этому вызывающему прямо сейчас:
`reference_available` (корпус и состояние открыты), `llm_available` (LLM-роль подключена, не остановлена, есть
ключ, политика экспорта не `"none"`, и — для преподавателя — `ANALYTICS_TEACHER_PAYER` непусто),
`data_bridge_available` (служба данных подключена и у её роли нет ошибки настройки — независимо от того, есть
ли хоть одна согласованная связь оборудования), `review_authority` (у `identity` есть действующее полномочие
согласования **или** `identity.role == "student"` при `ANALYTICS_REVIEWERS == "all_students"`),
`corpus_version` (строка, `"unavailable"` в JSON-ответе, если корпус не открыт).

## Состояние диалогов и заданий (`analytics/store.py`)

Собственный файл SQLite — `ANALYTICS_STATE_PATH`, отдельный от `core.db`. Соединение — на каждую операцию
(явные транзакции `BEGIN IMMEDIATE … COMMIT`); незавершённая транзакция откатывается закрытием соединения.
Версия схемы — `CURRENT_SCHEMA_VERSION = 2` (таблица `analytics_schema`, не `PRAGMA user_version`), с
автоматической миграцией более старой базы при открытии.

| Таблица | Назначение |
|---|---|
| `conversations` | диалог: `id`, `owner_login`, `mode` (`reference`/`deviation_review`), `created_at`, `last_activity_at`, `corpus_version` |
| `requests` | задание: `id`, `conversation_id`, `owner_login`, `client_request_id`, `state`, `stage_label`, `corpus_version`, `request_json`, `preanalysis_json`, `response_json`, `created_at`, `updated_at`; уникальность `(owner_login, conversation_id, client_request_id)` |
| `evidence_packs` | `id`, `request_id`, `created_at` — заголовок неизменяемого пакета доказательств |
| `evidence_items` | `(pack_id, item_id)` первичный ключ, `data_json` — содержимое одного элемента пакета |
| `analytics_heartbeat` | одна служебная строка (`id=1`) с временем последнего `ping()` |
| `analytics_schema` | одна строка (`id=1`) с номером версии схемы |

Владелец диалога — логин человека (`RequestIdentity.login`), не рабочее место: смена закреплённого места не
передаёт историю. Уникальность `(owner_login, conversation_id, client_request_id)` под `INSERT … ON CONFLICT …
DO NOTHING` в транзакции `BEGIN IMMEDIATE` — конкурентный повтор одного клиентского запроса не создаёт второе
задание и не списывает второй раз; первый вызов получает `created=True`, прочие читают уже вставленную строку с
тем же `request_id`.

`StoreError` — отказ по правилам (например «диалог не найден/чужой» в `create_request`, один и тот же текст для
обеих причин — чужой `id` не подтверждает существование ресурса). `StoreUnavailable` (подкласс) — настоящий сбой
самого SQLite (нет места, только чтение, заблокировано, файл повреждён) — отличим от `StoreError` по типу, не по
тексту; вызывающий (`gateway/analytics_api.py`) отображает его в 503 «временно недоступна», не в 404/500.

Ключевые методы `AnalyticsStore` (помимо очевидных CRUD): `publish_response` атомарно сохраняет итоговый
`JobResponse` и переводит задание в терминальную стадию, отказывая (`False`), если задание уже отменено или
ответ уже опубликован другим путём — конкурентная отмена не теряет и не повторяет оплату. `cancel_request`
возвращает `(cancelled, stage_before)` из одной транзакции — решение «прерывать ли фоновую задачу» опирается на
стадию из того же снимка, не на отдельное более раннее чтение. `evidence_pack_owner(pack_id) -> request_id |
None` — вторая проверка цепочки прав GET `.../evidence/{id}` (составной id несёт `request_id`/`pack_id`
раздельно; свой `request_id` с чужим `pack_id` без этой проверки проходил бы). `reap_unfinished_after_restart`
переводит все нетерминальные без опубликованного ответа задания в `failed` одной транзакцией при старте
процесса. `sweep_retention(now, *, history_days, evidence_days)` удаляет диалоги/задания старше
`ANALYTICS_HISTORY_RETENTION_DAYS` и пакеты доказательств старше `ANALYTICS_EVIDENCE_RETENTION_DAYS`.

## Назначенное согласование (`analytics/reviews.py`)

Роль `teacher` сама по себе не даёт права утверждать технологические нормы, связи оборудования с историаном или
местные сокращения — право это явно назначенное **полномочие** (логин + область `scope`, например «вся
подсистема» или конкретный узел/процесс + виды решений), и его может получить любая действующая учётка
технолога без смены роли. `ReviewStore` живёт на том же файле `ANALYTICS_STATE_PATH`, в своих таблицах, и
открывается независимо от `store.py` (деградирует отдельно).

**Таблицы:**

| Таблица | Назначение |
|---|---|
| `review_authority_grants` | `login`, `scope`, `decision_types` (через запятую), `granted_by`, `granted_at`, `revoked_at`, `valid_until` (срок, `NULL` — без ограничения) |
| `review_requests` | заявка: `kind`, `subject_id`, `old_value`/`new_value`, `scope`, `period_start`/`period_end`, `rationale`, `status` (текущий снимок), `created_by`, `decided_by`/`decided_at`/`comment`, `decided_by_role` |
| `review_decisions` | неурезаемый журнал: каждое успешное решение по заявке отдельной строкой (`request_id`, `decision`, `decided_by`, `decided_at`, `comment`) |

`ReviewKind` — `local_claim`, `equipment_link`, `local_norm`, `conflict`. `ReviewDecision`/`ReviewStatus` —
`accepted`/`rejected`/`info_requested` (плюс `pending` у статуса); `info_requested` **не** терминален — заявку
в этом статусе можно решить позже тем же или новым запросом сведений; терминальны только `accepted`/`rejected`
(повторное решение такой заявки — отказ, «нет переголосования без отдельного отзыва»). Для `local_claim`/
`local_norm` окончательное **принятие** не может вынести логин, который уже вынес хоть одно решение по этой же
заявке ранее — нужен второй независимый держатель права; для `equipment_link`/`conflict` одного правообладателя
достаточно.

**Отзыв/истечение полномочия действует «здесь и сейчас».** `revoke_authority` и истечение `valid_until`
обесценивают **применение** уже принятых решений немедленно (следующее обращение к `resolved_link`/
`approved_claim` видит держателя как постороннего), не переписывая сами строки заявок/журнала — история
остаётся видимой как решённая, с отдельной пометкой при показе.

**Режим `ANALYTICS_REVIEWERS`:**

| Значение | Поведение |
|---|---|
| `grants` (умолчание) | право решать заявку — только по явному назначению; создать заявку может любой вошедший технолог/преподаватель без права, решить — только держатель полномочия на эту область/вид, и не автор самой заявки |
| `all_students` | любой вошедший `student` (не `teacher`) видит ВСЕ заявки области и решает любую — любого вида, включая свою собственную, в одно действие, без второго согласующего и без запрета автору; `teacher` остаётся исключением — решает только по действующему полномочию, как в `grants` |

Переключение `all_students → grants` обесценивает для **нового** применения решения, принятые студентом без
назначенного полномочия (поле `decided_by_role`, записанное в момент решения), но не переписывает журнал —
заявка остаётся решённой, видна в истории.

**Операторские команды** (внутри контейнера `core`, без веб-маршрута — назначение/отзыв права через веб
отсутствует и не планируется):

```sh
docker compose exec core python -m pcbk_core.analytics.reviews bootstrap \
    --login <логин> --scope KDM1_PCBK --types local_claim,equipment_link,local_norm,conflict --by <логин-назначающего> \
    [--until ГГГГ-ММ-ДД[ЧЧ:ММ]]
docker compose exec core python -m pcbk_core.analytics.reviews grant \
    --login <логин> --scope <область> --types <виды> --by <логин-держателя-права> [--until ...]
docker compose exec core python -m pcbk_core.analytics.reviews revoke --login <логин> --scope <область> --by <логин-оператора>
docker compose exec core python -m pcbk_core.analytics.reviews list [--login <логин>]
```

`bootstrap` — единственный способ завести самое первое полномочие на полностью пустом хранилище
(`grant_authority` без исключения для пустого хранилища отказывает всем, включая операторскую личность CLI —
первое назначение только через `bootstrap`). `grant` работает, только если у `--by` уже есть действующее
полномочие (любого вида) в той же области. `list` печатает логин/область/виды/кем назначено/когда/до какого
срока/статус текстом («действует»/«истекло»/«отозвано»). `--db` — путь к файлу состояния, по умолчанию —
`ANALYTICS_STATE_PATH` из настроек процесса; команды, как и `ingestion/*`, не используют сеть.

`ReviewStoreError` — отказ по правилам («заявка не найдена», в т.ч. когда у вызывающего нет видимости заявки —
тот же ответ, что у несуществующего `id`, чтобы не раскрывать посторонним факт существования заявки);
`ReviewStoreUnavailable` (подкласс) — настоящий сбой SQLite, 503, отличимый от 404 по типу исключения.

## JSON-контракты (`analytics/contracts/*.schema.json`)

Четыре закрытых контракта (`additionalProperties: false`/pydantic `extra="forbid"` — лишнее поле отказ, не
тихий отброс), зеркало `models.py` (`CONTRACT_SCHEMAS`); тест `test_analytics_contracts.py` держит модели и
схемы синхронными на фикстурах.

**`analysis-request.schema.json`** (`AnalysisRequest`, вопрос технолога, клиент → сервер):

| Поле | Тип | Предел |
|---|---|---|
| `client_request_id` | строка | 1–80 |
| `question` | строка | 1–6000 |
| `mode` | `reference` \| `deviation_review` | — |
| `context.process_id` | строка или `null` | 1–80 |
| `context.period.start`/`.end` | дата-время (со смещением) | — |
| `context.unit_hint` | строка или `null` | 1–40 |

Личность, область, модель, пакет и права клиент не передаёт — их добавляет сервер из серверной сессии.

**`preanalysis.schema.json`** (`Preanalysis`, единственный достоверный результат координатора): `scope` —
константа `KDM1_PCBK`; `intent` (`definition`/`lookup`/`calculation`/`deviation`/`control`/`out_of_scope`);
`decision` (`ready`/`needs_clarification`/`limited_answer`/`refused`); `resolved_terms` (до 40, каждый — `original`,
до 10 `candidate_ids`, `selected_id`, `requires_confirmation`); `process_ids`/`conflict_ids`/`missing_fields`
(до 32 каждый); `risk` (`reference`/`calculation`/`local_claim`/`control`); `corpus_version`; `evidence_pack_id`;
`allowed_claim_ids` (до 48); `allowed_mechanism_ids` (до 12); `data_access_ready`; `llm_export_policy`.

**`llm-selection.schema.json`** (`LlmSelection`, единственный вид ответа модели): `reference_claim_ids` (до 20),
`mechanism_ids` (до 6), `clarification_keys` (до 9, из девяти фиксированных значений), `calculation_ids` (до 4,
из четырёх `CalculationId`) — все четыре списка без повторов. Схема запроса к модели дополнительно сужает
`enum`/`maxItems` под конкретный разрешённый пакет (см. раздел про `llm_adapter.py`).

**`job-response.schema.json`** (`JobResponse`, единственный публичный результат): `request_id`/`conversation_id`
(1–100); `state` (десять значений `JobState`); `corpus_version`; `stage_label` (1–120); `sections` (до 24,
каждая — `kind` из семи `SectionKind`, `text` 1–4000, `evidence_refs` до 12 с локатором `pdf_page`/`xlsx_cell`/
`image_label`/`public_section`, `rendered_by` всегда `"server"`, `claim_id`); `clarification_keys` (до 12);
`error_code` (`unavailable`/`invalid_input`/`policy_refused`/`source_conflict`/`validation_failed`/
`interrupted`/`busy` или `null`). До завершения проверки `sections` пуст; сырые ответы модели, системный промпт
и рассуждения сюда не попадают ни при каком состоянии.

## API шлюза (`gateway/analytics_api.py`)

`analytics_router(role)` подключается в `GatewayRole.router()` только при `role.analytics_enabled`
(`ANALYTICS_ENABLED`) — выключена целиком, маршрутов нет вовсе (404, как у несуществующего пути), не 503: само
существование подсистемы не видно по коду ответа выключенным клиентам. Включена, но `role.analytics is None`
(сервис не подключён) — все ручки отвечают заглушкой 503 «Аналитика КДМ-1 ещё не готова». Порядок проверок у
всех ручек — зона (`front_only`) → ошибка настройки (`configured(role)`) → сессия (`current_account`, любая
вошедшая учётка, без сужения по месту) → у изменяющих состояние (`POST`) — дополнительно проверка источника
записи (`origin_checked`) после сессии.

| Путь | Метод | Доступ | Что делает |
|---|---|---|---|
| `/pcbk/api/analytics/capabilities` | GET | сессия | что доступно именно этому вызывающему (`Capabilities`) |
| `/pcbk/api/analytics/conversations` | GET | сессия | список своих диалогов |
| `/pcbk/api/analytics/conversations` | POST | сессия + источник | создать диалог (`{"mode": …}` → `{"id": …}`, 201) |
| `/pcbk/api/analytics/conversations/{id}` | GET | сессия, владелец | диалог + история заданий `{"question","response"}` |
| `/pcbk/api/analytics/conversations/{id}/questions` | POST | сессия + источник | отправить вопрос (`AnalysisRequest` → `{"request_id": …}`, 202) |
| `/pcbk/api/analytics/requests/{id}` | GET | сессия, владелец | текущая стадия/результат задания (`JobResponse`) |
| `/pcbk/api/analytics/requests/{id}/cancel` | POST | сессия + источник, владелец | отменить незавершённое задание, отдаёт `JobResponse` |
| `/pcbk/api/analytics/evidence/{id}` | GET | сессия, владелец цепочки | один элемент пакета доказательств |
| `/pcbk/api/analytics/reviews/requests` | GET | сессия | заявки, видимые вызывающему |
| `/pcbk/api/analytics/reviews/requests` | POST | сессия + источник | создать заявку согласования |
| `/pcbk/api/analytics/reviews/requests/{id}/decisions` | POST | сессия + источник | решить заявку |
| `/pcbk/api/analytics/links` | GET | сессия | состояние строк `equipment_links` текущего корпуса (`unbound`/`pending`/`linked`) |
| `/pcbk/api/analytics/links/{id}/candidates` | GET | сессия | справочный поиск кандидатов тега по подписи оборудования |

Коды ответа различают причину по **типу** исключения, не по тексту: 401 без строки журнала — нет учётки; 403 —
учётка без рабочего места/без права/автор решает свою заявку; 404 — чужой/несуществующий ресурс (в т.ч. «заявка
не найдена» для постороннего без видимости — тот же ответ, что у несуществующего `id`); 409 — заявка уже решена;
503 — четыре разных случая, отличимых по тексту и по тому, какую проверку они проходят: подсистема не готова
(роутер подключён, но `role.analytics is None`); состояние/корпус не открылись вовсе (`config_error`/
`corpus_error`); только согласование не открылось при старте (`reviews_error` — отдельный сбой, не блокирует и
не блокируется основным состоянием, проверяется лишь на `reviews/*`/`links/*`); и настоящий временный сбой уже
открытого хранилища на конкретной операции (`StoreUnavailable`/`ReviewStoreUnavailable`). Чтение уже
существующей истории не требует живого корпуса (старые ответы не исчезают из-за временной порчи корпуса) —
только создание диалога/вопроса.

Формы JSON-ответов — зеркало `web/src/analytics.ts`/`analyticsApi.ts` (строгий разбор на клиенте, `hasExactKeys`)
там, где нет отдельной JSON-схемы (`capabilities`/`conversations`/`evidence`/`reviews`/`links`); схемой описаны
только четыре публичных контракта выше. Отступать от этих форм без правки веба нельзя — даже если сам веб
сейчас не вызывает эти маршруты (см. «Состояние в текущей сборке»), код разбора на клиенте жив и совпадает с
тем, что отдаёт сервер.

## Переносимость: что специфично для КДМ-1/ПЦБК и как подготовить корпус другого участка

**Переносимо как есть** (общий механизм, не завязан на конкретное предприятие): весь координатор запроса
(`service.py`), контракты (`models.py`/`contracts/*.json`), хранение состояния и пакетов доказательств
(`store.py`), назначенное согласование (`reviews.py`), проверка выбора модели (`validator.py`), серверное
отображение (`rendering.py`), адаптер LLM (`llm_adapter.py`), связь со службой данных (`data_bridge.py`), карантин
и управление версиями корпуса (`ingestion/`), сама схема SQLite корпуса (`knowledge.py`: таблицы
`sources/fragments/processes/terms/claims/conflicts/equipment_links/mechanisms`, `seed_meta`, `kb_search`).
Четыре расчётные формулы (`calculations.py`) — физика общего вида (расход/плотность/доля сухого вещества,
масса 1 м², геометрическая оценка производительности, объединение интервалов простоя), применимая на любой
бумагоделательной/аналогичной машине с теми же величинами; для другого типа производства формулы нужно заменить
или дополнить (см. [21-extending.md](21-extending.md)).

**Специфично для КДМ-1/текущего корпуса:**

- Константа области `"KDM1_PCBK"` — литерал в контракте (`Preanalysis.scope`), в проверке манифеста
  (`knowledge._SCOPE_PREFIX`), в проверке `machine_scope` строк корпуса (`retrieval._MACHINE = "KDM1"`,
  `versions.py` проверяет префикс `KDM1`) и в примерах CLI/README. Перенос на другой участок/предприятие требует
  либо переименовать область по всему коду и корпусу (строка одна и та же везде, замена механическая, но
  затрагивает несколько модулей), либо держать её как внутреннее имя нового участка — сама схема данных от
  конкретного значения не зависит.
- Код «своей» машины в тексте вопроса (`preanalysis._IN_SCOPE_MACHINE_CODE = "кдм"`,
  `_IN_SCOPE_MACHINE_NUMBER = "1"`) и регулярка кодов других машин участка (`_MACHINE_CODE_RE`, формат
  «буквы+номер», например условные коды соседних агрегатов) — под конкретную номенклатуру оборудования
  предприятия; для другого участка нужно заменить оба значения и, при другом стиле кодов оборудования
  (не «буквы+номер»), саму регулярку.
- Содержимое корпуса (`knowledge/*.jsonl` пакета заказчика, собираемое внешним `tools/import_seed.py`) —
  полностью специфично: подписи оборудования и узлов, тексты карточек/механизмов, термины и их синонимы,
  связи согласования. Код аналитики **не хранит и не публикует** ни одной настоящей подписи тега предприятия —
  во всех примерах/тестах используется заведомо вымышленный вид (`20FAKE_001_PV`, `20FAKE_QT31`,
  `CLAIM-FAKE-003`, `MECH-FAKE-001`).
- Единицы измерения и формат процентных/базовых обозначений в `preanalysis._UNIT_TOKENS` и регулярках
  `calculations.py` — набор, собранный по реально встречающимся в документах участка величинам (кН/м, т/ч,
  г/м² и т.п.); для другого технологического процесса список нужно расширить/заменить под его единицы.
- Импортёр корпуса (`tools/import_seed.py`) — внешний инструмент пакета заказчика, в репозиторий не входит;
  `ingestion/versions.py` запускает его субпроцессом по интерфейсу `--knowledge DIR --output FILE`, так что для
  другого участка нужен свой импортёр с тем же интерфейсом командной строки (или адаптер к нему), выдающий файл
  SQLite той же схемы.
- Операторские значения в `.env`/CLI (конкретные логины, назначенные области и срок полномочий, выбранные
  модели LLM, значение `ANALYTICS_REVIEWERS`/`ANALYTICS_LLM_EXPORT_POLICY`) — настройки конкретной выкладки, не
  код; меняются без изменения кода.
- `validator.RESTRICTED_SOURCE_IDS` — жёстко заданные `id` двух источников текущего корпуса (страницы
  правообладателя стандартов, которые не передаются LLM и не отображаются без отдельного основания). Это
  единственный литерал модуля, завязанный на содержимое именно этого корпуса, а не только на его схему — при
  переносе на другой корпус нужно пересмотреть сам список (пустой список, если таких источников у нового участка
  нет, или новые `id` по тому же принципу).

**Как подготовить корпус для другого участка (минимальный путь):**
1. Собрать знания участка в том же построчном JSON-формате, что ждёт существующий импортёр (или написать свой
   импортёр с тем же интерфейсом командной строки), с собственной областью (`scope`) вместо `KDM1_PCBK`.
2. Если область переименована — поменять соответствующие литералы в `knowledge.py`/`retrieval.py`/
   `versions.py` (или держать новое имя области как уже принятое заказчиком, если `KDM1_PCBK` остаётся
   внутренним именем системы, а участок — её частью).
3. Поставить файлы в карантин (`ingestion quarantine`), собрать версию (`ingestion build`) и перепроверить
   отчёт сборки.
4. Опубликовать версию (`ingestion publish --approved-by …`).
5. Для синтетической проверки без настоящих данных — использовать схему тестовой фикстуры
   `core/tests/fixtures/kdm1_corpus.py` (та же структура таблиц, вымышленные подписи `20FAKE_*`) как образец,
   на котором уже проверены `knowledge.py`/`retrieval.py`/`terms.py`.

## Как проверить, что подсистема работает

- **Модульные тесты** — `core/tests/test_analytics_*.py` (по одному файлу на модуль: `contracts`, `knowledge`,
  `terms`, `retrieval`, `preanalysis`, `calculations`, `data_bridge`, `llm`, `validator`, `rendering`, `store`,
  `reviews`, `service`, `settings`, `ingestion`, `protected`) и `core/tests/test_gw_analytics_api.py` (маршруты
  шлюза — выключенная аналитика отвечает 404 везде, старые маршруты живы; включённая без подключённого сервиса —
  503-заглушки; с подключённым сервисом — полный путь справки без LLM через настоящий HTTP). Веб-сторона —
  `web/tests/analytics.test.ts`/`AnalyticsPage.test.tsx`/`AnalyticsLinks.test.tsx`/`AnalyticsReviews.test.tsx`
  (строгий разбор `JobResponse` и форм на стороне клиента). Про запуск тестов — [19-tests-and-bench.md](19-tests-and-bench.md).
- **Отчёт покрытия корпуса без веба и без LLM** — внутри контейнера: `knowledge.corpus_report(handle)` (число
  записей по каждой таблице и `kb_search`, без текста фрагментов) можно получить, открыв корпус тем же способом,
  что `ingestion list --corpus-dir <каталог>` — список версий уже включает число записей рабочей версии.
- **Через HTTP** (после включения `ANALYTICS_ENABLED` и входа в систему вошедшей учёткой): `GET
  /pcbk/api/analytics/capabilities` — `reference_available: true` подтверждает, что корпус и состояние открыты;
  `POST /pcbk/api/analytics/conversations` → `POST .../questions` → поллинг `GET
  /pcbk/api/analytics/requests/{id}` до терминальной стадии — сквозная проверка пути без LLM (если LLM-роль не
  настроена или политика экспорта `"none"`, ответ строится детерминированным путём, карточки пакета — ровно те,
  что нашёл преданализ).
- **Журнал `core`** — строки вида «аналитика КДМ-1: …» на каждый сбой открытия/переоткрытия корпуса, обрыв
  заданий после перезапуска, применение сроков хранения и смену версии корпуса без перезапуска процесса.
