# Служба данных (роль `data`)

Роль `data` (класс `DataRole`, пакет `core/pcbk_core/data/`) — единственная точка доступа к историану БДРВ в
репозитории. Она живёт не отдельным контейнером, а внутри одного процесса `core` (FastAPI-приложение,
`core/pcbk_core/app.py:create_app`) рядом с ролями LLM-прокси, шлюза и поправок базы знаний — все они делят один
`uvicorn` на порту `CORE_PORT` и одну базу SQLite `core.db`. Роль отдаёт:

- каталог тегов историана и поиск по нему;
- текущие значения, сводки за период, равномерный ряд и производные расчёты по тегам из белого списка участка;
- журнал каждого вызова (`agent_events`) и учёт собственных агентов студентов (`save_agent`, `my_agents`,
  `report_event`);
- ручку здоровья `/health/historian`.

Интерфейсы наружу — два: **MCP** (`/mcp`, инструменты для модели) и **HTTP** (`/api/data/*`, те же шесть
инструментов чтения для вкладки «Калькуляторы» веб-чата). У обоих общая реализация — `DataService` в
`core/pcbk_core/data/service.py`; MCP и HTTP — тонкие обёртки над ней (`mcp_server.py`, `http_api.py`).

**Перенос на другое предприятие.** Модуль переносим почти целиком: протокол MCP/HTTP, кэш, ворота, бюджет,
журнал событий и калькуляторы не знают, что речь о КДМ-1. Специфика заказчика — две вещи: (1) правило построения
белого списка тегов (`build_whitelist.py`: участок «20…25», служебные и состояние-хвосты) и (2) сетка смен
08:00–20:00 / 20:00–08:00 (`periods.py`). Чтобы перенести роль на другое предприятие или другой историан —
см. [21-extending.md](21-extending.md); здесь — только как это работает сейчас.

## 1. Подключение к историану

Драйвер — `python-tds` (`pytds`), диалект — Microsoft SQL Server через провайдер исторических данных
(архитектура Wonderware/AVEVA Historian: представления `Live`, `AnalogHistory`, `AnalogSummaryHistory`,
`StateSummaryHistory`, базовые таблицы `Tag`, `AnalogTag`, `EngineeringUnit` — см. `core/pcbk_core/data/sql.py`,
`PROVIDER_VIEWS`).

Учётные данные — только файлом, не переменной окружения: `core/pcbk_core/secrets.py:BdrvConfig.from_env_file`.
Файл — пары `KEY=VALUE` (как для `set -a; . файл`), путь — `Settings.BDRV_ENV_FILE`.

| Ключ файла | Обязателен | Умолчание | Смысл |
|---|---|---|---|
| `BDRV_HOST` | да | — | хост или `хост\ИМЯ_ЭКЗЕМПЛЯРА` (с обратным слэшем — порт ищет `pytds` через SQL Browser) |
| `BDRV_USER` | да | — | учётная запись SQL Server |
| `BDRV_PW` | да | — | пароль |
| `BDRV_PORT` | нет | `1433`, если в `BDRV_HOST` нет `\` | порт TCP; должен быть `0 < port < 65536` |
| `BDRV_DB` | нет | `Runtime` | имя базы историана |

Файл не читается или без `BDRV_HOST`/`BDRV_USER`/`BDRV_PW` → роль поднимается с `config_error`: фоновые циклы
(каталог, свежесть) не запускаются, ни один вызов не дойдёт до историана, `/health/historian` и остальные ручки
данных отвечают `unavailable`/503 с текстом причины (`core/pcbk_core/data/__init__.py`, `CONFIG_ERRORS`).

Соединение (`core/pcbk_core/data/historian.py:tds_query`) — одно на вызов ворот: вход → пролог
`SET LOCK_TIMEOUT 5000; SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;` → инструкции по одной → закрытие.
Автокоммит включён, повтор входа драйвером выключен (`disable_connect_retry=True`). Таймауты:

| Таймаут | Значение | Что ограничивает |
|---|---|---|
| `LOGIN_TIMEOUT_S` | 10 с | вход в SQL Server, не дольше остатка срока вызова |
| `READ_TIMEOUT_S` | 45 с | чтение каждой инструкции (сокет перенастраивается перед каждой `execute`), тоже не дольше остатка |
| `APPNAME` | `"pcbk-core"` | имя приложения в соединении (видно в DMV SQL Server) |

Ошибка классифицируется в один из четырёх кодов (`HistorianError.code`): `connect` (нет связи, в т. ч. таймаут
входа и ответ SQL Browser «нет такого экземпляра» — вход не начинался), `auth` (SQL Server отверг учётные
данные: номера сообщений `18452, 18456, 18486, 18487, 18488`; `4060` «база недоступна» приходит вместе с
`18456`), `timeout` (истёк срок чтения), `query` (прочая ошибка `pytds` при чтении). Текст ошибки SQL Server
(бывает с именем учётной записи и началом SQL) остаётся только в `HistorianError.detail` внутри процесса — в
журнал, события и ответы наружу идёт `HistorianError.public()`: код, класс исключения, номер сообщения.

### Часы историана

`HistClock` (`historian.py`) — одна строка `SELECT GETDATE() AS NowLocal, GETUTCDATE() AS NowUtc`
(`clock_sql()`). Смещение пояса — `(local − utc)`, округлённое до 15 минут (`OFFSET_STEP_S`); смещение больше 14
часов — ошибка разбора. Для участка КДМ-1 эта разница на практике равна поясу Пермского времени (UTC+05), но
число не захардкожено — оно читается из историана при каждом обновлении часов, а не хранится в коде.

Часы роли (`DataRole.clock`/`clock_mono`) обновляются при загрузке каталога и опросе свежести; «сейчас
историана» между опросами (`DataService._hist_now`) — последние часы плюс прошедшее по монотонным часам
процесса. Если часы старше `CLOCK_STALE_S` = 300 с, инструмент сам шлёт `[clock_sql()]` перед работой
(`_fresh_clock`, одна попытка на всех ждущих через `single-flight`).

## 2. Проверка свежести

Раз в `FRESH_POLL_S` = 30 с (переменная окружения `FRESH_POLL_S`) фоновый цикл опрашивает `Live` по набору из
`FRESH_TAGS` = 8 самых «свежих» аналоговых тегов белого списка, выбранных при загрузке каталога
(`Catalog.freshest(8)`). Логика — `core/pcbk_core/data/freshness.py:FreshnessTracker`:

- возраст = время с последнего **роста** наибольшей метки набора (по монотонным часам процесса), но не меньше
  возраста самой метки по часам историана на момент последнего опроса — поэтому метка, стоящая впереди часов
  историана, не даёт вечный «возраст 0», а остановленная ещё до старта службы подача видна сразу;
- при ошибке опроса (`connect`/`timeout`/`query`/`auth`/`catalog` — каталог не загружен/`no_tags` — список
  свежести пуст/`no_rows` — строк с меткой нет) прежняя метка и её растущий возраст сохраняются, их тексты —
  `ERROR_TEXTS` (не длиннее 80 знаков — под них рассчитана ручка сторожа);
- режим `freeze_stamps` (переменная `DRILL_FRESHNESS`) замораживает первую наблюдённую метку для учений — историан
  читается как обычно, но «растёт» ли метка решает тест, а не историан; `freeze_poll` останавливает сам опрос
  после первой попытки.

Результат отдаёт `GET /health/historian` — без токена и без проверки сети (контейнер `core` многодомный: у
него есть адрес в сети каждого места, и место достаёт эту ручку напрямую, не через шлюз):  `checked_at`,
`age_s`, `skew_s` (метка впереди часов — отрицательное число), `error`, `error_text`, `tags`, плюс
`catalog_age_s`, `catalog_error`, `gate` (§5), `tools` (§8) и `drill` (значение `DRILL_DATA`, если учение
включено, иначе `null`). Имён тегов в ответе нет — только числа и коды.

## 3. Каталог тегов и белый список

### Белый список

Белый список — список имён тегов в текстовом файле (`Settings.WHITELIST_PATH`, по умолчанию
`/app/data/whitelist.txt`), читает `core/pcbk_core/data/names.py:load_names`. Формат: одно имя в строке,
кодировка `utf-8-sig` (BOM допустим), строки на `#` и пустые — пропускаются, пробелы по краям снимаются, каждое
имя — `SAFE_NAME = [A-Za-z0-9_]{1,128}` (`sql.py`). Загрузка — в `main.py:build_roles`, до создания роли; два
разных исхода неудачи дают разный `/healthz`:

- файла нет (`FileNotFoundError`) — белый список пуст, но **без** `config_error`: фоновые циклы (каталог,
  свежесть) всё равно запускаются и ходят в историан, просто без единого тега в белом списке; `GET /healthz/data`
  отвечает `503` «белый список пуст или не найден» (`DataRole.health` — проверка пустого списка);
- файл есть, но хотя бы одна строка вне `SAFE_NAME` — тоже пустой белый список, но уже **с** `config_error`
  (`CONFIG_ERRORS["whitelist_unreadable"]` = «белый список не читается»): фоновые циклы не запускаются вовсе, как
  и при ошибке `bdrv.env` (§1); `GET /healthz/data` отвечает `503` с этим текстом — его `DataRole.health`
  проверяет раньше пустого списка, так что при этой причине ответ — не «пуст или не найден».

Ворота в обоих случаях не пускают ни одного тега.

Список не строит сама роль — его готовит отдельный CLI-инструмент
`python -m pcbk_core.data.build_whitelist` (запускается вручную на сервере тем, у кого есть доступ к учётным
данным историана и прежнему списку):

```bash
python -m pcbk_core.data.build_whitelist \
  --out /data/whitelist.txt \
  --extra /data/whitelist.extra \
  [--base /data/prior.txt] \
  [--env-file /run/secrets/bdrv.env]
```

Правило отбора (специфично для участка КДМ-1 — при переносе на другое предприятие меняется целиком):

1. имя — только `SAFE_NAME`;
2. тег в «участке»: без `--base` — имя начинается цифрами `20`…`25` (`SECTION_PREFIX`); с `--base` — имя есть
   в файле прежнего списка;
3. плюс имена из `--extra` (`whitelist.extra`) сверх правила 2;
4. аналоговые теги со служебными хвостами без учёта регистра (`_LMN`, `_TH`, `_HMI`, `_SP_HMI`, `_MV1`, `_m3`
   — `SERVICE_TAILS`) отсекаются;
5. дискретные теги допускаются только с хвостом состояния (`_RUN`, `_OPN`, `_CLS`, `_ON`, `_OFF`, `_STOP`,
   `_FLT`, `_ALM` — `STATE_TAILS`), с учётом регистра;
6. правила 4–5 действуют и на имена из `--extra`/`--base`;
7. «живость» тега (есть ли сейчас значение в `Live`) список не фильтрует;
8. пустой результат файл не перезаписывает (старый список остаётся).

Имени, которого нет в каталоге историана, в список попасть не может (правилам 4–5 неизвестен вид тега).
Инструмент печатает только числа — счётчики по правилам, по служебным хвостам (`по хвостам: _PV N, _SP N, …` —
`REPORT_TAILS`), но ни одного имени тега: он предназначен для запуска владельцем на сервере, а не для просмотра
в журнале. Файл пишется атомарно (временный файл + `os.replace`), права — `0444`.

### Каталог в памяти

`core/pcbk_core/data/catalog.py:Catalog` строится двумя запросами историана: `catalog_sql()` (`Tag` ⋈
`AnalogTag` ⋈ `EngineeringUnit`, типы `1`=аналог/`2`=дискрет — прочие типы отбрасываются) и `live_all_sql()`
(полный снимок `Live WHERE Value IS NOT NULL`). В каталоге — **все** теги историана, не только белого списка:
так различается «тег вне списка» (`unlisted`) от «такого тега вообще нет» (`unknown`). Свойства, поиск и
«похожие имена» отдаются только для тегов белого списка.

`TagInfo`: `name`, `description` (обрезано историаном на 50 знаках — у ответа `tag_period`/`catalog_search`
помечено отдельно), `kind` (`"analog"`/`"discrete"`), `unit` (`None`, если в историане литерал `""`, `"none"`,
`"null"`, `"-"` без учёта регистра), `min_eu`/`max_eu` (шкала прибора, не норматив), `live` (есть строка в
`Live` с непустым значением), `live_time`.

Загружается при старте и дальше раз в `CATALOG_REFRESH_S` = 86400 с (сутки; поле `Settings`, настраивается
переменной окружения `CATALOG_REFRESH_S`, как и прочие поля `Settings` — см. [03-configuration.md](03-configuration.md)),
общий срок двух запросов — `CATALOG_DEADLINE_S` = 60 с (переменная `CATALOG_DEADLINE_S`,
не меньше 10 с: два резерва ворот по 5 с, иначе каталог никогда не загрузится). Неудача оставляет прежний
каталог и увеличивает паузу до следующей попытки экспоненциально: `60 × 2^(неудач-1)` с, не больше 900 с
(`BACKOFF_BASE_S`/`BACKOFF_MAX_S`).

`Catalog.lookup(raw)` разбирает одно имя от вызывающего (пробелы по краям — вон, регистр не важен):

| `status` | Когда | Что в ответе |
|---|---|---|
| `ok` | тег в каталоге и в белом списке | `TagInfo` |
| `unlisted` | тег в каталоге историана, но не в белом списке | ничего, кроме факта |
| `unknown` | тега нет в каталоге историана вообще | до 5 похожих имён белого списка (`similar`) |

«Похожие» — имена белого списка с той же «основой» (имя без последнего хвоста `_ХВОСТ`) или содержащие введённую
строку.

`Catalog.search(query, limit=10)` — все слова запроса (после `norm`: нижний регистр, «ё»→«е», пробелы схлопнуты)
должны входить в `norm(имя + описание)` тега белого списка; порядок — точное совпадение имени, затем имя с
запроса, затем по алфавиту. Нет совпадений → `similar=True`: теги хотя бы с одним словом запроса (по убыванию
числа совпавших слов), плюс теги той же «основы», если запрос похож на имя тега.

`Catalog.equipment(query)` — группировка в «агрегаты» для инструмента `equipment` (см. §8): теги делятся по
«основе» имени (без последнего хвоста); основа с хотя бы одним тегом из `AGGREGATE_TAILS`
(`RUN, LOD, SPD, CUR, OP, OPN, CLS, ON, OFF, STOP, FLT, ALM`) — агрегат; если первое слово запроса стоит в
начале описания хотя бы одного её тега — это `Unit` (считается в `units_total`), иначе — `Mention` (упоминание,
отдельный счётчик, не входит в `units_total`); основа без тега из `AGGREGATE_TAILS` — «точка измерения»,
считается отдельным числом (`measure_points_total`), не агрегат и не упоминание.

## 4. Периоды

`core/pcbk_core/data/periods.py`. Всё время — местное время историана **без пояса** (поле `DateTime` в БДРВ так
и хранится). «Сейчас» всегда округляется вниз до `ROUND_S` = 30 с — так повторные вызовы в одну секунду получают
один и тот же ключ кэша.

| Пресет (`period`) | Границы |
|---|---|
| `last_hour` | `[сейчас − 1 ч, сейчас]` |
| `last_8h` | `[сейчас − 8 ч, сейчас]` |
| `last_24h` | `[сейчас − 24 ч, сейчас]` |
| `today` | `[полночь сегодня, сейчас]` |
| `yesterday` | `[полночь вчера, полночь сегодня]` |
| `last_7d` | `[сейчас − 7 сут, сейчас]` |
| `last_30d` | `[сейчас − 30 сут, сейчас]` |
| `current_shift` | `[начало текущей смены, сейчас]` |
| `prev_shift` | `[начало предыдущей смены, начало текущей смены]` |

Смены КДМ-1 (специфично для заказчика, константа `SHIFT_STARTS = (8, 20)`): дневная **08:00–20:00**, ночная
**20:00–08:00** следующих суток, местное время историана. У `current_shift`/`prev_shift` ответ инструментов
несёт заметку о границах смен (`shift_grid_assumed`/`SHIFT_NOTE`).

Свой период — `start`/`end` строками ISO 8601 вместо `period` (ровно один способ из двух, иначе отказ): строка с
поясом переводится в местное время историана через текущее смещение (`HistClock.offset`), без пояса — читается
как уже местное. Доли секунды отбрасываются. Проверки: начало раньше `2000-01-01` (`EARLIEST`) — отказ; начало
позже текущего «сейчас» — отказ; конец раньше начала — отказ; конец позже «сейчас» — не отказ, а молчаливое
обрезание до «сейчас» (`clamped: true` в ответе); период короче минуты (`MIN_PERIOD`) — отказ.

Период считается «ещё идущим» (`open: true`, заметка «период ещё идёт — числа изменятся»), если его конец не
старше `CLOSED_AFTER_S` = 300 с от «сейчас» — это же правило держит короткий срок кэша открытых периодов (§6).

## 5. Ворота (`gate.py`) — единственная дверь к историану

`HistorianGate` — всё обращение к историану идёт через неё, и только инструкцией, целиком совпавшей с одной из
форм `sql.TEMPLATE_FORMS` (`clock`, `catalog`, `live_all`, `live`, `summary`, `series`, `state`): комментарий,
`NOT`, `OR`, вторая инструкция или имя тега вне белого списка (вне `TagName IN (…)`) форму не пройдут даже с
виду безобидным текстом. Инструментам людей (не фоновым опросам) запрос без единого имени тега (голый снимок
`Live` или каталог) тоже не пройдёт — иначе один вызов мог бы забрать весь каталог тегов.

| Параметр | Значение | Смысл |
|---|---|---|
| `USER_SLOTS` | 2 | одновременных вызовов историана от людей (http/mcp/web) |
| `BACKGROUND_SLOTS` | 1 | одновременных фоновых вызовов (каталог, свежесть) |
| `GLOBAL_LIMIT` / `RATE_WINDOW_S` | 300 вызовов / 300 с | общий предел **только для людей**, после получения места |
| `CALL_DEADLINE_S` | 15 с | срок одного вызова по умолчанию (ждать место + сходить в историан) |
| `Q_MIN_S` | 5 с | места не ждут дольше `срок − min(5, срок/3)` |
| `CONNECT_COOLDOWN_S` | 30 с | после обрыва связи новые попытки сразу получают отказ `connect` |
| `PAUSE_AFTER_TIMEOUTS` / `USER_PAUSE_S` | 3 срока подряд / 60 с | после стольких таймаутов подряд у людей полоса людей встаёт на паузу — новые вызовы сразу `busy`, без места и SQL |

До первого удачного входа после старта процесса пропускается только один вызов за раз (общая с остальной
инфраструктурой учётная запись — повторные параллельные попытки входа с неверным паролем могли бы её
заблокировать); отказ входа по учётным данным (`auth`) защёлкивает ворота закрытыми до перезапуска службы.

Отказ ворот без обращения к историану — `GateRefused`, один из трёх кодов: `rate` (общий предел),
`busy` (не дождались места к сроку, или полоса людей на паузе), `unlisted` (SQL не прошёл форму/белый список).
`stats()` (используется `/health/historian`) отдаёт только числа: `sent_names_total`, `refused_unlisted`,
`in_flight` по полосам, `auth_latched`, `p95_ms` длительности вызовов людей за 5 минут (считается от 5 вызовов,
`P95_MIN_CALLS`), `timeouts_5m`, `busy_5m`, `user_paused` — без единого имени тега.

## 6. Бюджет тего-суток и кэш

### Бюджет (`budget.py`)

Цена запроса — «тего-сутки»: число тегов × длина окна в сутках, причём окно короче часа считается за час
(`min_window`). Пределы (`LIMITS`, применяются в указанном порядке):

| Проверка | Предел | Текст отказа (`status: budget`) |
|---|---|---|
| тегов за вызов | `max_tags` = 16 | «за один вызов — не больше 16 тегов» |
| длина окна | `max_window_days` = 31 сутки | «период длиннее 31 суток» |
| тего-сутки, 1 тег | `single_tag_days` = 31 | у одного тега предел — вся длина окна |
| тего-сутки, 2+ тегов | `max_tag_days` = 24 | «запрос стоит … тего-суток при пределе 24 …» |

Отдельно (после бюджета окна, до SQL) — предел точек ряда (`tag_series`, `calc_deviation`, `calc_spc`,
`calc_flow_total`, `calc_formula`): `тегов × points ≤ max_points` = 288 (`check_points`).

Вызывающий ограничен и по частоте: `PER_CALLER_LIMIT` = 60 вызовов инструментов чтения за `RATE_WINDOW_S` = 300 с
(5 минут) — отдельно от общего предела ворот (300/300 с на всех людей вместе).

### Кэш (`cache.py`)

`TTLCache` в памяти процесса, не больше `MAX_ENTRIES` = 256 записей (при переполнении сначала уходят протухшие,
затем — четверть записей с самым близким сроком). Ключ — `sha256` от инструмента, отсортированных имён тегов,
границ периода и доп. параметра (число точек — у `tag_series`, `calc_spc`, `calc_flow_total` и `calc_formula`, а
также у `calc_deviation`: он читает оба тега одним рядом тем же путём, что `tag_series`, и делит с ним кэш,
бюджет и срок записи под именем инструмента `"tag_series"`).

| Инструмент | Срок записи |
|---|---|
| `tag_now` | `TTL_NOW_S` = 15 с |
| любой за период, пока он ещё идёт (`is_open`) | `TTL_OPEN_S` = 30 с |
| любой за период, уже закрытый | `TTL_CLOSED_S` = 3600 с (1 час) |

`SingleFlight` — одинаковые вызовы «в полёте» делят один результат историана (ключ тот же, что у кэша): второй
и далее вызывающие не шлют повторный SQL, получают тот же снимок (`cache: "shared"` в ответе и событии, вместо
`"miss"` у ведущего и `"hit"` у попадания в кэш). Отказы и ошибки в кэш не кладутся.

## 7. Аутентификация вызывающих

Токены — заголовком `Authorization: Bearer <токен>`, сверка — в `core/pcbk_core/secrets.py:TokenTable` по файлу
`Settings.TOKENS_FILE` (по умолчанию `/run/secrets/core-tokens`): строки «`<id> <sha256 hex токена>`», сам токен
служба никогда не хранит и не пишет в журнал. Сверка — `hmac.compare_digest` по всем строкам без раннего выхода.
Пустая или нечитаемая таблица — у **всех** вызовов `401` (закрыто при сомнении); это не `config_error` —
фоновые циклы (каталог, свежесть) продолжают идти.

Таблица общая у `core` и gateway: в неё входят идентификаторы `student-01`…`student-11` (места) и, при желании
развёртывания, любые другие (например, `ops` или собственный id для внешнего клиента — см. §13).

**Сетевое ограничение (`core/pcbk_core/zones.py:caller_net_ok`)** действует только на id вида `student-NN`: такой
токен принимается лишь из сети самого места `{STU_NET}.N.0/28` (по умолчанию `STU_NET` = `172.31`) или из
административных сетей процесса (`127.0.0.0/8`, `::1/128`, две `/28`-сети контейнера `core`, см.
[20-security.md](20-security.md)); из чужой сети — тот же ответ, что без токена (`401`, без события в журнале).
Id, **не** начинающийся с `student-` (например, `ops` или имя, которое вы завели для своего MCP-клиента), этому
ограничению не подчиняется — он принимается из любой сети, лишь бы токен совпал. Это важно для §13: чтобы
подключить собственный MCP-клиент без привязки к сети конкретного места, заводите токену id без префикса
`student-`.

| Транспорт | Проверка |
|---|---|
| HTTP `/api/data/*` | каждый маршрут сам зовёт `authorize(request)`; нет/чужой токен → `401 {"detail": "нужен токен"}`, заголовок `WWW-Authenticate: Bearer`, без события |
| MCP `/mcp` | токен проверяется **до** транспорта MCP (`mcp_auth`, чистое ASGI-звено): не `POST` → `405`; нет/чужой/не из той сети токен → `401`, без события. Внутри инструмента вызывающего берёт тот же заголовок (`_caller`) |

## 8. MCP — инструменты службы данных

Сервер MCP — `mcp 1.30.0` (`FastMCP`), **Streamable HTTP без сессий** (`stateless_http=True`), ответ — JSON
(`json_response=True`), точный путь — **`/mcp`** (без хвостового `/`, без `Mount("/")`). Клиент — любой MCP-клиент
через `remote`/Streamable HTTP; защита от DNS rebinding выключена намеренно (токен — заголовок `Bearer`, не
cookie: страница браузера его не подставит и не узнает).

Модель видит инструменты с префиксом, который ставит сам MCP-клиент по ключу сервера в своей конфигурации
(в этом репозитории — ключ `"pcbk"`, поэтому имя у модели — `pcbk_<имя_инструмента>`, например `pcbk_tag_now`);
в самом MCP-сервере (`mcp_server.py`, `@mcp.tool(name=...)`) имена — без префикса.

Порядок разбора у каждого инструмента (общий, до его собственного тела): **токен → ошибка настройки
(`config_error` — ответ `unavailable`, историан не трогается) → аргументы (модель `pydantic`, ошибка —
`refused` с русской причиной через `refuse_args`, без обращения к историану) → тело инструмента**. У инструментов
чтения внутри тела ещё: **частота вызывающего (60/300 с) → учение `DRILL_DATA=tool_error`, если включено
(`error`, SQL не уходит) → каталог загружен → …**

Общие статусы ответа (`status`), одинаковые у всех инструментов чтения:

| `status` | Когда |
|---|---|
| `ok` | все запрошенные теги дали данные |
| `partial` | часть тегов дала данные, часть — нет (`no_value`/`no_data`/`unlisted`/`unknown`/…) |
| `refused` | неверные аргументы, ни одного годного тега, превышение частоты вызывающего (`message` — текст отказа) |
| `budget` | превышен бюджет тего-суток или точек ряда (ответ несёт пересчитанный `period` и `cost_tag_days`) |
| `unavailable` | роль с ошибкой настройки, каталог не загружен, нет связи/вход отклонён историаном, историан занят (`busy`), срок вызова истёк (`timeout`) |
| `error` | непредвиденный сбой службы, учение `DRILL_DATA=tool_error`, SQL вернул ошибку (`query`) |

### По инструменту

**`catalog_search`** — поиск по словам в имени и описании тега белого списка (`Catalog.search`, §3). Ответ:
`matches` (до `limit`: `tag`, `description`, `unit`, `kind`, `min_eu`, `max_eu`, `live`,
`description_truncated`), `similar` (точного совпадения не было — показаны похожие), `total` (сколько всего
найдено). Заметка `TRUNCATED_NOTE`, если хоть одно описание обрезано на 50 знаках.

**`tag_now`** — текущее значение `Live` по именам (до 16). Источник — `SOURCE_LIVE`. Элемент ответа (`items[]`):
`tag`, `status` (`ok`/`no_value` — нет текущего значения/`unlisted`/`unknown`), `description`, `unit`, `kind`,
`value`, `time` (ISO с поясом историана), `age_s`, `quality` («хорошее» или «недостоверное (код N)»),
`state_label` (у дискретных — подпись по хвосту имени, например «работает (по суффиксу)» у `_RUN`),
`item_notes` (метка впереди часов историана больше `AHEAD_NOTE_S` = 60 с; значение не менялось дольше
`STILL_NOTE_S` = 600 с — возможное залипание). Ответ несёт общее `asof`/`tz` — момент снятия снимка, не на каждый тег отдельно.

**`tag_period`** — сводка `AnalogSummaryHistory` одной корзиной на весь период: `avg`, `min`, `max`, `range`
(`max-min`), `std`, `percent_good`. Источник — `SOURCE_SUMMARY`. Вид среднего и σ (взвешено по времени или
арифметическое) — в ответе `avg_kind`/`std_kind`; дискретные теги в сводку не идут (`status: "discrete"`, «ряд
наработки даёт `calc_runtime`»). Заметка `quality_note`, если доля достоверных значений ниже 99 %.

**`tag_series`** — равномерный ряд `AnalogHistory` (режим `Cyclic`) на `points` точек на тег (до 4 тегов, до
96 точек каждый) плюс профиль (`first`/`last`/`change`/`min`/`max` с моментами). Источник — `SOURCE_SERIES`,
заметка `GRID_NOTE`: «всплески короче шага не видны — истинные минимум/максимум/среднее даёт `tag_period`».
Дискретные теги — `status: "discrete"` (как у `tag_period`), но с другим текстом: `ITEM_TEXTS["discrete_series"]`
— «тег состояния: ряд не строится — наработку даёт `calc_runtime`».

**`calc_runtime`** — наработка `StateSummaryHistory` по тегам состояний: часы, доля периода и число переходов в
каждом состоянии (`states[]`), `covered_percent` (сумма долей состояний с известным значением; заметка
`coverage_note`, если меньше 99 %). Аналоговые теги — `status: "analog"` (`ITEM_TEXTS["analog"]`: «аналоговый тег:
наработка считается только по тегам состояний — сводку даёт `tag_period`»).

**`calc_deviation`** — контрольная точка «измерение (`_PV`/`_MV`) против задания (`_SP`)»: читает оба тега
**одним** рядом (`tag_series`), по совпадающим меткам считает `|измерение − задание|`, сравнивает с `threshold`
(порог технолога — аргумент вызова, **не** норматив). Ответ: `max_abs_dev`, `mean_abs_dev`, `over_count`
(точек строго сверх порога), `intervals[]` (подряд идущие точки сверх порога: `start`, `end`, `points`,
`max_abs_dev`, `at`/`value`/`setpoint` точки с наибольшим отклонением). Математика — расчёт самой службы, не
модели; подробности формул — [11-calculations.md](11-calculations.md).

**`calc_spc`** — карта Шухарта по одному аналоговому тегу (`pcbk_core.spc`, не модель): `subgroup=1` — карта
индивидуальных значений (I-MR), `2..10` — карта средних подгрупп (X̄-R). Ответ: `cl`/`ucl`/`lcl`,
`sigma_within`/`sigma_overall`, `violations[]` (интервалы нарушений 8 правил Нельсона), `rule_counts`,
`capability` (Cp/Cpk/Pp/Ppk — только если переданы `lsl`/`usl`), `sparkline` (строка-мини-график),
`plot` (числа для построения графика, округлены до `SPC_PLOT_DIGITS` = 5 значащих цифр — отдаёт чат/клиент, не
для пересказа моделью); `violations[]` обрезан на первых `SPC_MAX_INTERVALS` = 40 интервалах (заметка, если
нарушений больше). Математика — [11-calculations.md](11-calculations.md).

**`calc_flow_total`** — суммарный расход за период по мгновенным показаниям расходомера: интеграл методом
трапеций по фактическим интервалам точек равномерной сетки (`pcbk_core.flow`). Единица — из каталога тега, а
если её там нет — из аргумента `unit`; накопительный счётчик (единица без «/время») — отказ до SQL: такую
величину нельзя интегрировать повторно. Неполное покрытие периода → `status: "partial"` с частичным итогом и
списками покрытых/непокрытых интервалов. Математика — [11-calculations.md](11-calculations.md).

**`calc_formula`** — производный показатель по формуле над рядами до 4 тегов (теги по порядку — `A, B, C, D` в
формуле; `+ - * / **`, скобки, функции `mean/sum/min/max/std/median/count/first/last/abs`, парные
`corr/slope/intercept/r2`). Разбор — `ast` с белым списком узлов, без `eval` (`pcbk_core.formula`). Результат —
число (`result_kind: "number"`) или ряд (`"series"`, со сводкой и точками). Математика — [11-calculations.md](11-calculations.md).

**`equipment`** — подсчёт агрегатов каталога по словам запроса (группировка — `Catalog.equipment`, §3), не
модель: `units_total`/`units[]` (агрегаты, у которых слово запроса — в начале названия; обрезка вывода —
300 штук, `units_total` без обрезки; `truncated` — `true`, если показаны не все), `tags_total` (сумма тегов
белого списка у показанных `units`), `mentions_total`/`mentions[]` (слово в описании, но не в начале —
отдельный счётчик, **не** входит в `units_total`; в ответе — до 100 штук, `mentions_total` без обрезки),
`measure_points_total` (точки измерения — не агрегаты),
`groups` (счёт по группам кодов). `with_state=true` — дополнительно читает `_RUN` каждого найденного агрегата
из `units` (до 120 за вызов, иначе отказ `EQUIPMENT_RUN_LIMIT_MESSAGE`) и даёт `state_counts`/`state` у каждого
элемента (`running`/`stopped`/`no_data`/`no_run_tag`).

## 9. HTTP API `/api/data/*`

Шесть маршрутов, модели тел — `pydantic` (`core/pcbk_core/data/http_api.py`), общий порядок обработчика: токен →
ошибка настройки → инструмент. Ошибка разбора тела (битый JSON, лишние поля, неизвестный `period`) ловится
единым обработчиком `RequestValidationError` в том же порядке: `401` → `503` (`config_error`) → `422` с русской
причиной и событием `refused`. Предел тела — общий `BodyLimit` всего приложения, по умолчанию **65536 байт**
(64 КиБ, `DEFAULT_BODY_LIMIT`), действует и на `/api/data/*`, и на `/mcp`.

| Маршрут | Метод | Тело | Соответствует MCP |
|---|---|---|---|
| `/api/data/catalog_search` | `POST` | `{"query": str, "limit"?: int}` | `catalog_search` |
| `/api/data/tag_now` | `POST` | `{"tags": [str]}` | `tag_now` |
| `/api/data/tag_period` | `POST` | `{"tags": [str], "period"?: str, "start"?: str, "end"?: str}` | `tag_period` |
| `/api/data/tag_series` | `POST` | то же + `"points"?: int` | `tag_series` |
| `/api/data/calc_runtime` | `POST` | `{"tags": [str], "period"?, "start"?, "end"?}` | `calc_runtime` |
| `/api/data/calc_deviation` | `POST` | `{"measure_tag": str, "setpoint_tag": str, "threshold": float, "period"?, "start"?, "end"?, "points"?: int}` | `calc_deviation` |

Доступ — тот же `Authorization: Bearer <токен>` и те же правила сети (§7); ответ — тот же JSON, что у MCP (тело
`DataService`). Код ответа не несёт исход самого инструмента: какой бы ни был `status` внутри тела
(`ok`/`partial`/`refused`/`budget`/`unavailable`/`error`, если это отказ или сбой инструмента, а не настройки роли
или разбора тела) — код `200`. Три исключения — не исход инструмента, а более ранние шаги того же обработчика
(см. начало раздела): нет или чужой токен — `401`; ошибка настройки роли (`config_error`, тело той же формы,
`status: "unavailable"`) — `503`; ошибка разбора тела — `422`. Эти шесть маршрутов использует вкладка «Калькуляторы» веб-чата
через роль шлюза, подробнее — [13-gateway.md](13-gateway.md) и [17-web-chat-and-edge.md](17-web-chat-and-edge.md).

## 10. Запись: `save_agent`, `report_event`, `my_agents`

Только MCP, без HTTP-ручки. Вызывающий — только `student-01`…`student-11` (`place_of_caller`, иначе `refused`
«не студент»); место берётся из самого токена, не из аргументов.

**`save_agent`** (`save_agent.py`) — проверяет черновик собственного агента студента (аргументы — почти
буквально схема для модели) и сам пишет файл по шаблону в каталог места (`AgentStore.save`/`replace`,
подробности файла и учёта — [14-workplaces-and-agents.md](14-workplaces-and-agents.md)); права и правила стенда
добавляет сама служба, не студент. Частота — `SAVE_LIMIT` = 20 вызовов за `SAVE_WINDOW_S` = 600 с на
вызывающего, считаются все вызовы, в т. ч. отказы.

| Поле | Тип/пределы |
|---|---|
| `name` | `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`, 3–40 знаков |
| `title` | строка, 3–60 знаков |
| `node` | строка, 2–100 знаков |
| `purpose` | строка, 10–200 знаков |
| `tools` | массив уникальных строк из `catalog_search, tag_now, tag_period, tag_series, calc_runtime, calc_deviation, equipment, calc_spc, report_event, calc_formula` (1…столько же) |
| `tags` | массив строк (без предела числа), каждая до 128 знаков, точно как вернул `catalog_search` |
| `prompt` | строка, 200–4000 знаков (и не больше 8000 байт UTF-8) |
| `student_reply` | строка, 1–200 знаков — дословное согласие студента на последний показанный черновик |
| `replace` | bool, умолч. `false` — заменить прежнюю версию агента с тем же `name` |

Отказ — не ошибка протокола, а обычный ответ: `{"status": "refused", "problems": [...]}` — модель должна
исправить и повторить (замечание говорит, какое поле и что не так). Успех — `status: "ok"`, `already: true`
(повтор того же черновика) или `replaced: true` (при `replace: true`); имя уже занято другим агентом —
`refused` с кодом `name_taken`; `replace: true` без такого агента у места — `refused` `replace_missing`.
Инструмент `tools` ограничивает список `AGENT_TOOLS` — заметьте, что `calc_flow_total`, `my_agents` и
`save_agent` **не** входят в список, который можно выдать собственному агенту студента. По умолчанию модель
ассистента студента (`student/config/opencode.json`, `permission.pcbk_save_agent: "deny"`) сама вызвать
`save_agent` не может — какой агент это переопределяет, см. [14-workplaces-and-agents.md](14-workplaces-and-agents.md).

**`report_event`** (`report_event.py`) — агент студента записывает найденное: отклонение от задания или
заметку, в отдельную таблицу `agent_findings` (не `agent_events`). Частота — `REPORT_LIMIT` = 30 вызовов за
`REPORT_WINDOW_S` = 600 с, считаются все вызовы.

| Поле | Проверка |
|---|---|
| `agent` | имя живой (не архивной) строки учёта **этого** вызывающего — иначе `agent_unknown` |
| `kind` | `"deviation"` или `"note"` |
| `title` | 3–120 знаков, одна строка |
| `tags` | 1–4 строки, каждая должна пройти `catalog.lookup` со статусом `ok` (каталог не загружен → `unavailable`) |
| `period_start`/`period_end` | `null` или ISO 8601 **с часовым поясом** |
| `value`/`setpoint` | `null` или конечное число (не `NaN`/`inf`, не `bool`) |
| `text` | 10–600 знаков, одна строка |

Успех — `{"status": "ok", "id": <номер строки agent_findings>}`. Эти строки читает `GET /pcbk/api/events` шлюза
(показ студентам/преподавателю) — подробнее [13-gateway.md](13-gateway.md).

**`my_agents`** (`my_agents.py`) — без аргументов: живые строки учёта **своего** места (без архивных и
отправленных на карантин), для каждой — карточка (`name`, `title`, `node`, `purpose`, `tools`, `tags`) и текст
инструкции из файла агента (без служебных строк шаблона). Нужен Конструктору, чтобы найти свой агент и
предложить правку.

Все три пишут в `agent_events` строку с исходом (`ok`/`refused`/`rate`/`unavailable`/`error`), но **без** текста
находки/инструкции/имени агента в открытом виде за пределами соответствующей таблицы (`agent_findings`,
файл агента) — в `agent_events.summary` только код и число (например, `"ok: id=42"` у `report_event`,
`"agents 5"` у `my_agents`).

## 11. Журнал событий (`events.py`)

SQLite, таблица `agent_events`, тот же файл `core.db` (`Settings.DB_PATH`), что у учёта агентов и журнала
действий шлюза — режим `WAL`. Пишется **на каждый** вызов любого инструмента данных, включая фоновые опросы
каталога/свежести (`caller="system"`, `channel="system"`) — событие доказывает, что ушло (или не ушло) в
историан.

| Столбец | Смысл |
|---|---|
| `ts`, `caller`, `agent`, `channel` (`mcp`/`http`/`web`/`system`), `tool` | кто, когда, через что, какой инструмент |
| `requested` | сырой ввод (до 16 строк по 128 знаков) |
| `tags` | канонические имена со статусами после разбора каталогом |
| `sent` | имена, фактически переданные драйверу (их возвращают ворота — заполнено и при части отказов после отправки SQL) |
| `period_start`, `period_end` | границы периода, если инструмент его использовал |
| `outcome` | `ok`/`partial`/`refused`/`budget`/`rate`/`busy`/`timeout`/`unavailable`/`error` |
| `summary` | короткий текст исхода (без значений тегов) |
| `cost` | цена в тего-сутках |
| `cache` | `hit`/`miss`/`shared`/`none` |
| `row_count`, `duration_ms` | строк историана, время вызова |
| `returned` | у `catalog_search` — имена из `matches` (до 50), у прочих — пусто |

Запись — отдельное соединение SQLite на операцию; при блокировке (`SQLITE_BUSY`/`SQLITE_LOCKED`) — до 3 попыток
с паузой 0,25 с (`WRITE_ATTEMPTS`/`WRITE_RETRY_S`), итого не дольше 2 с на событие (`WRITE_WINDOW_S`); дальше —
сбой записи (счётчик `consecutive_failures`, текст в `last_error`), вызов или опрос не ждёт дольше. Свободный
текст (`requested`, `agent`, `summary`) зачищен от одиночных суррогатов (иначе `sqlite3`/`json` не закодирует
строку, и доказательство вызова пропало бы). Фоновая проверка записи (`writable()` — `BEGIN IMMEDIATE` + вставка
+ `ROLLBACK`) идёт раз в `EVENTS_CHECK_S` = 30 с в отдельном потоке; её итог отдаёт `DataRole.health()`.

Чтение — `EventLog.recent(limit=50, channel=None)` / `count(channel=None)`: применяют и тесты, и прочие роли
через общий `core.db` (отдельного API наружу для чтения событий у роли данных нет — просмотр для людей делает
шлюз, см. [13-gateway.md](13-gateway.md)).

## 12. Защищённые файлы КДМ-1

Все `.py`-файлы `core/pcbk_core/data/` (`__init__.py`, `budget.py`, `build_whitelist.py`, `cache.py`,
`catalog.py`, `events.py`, `freshness.py`, `gate.py`, `historian.py`, `http_api.py`, `mcp_server.py`,
`my_agents.py`, `names.py`, `periods.py`, `report_event.py`, `save_agent.py`, `service.py`, `sql.py`) входят в
список защищённых файлов `docs/kdm1/PROTECTED_DATA_BASELINE.current.json` — рядом с
`core/pcbk_core/gateway/calc_api.py`. У каждого файла зафиксирован `sha256`; причина в самом файле —
«Прямое указание пользователя: не менять общий разрешенный список тегов и его функции». Это значит: правка
любого из них требует отдельного решения владельца репозитория, а не только технического ревью. В частности,
без такого решения нельзя менять правило построения белого списка и поведение уже существующих инструментов;
новый инструмент чтения в этих файлах возможен и без изменения списка тегов и прежних функций, но тоже только
с отдельным решением владельца — список защищённых файлов одинаков для любой правки, маленькой или большой.

## 13. Как поднять службу данных отдельно

Роль `data` не выделена в отдельный Docker-сервис compose-файла — в контейнере `core` она всегда идёт вместе с
LLM-прокси, шлюзом и ролью базы знаний (`core/pcbk_core/main.py:build_roles`). Два пути получить **только** эту
роль:

**А. Весь образ `core`, но обращаться только к `/mcp`/`/api/data/*`.** `core/pcbk_core/main.py:Settings.from_env`
читает пути к секретам из переменных окружения по имени поля — Docker не обязателен. Для одной роли данных
нужны только три файла (`BDRV_ENV_FILE`, `WHITELIST_PATH`, `TOKENS_FILE`) и путь к базе `DB_PATH`; роли `llm`,
`gateway`, `kb` при отсутствии своих секретов просто поднимутся с `config_error` (без влияния на роль данных) —
переменные `LLM_*`/`GW_*` можно не задавать. Пример для разработки — без Docker secrets, прямыми путями (учётные
данные историана здесь вымышленные; с настоящим `bdrv.env` — то же самое, но против боевого историана):

```bash
printf 'BDRV_HOST=192.0.2.10\nBDRV_USER=test\nBDRV_PW=test\n' > /tmp/bdrv.env   # или путь к настоящему секрету
printf '20FAKE_001_PV\n' > /tmp/whitelist.txt                                   # или настоящий список (§3)
TOKEN=$(openssl rand -hex 24)
printf 'dev %s\n' "$(printf '%s' "$TOKEN" | sha256sum | cut -d' ' -f1)" > /tmp/core-tokens
BDRV_ENV_FILE=/tmp/bdrv.env WHITELIST_PATH=/tmp/whitelist.txt \
  TOKENS_FILE=/tmp/core-tokens DB_PATH=/tmp/core.db \
  python -m pcbk_core.main
```

Id токена — `dev` (не `student-NN`), поэтому сетевое ограничение §7 на него не действует: клиент может быть в
любой сети, которая видит порт `8000`. Проверка — `GET /health/historian` без токена (отвечает всегда, даже с
ошибкой историана) и вызов инструмента чтения с токеном из `$TOKEN`:

```bash
curl -s http://127.0.0.1:8000/health/historian
curl -s -X POST http://127.0.0.1:8000/api/data/catalog_search \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"query": "FAKE"}'
```

С вымышленным `bdrv.env` выше (адрес `192.0.2.10` из диапазона `TEST-NET-1`, недостижим) каталог тегов (§3)
никогда не загрузится, поэтому `catalog_search` ответит `status: "unavailable"` с сообщением «каталог тегов
ещё не загружен» (`_loaded_catalog`, §8) — но это уже значит, что роль поднялась, токен принят и ворота (§5)
работают: запрос дошёл до службы. Точную причину, по которой историан недостижим (код `connect` фонового
опроса каталога), покажет `GET /health/historian` → `catalog_error`; настоящий, доступный историан довёл бы
каталог до загрузки и дал `ok`/`partial`. Этим же приёмом (вымышленный `bdrv.env` и `whitelist.txt` с одним
именем `20FAKE_001_PV`) пользуется тестовая фикстура `tests/integration/conftest.py`.

MCP-клиенту (как у рабочих мест, `student/config/opencode.json`) нужен тот же адрес и токен:

```json
{
  "mcp": {
    "pcbk": {
      "type": "remote",
      "url": "http://<хост core>:8000/mcp",
      "enabled": true,
      "oauth": false,
      "headers": {"Authorization": "Bearer <ваш токен>"}
    }
  }
}
```

**То же самое через Docker Compose.** Вместо прямого запуска `docker compose up -d --no-build core` поднимает тот же процесс
в контейнере, но Compose создаёт секреты из файлов при старте контейнера и откажется поднимать `core`, если
не хватает хотя бы одного — в том числе секретов и bind-томов ролей, которые для одной роли данных не нужны
(`llm-tokens`, `openrouter.key`, `openrouter-mgmt.key`, одиннадцать `student-NN.pw`, `AGENTS_DIR`,
`LESSONS_DIR`). Полный список и приём с заглушками для ненужных ролей —
[02-build-and-deploy.md](02-build-and-deploy.md) §6.1 («Только служба данных»), там же — как достать порт
`8000` без публикации наружу (адрес `core` в сети `pcbk-egress` или `compose.override.yaml`).

**Б. Только код роли, без Docker** — для разработки или нестандартного развёртывания: `DataRole` ничего не
знает про другие роли, и `create_app` (`core/pcbk_core/app.py`) принимает список ролей любой длины:

```python
import uvicorn
from pcbk_core.app import create_app
from pcbk_core.data import DataRole
from pcbk_core.data.historian import tds_query
from pcbk_core.data.names import load_names
from pcbk_core.secrets import BdrvConfig, TokenTable
from pcbk_core.settings import Settings

settings = Settings(BDRV_ENV_FILE="/путь/к/bdrv.env", WHITELIST_PATH="/путь/к/whitelist.txt",
                     TOKENS_FILE="/путь/к/core-tokens", DB_PATH="/путь/к/core.db")
cfg = BdrvConfig.from_env_file(settings.BDRV_ENV_FILE)
role = DataRole(settings, tds_query(cfg), load_names(settings.WHITELIST_PATH),
                 tokens=TokenTable.from_file(settings.TOKENS_FILE))
app = create_app(settings, [role])
uvicorn.run(app, host="0.0.0.0", port=settings.CORE_PORT)
```

Это ровно то, что делают тесты службы данных (`core/tests/helpers.py:make_app`), только вместо `tds_query(cfg)`
там — двойник историана в памяти (`FakeHistorian`), без реального SQL Server. Тот же приём годится для
локального запуска без реального историана при разработке: подставьте свою функцию типа `QueryFn`
(`core/pcbk_core/data/historian.py`: `Callable[[Sequence[str], float], list[list[Row]]]` — список инструкций и
остаток срока в секундах → список результатов каждой) вместо `tds_query(cfg)`.

MCP-клиент в обоих случаях видит один и тот же набор инструментов — адрес один: `POST /mcp`, заголовок
`Authorization: Bearer <токен>`, тело — стандартный JSON-RPC MCP (`tools/list`, `tools/call`). HTTP-клиенту без
MCP достаточно адреса `/api/data/<инструмент>` из §9 с тем же заголовком.
