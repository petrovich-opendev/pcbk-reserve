# Сторож (`watchdog`) и эксплуатационные скрипты

Сторож — отдельная служба (отдельный контейнер `pcbk-watchdog`, не часть процесса `core`), которая раз в такт
опрашивает остальные компоненты стенда и показывает одну страницу состояния. Эксплуатационные скрипты
`deploy/ops/` дополняют его: самолечение зависших контейнеров и синхронизация учётки историана с Dify — оба
через `cron` пользователя выкладки на сервере, не внутри сторожа.

**Переносимость.** Сам сторож (`watchdog/pcbk_watchdog/`) и механизм в целом (такт, журнал переходов, страница,
`/status.json`) не знают про КДМ-1 — переносимы как есть. Специфика заказчика — только содержимое
`watchdog/components.json` (какие компоненты и под какими именами существуют на этом стенде: число мест — 11,
имена контейнеров `pcbk-student-NN`, адреса `pcbk-core`/`pcbk-edge`) и часть текстов строк («Поправки базы
знаний», «Историан БДРВ»). При переносе на другое предприятие меняется только этот файл (раздел 7) — код
`checks.py`/`main.py`/`page.py` трогать не нужно, если не добавляется новый *вид* проверки. Оба `deploy/ops/`
скрипта тоже переносимы буквально, кроме путей `/opt/dify/scripts/.bdrv.env` и `/opt/pcbk-reserve` —
они жёстко вписаны в `pcbk-bdrv-sync.sh` и ожидают конкретного расположения учётки историана у Dify.

## 1. Как работает такт

Процесс `main.py:main()` при старте: читает `Settings.from_env()` (ошибка в любом поле — исключение, контейнер
не поднимается), загружает `components.json` (`load_components`, тоже с проверкой — раздел 7), открывает журнал
лениво (`LazyJournal`, сбой открытия не роняет сторожа — покажется на первом такте), запускает HTTP-сервер
(`make_server`) и отдельный поток `tick` с именем `"tick"` (`daemon=True`).

Один такт (`tick()`):
1. `run_checks()` — проверяет все компоненты по порядку `components.json` (раздел 2);
2. пробная запись в журнал (`journal.probe()`) — сбой превращается в собственную строку `journal` на странице;
3. `state.snapshot = Snapshot(now, checks)` — публикуется **до** записи в журнал (если запись упадёт, снимок
   всё равно свежий);
4. `journal.record(...)` — пишет только переходы состояния (раздел 4), строки `absent` и строку про сам журнал
   не пишет.

Такт повторяется раз в `TICK_S` секунд (умолчание 10): `run_loop()` ждёт `max(0, TICK_S − длительность такта)`
между итерациями; исключение внутри такта — запись в лог («такт упал»), сам цикл не останавливается.

**Остановка.** `main()` сам ставит обработчик `SIGTERM` (`_exit_now`, поднимает `SystemExit(0)`) — без него процесс
как `PID 1` контейнера сигнал не получил бы. Поэтому `docker stop`/пересоздание контейнера завершает процесс быстро,
не дожидаясь конца текущего такта; незавершённая запись в журнал (SQLite) при этом откатывается самим `sqlite3`
(транзакция `with db:` в `journal.py`), частично записанных событий не остаётся. Поток `tick` — `daemon=True`,
отдельно его не дожидаются.

**Срок такта (`tick_budget_s`).** Если прокси сокета или одна из служб зависает, сетевые проверки не должны
растягивать такт настолько, что снимок устареет ещё до следующего такта. `Settings.tick_budget_s` — предел
времени (от начала такта), после которого *новые* сетевые проверки не начинаются (уже начатая — донашивает своё
время вплоть до `HTTP_CHECK_SPANS` сроков сокета, `HTTP_CHECK_SPANS = 2`); не начавшиеся получают состояние
`unknown` с текстом «проверка пропущена: такт не уложился в срок». Формула:
`tick_budget_s = min(STALE_AFTER_S − TICK_S, STALE_AFTER_S / 2) − 2 × max(DOCKER_TIMEOUT_S, NET_CHECK_TIMEOUT_S)`.
При умолчаниях (`TICK_S=10`, `STALE_AFTER_S=30`, `DOCKER_TIMEOUT_S=3`, `NET_CHECK_TIMEOUT_S=3`, константа
`checks.py`, не переменная окружения) `tick_budget_s = 9` секунд. Значение `≤ 0` — `Settings` отказывается
стартовать («срок такта не больше нуля — снимок устареет между тактами»).

Правило «новая сетевая проверка после срока такта не начинается» не касается только проверок без сети (`kind`
в `LOCAL_KINDS = {"memory", "absent"}`) — они не занимают сокет вовсе; все прочие виды, включая `historian`/
`llm`/`gateway`/`web`/`agents`/`teacher`, при перегруженном такте пропускаются точно так же, как `http`/`tls`/
`container`. Отдельно от этого — пороги свежести самих этих пяти ручек (`HIST_WARN_S`/`HIST_FAIL_S`/
`HIST_STALE_S`, `GW_STALE_S`, `AGENTS_STALE_S`, `LLM_RUN_SILENT_S`, `TEACHER_STALE_S`) проверяются в
`__post_init__` сами по себе (обычно только `> 0`) и **не входят в формулу `tick_budget_s`**: каждая из этих
проверок — один HTTP-запрос к `core`, а не цикл по многим контейнерам, поэтому её порог можно менять без
пересчёта срока такта.

Если прокси сокета (`sp-ro`) уже не ответил в этом такте (поймано `DockerUnavailable`), оставшиеся проверки
вида `container` в этом же такте не ждут его по отдельности — сразу получают `unknown` «нет связи с прокси
сокета» (`run_checks`, флаг `docker_down`).

### Учения `DRILL_FREEZE_LOOP`

Переменная `DRILL_FREEZE_LOOP=1` (умолчание `0`) — после первого такта цикл проверок замирает навсегда (поток
`tick` возвращается из `run_loop`), а HTTP-сервер продолжает отвечать: так проверяется, что страница сама
показывает полосу молчания при живом процессе. При старте с этим флагом сторож пишет в лог предупреждение.

## 2. HTTP-сервер: `/status`, `/status.json`, `/status.js`, `/healthz`

`make_server()` — `http.server.ThreadingHTTPServer` на `LISTEN_PORT` (умолчание `8090`), слушает все интерфейсы
контейнера. Каждый запрос — свой поток, `timeout = 10` с на медленного клиента. Все ответы — заголовки
`Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`; `/status` —
дополнительно `Content-Security-Policy: default-src 'none'; script-src 'self'; connect-src 'self'; style-src
'unsafe-inline'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` (константа `CSP`, `main.py`).
Доступа в лог нет у `do_GET` (`log_message` — пустой): страницу опрашивают каждые 5 с, писать это в лог незачем.

| Маршрут | Метод | Что отдаёт |
|---|---|---|
| `/status` | GET | HTML страницы состояния (без внешних ресурсов, без встроенного JS — только `<script type="module" src="/status.js">`); код всегда `200` |
| `/status.json` | GET | JSON снимка (формат — ниже); код `200`, если снимок уже есть, иначе `503` |
| `/status.js` | GET | модуль опроса страницы, `text/javascript` |
| `/healthz` | GET | `ok\n` (`200`) при свежем снимке, `stale\n` (`503`) при устаревшем или отсутствующем — используется `HEALTHCHECK` образа (раздел 8) |
| всё прочее | — | `404 text/plain` |

«Свежесть» везде считается **в момент запроса**, не на момент последнего такта: `is_stale(snapshot, now,
STALE_AFTER_S)` — `True`, если снимка ещё нет или `(now − checked_at) > STALE_AFTER_S` секунд (умолчание 30).

**Тело `/status.json`** (`page.status_json`):

| Поле | Тип | Значение |
|---|---|---|
| `checked_at` | строка ISO или `null` | время последнего такта; `null`, если такта ещё не было |
| `stale` | булево | устарел ли снимок на момент запроса (правило выше) |
| `stale_after_s` | целое | текущее значение `STALE_AFTER_S` |
| `age_s` | целое или `null` | возраст снимка в секундах на момент запроса |
| `overall` | строка | худшее состояние среди всех строк по порядку `fail > unknown > warn > ok` (`absent` в общий итог не входит); `unknown`, если снимка ещё нет |
| `checks` | список объектов | по одному на каждую строку `components.json` в её порядке: `{"component", "title", "state", "detail", "note"}` |

### `status.js` — опрос страницы браузером

`/status` при открытии уже несёт готовый HTML (сервер отрисовал его на момент запроса), а подключённый модуль
`status.js` дальше сам опрашивает `/status.json` раз в `pollMs = 5000` мс (срок запроса `timeoutMs = 4000` мс,
через `AbortController`) и обновляет DOM без перезагрузки страницы. Полоса молчания (`#silence`) показывается,
если: опрос вернул не `200`, не JSON или `stale: true`, либо с последнего удачного ответа прошло больше
`staleAfterS` секунд (читает `data-stale-after-s` из `<body>`) — отслеживается по **часам браузера**
(`performance.now()`), отдельным таймером раз в секунду, так что полоса появляется даже если сам `fetch` к
`/status.json` просто повис. При возвращении вкладки из фона (`visibilitychange`) опрос делается немедленно, не
дожидаясь следующих 5 секунд.

### `healthcheck()` — режим для `HEALTHCHECK` образа

`python -m pcbk_watchdog.main --healthcheck` — не поднимает сервер и такт, а делает короткий HTTP-запрос
`GET /healthz` к уже работающему процессу на `127.0.0.1:LISTEN_PORT` (срок 5 с) и возвращает код выхода `0`
(ответ `200`) или `1` (иначе, в том числе сеть недоступна). Так `HEALTHCHECK` Docker проверяет не «процесс жив»,
а «цикл проверок не зависает» — зависший такт делает контейнер `unhealthy`, хотя HTTP-сервер и сам процесс
продолжают отвечать.

## 3. Доступ к Docker: прокси `sp-ro`

Сторож не ходит в `/var/run/docker.sock` напрямую — только через отдельный контейнер-прокси
`wollomatic/socket-proxy:1.13.1` с именем `pcbk-sp-ro` (своя сеть `pcbk-ro`, адрес `DOCKER_URL` =
`http://pcbk-sp-ro:2375`, не параметр `.env` — жёстко в `compose.yaml`). Это не тот же прокси, что у шлюза
(`pcbk-sp-ctl` — у него свой список разрешённых операций, включая `POST start`/`stop`, и он служит `core`, не
сторожу; подробности — [13-gateway.md](13-gateway.md)). Прокси `sp-ro` принимает только:

```
-allowfrom=pcbk-watchdog
-allowGET=(/v1\.[0-9]+)?/(_ping|containers/pcbk-(student-(0[1-9]|1[01])|sp-ctl|core)/json)
```

То есть сторож может сделать только `GET /_ping` и `GET /containers/<имя>/json` для контейнеров
`pcbk-student-01`…`pcbk-student-11`, `pcbk-sp-ctl` и `pcbk-core` — список всех контейнеров сервера
(`GET /containers/json`, который выдал бы заодно командные строки контейнеров Dify) сторожу недоступен в
принципе, не только по коду. **Ни `pcbk-edge`, ни сам `pcbk-watchdog` через `sp-ro` не инспектируются** — у
`edge` на странице своя проверка видом `tls` (раздел 5.1), а собственное состояние сторож не проверяет вовсе
(раздел 6).

`DockerReader` (`docker_api.py`): `ping()` — `GET /_ping`, успех только если код `200` и тело ровно `OK`.
`inspect(name)` — сначала сверяет `name` с той же регуляркой, что и прокси (`CONTAINER_NAME = re.compile(r"pcbk-
[a-z0-9-]+")`; `main.load_components` сверяет ею же имена в `components.json` при старте — чужое имя контейнера
там не пройдёт конфигурацию); код `404` — контейнера нет (`None`, не ошибка); код, отличный от `200`/`404`
(`403`/`405` — отказ прокси, `5xx` — сбой Docker), или тело не JSON — исключение `DockerUnavailable`. Префикс
API — `/v1.44` (принимают все Docker 29.x), срок каждого HTTP-запроса — `DOCKER_TIMEOUT_S` (умолчание 3 с).

## 4. Журнал переходов (`journal.py`)

SQLite-файл по пути `JOURNAL_PATH` (умолчание `/var/lib/pcbk-watchdog/journal.db`, том `pcbk-watchdog-journal`),
одна таблица `events (ts TEXT, component TEXT, state TEXT, detail TEXT)`. Пишутся **только переходы**, не
каждый такт: `Journal._is_transition(check)` — `True`, если состояние компонента изменилось, или если
состояние `warn`/`fail` и изменился текст `detail` (у `ok`/`unknown`/`absent` смена одного `detail` без смены
состояния — не событие). Последнее записанное состояние каждого компонента держится в памяти (`self._last`) и
переживает перезапуск процесса — читается из таблицы при открытии (`SELECT … WHERE rowid IN (SELECT MAX(rowid)
FROM events GROUP BY component)`), так что рестарт сторожа не пишет ложных «переходов» по всем строкам сразу.

Строка `Event(ts, "watchdog", "ok", "сторож запущен")` пишется один раз при каждом старте процесса
(`Journal.started`, вызывается из `main()` сразу после открытия журнала, до первого такта). Строка `journal` на
самой странице (детали — раздел 1) появляется только если запись в журнал ломается — `self._open().started/
probe/record` этого не пишет, это уже синтетический `Check` со стороны `main.tick`.

`probe()` — проверка, что журнал **можно писать**, без побочного эффекта: `BEGIN IMMEDIATE`, вставка пробной
строки `component='probe'`, `ROLLBACK`. Одного соединения мало: на файле только для чтения `BEGIN IMMEDIATE`
сам по себе проходит, а вот `INSERT` — нет, поэтому проба именно пишет и откатывает. Каждая операция открывает
своё соединение (`timeout=5`) — журнал читают параллельно потоки HTTP-сервера, писать из одного держать не на
кого.

`recent(limit=50)` — последние события, новые сверху (`ORDER BY rowid DESC`); страница `/status` показывает
`EVENTS_ON_PAGE = 20` из них (`main.py`).

**Журнал не трогается при обычном откате и не удаляется сам.** `deploy/README.md`, раздел «Откат»: `docker
compose down -v` на сервере запрещён именно потому, что удаляет том `pcbk-watchdog-journal`; снять его можно
только явно — `docker volume rm pcbk-reserve_pcbk-watchdog-journal`. При переустановке/пересборке образа
сторожа том и журнал сохраняются.

## 5. Что проверяет каждая строка `components.json`

Файл — JSON-список объектов `{"id", "title", "kind", …}` в порядке появления на странице; у каждого вида
(`kind`) свой набор обязательных полей (таблица `KINDS` в `main.py`, раздел 7). На живом сервере
`watchdog/components.json` (24 строки) — четыре группы по порядку страницы: инфраструктура (1–4: `edge`,
`sp-ro`, `sp-ctl`, `memory`), 11 рабочих мест (5–15, вид `container`), серверный слой и его роли (16–23:
`core`/`core-container`/`historian`/`llm`/`gateway`/`web`/`agents`/`teacher`), поправки базы знаний (24, вид
`http`).

**Общий принцип для видов `historian`/`llm`/`gateway`/`agents`/`teacher`: сторож не опрашивает чужую службу
сам — он читает JSON ручки `/health/*` у `core`, которая эту службу (историан, OpenRouter) опрашивает
самостоятельно в своём потоке.** Если ответ `core` не разобрать по договору (неверный тип поля, лишний или
недостающий ключ, число вне диапазона) — сторож не падает, а показывает отдельную строку «… ответил(а) не по
договору» (раздел 6 перечисляет такие тексты). Общий для всех HTTP-проверок срок на операцию сокета —
`NET_CHECK_TIMEOUT_S = 3.0` секунды (константа **в коде**, `checks.py`, не переменная окружения и не то же, что
`DOCKER_TIMEOUT_S`); вся проверка целиком (соединение + заголовки + тело) — не дольше `HTTP_CHECK_SPANS = 2`
таких сроков; тело ответа читается не больше `MAX_BODY_BYTES = 64` КиБ. Во всех состояниях `warn`/`fail`
**текст `detail` постоянный** (не несёт меняющихся чисел) — журнал пишет переход, а не каждый такт; числа и
подробности — в поле `note`, которое в журнал не попадает и не обрезается 80 знаками (`REASON_CHARS`,
действует только на `detail`).

### 5.1. `tls` — `edge` (id `edge`, host `pcbk-edge`, port `8443`)

TLS-рукопожатие напрямую (не через `core`), доверие только файлу `TLS_CAFILE` (копия `cert.pem`, тот же, что у
`edge`), без проверки имени хоста (`check_hostname = False`, но `VERIFY_X509_PARTIAL_CHAIN`).

| Состояние | Когда | Текст |
|---|---|---|
| `fail` | нет соединения | «не отвечает» |
| `fail` | `X509_V_ERR_CERT_HAS_EXPIRED` | «сертификат истёк» |
| `fail` | `X509_V_ERR_CERT_NOT_YET_VALID` | «сертификат ещё не действителен» |
| `fail` | рукопожатие прошло, сертификат не проверился иначе | «отдаёт не тот сертификат» |

### 5.2. `docker_ping` — прокси `sp-ro` (id `sp-ro`)

`docker.ping()` — `GET /_ping` через сам `sp-ro`. `ok` «отвечает»; сбой (включая отказ прокси) — `fail`
«не отвечает» (ветка `DockerUnavailable` в `run_checks`, не сама функция проверки).

### 5.3. `container` — `sp-ctl`, 11 мест, `core-container`

Вердикт по `docker inspect` (`check_container`, таблица правил по порядку):

| Состояние | Условие (`inspect["State"]`, `RestartCount`) | Текст |
|---|---|---|
| `fail` | контейнера нет (`inspect is None`) | «нет контейнера» |
| `fail` | `Paused` | «приостановлен» |
| `fail` | работает/перезапускается, `RestartCount ≥ 3` и запуск моложе 15 мин | «падает в цикле (перезапуски подряд)» (+ «последний — убит по памяти/сбой не по памяти» в `note`, если причина известна) |
| `warn` | `Restarting` (и не цикл падений) | «перезапускается» |
| `fail` | `Health.Log` молчит дольше 2 минут от последнего `End` (монитор Docker ждёт без своего срока) | «проверка здоровья молчит» |
| `fail` | `Health.Status == "unhealthy"` | `unhealthy_detail` из `components.json`, умолчание «OpenCode не отвечает» |
| `warn` | `Health.Status == "healthy"`, но последние строки `Health.Log` этого запуска несут `mcp=<слово>` вне `{connected, unknown, disabled}` | «нет связи со службой данных (MCP)» |
| `warn` | то же, слово `unknown` все 5 последних записей подряд и старейшая кончилась больше 120 с назад | «состояние MCP не читается» |
| `warn` | работает, `RestartCount > 0`, запуск моложе 15 мин, причина известна | «перезапущен: убит по памяти / сбой не по памяти в ЧЧ:ММ UTC±ЧЧ:ММ (N с последнего запуска)» |
| `warn` | то же, причина не определена (счётчик `oom_kill` не читался или контейнер не был виден работающим до перезапуска) | «перезапущен после сбоя в ЧЧ:ММ UTC±ЧЧ:ММ (N с последнего запуска)» |
| `ok` | работает, `RestartCount > 0`, запуск старше 15 мин | «работает, сбоев с последнего запуска: N» |
| `ok` | работает, без перезапусков | «работает» |
| `fail` | остановлен, `OOMKilled` | «убит по памяти» |
| `fail` | остановлен, есть `State.Error` | «не запускается: <причина, без пути `/opt/pcbk-reserve…`, до 80 знаков>» |
| `ok` | остановлен, `sleeping_ok=true` и код выхода `0`/`137`/`143` | «спит» |
| `fail` | остановлен иначе | «остановлен, код N» |

`sleeping_ok` — поле `components.json` (`true` у 11 мест, `false` у `sp-ctl` и `core-container`): только местам
разрешено «спать» без сигнала тревоги (их усыпляет шлюз после простоя — [13-gateway.md](13-gateway.md)).
`unhealthy_detail` задан в файле только у строки `core-container`: «процесс core не отвечает на проверку
здоровья» (≤ 80 знаков). У 11 мест своего `unhealthy_detail` нет — используется умолчание `UNHEALTHY_DETAIL`
«OpenCode не отвечает», и у них это осмысленно: образ места несёт собственный Docker `HEALTHCHECK`. Код
применил бы то же умолчание и к `sp-ctl`, но на практике эта ветка для него не срабатывает: по
[03-configuration.md](03-configuration.md) у образа `sp-ctl` своего `HEALTHCHECK` нет, Docker никогда не
проставляет ему `Health.Status`, и его строка идёт по обычным правилам «работает»/«остановлен», минуя ветку
`unhealthy`.
Тексты MCP (`mcp=`) — часть протокола проверки здоровья **образа места** (`student`, см.
[14-workplaces-and-agents.md](14-workplaces-and-agents.md)), сторож их только разбирает по готовому `Health.Log`,
сам ничего к местам не посылает. Причины перезапуска по памяти (`restart_reason`/`last_reason` в `note`) —
из `memory.RestartReasons`, см. раздел 5.9.

### 5.5. `http` — `core` (здоровье службы данных) и `kb` (поправки базы знаний)

`check_http`: `GET url`; `2xx` — `ok` с `ok_detail` из `components.json` («жива» у `core`, «хранилище открыто» у
`kb`); код `503` с телом `{"detail": "…"}` — `fail` с этим текстом (до 80 знаков, без путей каталога выкладки);
иначе — `fail` «отвечает ошибкой HTTP N»; нет соединения — `fail` «не отвечает».

### 5.6. `historian` — «Историан БДРВ» (id `historian`, `GET http://pcbk-core:8000/health/historian`)

Сторож читает ручку `core`, которая сама хранит возраст последней метки историана (`age_s`) и признаки нагрузки
— сам историан заново не опрашивается. Сначала — сетевой слой `check_historian`: нет соединения, срок истёк,
код ответа не `200` или тело не JSON — `unknown` «служба данных не отвечает — свежесть неизвестна»; тело
разобралось как JSON, но не по договору (не тот тип поля, нет ключа) — `unknown` «служба данных ответила не по
договору — свежесть неизвестна». Если ответ прочитан, первая подходящая строка самого договора
(`historian_verdict`/`_historian_row`):

| Состояние | Условие | Текст |
|---|---|---|
| `unknown` | `checked_at` ещё `null` | «служба ещё не опрашивала историан» |
| `unknown` | `now − checked_at >` `HIST_STALE_S` (умолчание 140 с) | «служба давно не опрашивала историан» |
| `fail` | `error` непусто | текст из `error_text` (или код ошибки), до 80 знаков |
| `fail` | `age_s ≥` `HIST_FAIL_S` (умолчание 900) | «последняя метка старше 900 с» |
| `warn` | `age_s ≥` `HIST_WARN_S` (умолчание 300) | «последняя метка старше 300 с» |
| `warn` | `gate.user_paused` истинно | «запросы людей к историану на паузе после сроков подряд» |
| `warn` | `gate.p95_ms > 5000` | «историан отвечает медленно: p95 больше 5 с» |
| `warn` | доля ошибок инструментов `tools.errors/tools.recent ≥ 0,2` при `tools.recent ≥ 10` | «инструменты отвечают ошибкой» (`note`: «N из M») |
| `warn` | `tools.failing` непусто (серия ошибок подряд у конкретных инструментов) | «инструменты службы данных отвечают ошибкой подряд» (`note`: имена) |
| `warn` | `catalog_age_s > 172800` (двое суток) | «каталог тегов старше двух суток» |
| `ok` | иначе | «последняя метка N с назад» |

Поле `drill` ответа (режим учений службы данных `tool_error`) добавляет к `note` любой строки пометку
«учения: tool_error» через «; ».

`check_llm`: «сама служба OpenRouter заново не опрашивает»). Первая подходящая строка (`llm_verdict`, сильно
усечённая здесь таблица — полный договор ручки и смысл полей `run`/`run_brake` — [12-llm-proxy.md](12-llm-proxy.md)):

| Состояние | Условие (сокращённо) | Текст |
|---|---|---|
| `fail` | `stopped` | «LLM-прокси остановлен администратором» |
| `fail` | `config_error` непуст | «ошибка настройки: …» |
| `fail` | `tokens_error` непуст | «токены LLM не читаются» |
| `fail` | `key == "missing"` | «нет ключа OpenRouter» |

| `unknown` | опроса ещё не было / `upstream_state == "unknown"` / опрос старше `LLM_STALE_S = 180` с (константа `checks.py`) | соответствующий текст |

| `warn` | потолок прогона отбора исчерпан | «потолок прогона отбора исчерпан — вызовы прогона получают отказ» |

| `warn` | доля бюджета сверх 95/80/50 % (первая подходящая) | «израсходовано больше 95/80/50 % бюджета» |

`note` — числа расхода и прогона, собранные `llm_note` (расход/бюджет, резерв на оценку, расход по ключу
OpenRouter, прогон отбора, доли, остаток счёта, учения `DRILL_LLM`, подробности тормоза).

### 5.8. `gateway`/`web`/`agents`/`teacher` — шлюз, веб-чат, агенты студентов, кабинет преподавателя

Четыре строки устроены одинаково: ручка `core` → вердикт по первой подходящей строке своей таблицы →
`fail`/`warn`/`ok`; нет ответа, код не `200` (и не `404` у `agents`/`teacher`) или тело не по договору — отдельный
«не отвечает»/«ответил(а) не по договору»; `404` у `agents`/`teacher` — `unknown` «… ещё не выложен(а)» (бывает

час и как это читать с точки зрения самой роли — в документах ролей; здесь — что видно **на странице сторожа**.

### 5.9. `memory` — «Память сервера» подробно (`memory.py`)

Замер — **в начале каждого такта** (10 с по умолчанию), независимо от `components.json`: `/proc/meminfo`
(`MemAvailable`, `MemTotal`, `SwapTotal`, `SwapFree` — обязателен только `MemAvailable`, без него замер
`None`), `/proc/vmstat` (счётчик `oom_kill`, накопительный с момента загрузки ядра) и `/proc/pressure/memory`
(строки `some`/`full`, поле `avg10`) — оба необязательны (их отсутствие не рушит замер, только две части `note`
получают «нет данных: …»). Сторож и `core` видят эти файлы **хоста**, так как оба работают под `runc` (не под
`runsc`/gVisor — файлы `/proc` под gVisor были бы файлами контейнера, не хоста).

Первая подходящая строка (`memory_verdict`):

| Состояние | Условие | `detail` |
|---|---|---|
| `unknown` | `MemAvailable` не прочитан | «нет данных о свободной памяти» |
| `fail` | свободно < `MEM_FAIL_MIB` (умолчание 1024 МиБ) | «свободно меньше 1024 МиБ» |
| `unknown` | датчик (`swap`/`vmstat`/`pressure`), который в этой истории уже давал данные, в этом замере замолчал | «датчик памяти замолчал — убийства, давление или swap не читаются» |
| `warn` | были необъяснённые убийства по памяти (не отнесённые к перезапуску своей строки `container`) старше `2×TICK_S` и не старше часа | «сервер убивал процессы по памяти вне мест и core» |
| `warn` | давление `full avg10 > PSI_FULL_MAX` (умолчание 10 %) три такта подряд (снимается тоже после трёх тактов подряд не выше) | «сервер ждёт освобождения памяти — давление выше порога» |
| `warn` | занятый swap вырос за 10 минут на `≥ SWAP_GROW_WARN_MIB` (умолчание 512 МиБ) | «сервер вытесняет память в swap» |
| `warn` | свободно < `MEM_WARN_MIB` (умолчание 2048 МиБ) | «свободно меньше 2048 МиБ» |
| `ok` | иначе | «свободно N МиБ» |

`note` (не входит в 80-знаковый предел `detail`) — через « · »: «свободно N МиБ» (кроме `ok`), «swap занят N МиБ
(+N МиБ за 10 мин)» (или «нет данных: swap»), «давление памяти some X %, full Y %» (или «нет данных: давление»),
«убийств по памяти вне мест и core за час: N» (только если > 0), «нет данных: vmstat» (если этот датчик без
данных), и пометка «учения: порог выше всей памяти», если `MEM_WARN_MIB`/`MEM_FAIL_MIB` специально выставлены
выше физической памяти сервера (учения).

**Причины перезапуска контейнеров (`RestartReasons`)** — отдельно от самой строки памяти, но питают `note`
строк вида `container` (раздел 5.3): счётчик `oom_kill` читается сторожем **до** и **после** `inspect()` каждого
контейнера в такте; прирост между двумя замерами на фоне перезапуска этого контейнера даёт причину `oom`
(«убит по памяти»), её отсутствие при новом `RestartCount` — причину `crash` («сбой не по памяти»). Необъяснённые
приросты, не привязанные ни к одному перезапуску своей строки, попадают в счётчик «вне мест и core» строки
памяти — то есть к процессам, у которых на странице нет своей строки вида `container` с историей перезапуска
(через которую прирост мог бы быть объяснён): Dify, процессы системы хоста, `edge` (у него строка вида `tls`,
не `container`), сам прокси `sp-ro` (его строка — вида `docker_ping`, не `container`) и сам сторож (у него нет
строки вовсе). Контейнеры `sp-ctl`, `core-container` и 11 мест в этот счётчик не попадают — их перезапуски
`RestartReasons` объясняет по своей строке.

Пороги раздела (`MEM_WARN_MIB`, `MEM_FAIL_MIB`, `SWAP_GROW_WARN_MIB`, `PSI_FULL_MAX`) настраиваются через
`.env`/окружение контейнера и пересоздание сторожа (`docker compose up -d --no-build --force-recreate
watchdog`). Строгий диапазон проверяет `__post_init__` только у двух из них: `SWAP_GROW_WARN_MIB` — целое от 1
до 1 048 576 МиБ, `PSI_FULL_MAX` — число `0 < x ≤ 100`; `MEM_WARN_MIB`/`MEM_FAIL_MIB` — просто целые (любое
значение, кроме нечислового, принимается — так учения «порог выше всей памяти», раздел выше, и ставят порог
заведомо больше объёма сервера). Нарушение валидируемого диапазона или нечисловая строка в любой из четырёх
переменных — сторож не стартует вовсе (`ValueError`). Полный список с проверками —
[03-configuration.md](03-configuration.md), раздел 3.

## 6. Чего сторож не проверяет

- **Не опрашивает OpenRouter, историан, шлюз, агентов и кабинет преподавателя напрямую** — только читает уже
  готовый результат опроса `core` (ручки `/health/*`); если `core` не ответит вовсе, соответствующая строка
  (а не сторож) покажет «не отвечает»/«неизвестно», но сторож не делает собственного сетевого похода к
  OpenRouter или историану.
- **Не инспектирует через Docker API ни `pcbk-edge`, ни сам `pcbk-watchdog`** — правило доступа `sp-ro`
  (раздел 3) этого физически не разрешает; состояние `edge` видно только косвенно через TLS-рукопожатие
  (строка `tls`), собственное зависание сторожа видно только по `/healthz` и по тому, что страница сама
  показывает полосу молчания (раздел 2 и `status.js`) — изнутри себя сторож не проверяет.
- **Не видит полного списка контейнеров сервера** и не умеет `exec`/`logs`/`start`/`stop` — `sp-ro` отдаёт
  только `_ping` и `inspect` поимённо разрешённых контейнеров (раздел 3); пробуждением и остановкой мест
  занимается шлюз через отдельный прокси `sp-ctl` ([13-gateway.md](13-gateway.md)), не сторож.
- **Не знает логинов, паролей, номеров мест конкретных студентов, имён тегов и содержимого разговоров** —
  ручки `/health/*`, которые он читает, отдают только счётчики и флаги (докстринги `check_gateway`/
  `check_agents`/`check_teacher`: «без логинов и номеров мест»).
- **Не имеет своей строки для аналитики корпуса (роль `analytics`)** — в `components.json` такой строки нет;
  опциональная роль `analytics` ([16-analytics.md](16-analytics.md)) на странице состояния не отражена.
- **Сам ничего не перезапускает и не лечит** — он только показывает состояние; `docker restart` зависшего
  контейнера делает отдельный скрипт `pcbk-autoheal.sh` по `cron` (раздел 10), не сторож и не его HTTP-сервер.
- **Не хранит и не показывает данные дольше `EVENTS_ON_PAGE = 20` последних событий на странице** — для более
  длинной истории нужно читать `journal.db` напрямую (SQLite, раздел 4).

## 7. Как добавить свою проверку

**Новая строка существующего вида** — просто новый объект в `watchdog/components.json` с полями, какие требует
`KINDS` (таблица в `main.py`):

| `kind` | Обязательные поля сверх `id`/`title` | Необязательные |
|---|---|---|
| `memory` | — | — |
| `http` | `url` | `ok_detail` (непустая строка) |
| `tls` | `host`, `port` | — |
| `docker_ping` | — | — |
| `container` | `container` (имя вида `pcbk-[a-z0-9-]+`), `sleeping_ok` (булево) | `unhealthy_detail` (непустая строка, ≤ 80 знаков) |
| `historian` / `llm` / `gateway` / `web` / `agents` / `teacher` | `url` | `web`: `reports_url` (строка `http://` с хостом) |
| `absent` | — | служит для тестов/синтетических наборов — в живом `components.json` такой строки нет |

Правила `load_components` (при нарушении — исключение при старте, контейнер не поднимается): `id` уникален и не
совпадает с зарезервированными `journal`/`watchdog`; вид — из `KINDS`; у вида `container` имя контейнера должно
совпасть с `CONTAINER_NAME`; `ok_detail` — только у `http`, непустая строка; `unhealthy_detail` — только у
`container`, непустая строка до 80 знаков; `reports_url` — только у `web`, строка `http://` с непустым хостом.
После правки файла — пересборка и пересоздание образа сторожа:
```bash
docker compose build watchdog && docker compose up -d --no-build --force-recreate watchdog
```
и проверка `curl -sk https://127.0.0.1:8443/status.json | python3 -m json.tool` — новая строка в `checks`,
`stale: false`.

**Место 12 и дальше** (добавление целого диапазона мест, не одной строки) требует правки в нескольких местах
сразу: регулярок `sp-ro`/`sp-ctl` в `compose.yaml` (раздел 3 — список разрешённых имён), новой подсети места,
блока `student-NN` в `compose.yaml`, новой строки `container` в `components.json`, пересборки сторожа и тестов
границ диапазона (в т.ч. `test_components_file_d4a`, который сверяет точное число строк — сейчас `24`); число
мест вынесено в одну константу `core/pcbk_core/places.py` (`PLACE_MAX`) — от неё зависят несколько модулей
`core`, но **не** `watchdog/components.json`: список строк для него нужно дополнять руками.

**Новый вид проверки** (не укладывается в одиннадцать видов живого `components.json`, таблица выше; двенадцатый,
`absent`, в `KINDS` есть, но служит только тестам) — код: функция `check_<вид>()` в
`checks.py` (чистая функция `(id, title, …) -> Check`, без побочных эффектов и без исключений наружу, кроме
документированных), запись в `KINDS` (`main.py`) с обязательными полями, ветка в `_check_one()`, при
необходимости — новая настройка в `Settings` (валидация в `__post_init__`, правило `tick_budget_s`, если
проверка идёт по сети и должна укладываться в срок такта), тесты (аналоги существующих в `tests/test_checks.py`
и `tests/test_main.py`), новая строка в `components.json`, пересборка образа.

## 8. Образ и развёртывание

`watchdog/Dockerfile`: база `python:3.12-slim` (закреплена по дайджесту), без пакетов — только копия
`components.json` и пакета `pcbk_watchdog`. Непривилегированный пользователь и группа с фиксированным `uid`/
`gid` `10002` (`pcbk-watchdog`), каталог журнала `/var/lib/pcbk-watchdog` создаётся и передаётся этому
пользователю на этапе сборки (`0750`). Процесс слушает `8090`. `HEALTHCHECK` (раздел 2) — `interval=30s
timeout=5s start-period=20s retries=3`.

В `compose.yaml` (сервис `watchdog`): `pull_policy: never` (свой образ, не с Docker Hub), `restart:
unless-stopped`, `read_only: true`, `cap_drop: [ALL]`, `security_opt: ["no-new-privileges:true"]`,
`mem_limit: 128m`. Тома: сертификат (`${TLS_DIR}/cert.pem`, `:ro`, вид проверки `tls`) и именованный том
`pcbk-watchdog-journal` на `/var/lib/pcbk-watchdog`. Сети: `pcbk-front` (к `core` и `edge`) и `pcbk-ro` (к
`sp-ro`) — **не** `pcbk-ctl` (туда сторожу ходить незачем, это сеть `sp-ctl` и `core`) и не сети мест
`pcbk-stu-NN`. Полный список переменных окружения сервиса, тома и сети стенда целиком —
[03-configuration.md](03-configuration.md), [01-architecture.md](01-architecture.md); порядок выкладки и
совместимость версий `watchdog`/`core` при обновлении (кто из них выкладывается раньше) —
[02-build-and-deploy.md](02-build-and-deploy.md).

Замена сертификата (`edge`/`watchdog` читают один и тот же файл из `TLS_DIR`): после копии нового `cert.pem`/
`key.pem` — `docker compose restart edge watchdog` (не `up`: файл уже смонтирован, перезапуск достаточен).

## 9. Тесты как спецификация поведения

`watchdog/tests/` целиком — `pytest` без внешних сервисов (фальшивые HTTP-серверы и фальшивый прокси сокета
через фикстуры `conftest.py`/`helpers.py`): `test_checks.py` (вердикты всех видов проверок и разбор ответов
служб), `test_main.py` (настройки, срок такта, HTTP-сервер, `load_components`, проводка памяти через такт),
`test_memory.py` (история тактов, причины перезапуска, давление, swap), `test_journal.py` (переходы,
переживание перезапуска), `test_docker_api.py` (`DockerReader`). `tests/js/status.test.mjs` — тест модуля
`status.js` на Node (без браузера): опрос, полоса молчания по часам браузера, устаревание. Два теста
(`test_browser_runs_status_js_on_stale_json`, `test_browser_on_real_server_with_csp`) пропускаются, если на
машине нет `google-chrome` (`CHROME is None`) — они рисуют страницу настоящим браузером под CSP сервера и
проверяют, что полоса молчания появляется у реального DOM, а не только в разборе Python/Node. Подробности
запуска тестов всего репозитория — [19-tests-and-bench.md](19-tests-and-bench.md).

## 10. Самолечение (`pcbk-autoheal.sh`)

Назначение — Docker сам поднимает **упавший** контейнер (`restart: unless-stopped`), но не делает ничего с
контейнером, который жив, но его собственный `HEALTHCHECK` считает нездоровым (`unhealthy`); этот разрыв
закрывает скрипт.

Раз в запуск (по `cron`, раздел 12 — каждые 2 минуты) для трёх контейнеров `pcbk-core`, `pcbk-edge`,
`pcbk-watchdog`:
1. `docker inspect -f '{{if .State.Health}}{{.State.Health.Status}}{{else}}none{{end}}' <контейнер>`;
2. если состояние не `unhealthy` — счётчик подряд (`logs/autoheal/<контейнер>.count`) сбрасывается в `0`, скрипт
   переходит к следующему контейнеру;
3. иначе счётчик увеличивается; при счётчике `≥ 3` (то есть контейнер застаёт `unhealthy` три запуска скрипта
   подряд — при периоде `cron` этого скрипта раз в 2 минуты, раздел 12, это примерно 6 минут непрерывной
   «нездоровости») **и** если с прошлого перезапуска этого контейнера
   прошло `≥ 1800` с (30 минут, файл `logs/autoheal/<контейнер>.last`) — `docker restart -t 30 <контейнер>`,
   счётчик и время сбрасываются.

Контейнер, остановленный администратором (`exited`, не `unhealthy`), не трогается — условие проверяет именно
`unhealthy`, а `inspect` остановленного контейнера либо не покажет `Health` вовсе (возвращает `none`), либо
последнее известное состояние не помешает скрипту (ветка `[ "$h" != unhealthy ]` пропускает его). Рабочие места
(`student-NN`) скрипт не трогает вовсе — их сон/пробуждение и перезапуск после сбоя — забота шлюза
([13-gateway.md](13-gateway.md)), не `autoheal`. Журнал — `/opt/pcbk-reserve/logs/autoheal.log` (строка на
каждое фактическое срабатывание `docker restart`, не на каждую проверку); пустой файл — вмешиваться не
пришлось. Скрипт использует только `set -u` (не `set -e`) — отсутствие файла счётчика при первом запуске не
прерывает цикл (`$(cat … 2>/dev/null || echo 0)`).

## 11. Синхронизация учётки историана (`pcbk-bdrv-sync.sh`)

Назначение — учётка (пароль) историана БДРВ заведена и обновляется на стороне Dify
(`/opt/dify/scripts/.bdrv.env`), а резервный стенд держит у себя только копию (`SECRETS_DIR/bdrv.env`). Если
пароль у Dify сменился, без этого скрипта связь `core` с историаном рвётся до ручного повтора процедуры
«Учётка историана» (копирование файла и пересоздание `core` — [10-data-service.md](10-data-service.md)).

Раз в запуск (по `cron`, раздел 12 — каждые 10 минут):
1. читает `SECRETS_DIR` из `/opt/pcbk-reserve/.env` (`grep '^SECRETS_DIR=' .env | cut -d= -f2`); нет значения
   или каталог не существует — строка в `logs/bdrv-sync.log` и выход с кодом `1`;
2. файл Dify (`/opt/dify/scripts/.bdrv.env`) не читается — строка в журнал, выход с кодом `0` (не ошибка:
   возможно, Dify сейчас выключен или путь временно недоступен — это не повод шуметь кодом выхода для `cron`);
3. `cmp -s` — содержимое совпадает с текущей копией — выход без действий;
4. иначе: копия — через временный файл в том же каталоге (`mktemp "$SD/.bdrv.env.XXXXXX"`, `umask 077`,
   `chmod 0444`, атомарное `mv -f` поверх `$SD/bdrv.env`) — так читающий файл `core` никогда не увидит
   частично записанный секрет; любой сбой на этом шаге — строка «не удалось обновить копию учётки» в журнал,
   временный файл удаляется, выход с кодом `1`;
5. строка в `logs/bdrv-sync.log` («учётка историана у Dify изменилась — копия обновлена, пересоздаю core») и
   `docker compose up -d --no-build --force-recreate core` (именно пересоздание, не `restart`: секрет привязан
   к контейнеру файлом при создании, `restart` не перечитал бы новый файл).

Скрипт **только читает** файл Dify и ничего в `/opt/dify` не меняет; `Dify` как сервис этим скриптом не
управляется и не трогается, только файл `core` на резервном стенде.

## 12. Установка `cron` и журналы

Оба скрипта ставятся **от пользователя выкладки** (не `root`), без `sudo`:
```bash
install -d -m 0755 /opt/pcbk-reserve/ops && install -d -m 0750 /opt/pcbk-reserve/logs
install -m 0755 ops/pcbk-bdrv-sync.sh ops/pcbk-autoheal.sh /opt/pcbk-reserve/ops/
( crontab -l 2>/dev/null; echo "*/10 * * * * /opt/pcbk-reserve/ops/pcbk-bdrv-sync.sh"; echo "*/2 * * * * /opt/pcbk-reserve/ops/pcbk-autoheal.sh" ) | crontab -
crontab -l
```
Строки добавляются к уже существующим записям `crontab` того же пользователя, не заменяют их. Проверка —
`tail /opt/pcbk-reserve/logs/autoheal.log /opt/pcbk-reserve/logs/bdrv-sync.log` (пустой вывод — ни одного
срабатывания с момента установки). Снять — вручную удалить две строки через `crontab -e`; сами файлы скриптов
в `/opt/pcbk-reserve/ops/` при этом можно оставить.

| Файл журнала | Кто пишет | Когда непусто |
|---|---|---|
| `/opt/pcbk-reserve/logs/autoheal.log` | `pcbk-autoheal.sh` | только при фактическом `docker restart` |
| `/opt/pcbk-reserve/logs/bdrv-sync.log` | `pcbk-bdrv-sync.sh` | при каждом обновлении копии учётки, и при двух видах ошибки (нет `SECRETS_DIR`, не удалось записать копию) |
