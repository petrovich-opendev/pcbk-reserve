## Главное для Д3

1. SQL — только литералами: провайдер `INSQL` не принимает параметры
   драйвера и отвечает `History queries must contain at least one valid
   tagname` [П 02.09].
2. **Не больше одного `LIKE`** в запросе к таблице историана: иначе `Only one
   LIKE predicate is allowed for this version of the OLE DB provider` [П 14.09].
   Лучше вовсе без `LIKE`: каталог держать в памяти службы, в SQL слать только
   `TagName = '…'` / `TagName IN ('…')` с именами из каталога.
3. Работали обращения к представлениям базы `Runtime` без префикса (`Live`,
   `AnalogHistory`, `AnalogSummaryHistory`, `StateSummaryHistory`, `Tag`,
   `AnalogTag`, `EngineeringUnit`). SQL Server сам переправляет их связанному
   серверу `INSQL` [П]. `OPENQUERY` в живых запросах не применялся ни разу.
4. Замеренный контракт: не больше 16 тегов, 31 суток и 288 точек, бюджет
   **24 тего-суток** (для одного тега — 31). На нём худший ответ — 3,91 с при
   критерии p95 ≤ 5 с. При 96 единицах ответ шёл 6,79 с [П 08.09].
5. Соединение: python-tds 1.17.1, `autocommit=True`, `READ UNCOMMITTED`,
   `LOCK_TIMEOUT 5000`, вход — 10 с, чтение — 45 с. **TLS не было** [П/Д].
6. «Сейчас» брать с часов историана (`GETDATE()`). Метка в `Live` опережает
   эти часы на десятки секунд [П 08.09]. Часовой пояс историана не
   проверен [?].
7. Среднее, минимум, максимум и σ считает сам историан по сырым данным
   (`AnalogSummaryHistory`, `wwCycleCount = 1`) [П]. Взвешено ли среднее по
   времени, не установлено [?]. Равномерная сетка (`Cyclic`) пропускает
   короткие всплески [П].
8. Наработка считается только по дискретным тегам состояний
   (`StateSummaryHistory`). Порога по аналоговому тегу не было [П].
9. Описания обрезаны на 50 символах, у большинства аналоговых тегов нет
   единицы, смысл `_MV` на регуляторах неоднозначен [П].
10. Смены 06/14/22 — допущение, технологом не подтверждено [Д].

## 2. Запросы, которые работают, и ограничения

### 2.1 Как адресуются таблицы

* **Работало:** короткие имена представлений базы `Runtime` при соединении с
  `database=Runtime`. Это `Live`, `AnalogHistory`, `AnalogSummaryHistory`,
  `StateSummaryHistory`, а для метаданных `Tag`, `AnalogTag`,
  `EngineeringUnit` [П 08.09–14.09]. Все пять инструментов плагина прошли
  приёмку на этих запросах. Источник: pcbk/plugins/pcbk_bdrv/lib/queries.py:28–101.
* SQL Server сам переправляет такое имя связанному серверу. В тексте ошибки
  14.09 видно, что запрос к `Live` ушёл провайдеру в виде
  `… FROM Runtime.dbo.Live … for execution against OLE DB provider "INSQL"`
  [П]. Поэтому ограничения провайдера действуют и без явного `INSQL.` в
  тексте запроса.
* **`OPENQUERY` в живых запросах не применялся** [П: в коде его нет]. По
  мануалу внутри `OPENQUERY` нельзя `JOIN`, `ORDER BY` и `GROUP BY`, из
  агрегатов допустимы только MIN/MAX/AVG/SUM. Строка ограничена 8000
  символами, переменные не допускаются, дата пишется как
  `гггг-дд-мм чч:мм:сс.ммм` [Д SQL.pdf с. 92–93, 95; kb/data-access.md:173,
  187, 287]. `WideHistory` доступна только через `OPENQUERY`/`OPENROWSET`
  [Д kb/data-access.md:43–49].
* Четырёхчастные имена `INSQL.Runtime.dbo.*` мануал рекомендует [Д с. 96;
  kb/data-access.md:51–57]; в живых запросах они не проверялись [?].
  `AnalogHistory` и другие типовые таблицы мануал называет устаревшими, но на
  этом сервере они работали [П; Д kb/data-access.md:59].

### 2.2 Параметры запрещены

* Параметры драйвера (RPC) для `TagName` провайдер не принимает. Имя тега
  обязано стоять литералом в тексте SQL, иначе приходит `History queries must
  contain at least one valid tagname`, даже когда значение параметра
  верное [П 02.09]. Источники: pcbk/REPORT-bdrv-live-verification-2026-09-02.md:22–26;
  память pcbk-obuchenie-project.md:15; pcbk/plugins/pcbk_bdrv/lib/queries.py:11–13.
* **Почему** [Д, вывод из текста ошибки]: провайдер ищет имена тегов в
  тексте `WHERE` ещё при подготовке запроса, а у параметра значения в этот
  момент нет.
* Следствие для службы: подстановка литерала неизбежна. Защищает не
  экранирование, а правило «в SQL уходит только строка из каталога» (2.9).

### 2.3 Одно условие `LIKE`

* **Дословно [П 14.09]:** запрос к `Live` вида
  `WHERE Value IS NOT NULL AND (TagName LIKE '%[_]MV' OR TagName LIKE '%[_]LMN' OR TagName LIKE '%[_]PV')`
  завершился ошибкой `OLE DB provider "INSQL" for linked server "INSQL" returned
  message "Only one LIKE predicate is allowed for this version of the OLE DB
  provider"`. Источник — транскрипт сессии 14.09.2026, 12:20 UTC
  (`~/.claude/projects/-home-dev/ea9aa071-a171-4515-a166-3f915b79ecbc.jsonl`,
  строка 21139); запись в резерве — ZADACHA:600–603. В отчётах
  `pcbk-ai-lab` этого факта нет.
* Обход, который сработал [П 14.09]: `SELECT TagName, Value FROM Live WHERE Value IS NOT NULL`
  без фильтра по имени, отбор по суффиксу — в Python.
* Где действует ограничение: ошибку дал провайдер на таблице историана
  (`Live`). На обычной таблице `Tag` одиночный `NOT LIKE '$%'` работал
  [П, pcbk/scripts/bdrv/gen_whitelist.py:197–202]. Несколько `LIKE` на `Tag`
  не проверялись [?].
* Прочие ограничения по мануалу [Д]:
  * `LIKE` допустим только для столбцов `TagName` и `Value` (с. 94);
  * `LIKE` внутри `IN` для аналоговых и дискретных тегов запрещён (с. 94);
  * `OR` для нескольких условий по времени запрещён (с. 95);
  * `IN` и `OR` по ww-столбцам запрещены — например
    `wwVersion IN ('original','latest')` (с. 100; kb/data-access.md:288).
* В `LIKE` подчёркивание — подстановочный знак, его экранируют как `[_]`.
  Такую запись провайдер принял; отказ был только из-за числа условий [П].
  Строковые литералы SQL Server передаёт провайдеру как `N'…'` [П, текст
  ошибки].

### 2.6 Формат даты

* В запросы подставлялся литерал **`'YYYY-MM-DD HH:MM:SS.000'`** (время
  сервера историана, без пояса), и он работал: сводка сошлась с прямым SQL
  с разницей 0,000e+00 [П 08.09]. Источники:
  pcbk/plugins/pcbk_bdrv/lib/periods.py:65–69; pcbk/REPORT-C9-bdrv-plugin-2026-09-08.md:23–24.
* Мануал рекомендует `ГГГГММДД чч:мм:сс.ххх` (с. 23), а внутри `OPENQUERY` —
  `гггг-дд-мм чч:мм:сс.ммм` (с. 92) [Д].
* Для типа `datetime` строка `YYYY-MM-DD` читается по-разному в зависимости
  от языка сессии (`DATEFORMAT`) [Д, общая документация SQL Server]. Язык
  по умолчанию у учётки историана не проверен [?].
* pytds возвращает `datetime` без пояса [П: код форматирует его через
  `strftime`].

### 2.9 Перцентили, профиль, наработка

* Перцентили: `SELECT DISTINCT TagName, PERCENTILE_CONT(0.50|0.95) WITHIN GROUP (ORDER BY Value) OVER (PARTITION BY TagName)`
  по `AnalogHistory` с `Cyclic` и `wwCycleCount = 1440`. Окно считает сам SQL
  Server по строкам, которые отдал провайдер [П; queries.py:58–75].
* Профиль: `AnalogHistory`, `Cyclic`, `wwCycleCount = N`,
  `ORDER BY TagName, DateTime` [П; queries.py:78–89].
* Наработка:
  `SELECT TagName, vValue, StateTimeTotal, StateTimePercent, StateCount FROM StateSummaryHistory WHERE … AND wwCycleCount = 1`.
  `StateTimeTotal` — в миллисекундах. Бывают строки с `vValue IS NULL` и
  нулевым временем; их отбрасывали как шум [П; queries.py:92–101;
  tools/bdrv_runtime.py:45–54].

### 2.10 Предел строк в старом контракте

Не больше 16 тегов за вызов. Профиль — до 288 точек на тег, то есть до 4608
строк. Перцентили обрабатывают до 1440 точек на тег (до 23 040 строк) на
стороне сервера, а наружу уходит одна строка на тег
[П; lib/budget.py:24–32].

### 2.11 Качество

* `Live.Quality`: **0 — хорошее у этого историана** [П, «проверено на живых
  данных», tools/bdrv_now.py:26–27]. Любое другое значение — подстановка или
  потеря связи.
* При потере связи с ПЛК историан держит последнее значение, и по возрасту
  метки это не видно — ловится только по качеству [Д: довод ревью, живьём
  не воспроизводили; pcbk/REPORT-review-2026-09-08.md:23–27].
* `PercentGood` из сводки показывался, если он ниже 99 % [П;
  tools/bdrv_summary.py:92–93].
* `OPCQuality` и `QualityDetail` не использовались. По мануалу
  `QualityDetail = 192` значит хорошее качество от сервера ввода-вывода,
  справочники кодов — таблицы `QualityMap` и `OPCQualityMap` базы `Runtime`
  [Д с. 35–37].
* Профиль и наработка качество не учитывали [П]; ревью оставило это
  открытым (REPORT-review:94–96).

### 2.12 Имена тегов в SQL

* Экранирование — не главный механизм. В SQL уходит только строка из
  каталога: ввод пользователя сверяется с каталогом на точное совпадение
  (регистр неважен) и дальше отбрасывается [П; lib/whitelist.py:1–7, 74–83;
  REPORT-C9:40–47].
* Вторая линия защиты: `re.fullmatch(r"[A-Za-z0-9_.$-]+")`. Именно
  `fullmatch`: у `match` знак `$` пропускает хвостовой перевод строки
  (нашло ревью) [П; lib/whitelist.py:16–20].
* Все 1104 имени в белом списке состоят из латиницы, цифр и `_` [П, подсчёт
  по файлу]. В самом историане есть имена с точкой и обратной косой чертой
  (диагностика приводов) и с префиксом `$` (системные); в список они не
  брались [П; gen_whitelist.py:120–125, 200].
* Регистр имён тегов зависит от сравнения (collation) сервера [Д
  kb/data-access.md:289]; на этом сервере не проверялось [?]. Значения
  ww-параметров к регистру нечувствительны [Д с. 100].

### 3.6 Правило белого списка в `pcbk-ai-lab`

Правило, а не список; сам список — производственные данные, в git его нет
(решение владельца №10, 07.09 [Д]; README резерва).

1. **Аналоговые** — все `TagType = 1` вместе с единицей и шкалой. Отбрасывались
   служебные хвосты `_LMN`, `_TH`, `_HMI`, `_SP_HMI`, `_MV1`, `_m3`
   [П; gen_whitelist.py:114–118, 161–180]. **Выход регулятора `_LMN` в список
   не входил**, хотя §4 резерва перечисляет его среди суффиксов.
2. **Дискретные** — `TagType = 2`, кроме имён на `$`. В список шли только
   хвосты состояний (`_RUN/_OPN/_CLS/_ON/_OFF/_STOP/_FLT/_ALM`). Отбрасывались
   диагностика приводов (на одном узле её 217 тегов) и мониторинг связи с ПЛК
   [П; gen_whitelist.py:120–125, 196–225].
3. **Узел определялся по описанию, а не по номеру в имени.** Русские
   регулярные выражения проверялись по порядку, первое совпадение выигрывало,
   общие по машине шли первыми. Первая версия раскладывала по номеру в имени
   и ошиблась: в мокрую часть попали узлы прессовой части и маслостанции
   [П; gen_whitelist.py:31–67].
4. Группа качества полотна отбиралась по префиксу имени системы качества
   [П; gen_whitelist.py:110–112, 143–150].
5. **Проход 2** — «однофамилец»: неотнесённый тег получал узел другого тега с
   той же основой имени. **Проход 3** — ручная таблица из 10 семейств с
   описанием из историана в комментарии [П; gen_whitelist.py:80–104, 227–253].
6. **Отчёт о каждом неотнесённом теге участка.** Участок — имена, которые
   начинаются с номера участка 20…25. Остальное (16xx, 17xx, 18xx, 29xx, 33xx)
   законно вне пилота [П; gen_whitelist.py:106–108, 255–261].
7. **Живость**: в `Live` есть строка с `Value IS NOT NULL`. Проверялось
   отдельным запросом на каждый тег; можно одним запросом, см. 2.7
   [П; gen_whitelist.py:263–273].
8. Пустой результат не записывался поверх рабочего файла [П;
   gen_whitelist.py:280–284].
9. Поля записи: `tag`, `kind`, `desc`, `unit`, `min_eu`, `max_eu`, `live`
   [П].
10. В форме калькулятора — до 40 измерений (порядок хвостов `_PV`, без
    хвоста, `_MV`, `_SP`, `_LOD`, `_SPD`, `_OP`) и до 20 состояний; остальное
    агенту доступно через инструмент [П; gen_calculator.py:51–58].

По резерву (вопрос 6): каталог служба берёт из историана сама, агент ищет
тег по словам, при промахе показывает несколько похожих; словаря сокращений
нет [Д; ZADACHA:233–243; DESIGN-platform:157–167].

### 4.3 Кэш

Устройство [П: код и ревью; lib/cache.py:16–32; lib/periods.py:92–101;
lib/base.py:73–90]:

* ключ — sha256 от инструмента, тегов, границ периода и параметров;
* время жизни: закрытый период (конец старше 300 с) — **3600 с**, открытый —

  протухнет раньше;
* **single-flight**: одинаковые параллельные запросы считаются один раз;
* «сейчас» **округляется до 30 с**, иначе ключ открытого периода менялся
  каждую секунду.

Кэш жил в памяти процесса и обнулялся при переустановке.

  разу;
* десять одинаковых тяжёлых запросов от десяти студентов уходили на сервер
  по одному на каждого — лечится single-flight;
* каждый SELECT висел в незакоммиченной транзакции (1.11);
* «последние 30 суток» были недостижимы ни при каком числе тегов, пока не
  ввели послабление для одного тега;
* журнал INFO не доходил до лога: у корневого журнала уровень WARNING
  (lib/budget.py:42–57).

**Настоящего таймаута запроса к историану в отчётах нет** [?]: ни одного
случая не записано.

### 4.5 Одна служба на стенд

Защита держалась на том, что плагин был **одним долгоживущим процессом**.

lib/periods.py:3–14; lib/base.py:100–104; PLAN-stand-autonomy:310; REPORT-C9:126].

### 5.5 Часовой пояс

  своего сервера (с. 23, 139–140) [Д].

* Пояс сервера стенда — Asia/Yekaterinburg [П 03.09;
  pcbk/REPORT-nightagent-blockB-deployed-2026-09-03.md:9]. Пояс сервера
  историана не проверен [?].

## 6. Ловушки историана

1. **Параметры драйвера** → `History queries must contain at least one valid
   tagname` [П] (2.2).
2. **Больше одного `LIKE`** → `Only one LIKE predicate is allowed…` [П] (2.3).
3. **Нет тега — ответы разные.** Базовое имя или несуществующий тег в
   истории дают ошибку; в `AnalogSummaryHistory` — 0 строк без ошибки; в
   `Live` — нет строки. «Нет тега» и «нет данных» служба различает по
   каталогу, не по ответу историана [П].
4. **Запрос к истории без имени тега** падает [П]; весь `Live` без имени —
   нет [П].
5. **Метка `Live` впереди часов историана** на десятки секунд (однажды
   −31 с), и возраст выходил отрицательным. Возраст приводили к нулю, а
   расхождение больше 60 с объясняли строкой [П 08.09;
   tools/bdrv_now.py:33–39, 50–51, 71–73].
6. **Задержка живых данных.** Владелец 02.09 ждал задержки «десятки секунд —
   минуты» [Д, память pcbk-obuchenie-project.md:13]; живьём её не мерили
   [?]. Старый инструмент считал значение залипшим после 600 с
   (tools/bdrv_now.py:47).
7. **Мёртвые теги**: 325 из 1104 тегов списка живого значения не дают;
   причина по каждому — вопрос АСУТП [П, подсчёт; kb/data-access.md:266–267].
8. **Залипшее значение при потере связи** видно только по качеству [Д] (2.11).
9. **Обрезанные описания** ломают поиск по словам и правила отнесения [П] (3.3).
10. **Единица `None`**, у большинства тегов единицы нет [П] (3.4).
11. **`_MV` на регуляторах**, **`_CLS` = 1 — закрыт**, **`…_1_PV` ≠ `…_PV`**
    [П] (3.5).
12. **Сетка `Cyclic` теряет короткие события**: всплеск и события короче шага
    [П] (2.8, 5.2).
13. **Квантование и сглаживание на части тегов**: соседние отсчёты часто
    совпадают. На таких участках статистика устойчивого режима давала
    ложные всплески на два порядка выше сигнала от настоящего события [П 02.09;
    REPORT-bdrv-live-verification:44–69]. Это касается σ и оценок «ровно или
    колеблется».
14. **Пояс и летнее время.** Хранится UTC, отдаётся местное время сервера
    историана. Пояс историана не проверен [?]. Перехода на летнее время в РФ
    с 26.10.2014 нет [Д, общее знание], но правила пояса в Windows сервера
    историана должны быть актуальны [?].
15. **Формат даты** зависит от языка сессии [Д/?] (2.6).
16. **Нет TLS** [П/Д] (1.8).
17. **Без `autocommit` каждый SELECT живёт в открытой транзакции** [П] (1.11).
18. **Мануал 9.0 старше сервера** [П/Д]. Ограничения `OPENQUERY`, пределы
    строк `Delta` и `Cyclic` и умолчания ww-параметров — по мануалу [Д].
19. **Усечённый `WHERE`.** В редких случаях SQL Server отбрасывает «лишнее»
    условие (`WHERE TagName LIKE '%'`); лечится ещё одним условием [Д с. 97].
20. **Кириллица.** Описания и единицы — `nvarchar`, pytds читает их без
    искажений [П]. Для поиска по словам нужны нижний регистр и замена «ё» на
    «е» [Д].

## Рекомендации для плана Д3

1. **Начать день с пробы на 8–10 читающих запросов** (О1–О4, О11): версия,
   пояс, язык, столбцы сводки, два формата даты, разброс возраста `Live`.
   Итоги — вердиктами в `docs/checks/D3.md`, без адресов и значений тегов.
2. **Шаблоны SQL фиксированы и без `LIKE`** к таблицам историана. Имя тега
   попадает в SQL только из каталога службы, через `=` или `IN` (до 16
   имён). Вторая линия — `fullmatch` безопасного набора символов и удвоение
   `'`. Тест без историана проверяет каждый шаблон: нет параметров
   драйвера, не больше одного `LIKE`, `IN`/`OR` не стоят на ww-столбцах, нет
   `wwResolution` вместе с `wwCycleCount` в `Cyclic`.
3. **Каталог — в памяти службы.** Грузить при старте и раз в сутки: `Tag`,
   `AnalogTag` и `EngineeringUnit` одним запросом, живость — одним снимком
   `Live WHERE Value IS NOT NULL`. Поиск по словам — в Python (нижний
   регистр, «ё»→«е», поиск и по имени, и по описанию). При промахе —
   варианты по основе имени и суффиксу. Файл каталога — на сервере, не в
   git.
4. **Соединение**: python-tds, `autocommit=True`, в начале каждого запроса
   `SET LOCK_TIMEOUT 5000; SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED`,
   `login_timeout=10`, `timeout=45`. Поверх — **общий предел на вызов
   инструмента** (например, 15 с) и **одно соединение на вызов**, а не три.
   TLS — по ответу на О5.
5. **Учётные данные — файлом `:ro`** (правило Д1), не переменными
   окружения. Имена полей оставить как прежде (`BDRV_HOST`, `BDRV_DB`,
   `BDRV_USER`, `BDRV_PW`, `BDRV_PORT`), чтобы исходник взять из
   `/opt/dify/scripts/.bdrv.env` без переименований. §4 проекта поправить.
6. **Бюджет и кэш — замеренные числа как стартовый контракт**: 16 тегов,
   31 сутки, 288 точек, 24 тего-суток (1 тег — 31), 60 вызовов за 5 мин на
   студента. Кэш 3600/30/15 с, округление «сейчас» до 30 с, single-flight.
   Добавить то, чего не было: **общий предел одновременных запросов к
   историану** (семафор на 2–3) и общий счётчик частоты на всю службу.
7. **Каждый ответ говорит, что посчитано**:
   * источник (сводка по сырым данным или сетка);
   * вид среднего (по итогам О2);
   * пояс и сдвиг (по итогам О3);
   * флаг допущения смен;
   * доля достоверных, качество и возраст значения;
   * «нет тега» и «нет данных» — разными словами.
8. **`tag_period`**: среднее, минимум, максимум и σ — из сводки; размах =
   `Maximum − Minimum` той же сводки, а не по сетке; «последнее» — из
   столбца сводки, если он есть (О2), иначе отдельным шаблоном. Перцентили
   и профиль — `Cyclic` с `wwCycleCount`. Наработка — позже (Д9), тем же
   путём через `StateSummaryHistory`, с подписью по суффиксу и проверкой
   полноты периода.
9. **Свежесть историана для сторожа**: максимум `Live.DateTime` по
   нескольким всегда живым тегам против `GETDATE()`. Метки из будущего
   приводить к нулю, а расхождение показывать; порог — по итогам О11.
   Учение «метка историана устарела» — подменой порога или часов в тесте, не
   трогая историан.
10. **Сверка «служба = прямой расчёт» (критерий Д3)** — независимым путём:
    для одного тега за короткий период взять сырой `Delta` и посчитать
    среднее по времени и арифметическое самим. Повтор того же запроса к
    сводке определения среднего не проверяет.
11. **Журнал вызовов** — в поток ошибок или в файл, уровень INFO, с явной
    настройкой обработчика. Записывать тег, период, стоимость, попадание в
    кэш, число строк и время — это же события агента из §4.
