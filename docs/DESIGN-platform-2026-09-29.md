## 1. Компоненты (раздел 1, согласован; редакция 2 — дополнено)

```
Браузер ──► НАШ ПРОКСИ :8443 (или :443, §2) ─┬─► СЕРВЕРНЫЙ СЛОЙ (Python, FastAPI)
                                              │     ├─ шлюз ─────► OpenCode студента N
                                              │     │               (своя сеть на студента)
                                              │     ├─ LLM-прокси ◄── ─┘      └─► OpenRouter
                                              │     └─ служба данных (MCP) ◄──┘  └─► БДРВ :1433
                                              └─► СТОРОЖ: страница состояния (в обход
                                                  серверного слоя), журнал
```

1. **Наш прокси** — единственная точка входа снаружи: TLS с сертификатом
   `ai-lab.pcbk.ru`, отдаёт веб, шлюз и страницу состояния сторожа.
2. **Веб** — React, TypeScript, assistant-ui (`@assistant-ui/react-opencode`).
   Студент: чат, свои агенты, калькуляторы (прямой вызов тех же калькуляторов
   службы), страница состояния. Преподаватель: разговоры и агенты студентов
   только на чтение, учётные записи, доли бюджета. **Предупреждение о статусе
   стенда видно постоянно** («Состав задачи», п. 1).
3. **Серверный слой** — одно приложение на Python (FastAPI), три роли в одном
   процессе; снаружи доступен только шлюз, через наш прокси:
   * **шлюз** — вход, роли, выбор контейнера по учётной записи, белый список
     вызовов, вырезание опасных полей и параметров, поток ответа (SSE);
   * **LLM-прокси** — OpenAI-совместимая точка для OpenCode, ключ OpenRouter,
     учёт цены, доли и жёсткий стоп;
   * **служба данных** — MCP (Streamable HTTP) для агентов и HTTP для веба;
     пароль БДРВ, белый список тегов, общий бюджет запросов и кэш — только
     здесь.
   Один процесс — бюджет, кэш и учёт расходов в одном месте; Python —
   калькуляторы по ответу 1 постановки — Python-скрипты.
4. **Контейнеры студентов** — OpenCode **v1.18.33** (Б3), образ собираем сами
   (§6). **Решение владельца 29.09.2026 — готовые контейнеры и узкий прокси
   сокета:** десять контейнеров `student-01…10` создаёт администратор один раз
   при выкладке (Docker Compose, фиксированные настройки §6); во время работы
   серверный слой ходит к Docker только через готовый прокси сокета
   (docker-socket-proxy), который разрешает запуск, остановку, осмотр и список
   контейнеров и запрещает создание, exec, тома, образы и всё прочее. Даже при
   ошибке в нашем коде нельзя создать новый, в том числе привилегированный,
   контейнер. Новый студент — правка Compose администратором. Проверить [?]:
   текущая версия прокси умеет пускать start/stop без общего разрешения POST.
   Причина: полный сокет — это права root на сервере рядом с Dify, а до
   серверного слоя из сети каждого студента доходят служба данных и LLM-прокси;
   изоляция студентов и пароля БДРВ обязательна (вопрос 15 постановки).
5. **Хранение** — SQLite: учётные записи, доли и учёт расходов, события
   агентов. Файлы агентов — на сервере, в контейнер только на чтение.
   Разговоры — том контейнера студента.
6. **Сторож** — отдельный контейнер: ловит тишину, ведёт журнал и **сам отдаёт
   страницу состояния** через наш прокси, в обход серверного слоя, — чтобы
   страница работала, когда серверный слой лёг (§8). Состояние контейнеров
   студентов видит через тот же прокси сокета, только на чтение.
7. **Прокси сокета Docker** — отдельный контейнер (п. 4); единственный, у кого
   есть `docker.sock`.

## 2. Вход и сеть (поправка к разделу 1, согласована; редакция 2 — сеть)

* **Вход А, сначала:** наш прокси на отдельном порту (например 8443) с тем же
  сертификатом; Dify не трогаем. Проверка — из сети ПЦБК в первом слайсе (нужен
  человек там).
* **Вход Б, если периметр режет порт:** наш прокси на 80/443 перед Dify и нами,
  nginx Dify — на внутренний порт через `/opt/dify/docker/.env`; короткий
  перерыв Dify, откат готов; сбой нашего прокси кладёт и Dify.
* Причина: вход 80/443 держит nginx внутри Dify [П], за ним критерий 3 «Dify
  выключен целиком» не выполняется.
* Факты [П]: с машины разработчика до сервера доходит только SSH — веб
  проверяем через SSH-туннель; на сервере ufw с политикой `DROP`, порты
  Docker идут в обход ufw; пропустит ли периметр заказчика новый порт — [?].
* **Сеть — своя на каждого студента** (редакция 2): в сети студента только его
  контейнер и серверный слой, `internal: true` (ни БДРВ, ни интернета).
  Причина: в одной общей сети контейнеры видят друг друга, и путь «контейнер
  А → OpenCode студента Б» шёл бы мимо шлюза.
* **Свой пароль сервера OpenCode на каждый контейнер**
  (`OPENCODE_SERVER_PASSWORD`): знают его шлюз и сам контейнер, другие
  контейнеры — нет.

## 3. Пути пользователя (раздел 2, согласован)

1. **Вход.** Логин и пароль (учётки заводит преподаватель). Спящее рабочее
   место шлюз поднимает — «Готовлю рабочее место…»; холодный старт замерить
   [?]. При первом входе — предупреждение, что преподаватель видит разговоры.
2. **Создание агента в чате — успех 1.** Встроенный агент «Конструктор» (наша
   редакция генератора OpenCode `generate.txt` под технологов) расспрашивает:
   узел, цель, вопросы; сам ищет теги в каталоге; показывает черновик (имя,
   назначение, инструменты, правило «не выдумывать нормативы»); по согласию
   вызывает `save_agent`. Служба проверяет черновик (инструменты только из
   нашего списка, без оболочки, правки файлов и `apply_patch`, имя уникально),
   пишет файл в каталог агентов студента. Перезагрузка OpenCode студента
   (`POST /instance/dispose` [?]) — **после окончания хода Конструктора**, чтобы
   не оборвать его ответ; проверить на живом потоке [?].
3. **Число из БДРВ — успех 2.** Агент вызывает калькулятор или запрос по тегу с
   токеном студента; служба: белый список, бюджет запросов, кэш, SQL строит
   сама; ответ — число, тег, период, время. Каждый вызов — событие агента.
4. **Просмотр преподавателем.** Список студентов, их разговоры и агенты — только
   чтение. Студенты друг друга не видят. Как читать разговоры спящего студента
   — будить его контейнер только на чтение или читать его том напрямую —
   решить в плане [?].
5. **Деньги.** LLM-прокси считает цену каждого вызова по данным OpenRouter;
   доля студента по умолчанию **$100** из **$1000** на всё обучение (решение
   18), преподаватель перераспределяет; на 100 % доли или общего бюджета —
   понятное сообщение в чате; у агента — предел шагов на ответ.

## 4. Служба данных

**Состав** — по «Составу задачи», п. 3: калькуляторы — среднее, минимум,
максимум, размах, профиль, наработка; запрос по тегу — текущее значение, ряд,
сводка по любому тегу белого списка за любой период в пределах бюджета;
каталог тегов из историана с поиском по словам.

**Инструменты агентов (MCP) — предложение, имена и порядок уточняются в плане:**

| Инструмент | Что делает | Когда |
|---|---|---|
| `catalog_search` | поиск тегов участка по словам в имени и описании | первый работающий чат |
| `tag_now` | текущее значение, время, качество | первый работающий чат |
| `tag_period` | сводка за период: среднее, минимум, максимум, размах, последнее | первый работающий чат |
| `tag_series` | ряд значений за период с ограничением числа точек | следующие слайсы |
| `calc_profile`, `calc_runtime` | профиль, наработка | следующие слайсы |
| `save_agent` | проверка и запись файла агента | первый работающий чат, только Конструктор |

Калькуляторы — Python-код службы, один и тот же для агента, для страницы
калькуляторов в вебе и для проверки успеха 2. Какое среднее считается (по
времени или арифметическое), границы смены и часовой пояс — определить явно и
писать в ответе инструмента.

**Требования из фактов об историане** (решение 17 — переходят как требования,
не как код):

* учётка только на чтение; пароль — в переменных службы, в git никогда;
* в запросе к INSQL — одно условие LIKE, без параметров: SQL строится из
  шаблонов службы с экранированием, свободного SQL нет;
* суффиксы `_PV/_SP/_MV/_LMN`; **смысл `_MV` на регуляторах не установлен**
  (вопрос технологу и АСУТП) — служба не угадывает, а показывает описание тега;
* описания тегов обрезаны на 50 символах — при промахе агент показывает
  студенту несколько похожих тегов на выбор;
* белый список — теги участка по правилу и исключения; сам список —
  производственные данные, живёт на сервере, не в git.

**События агента** — на каждый вызов: время, студент, агент, инструмент, тег,
период, результат кратко. Нужны преподавателю и слою событий мнемосхем
(подпроект 2).

## 6. Контейнер студента

* gVisor (`runsc`, платформа systrap — без KVM [Д]); **на сервере не
  установлен [П]** — ставится в плане, нужен sudo;
* пользователь без root, корневая ФС только чтение, `cap-drop ALL`,
  `no-new-privileges`, лимиты памяти, процессов и процессора (предложение:
  память 1 ГБ — на 10 контейнеров хватает: доступно 11,7 ГБ [П]; замерить [?]);
* тома: свой — разговоры (запись), каталог агентов — только чтение; сокета
  Docker нет;
* OpenCode: провайдер — наш LLM-прокси; MCP remote — служба данных с токеном
  студента (`{env:…}` [Д]); свой пароль сервера (§2);
* **заглушки** `bash`, `edit`, `write` и `apply_patch` (последний v1.18.33
  включает для моделей `gpt-*` вместо edit/write) — в **глобальном** каталоге
  инструментов образа `~/.config/opencode/tools/`, а не в проектном
  `.opencode/tools/`: проектный каталог зависит от выбранного каталога
  экземпляра (§7) [Д]. Каждая заглушка экспортируется через `export default`
  (иначе имя станет `bash_<имя>`) [Д]. Каталоги, которые OpenCode читает позже
  и которые перебивают глобальный (проектный `.opencode`, `~/.opencode`,
  `OPENCODE_CONFIG_DIR`), в образе отсутствуют и недоступны на запись [Д];
* при корневой ФС только на чтение OpenCode не доустановит
  `@opencode-ai/plugin` — пакет и служебные файлы кладутся в образ заранее [?];
* `share: disabled`; автообновление и загрузка списка моделей выключены;
* контейнеры созданы заранее (§1 п. 4); запуск при входе, остановка после 30
  минут простоя; падение или убийство по памяти — перезапуск и запись в
  журнал.

## 7. Изоляция (раздел 3, согласован; редакция 2 — дополнено)

Три слоя, каждый держит сам:

1. **Контейнер и сеть** — §6 и §2: своя сеть на студента, свой пароль

   `x-opencode-directory` вырезаются, каталог экземпляра задаёт шлюз**
   (OpenCode v1.18.33 берёт каталог из них без проверки [Д]); ручки оболочки, терминала, файлов, конфигурации, MCP, ключей,
   обновлений — отказ [Д, research/02]; преподавателю — только чтение.
3. **Служба и прокси** — §4, §5.

## 8. Наблюдаемость (Б5 с поправкой; редакция 2 — раньше и в обход)

* **Ловим тишину, а не только ошибки:** служба данных молчит дольше минуты; у
  историана стоят метки времени; OpenRouter отвечает 402 или ошибками подряд;
  бюджет на 50 / 80 / 95 %; контейнер студента упал или убит по памяти; память
  сервера ниже порога (рядом Dify); сердцебиение самого сторожа — его ловит
  серверный слой, и если страница сторожа не отвечает или устарела, баннер в
  вебе показывает «состояние неизвестно».
* **Куда:** страница состояния (её отдаёт сам сторож, в обход серверного слоя)
  и баннер у преподавателя и студентов; журнал — дополнительно. Раз Telegram
  отложен, страница и баннер — единственное место, куда смотрит человек,
  поэтому они строятся **в первом же веб-слайсе**, а не в конце (§12).
* **Отложено владельцем:** Telegram и внешнее сердцебиение. Сторож устроен
  так, чтобы канал подключался позже без переделок.

## 9. Проверка критериев (раздел 3, согласован; редакция 2 — дополнено)

| Критерий | Как проверяем |
|---|---|
| Успех 1 — агент за один разговор | вручную: студент-доброволец после одного показа, секундомер, без помощи; автоматически: бот-студент (Opus в роли технолога) на отборе модели |
| Успех 2 и неуспех 4 — число = калькулятор | автотест: набор тегов и периодов, ответ агента против прямого вызова калькулятора |
| Успех 3 — без Dify | все сквозные тесты при полностью остановленном Dify, затем Dify включаем |
| Успех 4 — белый список и бюджет | 10 ботов-студентов одновременно; по журналу службы — ноль запросов мимо списка, бюджет не превышен |
| Успех 5 и неуспех 3 — только своё | автотест через шлюз: студент А пытается получить сессии и агентов Б подменой id и заголовков — 403; **из контейнера А нет маршрута к контейнеру Б** |
| Успех 6 — $1000 | учёт LLM-прокси; прогноз пересчитывается через две недели работы |
| Неуспех 1 — оболочка, пароль | автотест: опасные вызовы OpenCode через шлюз — 403; **запрос с чужим `directory` или `x-opencode-directory` — параметр вырезан, заглушки на месте**; изнутри контейнера нет пароля в переменных и файлах, нет маршрута к 1433 и в интернет |
| Неуспех 2 — выдуманный норматив | ловушки на отборе модели + правило в промпте агента, проверяет судья |
| Наблюдаемость (правило владельца) | остановить службу, состарить метку историана, убить контейнер студента — страница состояния и баннер показывают сбой не позже порога |

В конце реализации — скан claude-security (ставится с согласия владельца, Б1).

## 10. Выбор модели (Б4)

Отбор — один дневной слайс **сразу после первого работающего чата**. Первый
работающий чат здесь — веб, шлюз, контейнер студента, служба с `tag_now`,
`tag_period`, `catalog_search`, `save_agent` и минимальный Конструктор: без

## 13. Уточнения по проверке фактов 29.09.2026 (до плана Д1)

Проверки — [`research/04-d1-facts.md`](research/04-d1-facts.md). Решения
владельца не меняются; меняются средства.

1. **Прокси сокета (§1 п. 4, 7)** — вопрос [?] закрыт: у
   tecnativa/docker-socket-proxy start/stop без общего разрешения POST не
   работают, а с ним открываются create и exec. Берём
   **wollomatic/socket-proxy 1.13.1 двумя копиями**: `sp-ctl` для серверного
   слоя (осмотр и start/stop **только** контейнеров `pcbk-student-01…10`) и
   `sp-ro` для сторожа (только осмотр своих контейнеров). **Списка
   контейнеров нет ни у одной копии**: `GET /containers/json` отдаёт все
   контейнеры сервера с командами запуска (у Redis в Dify там пароль), а
   строку запроса с фильтром прокси не проверяет. С этим ограничением прокси
   уже, чем решение владельца: контейнеры Dify он не показывает и не трогает.
   Сокет Docker есть только у этих двух копий. Осмотр отдаёт и окружение
   контейнера, поэтому **секреты контейнерам — только файлами**, не
   переменными окружения.
2. **Сеть (§2)** — под gVisor не работает встроенный DNS Docker, поэтому у
   рабочего места статический адрес в своей сети, серверный слой — тоже по
   статическому адресу (`extra_hosts`). Внутренняя сеть Docker сама по себе
   **не** отрезает контейнер от сервера: на мосту остаётся адрес хоста, и из
   контейнера видны SSH, xrdp и nginx Dify. Все сети стенда, кроме
   публичной сети входного прокси, — внутренние и с изолированным шлюзом
   (`com.docker.network.bridge.gateway_mode_ipv4: isolated`, Docker 29); у
   публичной сети выключен маскарад. Исключение с Д3 — сеть выхода только
   для серверного слоя (историан и OpenRouter).
3. **Контейнер студента (§6)** — OpenCode ставится бинарником выпуска с
   проверкой суммы; каталоги данных, кэша и временных файлов — на запись с
   правом исполнения; `HOME` и каталог конфигурации — только чтение, в нём
   обязателен `.gitignore`; ripgrep — в образе; `OPENCODE_DISABLE_PROJECT_CONFIG=1`;
   заглушки — без импортов, пакет `@opencode-ai/plugin` не нужен; политика
   перезапуска — `unless-stopped`; `pids_limit` — сотни и больше, по замеру.
4. **gVisor** ставится тарболом выпуска и подключается `systemctl reload
   docker` — без остановки Dify; `restart` запрещён.
5. **Шлюз (§7 п. 2)** вырезает ещё и `?auth_token=`: OpenCode принимает пароль
   в строке запроса. Готовность рабочего места — `GET /global/health` с
   коротким таймаутом и повторами: первые секунды после старта запросы висят.
6. **LLM-прокси (§5, §11 п. 4)** — по документации и исходникам цена приходит
   в последнем чанке потока всегда, добавлять в запрос ничего не нужно; для
   оборванных потоков — дозапрос по `X-Generation-Id`. Остаток аккаунта видит
   только ключ управления OpenRouter — он хранится только в серверном слое.
   Живьём — в начале Д4.
