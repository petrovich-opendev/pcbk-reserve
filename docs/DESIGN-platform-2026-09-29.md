## 0. Что входит и что нет

**Входит** — всё, что нужно для критериев успеха 1–6 и неуспеха 1–4 раздела 8
постановки: вход в веб, чат со своим OpenCode, создание агента в чате, числа из
БДРВ через службу, просмотр преподавателем, учёт расходов на модель,
наблюдаемость.

**Не входит:**

* мнемосхемы (критерии М1–М5, Н1–Н4) — подпроект 2, свой брейншторм. Из этого
  подпроекта ему нужно одно: служба с первого дня пишет события агента;
* уведомления вовне (Telegram, внешнее сердцебиение) — отложены владельцем
  (поправка к Б5);
* переезд на OpenCode v2 — после пилота (Б3);
* всё из «Не делаем» постановки: база знаний, резерв курса с зачётом,
  свободный SQL, локальные модели, резерв провайдера, шифрование входа сверх
  имеющегося, перенос кода из `pcbk-ai-lab` (решение 17).

## 1. Компоненты (раздел 1, согласован)

```
Браузер ──► наш прокси :8443 (или :443, см. §2) ──► СЕРВЕРНЫЙ СЛОЙ (Python, FastAPI)
                                                      ├─ шлюз ─────────────► OpenCode студента 1..10
                                                      ├─ LLM-прокси ◄─────── (внутренняя сеть)
                                                      │     └─► OpenRouter
                                                      └─ служба данных (MCP) ◄─ (внутренняя сеть)
                                                            └─► БДРВ (MSSQL/InSQL, 1433)
СТОРОЖ (отдельный контейнер) — следит за всеми, пишет журнал, отдаёт состояние
```

1. **Веб** — React, TypeScript, assistant-ui (`@assistant-ui/react-opencode`).
   Студент: чат, свои агенты, страница состояния. Преподаватель: разговоры и
   агенты студентов только на чтение, учётные записи, доли бюджета.
2. **Серверный слой** — одно приложение на Python (FastAPI), три роли в одном
   процессе; наружу слушает только шлюз:
   * **шлюз** — вход, роли, выбор контейнера по учётной записи, белый список
     вызовов, вырезание опасных полей, поток ответа (SSE);
   * **LLM-прокси** — OpenAI-совместимая точка для OpenCode, ключ OpenRouter,
     учёт цены, доли и жёсткий стоп;
   * **служба данных** — MCP (Streamable HTTP) для агентов; пароль БДРВ, белый
     список тегов, общий бюджет запросов и кэш — только здесь.
   Один процесс — потому что бюджет, кэш и учёт расходов обязаны жить в одном
   месте; Python — потому что калькуляторы по ответу 1 постановки —
   Python-скрипты.
3. **Контейнер студента** — OpenCode **v1.18.33** (Б3), образ собираем сами.
4. **Хранение** — SQLite: учётные записи, доли и учёт расходов, события
   агентов, журнал сторожа. Файлы агентов — на сервере, в контейнер только на
   чтение. Разговоры — том контейнера студента.
5. **Сторож** — отдельный контейнер: ловит тишину, пишет журнал, отдаёт
   состояние для страницы и баннера (§8).

## 2. Вход и сеть (поправка к разделу 1, согласована)

* **А, сначала:** свой прокси на отдельном порту (например 8443) с тем же
  сертификатом `ai-lab.pcbk.ru`; Dify не трогаем. Проверка — из сети ПЦБК в
  первом слайсе (нужен человек там).
* **Б, если периметр режет порт:** наш прокси на 80/443 перед Dify и нами, nginx
  Dify — на внутренний порт через `/opt/dify/docker/.env`; короткий перерыв
  Dify, откат готов; сбой нашего прокси кладёт и Dify.
* Причина: вход 80/443 держит nginx внутри Dify [П], за ним критерий 3 «Dify
  выключен целиком» не выполняется.
* Факты [П]: с машины разработчика до сервера доходит только SSH — веб
  проверяем через SSH-туннель; на сервере ufw с политикой `DROP`, порты
  Docker идут в обход ufw; пропустит ли периметр заказчика новый порт — [?].
* Внутренняя сеть Docker `internal: true`: контейнеры студентов видят только
  серверный слой — ни БДРВ, ни интернета.

## 3. Пути пользователя (раздел 2, согласован)

1. **Вход.** Логин и пароль (учётки заводит преподаватель). Спящее рабочее
   место шлюз поднимает — «Готовлю рабочее место…»; холодный старт замерить
   [?]. При первом входе — предупреждение, что преподаватель видит разговоры.
2. **Создание агента в чате — успех 1.** Встроенный агент «Конструктор» (наша
   редакция генератора OpenCode `generate.txt` под технологов) расспрашивает:
   узел, цель, вопросы; сам ищет теги в каталоге; показывает черновик (имя,
   назначение, инструменты, правило «не выдумывать нормативы»); по согласию
   вызывает `save_agent`. Служба проверяет черновик (инструменты только из
   нашего списка, без оболочки и правки файлов, имя уникально), пишет файл в
   каталог агентов студента и перезагружает его OpenCode
   (`POST /instance/dispose` [?]) — агент в списке.
3. **Число из БДРВ — успех 2.** Агент вызывает калькулятор или запрос по тегу с
   токеном студента; служба: белый список, бюджет запросов, кэш, SQL строит
   сама; ответ — число, тег, период, время. Каждый вызов — событие агента.
4. **Просмотр преподавателем.** Список студентов, их разговоры и агенты — только
   чтение. Студенты друг друга не видят.
5. **Деньги.** LLM-прокси считает цену каждого вызова по данным OpenRouter;
   доля студента по умолчанию **$100** из **$1000** на всё обучение (решение
   18), преподаватель перераспределяет; на 100 % доли или общего бюджета —
   понятное сообщение в чате; у агента — предел шагов на ответ.

## 4. Служба данных

**Инструменты агентов (MCP) — предложение, состав уточняется в плане:**

| Инструмент | Что делает | Для чего |
|---|---|---|
| `catalog_search` | поиск тегов участка по словам в имени и описании | Конструктор и агенты находят теги |
| `tag_now` | текущее значение, время, качество | «что сейчас» |
| `tag_period` | сводка за период: среднее, минимум, максимум, последнее | «что было за смену» |
| `save_agent` | проверка и запись файла агента | только Конструктор |

Калькуляторы (`tag_now`, `tag_period` и следующие) — Python-код службы, один и
тот же для агента и для проверки успеха 2. Какое среднее считается (по времени
или арифметическое), границы смены и часовой пояс — определить явно и написать
в ответе инструмента.

**Требования из фактов об историане** (решение 17 — переходят как требования,
не как код):

* учётка только на чтение; пароль — в переменных службы, в git никогда;
* в запросе к INSQL — одно условие LIKE, без параметров: SQL строится из
  шаблонов службы с экранированием, свободного SQL нет;
* суффиксы `_PV/_SP/_MV/_LMN`; `_MV` неоднозначен (у регуляторов = выход, у
  большинства — измерение) — служба не угадывает, а показывает описание тега;
* описания тегов обрезаны на 50 символах — при промахе агент показывает
  студенту несколько похожих тегов на выбор;
* белый список — теги участка по правилу и исключения; сам список —
  производственные данные, живёт на сервере, не в git.

**События агента** — на каждый вызов: время, студент, агент, инструмент, тег,
период, результат кратко. Нужны преподавателю и слою событий мнемосхем
(подпроект 2).

## 5. LLM-прокси и деньги

* OpenCode студента ходит к прокси вместо OpenRouter (`baseURL`) со своим
  токеном; ключ OpenRouter — только в прокси.
* Модель — одна, закреплена по итогам отбора (Б4); другие модели прокси не
  пускает.
* Учёт цены — по данным ответа OpenRouter [?: есть ли цена в потоковом ответе
  через OpenCode — проверить первым]; доли студентов и общий бюджет $1000;
  пороги 50 / 80 / 95 % — в журнал сторожа и на страницу состояния.

## 6. Контейнер студента

* gVisor (`runsc`, платформа systrap — без KVM [Д]); **на сервере не
  установлен [П]** — ставится в плане, нужен sudo;
* пользователь без root, корневая ФС только чтение, `cap-drop ALL`,
  `no-new-privileges`, лимиты памяти, процессов и процессора (предложение:
  память 1 ГБ — на 10 контейнеров хватает: доступно 11,7 ГБ [П]; замерить [?]);
* тома: свой — разговоры (запись), каталог агентов — только чтение; сокета
  Docker нет;
* OpenCode: провайдер — наш LLM-прокси; MCP remote — служба данных с токеном
  студента (`{env:…}` [Д]); `bash`, `edit`, `write` заменены заглушками
  (`.opencode/tools/*.ts`); `share: disabled`; автообновление и загрузка
  списка моделей выключены;
* старт при входе, остановка после 30 минут простоя; падение или убийство по
  памяти — перезапуск и запись в журнал.

## 7. Изоляция (раздел 3, согласован)

Три слоя, каждый держит сам:

1. **Контейнер** — §6.
2. **Шлюз** — контейнер выбирается по учётной записи, не по параметру из
   браузера; белый список — вызовы адаптера assistant-ui (сессии, сообщения,
   поток событий, ответы на разрешения и вопросы); вырезаются `permission`,
   `tools`, `system`, поле `agent` — только из агентов студента; ручки
   оболочки, терминала, файлов, конфигурации, MCP, ключей, обновлений —
   отказ [Д, research/02]; преподавателю — только чтение.
3. **Служба и прокси** — §4, §5.

## 8. Наблюдаемость (Б5 с поправкой)

* **Ловим тишину, а не только ошибки:** служба данных молчит дольше минуты; у
  историана стоят метки времени; OpenRouter отвечает 402 или ошибками подряд;
  бюджет на 50 / 80 / 95 %; контейнер студента упал или убит по памяти; память
  сервера ниже порога (рядом Dify); сердцебиение самого сторожа.
* **Куда:** журнал, страница состояния, баннер у преподавателя и студентов.
* **Отложено владельцем:** Telegram и внешнее сердцебиение. Сторож устроен
  так, чтобы канал подключался позже без переделок.

## 9. Проверка критериев (раздел 3, согласован)

| Критерий | Как проверяем |
|---|---|
| Успех 1 — агент за один разговор | вручную: студент-доброволец после одного показа, секундомер, без помощи; автоматически: бот-студент (Opus в роли технолога) на отборе модели |
| Успех 2 и неуспех 4 — число = калькулятор | автотест: набор тегов и периодов, ответ агента против прямого вызова калькулятора |
| Успех 3 — без Dify | все сквозные тесты при полностью остановленном Dify, затем Dify включаем |
| Успех 4 — белый список и бюджет | 10 ботов-студентов одновременно; по журналу службы — ноль запросов мимо списка, бюджет не превышен |
| Успех 5 и неуспех 3 — только своё | автотест: студент А пытается получить сессии и агентов Б подменой id и заголовков — отказ 403 |
| Успех 6 — $1000 | учёт LLM-прокси; прогноз пересчитывается через две недели работы |
| Неуспех 1 — оболочка, пароль | автотест: опасные вызовы OpenCode через шлюз — 403; изнутри контейнера нет пароля в переменных и файлах, нет маршрута к 1433 и в интернет |
| Неуспех 2 — выдуманный норматив | ловушки на отборе модели + правило в промпте агента, проверяет судья |

В конце реализации — скан claude-security (ставится с согласия владельца, Б1).

## 12. Порядок постройки — эскиз для плана

Первый видимый результат по решению 14 — критерии 1 и 2: студент в вебе завёл

баннер → прогон без Dify. План дневными слайсами — следующий этап, после
согласования этого документа.
