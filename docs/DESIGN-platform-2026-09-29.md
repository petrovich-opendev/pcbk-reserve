## 1. Компоненты (раздел 1, согласован; редакция 2 — дополнено)

```
Браузер ──► НАШ ПРОКСИ :8443 (или :443, §2) ─┬─► СЕРВЕРНЫЙ СЛОЙ (Python, FastAPI)
                                              │     ├─ шлюз ─────► OpenCode студента N
                                              │     │               (своя сеть на студента)
                                              │     ├─ LLM-прокси ◄── ─┘      └─► OpenRouter
                                              │     └─ служба данных (MCP) ◄──┘  └─► БДРВ :1433
                                              └─► СТОРОЖ: страница состояния (в обход
                                                  серверного слоя), журнал
```

1. **Наш прокси** — единственная точка входа снаружи: TLS с сертификатом
   `ai-lab.pcbk.ru`, отдаёт веб, шлюз и страницу состояния сторожа.
2. **Веб** — React, TypeScript, assistant-ui (`@assistant-ui/react-opencode`).
   Студент: чат, свои агенты, калькуляторы (прямой вызов тех же калькуляторов
   службы), страница состояния. Преподаватель: разговоры и агенты студентов
   только на чтение, учётные записи, доли бюджета. **Предупреждение о статусе
   стенда видно постоянно** («Состав задачи», п. 1).
3. **Серверный слой** — одно приложение на Python (FastAPI), три роли в одном
   процессе; снаружи доступен только шлюз, через наш прокси:
   * **шлюз** — вход, роли, выбор контейнера по учётной записи, белый список
     вызовов, вырезание опасных полей и параметров, поток ответа (SSE);
   * **LLM-прокси** — OpenAI-совместимая точка для OpenCode, ключ OpenRouter,
     учёт цены, доли и жёсткий стоп;
   * **служба данных** — MCP (Streamable HTTP) для агентов и HTTP для веба;
     пароль БДРВ, белый список тегов, общий бюджет запросов и кэш — только
     здесь.
   Один процесс — бюджет, кэш и учёт расходов в одном месте; Python —
   калькуляторы по ответу 1 постановки — Python-скрипты.
4. **Контейнеры студентов** — OpenCode **v1.18.33** (Б3), образ собираем сами
   (§6). **Решение владельца 29.09.2026 — готовые контейнеры и узкий прокси
   сокета:** десять контейнеров `student-01…10` создаёт администратор один раз
   при выкладке (Docker Compose, фиксированные настройки §6); во время работы
   серверный слой ходит к Docker только через готовый прокси сокета
   (docker-socket-proxy), который разрешает запуск, остановку, осмотр и список
   контейнеров и запрещает создание, exec, тома, образы и всё прочее. Даже при
   ошибке в нашем коде нельзя создать новый, в том числе привилегированный,
   контейнер. Новый студент — правка Compose администратором. Проверить [?]:
   текущая версия прокси умеет пускать start/stop без общего разрешения POST.
   Причина: полный сокет — это права root на сервере рядом с Dify, а до
   серверного слоя из сети каждого студента доходят служба данных и LLM-прокси;
   изоляция студентов и пароля БДРВ обязательна (вопрос 15 постановки).
5. **Хранение** — SQLite: учётные записи, доли и учёт расходов, события
   агентов. Файлы агентов — на сервере, в контейнер только на чтение.
   Разговоры — том контейнера студента.
6. **Сторож** — отдельный контейнер: ловит тишину, ведёт журнал и **сам отдаёт
   страницу состояния** через наш прокси, в обход серверного слоя, — чтобы
   страница работала, когда серверный слой лёг (§8). Состояние контейнеров
   студентов видит через тот же прокси сокета, только на чтение.
7. **Прокси сокета Docker** — отдельный контейнер (п. 4); единственный, у кого
   есть `docker.sock`.

## 2. Вход и сеть (поправка к разделу 1, согласована; редакция 2 — сеть)

* **Вход А, сначала:** наш прокси на отдельном порту (например 8443) с тем же
  сертификатом; Dify не трогаем. Проверка — из сети ПЦБК в первом слайсе (нужен
  человек там).
* **Вход Б, если периметр режет порт:** наш прокси на 80/443 перед Dify и нами,
  nginx Dify — на внутренний порт через `/opt/dify/docker/.env`; короткий
  перерыв Dify, откат готов; сбой нашего прокси кладёт и Dify.
* Причина: вход 80/443 держит nginx внутри Dify [П], за ним критерий 3 «Dify
  выключен целиком» не выполняется.
* Факты [П]: с машины разработчика до сервера доходит только SSH — веб
  проверяем через SSH-туннель; на сервере ufw с политикой `DROP`, порты
  Docker идут в обход ufw; пропустит ли периметр заказчика новый порт — [?].
* **Сеть — своя на каждого студента** (редакция 2): в сети студента только его
  контейнер и серверный слой, `internal: true` (ни БДРВ, ни интернета).
  Причина: в одной общей сети контейнеры видят друг друга, и путь «контейнер
  А → OpenCode студента Б» шёл бы мимо шлюза.
* **Свой пароль сервера OpenCode на каждый контейнер**
  (`OPENCODE_SERVER_PASSWORD`): знают его шлюз и сам контейнер, другие
  контейнеры — нет.

## 3. Пути пользователя (раздел 2, согласован)

1. **Вход.** Логин и пароль (учётки заводит преподаватель). Спящее рабочее
   место шлюз поднимает — «Готовлю рабочее место…»; холодный старт замерить
   [?]. При первом входе — предупреждение, что преподаватель видит разговоры.
2. **Создание агента в чате — успех 1.** Встроенный агент «Конструктор» (наша
   редакция генератора OpenCode `generate.txt` под технологов) расспрашивает:
   узел, цель, вопросы; сам ищет теги в каталоге; показывает черновик (имя,
   назначение, инструменты, правило «не выдумывать нормативы»); по согласию
   вызывает `save_agent`. Служба проверяет черновик (инструменты только из
   нашего списка, без оболочки, правки файлов и `apply_patch`, имя уникально),
   пишет файл в каталог агентов студента. Перезагрузка OpenCode студента
   (`POST /instance/dispose` [?]) — **после окончания хода Конструктора**, чтобы
   не оборвать его ответ; проверить на живом потоке [?].
3. **Число из БДРВ — успех 2.** Агент вызывает калькулятор или запрос по тегу с
   токеном студента; служба: белый список, бюджет запросов, кэш, SQL строит
   сама; ответ — число, тег, период, время. Каждый вызов — событие агента.
4. **Просмотр преподавателем.** Список студентов, их разговоры и агенты — только
   чтение. Студенты друг друга не видят. Вопрос «будить контейнер спящего
   студента на чтение или читать его том напрямую» **закрыт в Д10а [Л]**
   (§13 п. 8):
   * разговоры читаются через само место, паролем шлюза, ровно тремя GET:
     `/experimental/session?roots=true&archived=true`, `/session/<id>` и
     `/session/<id>/message`. Путь собирается из шаблона и проверенного id,
     простой места эти запросы не продлевают. Тома мест к серверному слою не
     подключаются;
   * чтение спящее место не будит — ответ «Рабочее место студента спит —
     разбудите его для просмотра». Будит кнопка «Разбудить для просмотра» —
     обычным запуском места, как при входе студента: `sp-ctl start` и все
     воркеры места (сохранённые агенты перезагружаются, сломанный файл агента
     уходит в карантин). Засыпает место само, по простою;
   * агенты студента читаются из учёта и каталога службы — место для этого не
     нужно;
   * каждое чтение и пробуждение — строка журнала действий преподавателя
     **до** доступа; строка не записалась — доступа нет. Студенту ручки
     кабинета отвечают 403 на сервере.
5. **Деньги.** LLM-прокси считает цену каждого вызова по данным OpenRouter;
   доля студента по умолчанию **$100** из **$1000** на всё обучение (решение
   18), преподаватель перераспределяет; на 100 % доли или общего бюджета —
   понятное сообщение в чате; у агента — предел шагов на ответ. **Д10а [Л]:**
   доли мест — целые центы в `core.db`. Преподаватель в кабинете переводит
   долю с места на место и «останавливает место»; следующий же вызов модели
   студента идёт по новой доле. Правила — §5.

## 4. Служба данных

**Состав** — по «Составу задачи», п. 3: калькуляторы — среднее, минимум,
максимум, размах, профиль, наработка; запрос по тегу — текущее значение, ряд,
сводка по любому тегу белого списка за любой период в пределах бюджета;
каталог тегов из историана с поиском по словам.

**Инструменты службы — как сделано к Д9а [Л]** (агенты — MCP; HTTP
`/api/data/<tool>` — токен `ops` и стенд отбора; веб — вкладка «Калькуляторы»
чата студента через шлюз `POST /pcbk/api/calc/<tool>`; на сервере
инструментов ещё нет — §13 п. 7):

| Инструмент | Что делает | Пределы за вызов |
|---|---|---|
| `catalog_search` | поиск тегов участка по словам в имени и описании; нет точного совпадения — похожие на выбор | запрос до 200 знаков, до 50 совпадений |
| `tag_now` | текущее значение (Live): единица, время с поясом, возраст, качество; у тега состояния — подпись по суффиксу | до 16 тегов |
| `tag_period` | сводка историана одной корзиной: среднее, минимум, максимум, размах, σ, доля достоверных; последнее значение пока не считается (заметка) | до 16 тегов, окно до 31 суток, 24 тего-суток (у одного тега — 31) |
| `tag_series` | ряд и профиль: N точек на равномерной сетке историана (`Cyclic`) и по каждому тегу начало, конец, изменение, минимум и максимум сетки с моментами; только аналоговые теги | до 4 тегов, 2–96 точек на тег (по умолчанию 24), теги × точки — до 288; окно и тего-сутки — как у `tag_period` |
| `calc_runtime` | наработка (`StateSummaryHistory`): по каждому состоянию часы, доля периода, число переходов, подпись по суффиксу (`_RUN` 1 — работает, `_CLS` 1 — закрыт); только теги состояний | до 16 тегов; окно и тего-сутки — как у `tag_period` |
| `save_agent` | проверка черновика и запись файла агента | только Конструктор; вкладке недоступен |

Калькуляторы постановки: среднее, минимум, максимум и размах — `tag_period`,
профиль — `tag_series` (отдельного `calc_profile` нет, Д9-R84), наработка —
`calc_runtime`. Агенту студента доступны пять инструментов чтения
(`save_agent` — никогда), вкладке — те же пять. Частота — 60 вызовов за 5
минут на вызывающего: вкладка и агенты места — один вызывающий `student-NN`.
SQL — только шаблоны службы, ворота пускают инструкцию, лишь целиком
совпавшую с формой шаблона: у ряда — литерал `'Cyclic'` и число точек 2–96, у
наработки — одна корзина `wwCycleCount = 1`. [Л]

**Что пишется в ответе** инструмента за период [Л]:

* `period` — начало и конец с поясом историана, пояс, готовый период и
  признаки: границы смен — допущение, период ещё идёт, конец ограничен
  текущим временем историана;
* `source` — откуда числа: сводка по сырым данным одной корзиной;
  «равномерная сетка историана (Cyclic): N точек с равным шагом от начала
  периода»; «время в каждом состоянии по сырым данным историана
  (StateSummaryHistory)»;
* `cost_tag_days` — цена вызова в тего-сутках, `cache`; у `tag_period` — вид
  среднего и σ (`avg_kind`, `std_kind`; до сверки на живом историане — «вид
  не подтверждён сверкой»); у `tag_series` — `points`;
* `notes` дословно: «границы смен 06:00, 14:00, 22:00 — допущение, технологом
  не подтверждено», «период ещё идёт — числа изменятся», «конец периода
  ограничен текущим временем историана»; у ряда всегда — «сетка равномерная:
  всплески короче шага не видны — истинные минимум, максимум и среднее даёт
  tag_period»;
* у каждого тега — свой статус и текст: `no_data` «за период данных нет»;
  тег состояния в сводке или ряде — «наработку даёт calc_runtime»;
  аналоговый в наработке — «сводку даёт tag_period»; `unknown`,
  `unlisted`. Заметки элемента: `quality_note` — недостоверное качество
  (доля у сводки, «k из N» точек у ряда); `coverage_note` — «данные
  покрывают p % периода», если часы состояний покрывают меньше 99 %; нет
  доли у состояния с часами — покрытие неизвестно (`covered_percent` null,
  без заметки);
* отказ — статус и текст: аргументы (`refused`), бюджет (`budget`: что
  сократить, период и цена), частота (`rate`), сбой (`error`, `timeout`,
  `unavailable`).

Калькуляторы — Python-код службы, один и тот же для агента, для страницы
калькуляторов в вебе и для проверки успеха 2. Какое среднее считается (по
времени или арифметическое), границы смены и часовой пояс — определить явно и
писать в ответе инструмента. **[Л] Д9а:** один `DataService` — MCP, HTTP и
шлюз зовут его в процессе; автотест на двойнике сверяет ответ вкладки с
ответом `/api/data/<tool>` на тех же аргументах (кроме `cache`).

**Требования из фактов об историане** (решение 17 — переходят как требования,
не как код):

* учётка только на чтение; пароль — в переменных службы, в git никогда;
* в запросе к INSQL — одно условие LIKE, без параметров: SQL строится из
  шаблонов службы с экранированием, свободного SQL нет;
* суффиксы `_PV/_SP/_MV/_LMN`; **смысл `_MV` на регуляторах не установлен**
  (вопрос технологу и АСУТП) — служба не угадывает, а показывает описание тега;
* описания тегов обрезаны на 50 символах — при промахе агент показывает
  студенту несколько похожих тегов на выбор;
* белый список — теги участка по правилу и исключения; сам список —
  производственные данные, живёт на сервере, не в git.

**События агента** — на каждый вызов: время, студент, агент, инструмент, тег,
период, результат кратко. Нужны преподавателю и слою событий мнемосхем
(подпроект 2).

## 5. LLM-прокси и деньги

* OpenCode студента ходит к прокси вместо OpenRouter (`baseURL`) со своим
  токеном; ключ OpenRouter — только в прокси.
* Модели: на время отбора (Б4) прокси пускает только к моделям-кандидатам,
  после — только к выбранной. Другие модели прокси не пускает.
* Учёт цены — по данным ответа OpenRouter [?: есть ли цена в потоковом ответе
  через OpenCode — проверить первым]; доли студентов и общий бюджет $1000;
  пороги 50 / 80 / 95 % — на страницу состояния и в журнал.
* **Доли мест (Д10а, Д10-R97, R98) [Л]:**
  * доля — целые центы в таблице `llm_shares` `core.db`. Строка есть только у
    изменённых мест, прочие — по умолчанию `LLM_SHARE_USD`;
  * **пол доли** — оплаченное местом (`Ledger.settled`: пришедшие цены и
    окончательные оценки, без идущих вызовов), округлённое вниз до цента в той
    же арифметике, что отказ прокси (`spent >= share`), с запасом 1e-9 против
    шума float. На ровной сумме пол на цент ниже ($0,30 → 29 центов). Поэтому
    доля, сведённая к полу, даёт отказ «доля израсходована» следующему же
    вызову — при любом расходе, в том числе не кратном центу, и при идущих
    вызовах. Остаток ниже нуля бывает только на сумму меньше цента и на оценки
    вызовов, начатых до перевода;
  * изменение — всё или ничего, со сверкой «было» (две вкладки не затирают
    друг друга). Доля не ниже пола. Сумма долей десяти мест — не больше общего
    бюджета (`LLM_TOTAL_USD`) или не больше прежней суммы. Строка журнала
    действий — в той же транзакции;
  * **«Остановить место»** — одна серверная операция: доля места сводится к
    полу, разница уходит другому месту. Пол берёт сервер под замком перевода,
    клиент числа пола не передаёт;
  * **доля `ops`** («отбор и проверки», `LLM_OPS_SHARE_USD`) — вне таблицы и
    суммы долей мест. Деньги отбора держат общий стоп и потолок прогона
    (Д8-R69);
  * прокси отказывает по доле из памяти (`Budget.share_of`). Такт уборщика
    шлюза сверяет её с диском — сквозь `Budget`, по тем центам, по которым
    прокси отказывает. Расхождение память не чинит — строка «Кабинет
    преподавателя и доли» (§8) показывает сбой, лечит перезапуск `core`. Доли
    не загрузились при запуске — LLM-прокси закрыт (все вызовы — 403), а не
    открыт по умолчанию.
* Предложение: расход на отбор модели и на ботов-студентов в автотестах
  учитывается в тех же $1000 (тот же аккаунт OpenRouter); оценка — десятки
  долларов [?], фактический расход показывается отдельной строкой.

## 8. Наблюдаемость (Б5 с поправкой; редакция 2 — раньше и в обход)

* **Ловим тишину, а не только ошибки:** служба данных молчит дольше минуты; у
  историана стоят метки времени; OpenRouter отвечает 402 или ошибками подряд;
  бюджет на 50 / 80 / 95 %; контейнер студента упал или убит по памяти; память
  сервера ниже порога (рядом Dify); сердцебиение самого сторожа — его ловит
  серверный слой, и если страница сторожа не отвечает или устарела, баннер в
  вебе показывает «состояние неизвестно».
* **Куда:** страница состояния (её отдаёт сам сторож, в обход серверного слоя)
  и баннер у преподавателя и студентов; журнал — дополнительно. Раз Telegram
  отложен, страница и баннер — единственное место, куда смотрит человек,
  поэтому они строятся **в первом же веб-слайсе**, а не в конце (§12).
* **Серия ошибок инструмента (Д9а, Д9-R83) [Л]:** три ошибки подряд
  (`error`, `timeout`, `unavailable`) у одного инструмента на каналах `http`,
  `mcp` и `web` — строка «Историан БДРВ» «внимание» «инструменты службы
  данных отвечают ошибкой подряд», имена — в пометке. Так виден и редкий
  калькулятор, который отвечает только ошибкой среди удачных вызовов
  других инструментов. Любой другой исход — `ok`, `partial`, `refused`,
  `budget`, `rate`, `busy` — серию обнуляет, хотя у отказов SQL не уходит;
  после обрыва серия держится до удачного вызова или 30 минут без вызовов.
  Под учением `DRILL_DATA=tool_error` к пометке строки дописано «учения:
  tool_error». Сторож старше Д9а поля серии не читает, сторож Д9а у службы
  старше Д9а строку не строит.
* **Строка «Кабинет преподавателя и доли» (Д10а, Д10-R96) [Л]** — последняя
  на странице. Источник — `GET /health/teacher` шлюза: 13 ключей, только числа
  и флаги, без логинов и номеров мест. Состояния:
  * «сбой» — журнал действий преподавателя не пишется («кабинет закрыт»);
    доли не загружены («LLM-прокси закрыт для студентов»); сверка не прочла
    таблицу долей; LLM-прокси считает доли не так, как сохранено (пометка
    «мест: N»); сверка молчит дольше `TEACHER_STALE_S` (120 с);
  * «внимание» — сумма долей мест больше общего бюджета; изменения
    преподавателя не проходят (от 3 сбоев за час и ни одной удачи); разговоры
    не читаются (от 3 сбоев за час); кабинет открывают без роли
    преподавателя (от 10 раз за час);
  * «неизвестно» — сверки долей ещё не было или `core` старше Д10а (404);
  * сроки: сверка — в такте уборщика шлюза (30 с), строка меняется после него
    и следующего такта сторожа.

  Учения `DRILL_TEACHER`: `shares_stale` — доли записаны, а память прокси нет;
  `journal_down` — журнал действий не пишется. К пометке строки дописано
  «учения: <режим>». Баннер чата студента эту строку не показывает, кроме
  «доли бюджета не загружены — LLM-прокси закрыт для студентов».
* **Отложено владельцем:** Telegram и внешнее сердцебиение. Сторож устроен
  так, чтобы канал подключался позже без переделок.
